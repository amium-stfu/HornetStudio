# IMPLEMENTATION HANDOFF

## Goal
Replace the current widget-owned CSV and SQL logging flow with a headless host-owned `ValueLog` system that is configured through folder-local files and managed through one shared browser/editor. Remove the existing `CsvLoggerControl` and `SqlLoggerControl` widgets completely.

## Scope
Included:
- Introduce a shared `ValueLog` concept for CSV and SQL logging.
- Store `ValueLog` definitions as folder-local files under `Folder/ValueLog/csv/*.yaml` and `Folder/ValueLog/sql/*.yaml`.
- Move runtime ownership, lifecycle, and registry publication into host-side runtime services.
- Build one browser/editor that lists both CSV and SQL value logs and allows creating, editing, deleting, starting, and stopping them.
- Remove the existing CSV and SQL logger widgets, picker entries, layout usage, and widget-specific runtime publishing.
- Update sample/demo data and relevant documentation.

Not included:
- Reworking `ProcessLog` as part of this work.
- Keeping the old CSV/SQL widget architecture alive in parallel as a long-term supported path.
- Adding a new replacement canvas widget in the same change.

## Starting Point
- `CsvLogger` and `SqlLogger` runtime classes already exist under `src/HornetStudio.Host/Logging/`.
- Logger start/stop ownership currently sits in `MainWindowViewModel`, including `_csvLoggers`, `_sqlLoggers`, `StartCsvLogging`, `StopCsvLogging`, `StartSqlLogging`, and `StopSqlLogging`.
- `EditorCsvLoggerControl` and `EditorSqlLoggerControl` currently publish `logger_runtime.*` items and trigger logger lifecycle from the UI.
- `FolderItemModel` currently contains logger widget runtime path helpers and output path helpers.
- The architectural direction is now explicit: CSV and SQL logging belong to host-side runtime ownership, not UI ownership.
- One shared browser should manage both types, with type selection during creation and one combined list in the browser.

## Tasks
1. Define the headless `ValueLog` domain model and folder-local file format for CSV and SQL value logs.
2. Implement host-side loading, persistence, registry projection, and lifecycle ownership for `ValueLog` definitions and running runtimes.
3. Build one shared `ValueLog` browser/editor that lists both types and edits file-backed definitions.
4. Remove the existing CSV and SQL logger widgets and all UI/layout integration that assumes they are placeable page widgets.
5. Update demo/sample content, runtime path usage, and documentation to the new browser-managed file-backed model.
6. Add or update tests that cover definition loading, persistence, runtime ownership, and browser-facing registry behavior.

## File-Level Changes
- `src/HornetStudio.Host/Logging/` -> introduce shared `ValueLog` definition/runtime/manager types and reuse existing CSV/SQL backends where appropriate.
- `src/HornetStudio.Host/Registries/` or other host runtime integration points -> publish stable runtime/status/command items for managed value logs.
- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs` -> remove logger instance ownership and route browser actions to host-managed `ValueLog` services.
- `src/HornetStudio.Editor/Models/PageItemModel.cs` -> remove CSV/SQL widget-specific runtime path helpers that only exist for canvas widgets; keep only logic still needed by browser/file-backed definitions.
- `src/HornetStudio.Editor/Widgets/CsvLogger/` -> delete.
- `src/HornetStudio.Editor/Widgets/SqlLogger/` -> delete.
- `src/HornetStudio.Editor/Controls/PageEditorControl.axaml` and related code-behind -> remove CSV/SQL widget rendering and add-actions.
- `src/HornetStudio.Editor/Widgets/FolderEditor/` and other picker/browser integration files -> replace widget creation flow with one `ValueLog` browser entry point.
- `samples/HornetStudioDemo/` -> migrate sample configuration away from widget/layout ownership to folder-local `ValueLog` files.
- `src/HornetStudio/docs/manual/` -> update handbook-level guidance if user workflows or concepts changed materially.
- `src/HornetStudio/docs/widgets/` and `src/HornetStudio/docs/widgets/help/` and `src/HornetStudio/docs/widgets/descriptions/` -> remove or replace CSV/SQL widget documentation because those widget types are being deleted.

## Implementation Order
1. Define `ValueLog` persisted model, file layout, and naming conventions.
2. Add host-side loader/manager/runtime ownership for file-backed `ValueLog` definitions.
3. Define the runtime registry schema for status, output path, last file, errors, commands, and enabled/running state.
4. Build the shared browser/editor on top of file-backed definitions and host runtime operations.
5. Migrate sample/demo data to `Folder/ValueLog/csv/*.yaml` and `Folder/ValueLog/sql/*.yaml`.
6. Remove the legacy CSV/SQL widget controls, picker entries, layout support, and `MainWindowViewModel` logger ownership.
7. Update documentation and tests.
8. Run solution-level verification.

## Technical Constraints
- Keep the architecture minimally fragmented; do not create speculative layers beyond what is needed for the two real backends CSV and SQL.
- Runtime ownership must not remain in Avalonia controls.
- Browser/runtime registry handling must be subscription-scoped and must filter registry events before posting UI work.
- File-backed browser resources are the source of truth; legacy widget definitions are compatibility input only if a focused migration step still requires them.
- If moving concepts out of `Folder.yaml` or layout data into folder-local resource files, update `samples/HornetStudioDemo/` in the same change.
- Follow existing solution naming and path conventions; user chat remains German, but code/comments/docs identifiers remain English.
- Avoid silent exception swallowing in new code paths; errors should be explicit and diagnosable.

## Acceptance Criteria
- CSV and SQL value logs are configured from folder-local files, not from page widgets.
- One shared browser lists both CSV and SQL value logs and supports create/edit/delete/start/stop flows.
- Runtime ownership for CSV and SQL logging exists outside Avalonia controls and outside widget lifecycle.
- `CsvLoggerControl` and `SqlLoggerControl` no longer exist as selectable or renderable widgets.
- The demo/sample project uses the new file-backed `ValueLog` structure.
- Runtime status and command items for value logs are available through a stable host-managed registry projection.

## Verification
- Build the full solution with the repository-standard solution build command.
- Add focused tests for value log definition loading/saving and host runtime ownership behavior.
- Add focused tests or self-test coverage for registry projection and command handling if those are implemented in testable host services.
- Manually verify that the shared browser can create one CSV log and one SQL log, persist them, and start/stop them without any page widget present.
- Manually verify that deleting the old widgets does not leave stale picker entries, layout render paths, or browser references.

## Out of Scope
- Replacing the removed CSV/SQL widgets with a new page widget in the same implementation.
- Refactoring unrelated logger types or unrelated browser systems.
- General redesign of all logging UI beyond the new shared `ValueLog` browser/editor.

## Risks / Watchouts
- `MainWindowViewModel` currently contains a lot of implicit logger knowledge; remove it carefully to avoid leaving partial ownership split across UI and host.
- SQL logging currently uses reflection-based setup from the UI; replacing this with typed host ownership is important to avoid carrying the current coupling forward.
- Widget removal may touch picker logic, layout loading, persistence mappings, and documentation in multiple places.
- If legacy layouts currently contain CSV/SQL logger widgets, decide explicitly whether to migrate them once or to drop compatibility; do not leave the support state ambiguous.
- Registry event filtering for the new browser must remain scoped; avoid broad `HostRegistries.Data.ItemChanged` reactions.

## Notes
- Prefer one combined `ValueLog` browser with a type selector over separate CSV and SQL management surfaces.
- Treat the browser as the main configuration surface and the host runtime as the main execution surface.
- Do not introduce a new page widget unless a concrete workflow later proves that browser-only operation is insufficient.
