# IMPLEMENTATION HANDOFF

## Goal
Simplify the ValueLog runtime so each concrete logger owns its own registry control items and lifecycle, while the manager only loads definitions, creates logger instances, stores them by stable runtime path, and releases them by folder.

The intent is to stop patching indirect registry-manager-entry-logger chains and move to:

`ValueLog YAML -> ValueLogRuntimeManager -> Dictionary<runtimePath, logger> -> logger.Items -> logger.StartAsync/StopAsync`

## Scope
Included:
- Replace the current `ValueLogEntry` wrapper/projection pattern with direct manager ownership of concrete logger runtime objects.
- Keep one folder-scoped dictionary keyed by stable value log runtime path or folder/id key.
- Make CSV and SQL value log runtimes expose their required registry/control items directly.
- Ensure `run=false` from a ButtonWidget cannot execute any stop work on the registry event/UI path.
- Keep persisted ValueLog source entries path-first. Source display metadata must be read from the current source item at start time.
- Fix CSV header semantics:
  - Header row 1 uses the source metadata item `Name`.
  - Header row 2 uses the source metadata item `text`.
  - Header row 3 uses the source metadata item `unit`.
  - Sampling uses the `read` child when available.
- Keep the shared ValueLog browser/editor.
- Update focused host tests for the simplified direct logger runtime flow.

Not included:
- Reintroducing CSV/SQL canvas widgets.
- Creating separate CSV and SQL browser windows.
- Reworking `ProcessLog`.
- Broad logger performance optimization beyond removing UI/event-path stop work.
- Preserving legacy source metadata overrides as the normal ValueLog behavior.

## Starting Point
- `ValueLogDefinition` remains the file-backed model.
- `ValueLogDefinitionFileCodec` now writes source `Path` and reads legacy `TargetPath`.
- `ValueLogRuntimeManager` currently stores `ValueLogEntry` objects and queues operations.
- `ValueLogEntry` currently owns registry projection, source resolution, status, and concrete `CsvLogger` / `SqlLogger`.
- This has become too indirect and has regressed more than once:
  - ButtonWidget `run=false` can still visibly freeze UI/ValueHistory/Chart paths.
  - CSV header metadata can be taken from `read` child items instead of parent signal items.

## Tasks
1. Define a small runtime contract for concrete value log runtimes.
2. Implement direct CSV and SQL value log runtime ownership, preferably by extending existing logger classes or adding very small concrete runtime classes only if needed.
3. Refactor `ValueLogRuntimeManager` to store concrete runtime instances in a dictionary and remove the wrapper-style `ValueLogEntry` responsibility.
4. Move registry control items into the concrete runtime object:
   - `run`
   - `status`
   - `output_directory`
   - `filename`
   - `last_file`
   - `error`
5. Ensure `run` change handlers enqueue lifecycle work and return immediately.
6. Split source resolution into metadata item and value item:
   - If configured path resolves to `*.read`, metadata item is the parent and value item is the `read` item.
   - If configured path resolves to a parent with a `read` child, metadata item is the parent and value item is the child.
   - Otherwise metadata item and value item are the resolved item.
7. Remove or heavily shrink `ValueLogEntry` after migrating responsibilities.
8. Update browser status lookup to use manager snapshots from concrete runtimes.
9. Update tests to prove direct logger runtime behavior and prevent the known regressions.

## File-Level Changes
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogRuntimeManager.cs` -> become the dictionary owner and definition synchronizer only. It should not translate every registry item change into lifecycle calls.
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogEntry.cs` -> remove or reduce to a tiny helper only if absolutely necessary. Prefer deleting it after direct runtimes own registry items.
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogDefinition.cs` -> keep data-only. Sources remain path-first.
- `src/HornetStudio.Host/Logging/CsvLogger.cs` -> expose or own the CSV runtime control items and async lifecycle surface as needed.
- `src/HornetStudio.Host/Logging/SqlLogger.cs` -> same for SQL.
- `src/HornetStudio.Editor/Persistence/ValueLog/ValueLogsBrowserDialogWindow.axaml.cs` -> keep browser operations non-blocking and read manager status.
- `src/HornetStudio.Host.Tests/Program.cs` -> replace wrapper-focused tests with direct runtime/manager tests.
- `docs/workitems/2026.06.06.0034-value_log_headless_browser/debug/2026.06.06.2311-debug.md` -> update if debugging findings change during implementation.

## Implementation Order
1. Add a minimal internal runtime contract, for example:
   - `Id`
   - `FolderName`
   - `RuntimePath`
   - `RootItem`
   - `IsRunning`
   - `Definition`
   - `StartAsync()`
   - `StopAsync()`
   - `UpdateDefinition(...)`
   - `RemoveProjection()`
   Keep it concrete and local to ValueLog; do not create a broad framework.
2. Create direct CSV/SQL runtime objects using existing `CsvLogger` and `SqlLogger` as the actual backend loops.
3. Move run-control item creation into the runtime object. The handler must only enqueue lifecycle work, for example through a manager-provided callback that uses `Task.Run` or an already-running background queue.
4. Move source resolution into the runtime object and explicitly return `(metadataItem, valueItem)`.
5. Refactor `ValueLogRuntimeManager` to:
   - build stable runtime paths,
   - create/update concrete runtimes,
   - store them in `Dictionary<string, IValueLogRuntime>`,
   - queue start/stop/release operations,
   - expose status snapshots.
6. Delete `ValueLogEntry` if no longer needed.
7. Update tests:
   - source path `signal_m001.read` produces CSV headers from parent `signal_m001`;
   - source path `signal_m001` samples `signal_m001.read` when present;
   - ButtonWidget/registry `run=false` returns quickly and does not execute stop work synchronously;
   - no `commands.start` / `commands.stop` projection exists;
   - path-only source YAML remains supported.
8. Run focused host tests and the full solution build.

## Technical Constraints
- Chat responses remain German.
- Code, comments, XML documentation, UI text, file names, and identifiers remain English.
- Keep `ValueLogDefinition` data-only.
- Prefer minimally fragmented architecture.
- Avoid services/managers/providers beyond the one existing ValueLog manager.
- Do not introduce a generic runtime framework.
- Registry event filtering must happen before any UI-thread work is scheduled.
- Runtime services must be host-owned and usable without Avalonia controls.
- Unknown or unrelated registry events must not enqueue UI work.
- Start/Stop must never block ButtonWidget, chart, ValueHistory, or browser UI paths.

## Acceptance Criteria
- `ValueLogRuntimeManager` owns a dictionary of direct concrete value log runtimes by stable path or folder/id key.
- Concrete CSV and SQL value log runtimes own their own registry/control items.
- `run=false` from a ButtonWidget returns immediately and does not freeze UI/ValueHistory/Chart updates.
- CSV headers use parent/source metadata:
  - row 1: item name, e.g. `signal_m001`
  - row 2: item text, e.g. `DummyTest`
  - row 3: item unit, e.g. `ppm`
- CSV values still sample the `read` child when present.
- Source YAML persists source paths, not stale `Caption`/`Unit` snapshots.
- `commands.start` and `commands.stop` remain removed.
- Existing ValueLog browser can create, save, start, stop, and delete logs.

## Out of Scope
- Rebuilding all logging architecture.
- Reworking RealtimeChart or ValueHistory.
- Changing non-ValueLog registry conventions.
- Adding legacy compatibility beyond reading old `TargetPath` source files.

## Risks / Watchouts
- If concrete logger classes directly subscribe to registry events, avoid per-logger global broad event scanning. Prefer the actual control item change event where possible.
- If `Item.Changed` fires on the UI path, the handler must only schedule background work and return immediately.
- Stop may still take time internally while queued writes drain; that is acceptable only if it is fully off the UI/event path.
- Be careful not to use `read` child metadata for headers.
- Avoid keeping both wrapper projection and direct logger item ownership; mixed ownership is the current source of confusion.

## Notes
- The key design rule is: the manager owns the collection; the logger owns its own items and lifecycle.
- Do not use `Dictionary<string, object>` in production code. Use a typed local interface or base class so tests and browser status remain readable.
- The desired simplification is not a new abstraction framework; it is removing the current wrapper/projection chain.
