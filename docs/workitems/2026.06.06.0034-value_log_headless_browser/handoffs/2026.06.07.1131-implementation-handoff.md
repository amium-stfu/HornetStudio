# IMPLEMENTATION HANDOFF

## Goal
Reduce the ValueLog runtime implementation to a simple logger ownership model:
project load reads `ValueLog/csv` and `ValueLog/sql`, creates configured `CsvLogger` and `SqlLogger` instances, stores them in one manager dictionary, and exposes only writable host items for control. The only external lifecycle control is `.run = true/false`. After implementation, clean up obsolete wrapper, command, and duplicate lifecycle code.

## Scope
Included:
- Keep `CsvLogger.cs`, `SqlLogger.cs`, and one manager as the runtime architecture.
- Read `ValueLog/csv/*.yaml` as CSV logger definitions and `ValueLog/sql/*.yaml` as SQL logger definitions.
- Create concrete logger instances during project/folder synchronization.
- Configure each logger from YAML and add resolved source items through `.AddItem(...)` or the closest existing equivalent.
- Store concrete logger instances in a dictionary keyed by folder and logger id.
- Publish host items for each logger, including `run`, `output_directory`, `filename`, status, and diagnostics.
- Make `.run = true/false` the only public lifecycle control.
- Remove public `commands.start` and `commands.stop` ValueLog items.
- Remove `ValueLogRuntime` and cleanup obsolete runtime wrapper references after the simplified model works.

Not included:
- Separate CSV and SQL browser UIs.
- Restoring CSV/SQL page widgets as runtime owners.
- Reworking unrelated logging systems such as `ProcessLog`.
- Keeping parallel legacy ValueLog runtime command paths after cleanup.

## Starting Point
- `CsvLogger` and `SqlLogger` are already the real background logging implementations.
- `ValueLogRuntime` currently wraps those loggers and duplicates lifecycle, registry projection, source resolution, and command handling.
- `ValueLogRuntimeManager` currently owns `ValueLogRuntime` wrappers instead of concrete loggers.
- The browser currently calls manager Start/Stop methods and may await work that should be detached from the UI path.
- The desired control surface is one writable item: `studio.<folder>.value_log.<id>.run`.

## Tasks
1. Define a small shared manager entry shape for a configured concrete logger.
2. Extend `CsvLogger` and `SqlLogger` only as needed so they can expose `Run`, status, output path, last file, error, and background lifecycle without Avalonia dependencies.
3. Refactor the manager to create concrete loggers directly from loaded YAML definitions.
4. Publish only the required host items for each logger.
5. Route `run` item changes to asynchronous logger lifecycle changes.
6. Update browser code so Start/Stop UI actions only write `.run` when such actions still exist in the browser surface.
7. Remove `commands.start`, `commands.stop`, `ValueLogRuntime`, and tests/docs/code paths that reference the wrapper model.
8. Run cleanup verification and solution build.

## File-Level Changes
- `src/HornetStudio.Host/Logging/CsvLogger.cs` -> own CSV runtime state, item source binding, output path fields, run-state handling, and non-UI background lifecycle.
- `src/HornetStudio.Host/Logging/SqlLogger.cs` -> own SQL runtime state, item source binding, output path fields, run-state handling, and non-UI background lifecycle.
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogRuntimeManager.cs` -> simplify to a dictionary owner for concrete CSV/SQL logger instances and host item projection. Rename only if the rename remains low-risk and complete.
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogRuntime.cs` -> delete after responsibilities are migrated.
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogDefinition.cs` -> keep only if useful as simple YAML/manager DTOs; do not add lifecycle behavior.
- `src/HornetStudio.Editor/Persistence/ValueLog/ValueLogsBrowserDialogWindow.axaml.cs` -> remove direct public Start/Stop lifecycle calls; use `.run` item write or manager run setter only as a host-item equivalent.
- `src/HornetStudio.Editor/Persistence/ValueLog/ValueLogsBrowserDialogWindow.axaml` -> remove visible command concepts if they expose Start/Stop as separate runtime commands rather than writing `run`.
- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs` -> keep project-load synchronization but point it at the simplified manager.
- `src/HornetStudio.Host.Tests/Program.cs` -> replace wrapper-specific tests with tests for project-load sync, `.run` item start/stop, output path item updates, and absence of command items.

## Implementation Order
1. Add or identify a minimal logger interface/internal abstraction only if needed for the manager dictionary, for example `IValueLogger` with `Id`, `Run`, `IsRunning`, `OutputPath`, `StartAsync`, and `StopAsync`. Do not create a new runtime wrapper class.
2. Update `CsvLogger` and `SqlLogger` so each can be configured from manager data and can run independently in the background.
3. Refactor the manager dictionary to store direct logger references, for example by folder then logger id.
4. Move YAML-to-logger construction into the manager: CSV directory creates `CsvLogger`, SQL directory creates `SqlLogger`.
5. Publish host items from the manager:
   - `run` writable bool
   - `output_directory` writable string
   - `filename` writable string
   - `is_running` read-only bool
   - `status` read-only string
   - `last_file` read-only string
   - `error` read-only string
6. Replace manager handling of `commands.start` and `commands.stop` with strict `.run` handling.
7. Ensure `run` writes start asynchronous lifecycle work and return immediately to the caller.
8. Update browser behavior to observe/write the `run` item and not expose or await public Start/Stop commands.
9. Delete `ValueLogRuntime.cs` and remove all references to it.
10. Cleanup stale tests, command item assertions, docs references, comments, and obsolete helper methods.
11. Run focused tests and build.

## Technical Constraints
- Always answer in German in chat; code, comments, XML documentation, UI text, file names, and identifiers remain English.
- Logger classes must not reference Avalonia UI controls or dispatchers.
- UI must not call public Start/Stop commands as lifecycle API. The external control contract is `.run = true/false`.
- Manager-owned registry event handling must filter to owned ValueLog runtime paths before doing any work.
- Do not keep duplicate lifecycle paths. `.run`, `commands.start`, and `commands.stop` must not coexist as public control paths.
- Keep the architecture minimally fragmented. No extra `ValueLogRuntime` wrapper or speculative lifecycle service.
- If a simple DTO remains for YAML parsing, it must stay data-only.

## Acceptance Criteria
- Project load reads `ValueLog/csv` and `ValueLog/sql` and creates direct `CsvLogger` / `SqlLogger` instances.
- The manager stores direct logger references in a dictionary and does not own `ValueLogRuntime` wrappers.
- Each logger exposes host items for runtime control/status.
- The only public lifecycle control item is `.run`.
- Writing `.run = true` starts the logger asynchronously.
- Writing `.run = false` stops the logger asynchronously.
- UI/browser interaction does not freeze on logger start or stop.
- `commands.start` and `commands.stop` are removed from ValueLog projection and tests.
- `ValueLogRuntime.cs` is deleted or no longer participates in runtime behavior.
- Cleanup removes stale wrapper references, duplicate lifecycle methods, and command-item documentation/tests.

## Verification
- Run focused host tests:
  `dotnet build src/HornetStudio.Host.Tests/HornetStudio.Host.Tests.csproj -v:minimal`
- Run the built host self-test executable directly if required by the existing test setup.
- Run solution build:
  `dotnet build HornetStudio.sln --no-restore -v:minimal`
- Manual smoke test:
  load the demo project, open the ValueLog browser, toggle `run` for one CSV and one SQL logger, and confirm the UI remains responsive.
- Manual smoke test:
  verify no `commands.start` or `commands.stop` items are published for ValueLog loggers.

## Out of Scope
- Replacing the shared ValueLog browser with separate CSV/SQL management windows.
- Changing the folder layout away from `ValueLog/csv` and `ValueLog/sql`.
- Full rewrite of CSV/SQL persistence internals beyond lifecycle and item-control cleanup.
- Reworking unrelated widget, monitor, controller, UDL, or ProcessLog systems.

## Risks / Watchouts
- If `SqlLogger.Stop()` waits on spin/sleep loops, removing `ValueLogRuntime` alone may not fully solve stop latency. Fix the concrete logger loop if needed.
- A manager-level registry subscription must be scoped to ValueLog paths only.
- If the browser still has visible Start/Stop buttons, they must become simple `.run` writers, not public command calls.
- Keep host item paths stable except for the deliberate removal of `commands.start` and `commands.stop`.
- Avoid carrying old wrapper names in tests or comments after cleanup.
