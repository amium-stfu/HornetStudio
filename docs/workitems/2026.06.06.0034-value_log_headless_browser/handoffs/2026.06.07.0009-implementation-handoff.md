# IMPLEMENTATION HANDOFF

## Goal
Simplify the ValueLog runtime architecture by removing the separate `ValueLogRuntime` wrapper layer and making `CsvLogger` and `SqlLogger` the concrete logger runtimes owned by one folder-scoped manager. Keep `ValueLogDefinition` as the persisted file-backed configuration model.

## Scope
Included:
- Replace per-log `ValueLogRuntime` instances with direct `CsvLogger` / `SqlLogger` instances managed by `ValueLogRuntimeManager` or a renamed `ValueLogManager`.
- Keep `ValueLogDefinition`, `ValueLogKind`, and `ValueLogSourceDefinition` as data-only configuration records loaded from folder-local YAML files.
- Move runtime status, output path updates, command handling, source binding, and registry projection out of `ValueLogRuntime` into the manager and/or the concrete logger classes.
- Extend `CsvLogger` and `SqlLogger` only with the runtime state and async lifecycle surface required for direct manager control.
- Make browser Start/Stop fire manager operations without freezing the UI.
- Update focused host tests to cover the simplified manager-owned CSV/SQL logger flow.

Not included:
- Replacing the shared ValueLog browser UI with separate CSV and SQL browsers.
- Removing file-backed ValueLog YAML definitions.
- Reintroducing canvas CSV/SQL logger widgets.
- Reworking `ProcessLog`.
- Broad cleanup of unrelated logger internals beyond what is required to remove the wrapper freeze.

## Starting Point
- `ValueLogDefinition` currently represents the shared persisted configuration and is still useful as a data-only model.
- `ValueLogRuntime` currently wraps either `CsvLogger` or `SqlLogger`, subscribes to `HostRegistries.Data.ItemChanged`, publishes registry items, maps definitions to logger setup, and owns lifecycle locks.
- `CsvLogger` and `SqlLogger` already contain the real background logging loops and file/database runtime behavior.
- `ValueLogRuntimeManager` currently stores `ValueLogRuntime` instances per folder/id and delegates Start/Stop through that wrapper.
- `ValueLogsBrowserDialogWindow` awaits `ValueLogRuntimeManager.StartAsync` and `StopAsync`; the current Stop path can block while concrete logger tasks drain.
- Existing host tests in `src/HornetStudio.Host.Tests/Program.cs` assert `ValueLogRuntime` behavior and must be rewritten around manager behavior.

## Tasks
1. Define the simplified runtime ownership contract for manager-controlled loggers.
2. Add minimal runtime state and async lifecycle members to `CsvLogger` and `SqlLogger`.
3. Refactor `ValueLogRuntimeManager` into the single owner of folder/id logger instances and registry projection.
4. Remove `ValueLogRuntime` and all direct dependencies on it.
5. Update the ValueLog browser to query manager status and queue Start/Stop without UI freeze.
6. Update tests from `ValueLogRuntime` assertions to manager/registry/control-item assertions.
7. Run focused host tests and solution build.

## File-Level Changes
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogDefinition.cs` -> keep as data-only persisted configuration. Do not add lifecycle logic here.
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogRuntime.cs` -> remove after migrating its responsibilities into the manager and concrete loggers.
- `src/HornetStudio.Host/Runtimes/ValueLog/ValueLogRuntimeManager.cs` -> refactor to own `CsvLogger` and `SqlLogger` instances directly. Optionally rename to `ValueLogManager` only if all references are updated cleanly.
- `src/HornetStudio.Host/Logging/CsvLogger.cs` -> add minimal state/properties needed by manager projection, such as `Id`, `Status`, `LastError`, `OutputPath`, `LastFile`, and an async Start/Stop API if needed.
- `src/HornetStudio.Host/Logging/SqlLogger.cs` -> add the same minimal state/properties and async lifecycle surface.
- `src/HornetStudio.Editor/Persistence/ValueLog/ValueLogsBrowserDialogWindow.axaml.cs` -> replace `TryGetRuntime(...).IsRunning` with manager status lookup and make Start/Stop handlers queue operations so the UI returns immediately.
- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs` -> keep folder-load synchronization, but call the simplified manager API.
- `src/HornetStudio.Host.Tests/Program.cs` -> replace `ValueLogRuntimePublishesControlItems`, `ValueLogRuntimeControlItemsUpdateOutputPath`, and `ValueLogRuntimeRunValueStartsAndStops` with manager-based tests.

## Implementation Order
1. Introduce a small internal manager-owned runtime entry model, for example a private record containing `ValueLogDefinition`, `CsvLogger?`, `SqlLogger?`, status, last error, and operation task.
2. Move source resolution, source name resolution, registry path construction, registry snapshot publishing, output directory/filename updates, and control item handling from `ValueLogRuntime` into `ValueLogRuntimeManager`.
3. Change `ValueLogRuntimeManager.SyncDefinitions(...)` to create/update direct logger entries instead of `ValueLogRuntime` instances.
4. Change `StartAsync`, `StopAsync`, `ReleaseFolder`, and auto-start handling so operations are serialized per folder/id but do not block UI callers unnecessarily.
5. Extend `CsvLogger` and `SqlLogger` so the manager can start/stop them directly and read their status without needing a wrapper.
6. Delete `ValueLogRuntime.cs` once no references remain.
7. Update browser status lookup and Start/Stop/Delete handlers.
8. Update host tests and any compile references.
9. Run verification.

## Technical Constraints
- Chat responses remain German; code, comments, XML documentation, UI text, file names, and identifiers remain English.
- Keep `ValueLogDefinition` data-only. It is persisted configuration, not runtime ownership.
- Prefer a minimally fragmented architecture: one manager plus concrete CSV/SQL logger runtimes.
- Browser-hosted controls and manager windows must use scoped registry relevance and must not broadly react to unrelated registry changes.
- Registry event filtering must happen before any UI-thread work is scheduled.
- Runtime services must be host-owned and usable without Avalonia controls.
- Do not restore CSV/SQL page widget ownership.
- Avoid silent exception swallowing in new lifecycle code. Log failures and publish an error status.

## Acceptance Criteria
- `ValueLogRuntime` no longer exists or has no remaining runtime-wrapper responsibility.
- `ValueLogRuntimeManager` or `ValueLogManager` directly owns `CsvLogger` and `SqlLogger` instances by folder/id.
- `ValueLogDefinition` remains the shared persisted configuration model for YAML-backed CSV and SQL logs.
- Loading a project creates or synchronizes logger entries from the folder-local ValueLog definitions.
- Start/Stop from the ValueLog browser does not freeze the UI while logger startup/shutdown work completes.
- Runtime registry items for run, output directory, filename, commands, status, last file, and errors continue to exist under stable value log paths.
- CSV and SQL logs can still start, stop, and write output from file-backed definitions.

## Verification
- Run focused host self-tests:
  `dotnet build src/HornetStudio.Host.Tests/HornetStudio.Host.Tests.csproj -v:minimal`
- Run the built host self-test executable directly if needed, because it is a console self-test project.
- Run the solution build:
  `dotnet build HornetStudio.sln --no-restore -v:minimal`
- Manual smoke test:
  load the demo project, open the ValueLog browser, start and stop one CSV log and one SQL log, and confirm the dialog remains responsive.
- Manual smoke test:
  change output directory or filename through registry/browser controls and confirm the next start uses the updated path.

## Out of Scope
- Changing the YAML file layout under `Folder/ValueLog/csv/*.yaml` and `Folder/ValueLog/sql/*.yaml`.
- Changing the shared browser into two independent management surfaces.
- Adding a replacement page widget.
- Refactoring unrelated monitoring, controller, UDL, enhanced signal, or process log runtimes.

## Risks / Watchouts
- Stop can still feel slow if `CsvLogger.Stop()` or `SqlLogger.Stop()` waits for queued writes to drain. The browser must not await this on the UI path unless it shows a non-blocking busy state.
- `SqlLogger.RunLogger` currently uses sleep/spin timing. If Stop remains slow after removing `ValueLogRuntime`, inspect the SQL logger loop directly.
- Global registry subscriptions must not multiply per logger. Prefer one manager-level subscription with strict path filtering.
- Keep registry paths stable so existing browser-facing workflows and tests do not break unnecessarily.
- If the manager is renamed, update all references and tests in one pass to avoid mixed `ValueLogRuntimeManager` / `ValueLogManager` naming.

## Notes
- The desired architecture is:
  `ValueLogDefinition files -> ValueLogManager -> CsvLogger / SqlLogger`.
- `ValueLogDefinition` is retained because removing it would only move the same persisted configuration shape into the browser, manager, or loose dictionaries.
- The implementation should prioritize eliminating the extra runtime wrapper and the Start/Stop freeze over cosmetic renames.
