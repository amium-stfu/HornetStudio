# DEBUG REPORT

## Problem
ValueLog Start and Stop initially froze the UI on some paths, published obsolete `commands.start` and `commands.stop`, and still carried a hidden fourth runtime layer in `value_log_runtime.cs`. Even after the public control path moved to `.run`, the internal architecture still did not match the intended end state of one manager plus direct `CsvLogger` / `SqlLogger` ownership.

## Expected Behavior
Starting or stopping a ValueLog should return control to the UI immediately and update the list/status asynchronously. ValueLog projections should expose `run`, `output_directory`, and `filename` without separate command items. The runtime architecture should be reduced to three files: `CsvLogger.cs`, `SqlLogger.cs`, and one manager file that owns direct logger entries and publishes the registry projection.

## Actual Behavior
The public behavior issues were already fixed, but the internal cleanup was incomplete: `value_log_runtime.cs` still owned lifecycle, source resolution, and registry projection, and `ValueLogRuntimeManager` still depended on those wrapper types. That meant the codebase still had an unnecessary runtime abstraction even though `.run` had become the public control path.

## Attempted Fixes
- Move backend logger startup work in `ValueLogRuntime.StartAsync()` into `Task.Run` -> reduced one synchronous segment but UI still blocked.
- Remove `RefreshFolderBindings(...)` from the ValueLog dialog save/start/delete path and replace it with direct background `SyncDefinitions(...)` execution plus UI-thread marshalled state updates.
- Remove synchronous `GetAwaiter().GetResult()` lifecycle transitions from `ValueLogRuntimeManager.SyncDefinitions(...)` and serialize `ValueLogRuntime` start/stop operations with an async lifecycle lock -> should prevent UI-thread freeze even if `SyncValueLogs(...)` is still called from UI code.
- Replace the public `ValueLogRuntime` wrapper with manager-owned `ValueLogEntry` instances and direct `CsvLogger` / `SqlLogger` ownership -> Browser Start/Stop no longer freezes.
- Route registry `run` writes through `ValueLogRuntimeManager` queue instead of calling `SetRunAsync` from `ValueLogEntry.OnRegistryItemChanged` -> ButtonWidget Stop no longer runs Stop work on the registry event path.
- Remove `commands.start` and `commands.stop` from the ValueLog registry snapshot -> only the `run` control remains for start/stop.
- Change CSV header row 2 to write `Caption`/Text only, without falling back to `Name` -> empty text stays empty.
- Change ValueLog source persistence to save `Path` only, while loading old `TargetPath` files for compatibility.
- Resolve `Name`, `Text`, `Unit`, and `Format` from the current registry item at CSV/SQL logger start -> SignalWidget metadata changes are picked up on the next start.
- Wrap initial queued folder operations in `Task.Run(...)` -> new start/stop operations no longer execute the first async segment on the registry event caller.
- Split source resolution into metadata item and value item -> `*.read` paths sample the read value but use parent signal metadata for CSV/SQL headers.
- Collapse `value_log_runtime.cs` into a manager-local direct logger entry type and remove the separate compile include -> the runtime now has only three participating files in this slice: `CsvLogger.cs`, `SqlLogger.cs`, and `ValueLogRuntimeManager.cs`.

## Current Hypothesis (optional)
- Confirmed root cause: the remaining mismatch was architectural, not behavioral. `value_log_runtime.cs` still contained the hidden fourth layer with lifecycle, source resolution, and registry projection logic, so the codebase had not actually reached the intended simplified logger-manager shape.
