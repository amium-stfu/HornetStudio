# IMPLEMENTATION HANDOFF

## Goal
Clean up PID controller runtime channel behavior so command channels update only on real changes, source telemetry remains current, scaled output is visible, and output writes reach the configured target.

## Scope
Included:
- Keep `controller.<name>.read` synchronized with the configured source independently of `run`.
- Stop repeatedly updating `run` and `set` when their values did not change.
- Ensure `run=true` computes and writes the scaled output value to the configured `outputPath`.
- Publish `out` as normalized percent and `out.scaled` as the scaled value written to `outputPath`.
- Change `alert` from text to boolean: `true` when the controller is blocked by an error/fault state, otherwise `false`.
- Keep `state` as the human-readable runtime state text for UI and MonitorWidget display.
- Add focused host/runtime tests.

Not included:
- No PID tuning changes.
- No new controller types.
- No new services, abstraction layers, or dependencies.
- No MonitorWidget implementation changes unless a directly required compatibility issue is found.
- No broad registry or browser-control refactoring.

## Starting Point
- The PID runtime is implemented in `src/HornetStudio.Host/PidControllerRuntime.cs`.
- `run` and `set` are command-like channels but are currently republished as part of broad snapshot publication.
- Source read synchronization was already identified as needing separation from PID output computation.
- Observed behavior: `run` and `set` epochs update continuously; `run=true` starts the runtime but the configured `outputPath` may not receive the output; `out` currently represents a scaled/final value ambiguously rather than exposing percent and scaled values separately.
- Desired MonitorWidget integration: monitor can trigger on `controller.<name>.alert == true` and display `controller.<name>.state`.

## Tasks
1. Review the current `PidControllerRuntime` snapshot publication path and identify which channels are commands, telemetry, output, and metadata.
2. Introduce local change-aware publication inside `PidControllerRuntime` so unchanged `run` and `set` values do not get republished each cycle.
3. Keep input refresh separate from PID compute/write logic.
4. Make output computation store both normalized percent output and scaled output.
5. Publish `out` as normalized percent and `out.scaled` as the scaled output value.
6. Write only the scaled output value to `outputPath`.
7. Convert `alert` publication to a boolean fault flag.
8. Keep `state` as the single textual status/detail channel.
9. Add tests for stopped source read, command channel stability, scaled output publication, output target write, and boolean alert semantics.
10. Update controller widget documentation/help if the public channel shape changes are documented there.

## File-Level Changes
- `src/HornetStudio.Host/PidControllerRuntime.cs` -> local runtime behavior changes: input refresh, change-aware command publication, output percent/scaled split, output target write, boolean `alert`.
- `src/HornetStudio.Host.Tests/Program.cs` -> focused self-tests for PID runtime channels and output writing.
- `src/HornetStudio/docs/widgets/ControllerWidget.md` -> update channel documentation if it describes `alert`, `out`, or output behavior.
- `src/HornetStudio/docs/widgets/help/ControllerWidget.help.md` -> update user-facing help if it describes `alert`, `out`, or output behavior.
- `samples/HornetStudioReference/Folders/main/Controllers/pid_1.yaml` -> change only if verification proves the sample output path is structurally wrong.

## Implementation Order
1. Add or extend host tests that capture current failures before changing runtime behavior.
2. In `PidControllerRuntime`, classify local state fields into:
   - command state: `run`, `set`
   - telemetry: `read`, `state`, `alert`
   - output: `out`, `out.scaled`
   - parameters: PID metadata
3. Replace broad command-channel rewriting with value comparison before publishing `run` and `set`.
4. Ensure source refresh updates `read` while stopped and does not trigger output computation.
5. Change PID output calculation to keep:
   - `outputPercent` from the normalized/clamped internal PID output
   - `scaledOutput` from `ScaleOutput(outputPercent, definition.Pid)`
6. Publish `snapshot["out"].Value` and `snapshot["out"].Properties["read"].Value` as `outputPercent`.
7. Publish `snapshot["out"]["scaled"].Value` and `snapshot["out"]["scaled"].Properties["read"].Value` as `scaledOutput`.
8. Write `scaledOutput` to `_outputCandidates`.
9. Replace text alert assignments with boolean fault semantics:
   - `false`: `Stopped`, `Running`, and other non-fault normal states
   - `true`: missing/non-numeric source while run is requested, missing/non-numeric setpoint while run is requested, invalid parameters, invalid output, output unavailable
10. Keep detailed text only in `state`.
11. Verify `run=true` writes the configured output item and does not merely update the controller's own `out`.
12. Update documentation if the changed channel structure is part of the documented widget/runtime contract.

## Technical Constraints
- Keep changes local to existing runtime classes.
- Do not introduce new dependencies.
- Use existing `EnhancedSignalPathHelper` path normalization and candidate resolution.
- Registry event handlers must continue to filter by owned runtime paths, configured source paths, output paths, or explicitly relevant descendant/ancestor paths.
- User-visible runtime state strings must be English.
- Code, comments, XML documentation, UI text, file names, and identifiers must be English.
- Prefer named parameters for calls with unclear or multiple similar parameters.
- Avoid repeatedly publishing unchanged values if that advances epochs unnecessarily.

## Acceptance Criteria
- `controller.<name>.read` mirrors the current numeric source even when `run=false`.
- `controller.<name>.run` epoch does not change repeatedly while the value remains unchanged.
- `controller.<name>.set` epoch does not change repeatedly while the value remains unchanged.
- With `run=true`, the configured `outputPath` receives the scaled output value.
- `controller.<name>.out` exposes the normalized output percent.
- `controller.<name>.out.scaled` exposes the scaled output value.
- `controller.<name>.alert` is boolean.
- Fault states set `alert=true` and put the readable reason into `state`.
- Normal states set `alert=false`.
- Existing PID runtime behavior remains compatible apart from the intentional `alert` and `out.scaled` channel shape changes.

## Out of Scope
- Reworking MonitorWidget behavior.
- Reworking EnhancedSignal runtime.
- Reworking UDL module simulation.
- Adding new PID parameter schema.
- Keeping a separate textual `alert` channel.

## Risks / Watchouts
- If `outputPath` points to a channel whose writes require a specific child/property convention, `TryWriteValue` may need to use the existing registry write API correctly rather than only updating a root value.
- Changing `alert` from string to bool is an intentional runtime contract change; update documentation and tests accordingly.
- Avoid recursive snapshot updates via `ItemChanged`.
- Avoid hiding diagnostics: `state` must remain clear enough for MonitorWidget display.
- `out` semantics must be explicit so users do not confuse percent with the physical output value.

## Notes
- The preferred runtime shape is:

```text
controller.<name>
  read
  set
  run
  out
    scaled
  state
  alert
  parameters
```

- `run` means requested enable/disable.
- `state` means actual runtime status or fault reason.
- `alert` means a boolean fault indicator suitable for MonitorWidget triggers.
- `outputPath` receives `out.scaled`, not `out`.
