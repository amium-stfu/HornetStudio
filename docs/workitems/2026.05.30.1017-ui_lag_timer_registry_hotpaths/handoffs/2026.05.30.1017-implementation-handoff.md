# IMPLEMENTATION HANDOFF

## Goal

Reduce UI lags during normal runtime by removing expensive timer and registry hotpath work from the UI-critical path.

The current startup is still not perfectly clean, but this workitem focuses on recurring UI lags while the process is running.

## Scope

Included:

- Optimize `RealtimeChart` sampling so timer ticks do not repeatedly resolve registry paths.
- Reduce `Monitor` steady-state UI-thread work where benchmark data shows repeated `Evaluate` and `PublishRuntime` costs.
- Keep existing UI behavior and persisted widget behavior.
- Keep diagnostics sufficient to verify whether lags moved or disappeared.

Not included:

- UDL browser migration.
- Old UDL control redesign.
- Full registry redesign.
- ScottPlot rendering redesign.
- New dependencies.

## Starting Point

Latest observed log:

- `src/HornetStudio/bin/Debug/net9.0-windows/logs/host-20260530.log`
- `UI benchmark summary`: `Status="Fail"`, `MaxUiDelayMs=13383.1`, `P95UiDelayMs=154.9`
- `UI responsiveness spike`: `76` spikes over the benchmark run
- `ChartRenderCount=434`, `ChartRenderMaxMs=18.4`, `ChartRenderP95Ms=4.5`
- `RealtimeChart.SampleCurrentValues.ResolveSamples`: `Count=926`, `MaxMs=663`, `P95Ms=37.4`
- `RealtimeChart.SampleCurrentValues.AppendSamples`: `Count=926`, `MaxMs=3`, `P95Ms=0`
- `MonitorRuleRow[monitor_rule_1].Evaluate`: `Count=72`, `MaxMs=159.4`, `P95Ms=70.3`
- `MonitorRuleRow[monitor_rule_2].Evaluate`: `Count=72`, `MaxMs=79.6`, `P95Ms=59.7`
- `MonitorRuleRow[monitor_rule_3].Evaluate`: `Count=72`, `MaxMs=67.7`, `P95Ms=63.3`
- `MonitorRuleRow[*].PublishRuntime` also appears repeatedly on the UI thread.

Interpretation:

- Chart rendering itself is not the main bottleneck.
- `RealtimeChart` sampling is expensive because it resolves source paths on every timer tick.
- `Monitor` evaluation/publishing is a separate UI-thread lag source.
- Startup UDL costs still exist, but they are not the focus of this workitem.

## Tasks

1. Optimize `RealtimeChart` sampling bindings.
2. Keep `RealtimeChart` rendering unchanged unless needed for integration.
3. Reduce `Monitor` steady-state UI-thread blocking.
4. Preserve and adjust diagnostics so benchmark summaries can compare before/after.

## File-Level Changes

- `src/HornetStudio.Editor/Widgets/RealtimeChart/RealtimeChartControl.axaml.cs`
  - Add a runtime binding model for chart series inside the existing chart control/state structure.
  - Resolve `ChartSeriesConfiguration.TargetPath` to `ItemModel` during configuration/rebind, not on every sample tick.
  - Re-resolve missing or changed bindings only on chart configuration changes or with a low-frequency retry.
  - Keep timer ticks cheap: read numeric values from already resolved items and append samples.
  - Keep existing lifecycle gates and per-state non-reentrant sampling guard.

- `src/HornetStudio.Editor/Widgets/Monitor/MonitorControl.axaml.cs`
  - Inspect `MonitorRuleRow` evaluation and runtime publishing.
  - Move expensive non-visual evaluation work off the UI thread where possible.
  - If UI-thread access is required for part of the rule, split evaluation into a cheap UI snapshot and background computation.
  - Coalesce or skip unchanged runtime publishing to avoid repeated UI-thread work.

- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs`
  - Keep current benchmark categories.
  - Add or adjust timing names only if needed to distinguish chart bind resolution from chart sample value reads.
  - Avoid high-frequency per-tick warning spam.

## Implementation Order

1. RealtimeChart binding cache
   - Identify the current `ChartSeriesConfiguration` flow.
   - Add an internal binding representation that contains the series configuration and the resolved `ItemModel?`.
   - Update bindings when chart series configuration changes.
   - Sample from bindings without calling `TryResolveSeriesItem` for every tick.

2. RealtimeChart retry and invalidation
   - If a binding cannot resolve, retry at a low frequency, not every sample tick.
   - Rebuild bindings when target paths, folder name, chart series definitions, or refresh/history settings change.
   - Keep append and trim behavior unchanged.

3. Monitor UI-thread reduction
   - Inspect `MonitorRuleRow.Evaluate`, `EvaluateState`, and `PublishRuntime`.
   - Separate data lookup/evaluation from UI state mutation.
   - Ensure timer ticks do not execute repeated heavy work on `Dispatcher.UIThread`.
   - Publish runtime state only when values actually changed or at a coalesced interval.

4. Diagnostics and verification
   - Ensure benchmark summaries still include chart sample timing and monitor timing.
   - Prefer aggregate summaries over per-event warnings.

## Technical Constraints

- Use existing project patterns and dependencies.
- Do not introduce new runtime dependencies.
- Keep code and identifiers in English.
- Chat/documentation for this handoff can remain concise, but code comments/XML docs must be English.
- Do not change public APIs unless necessary.
- Avoid broad refactoring outside the listed files.
- Timer and runtime work must not directly enqueue UI work unless relevance and change-type checks are cheap and explicit.

## Acceptance Criteria

- Chart rendering remains functional.
- Realtime Chart still updates while visible and active.
- `RealtimeChart.SampleCurrentValues.ResolveSamples` count and timing drop materially, or the timing is split so the per-tick path no longer includes repeated registry resolution.
- `RealtimeChart.SampleCurrentValues.AppendSamples` remains cheap.
- Monitor rule evaluation no longer produces repeated `50-150 ms` UI-thread operations during normal runtime.
- Benchmark `P95UiDelayMs` improves materially from the observed `154.9 ms`.
- No new warning storm appears in `host-20260530.log`.

## Out of Scope

- Fixing all startup UDL spikes in this workitem.
- Migrating UDL client controls to browser-hosted controls.
- Replacing ScottPlot.
- Changing persisted chart or monitor configuration formats unless unavoidable.

## Risks / Watchouts

- Cached chart bindings can become stale if registry items are replaced. Add explicit invalidation or low-frequency retry for unresolved/missing bindings.
- Reading `ItemModel` values from background timer threads must be safe. If not safe, use a cheap immutable value snapshot or registry-safe accessor rather than touching UI objects.
- Moving monitor evaluation off the UI thread can expose UI-object access that must be isolated into a UI snapshot step.
- Coalescing monitor publishing must not hide meaningful state transitions.
