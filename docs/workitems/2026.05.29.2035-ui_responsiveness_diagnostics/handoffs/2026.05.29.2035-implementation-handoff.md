# IMPLEMENTATION HANDOFF

## Goal
Add lightweight diagnostics to identify short, periodic UI stalls in HornetStudio without relying on the Visual Studio profiler.

## Scope
Included:
- Add an opt-in application-level UI thread responsiveness probe.
- Log only meaningful Dispatcher latency spikes.
- Add targeted timing around suspected UI paths after the global probe is available.
- Provide a repeatable manual validation workflow using `dotnet-counters`.

Explicitly NOT included:
- Do not optimize the realtime chart yet.
- Do not redesign chart rendering, registry updates, dialog creation, or widget architecture.
- Do not introduce new runtime dependencies.
- Do not add always-on noisy logging in normal user builds.

## Starting Point
- The realtime chart visibly exposes short lags because its timeline moves continuously.
- The UI also pauses briefly when dialogs are opened, so the issue is likely broader than `RealtimeChartControl`.
- Visual Studio profiler is currently unreliable in the user's installed version.
- Relevant likely causes are Dispatcher backlog, blocking UI-thread work, GC/allocation spikes, or expensive rendering/layout paths.

## Tasks
1. Locate the existing application startup and logging patterns.
2. Add an opt-in UI thread latency probe that schedules recurring Dispatcher callbacks and measures execution delay.
3. Gate diagnostics behind an environment variable, command line switch, debug setting, or existing diagnostics configuration pattern.
4. Log only latency spikes above useful thresholds, for example `> 50 ms`, `> 100 ms`, and `> 250 ms`.
5. Include compact context in spike logs where cheap and safe: active window/dialog state, current thread id, interval, delay, and timestamp.
6. Add targeted timing to dialog opening paths only after the global probe is present.
7. Add targeted timing to `RealtimeChartControl.RenderPlot()` only as diagnostic correlation, not as an optimization.
8. Document the manual verification workflow with `dotnet-counters`.
9. Build the solution and verify that diagnostics are disabled by default.

## File-Level Changes
- `src/HornetStudio/App.axaml.cs` -> initialize and stop the global responsiveness probe at application lifetime boundaries.
- `src/HornetStudio/MainWindow.axaml.cs` or an existing diagnostics location -> provide cheap active UI context if already available without broad coupling.
- `src/HornetStudio.Editor/Widgets/RealtimeChart/RealtimeChartControl.axaml.cs` -> add optional timing around render phases only when diagnostics are enabled.
- Dialog entry points such as common editor dialog windows -> add optional timing around construction/show paths after identifying the central opening path.
- `src/HornetStudio/docs/manual/` or existing diagnostics documentation location -> document how to enable diagnostics and how to run `dotnet-counters`, if such documentation exists or is appropriate.

## Implementation Order
1. Inspect existing logging, diagnostics, startup, and shutdown patterns.
2. Choose the smallest suitable location for a global UI responsiveness probe.
3. Implement the opt-in probe with fixed low overhead and spike-only logging.
4. Wire probe startup/shutdown in the application lifecycle.
5. Add one or two focused timing scopes around suspected dialog and chart paths.
6. Run a normal build with diagnostics disabled.
7. Run the app with diagnostics enabled and reproduce: idle, chart visible, dialog open, and normal navigation.
8. Run `dotnet-counters` alongside the app and compare UI spike timestamps with GC/allocation activity.

## Technical Constraints
- Use existing project logging and configuration patterns.
- Keep changes local and minimally fragmented.
- Do not add new dependencies.
- User-visible messages, code comments, XML documentation, and identifiers must be English.
- Chat responses remain German.
- Avoid noisy logs; diagnostics must be disabled by default.
- Do not block the UI thread from inside the diagnostic probe.
- Do not use `.Result` or `.Wait()`.

## Acceptance Criteria
- Diagnostics are disabled by default.
- When enabled, UI thread latency spikes are logged with timestamps and measured delay.
- Opening dialogs while diagnostics are enabled produces enough timing information to identify whether construction/show/layout work correlates with spikes.
- Realtime chart render timing can be correlated with global UI latency spikes.
- Normal operation is not meaningfully affected when diagnostics are disabled.
- No chart optimization or behavioral change is included in this diagnostic-only work.

## Verification
- Build: `dotnet build HornetStudio.sln --no-restore`
- Manual run with diagnostics disabled: no responsiveness logs are emitted.
- Manual run with diagnostics enabled: idle run logs no excessive noise, deliberate UI-heavy actions produce spike logs if they block the Dispatcher.
- External counters:
  - Find process id.
  - Run `dotnet-counters monitor --process-id <PID> System.Runtime`.
  - Compare UI spike timestamps with allocation rate and GC counter changes.

## Out of Scope
- Replacing ScottPlot rendering strategy.
- Changing registry event behavior.
- Refactoring dialog architecture.
- Adding a persistent in-app performance dashboard.
- Creating release/version changes.

## Risks / Watchouts
- A probe interval that is too aggressive can become part of the problem; prefer a modest interval such as `50 ms`.
- Logging every probe result will distort performance; log only spikes.
- Adding context collection inside the probe must stay cheap and must not traverse large visual trees.
- Chart timing should not allocate heavily in the hot path when diagnostics are disabled.
- Dialog timings should target a central path if one exists, otherwise keep instrumentation very narrow.

## Notes
- Treat the first implementation as a measurement layer only.
- If logs show GC correlation, the next workitem should focus on allocation sources.
- If logs show Dispatcher spikes without GC, the next workitem should inspect blocking UI-thread work and Dispatcher flooding.
- If chart render timing correlates with spikes, optimize chart rendering in a separate focused workitem.
