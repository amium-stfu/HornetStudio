# IMPLEMENTATION HANDOFF

## Goal
Add lightweight diagnostics to identify short, periodic UI stalls, with the browser-widget migration treated as the primary suspect.

## Scope
Included:
- Add an opt-in application-level UI thread responsiveness probe.
- Prioritize diagnostics around browser-hosted widgets, registry event handling, and Dispatcher posting.
- Add targeted timing around browser dialog creation/opening paths for Functions, Monitor, Custom Signals, Enhanced Signals, Controllers, and related browser windows.
- Keep realtime chart timing as a visible lag correlation aid only.
- Provide a repeatable manual validation workflow using page scenarios and `dotnet-counters`.

Explicitly NOT included:
- Do not optimize the realtime chart yet.
- Do not redesign browser widgets, registry ownership, or dialog architecture.
- Do not replace browser-hosted widgets with native UI.
- Do not introduce new runtime dependencies.
- Do not add always-on noisy logging in normal user builds.

## Starting Point
- The realtime chart visibly exposes short lags because its timeline moves continuously.
- The UI also pauses briefly when dialogs are opened.
- The user observed that these lags appeared after Functions, Monitor, and similar areas moved from native UI elements to browser-style widgets/dialogs.
- Visual Studio profiler is currently unreliable in the user's installed version.
- Repository rules already state that browser-hosted controls and widgets must not react to all `HostRegistries.Data.ItemChanged` events globally; handlers must filter by relevant owned/configured paths.

## Tasks
1. Inspect existing startup, shutdown, logging, and diagnostics patterns.
2. Add an opt-in global UI thread latency probe that measures Dispatcher callback delay and logs only spikes.
3. Add a small diagnostic classification for spike context, if cheap: active window/dialog name, active page name, visible browser-widget types, and timestamp.
4. Instrument browser dialog open paths before chart internals:
   - Function Browser
   - Monitor Browser
   - Custom Signals Browser
   - Enhanced Signals Browser
   - Controllers Browser
   - Application Explorer if it participates in the same browser-hosted pattern
5. Instrument browser-widget registry event handlers to count:
   - total `ItemChanged` events observed
   - events ignored by filtering
   - events accepted for processing
   - Dispatcher posts generated from registry events
6. Instrument suspicious `Dispatcher.UIThread.Post(...)` paths in browser widgets and related view models to detect posting bursts.
7. Add narrow timing around browser-hosted control initialization, refresh/rebuild methods, and file-backed definition loading where those paths are central and easy to isolate.
8. Keep `RealtimeChartControl.RenderPlot()` timing optional and secondary, used only to correlate visible chart lag with global UI stalls.
9. Document manual test scenarios and `dotnet-counters` correlation.
10. Build the solution and verify diagnostics are disabled by default.

## Implementation Order
1. Confirm or create a minimal diagnostics helper that is disabled by default.
2. Wire a global Dispatcher latency probe with modest interval, for example `50 ms`, and spike-only logging.
3. Add counters/timing around browser dialog open and activation paths.
4. Add counters around browser-widget `HostRegistries.Data.ItemChanged` handlers, especially accepted/ignored event ratios.
5. Add counters around Dispatcher posts emitted by browser widgets.
6. Add targeted timing around heavy browser refresh/rebuild/load methods found during inspection.
7. Add optional chart render timing only after browser instrumentation is in place.
8. Run manual scenarios:
   - page without browser widgets
   - page with one browser widget
   - page with multiple browser widgets
   - chart visible as lag indicator
   - open/activate each browser dialog
   - perform normal data updates while browser widgets are visible
9. Run `dotnet-counters` in parallel and correlate timestamps with GC/allocation activity.
10. Build the solution and keep behavior unchanged when diagnostics are disabled.

## Technical Constraints
- Use existing project logging and configuration patterns.
- Keep changes local and minimally fragmented.
- Do not add new dependencies.
- Diagnostics must be disabled by default.
- Log only spikes and aggregate counts; avoid per-event spam.
- Do not block the UI thread from inside diagnostics.
- Do not traverse large visual trees or enumerate registry contents from every probe tick.
- Browser-hosted controls must filter registry events by owned runtime paths, configured source paths, command paths, or explicitly relevant descendant/ancestor paths.
- User-visible messages, code comments, XML documentation, and identifiers must be English.
- Chat responses remain German.

## Acceptance Criteria
- Diagnostics are disabled by default.
- When enabled, global UI thread latency spikes are logged with timestamp and measured delay.
- Browser dialog opening logs enough timing to show whether construction, attach, activation, refresh, or definition loading correlates with UI stalls.
- Browser widget registry handlers report accepted/ignored event counts and Dispatcher-post counts without noisy per-event logs.
- The diagnostics can distinguish:
  - UI stalls with browser widgets absent
  - UI stalls with browser widgets visible
  - UI stalls during browser dialog opening
  - UI stalls correlated with registry event bursts
  - UI stalls correlated with GC/allocation activity
- Realtime chart timing is secondary and does not drive the first investigation.
- No behavior or optimization change is included beyond diagnostic instrumentation.

## Verification
- Build: `dotnet build HornetStudio.sln --no-restore`
- Manual diagnostics disabled: no responsiveness/browser diagnostic logs are emitted.
- Manual diagnostics enabled:
  - idle page without browser widgets produces little or no spike logging.
  - opening browser dialogs emits compact timing logs.
  - visible browser widgets emit aggregate registry/Dispatcher counters.
  - chart-visible scenario can correlate visual lag with global UI spikes.
- External counters:
  - Find process id.
  - Run `dotnet-counters monitor --process-id <PID> System.Runtime`.
  - Compare UI spike timestamps with allocation rate and GC counter changes.

## Out of Scope
- Optimizing `RealtimeChartControl`.
- Rewriting browser-hosted widgets.
- Changing persisted widget formats.
- Changing registry semantics.
- Adding a permanent in-app performance dashboard.
- Creating release/version changes.

## Risks / Watchouts
- Diagnostics can distort the issue if logging is too frequent; use aggregation and thresholds.
- Dispatcher-post burst counting must not require wrapping every call site if a smaller central pattern exists.
- Registry-event instrumentation should not call expensive path resolution for events that would otherwise be ignored.
- Browser dialog timing should not accidentally force eager initialization that did not previously happen.
- The chart may still allocate heavily, but do not let that distract from browser migration evidence until browser scenarios are measured.

## Notes
- Treat browser migration as the leading hypothesis.
- The first useful answer is not "which method is slow" but whether stalls correlate with browser visibility, browser dialog activation, registry event bursts, Dispatcher post bursts, or GC.
- If browser registry handlers accept too many events, create a follow-up fix workitem focused on filtering and batching.
- If Dispatcher posts are bursty but each unit is cheap, create a follow-up fix workitem focused on coalescing/debouncing.
- If GC correlates strongly, create a follow-up fix workitem focused on allocations in browser refresh/rebuild and chart rendering paths.
