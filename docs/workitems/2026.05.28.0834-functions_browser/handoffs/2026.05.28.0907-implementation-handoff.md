# IMPLEMENTATION HANDOFF

## Goal
Move the folder-local Functions catalog out of the normal canvas widget workflow and make it available through an explicit Admin-only Browser section in the right legend/sidebar. The legend should be split conceptually into a top-down folder area and a bottom-up browser area. Keep existing `Functions` widgets loadable for compatibility, but stop presenting `Functions` as a normal widget for new folder UI composition.

## Scope
Included:
- Add or adapt the right legend/sidebar layout so folder management remains in the upper area and a new `Browser` area appears at the bottom.
- Add a `Functions` browser entry under the `Browser` area.
- Show the Browser area only for Admin-level users.
- Open the folder-local Function Browser from the `Functions` browser entry.
- Reuse the existing `FunctionsControl` catalog/editor behavior as the basis for the browser/dialog where practical.
- Hide or remove `Functions` from the widget selection flow for new widget placement.
- Preserve loading/rendering of existing `ControlKind.Functions` entries from old `Folder.yaml` files.
- Keep `FunctionRegistry`, `RunFunction`, declarative YAML files, Python registry entries, execution, and button integration unchanged unless a minimal adapter is needed for browser hosting.
- Update documentation so Functions are described as a folder-level browser/registry workflow instead of a normal canvas widget.

Not included:
- Moving Custom Signals, Enhanced Signals, Clients, Monitor definitions, or other registries out of `Folder.yaml`.
- Implementing additional browser entries beyond `Functions`; the layout should be ready to add entries such as `Clients` later.
- Changing the `Scripts/Functions/` YAML file format.
- Changing Python function registration or runtime invocation behavior.
- Release/version changes.
- Broad widget-system or permission-system refactoring.

## Starting Point
- The right legend/sidebar already contains folder-related UI such as folder rows, add folder, and delete folder behavior.
- `FunctionRegistry` already exposes folder-local entries independent of any widget placement.
- Declarative function files already live outside `Folder.yaml` below `Scripts/Functions/`, with legacy discovery below `Scripts/Workflows/`.
- `FunctionsControl` currently lives under `src/HornetStudio.Editor/Widgets/Workflow/` and is rendered as a `ControlKind.Functions` widget through `PageEditorControl.axaml` and `FolderEditorControl.axaml`.
- The Functions widget currently acts as a catalog/browser/editor for all functions in the folder, so multiple placed instances show the same content.
- `RunFunction` already resolves stable registry references without requiring a `Functions` widget on the page.
- The migration decision is: make `Functions` available through the Admin-only Browser area, hide it from new widget selection, and keep existing persisted widgets loadable.

## Tasks
1. Locate the current right legend/sidebar structure and identify where the folder list, add folder, and delete folder areas are defined.
2. Split the legend/sidebar layout into a top-down folder-management area and a bottom-aligned Browser area.
3. Determine the existing user-level/admin visibility mechanism and bind the Browser area visibility to Admin access only.
4. Add a Browser header/section and a `Functions` entry with the existing theme and icon conventions.
5. Add a Function Browser dialog/window that hosts the current function catalog/editor UI with the active folder context.
6. Refactor only the minimum needed so `FunctionsControl` can be hosted both by legacy widgets and the new browser, or extract the shared catalog surface into a small focused control if direct reuse is not practical.
7. Wire the `Functions` Browser entry to open the Function Browser for the active folder.
8. Remove or hide `ControlKind.Functions` from the widget selection dialog/list so new pages do not place it as a normal widget.
9. Keep `ControlKind.Functions`, `PageItemModel.IsFunctions`, and existing XAML rendering paths intact enough that older `Folder.yaml` files still open.
10. Update docs and descriptions to explain that Functions are managed through the Admin-only Browser area and are not required as a placed widget.
11. Add or update focused tests where existing test coverage asserts widget selection, user-level visibility, or default item creation behavior.

## Implementation Order
1. Inspect the folder editor sidebar/legend XAML and code-behind to locate layout ownership and user-level visibility patterns.
2. Add the bottom-aligned Admin-only Browser section with a `Functions` entry, using existing theme resources and icon patterns.
3. Add the Function Browser window/dialog shell using existing Avalonia dialog/window conventions from nearby widget editor dialogs.
4. Reuse or minimally adapt `FunctionsControl` so it can receive the active folder context outside canvas placement.
5. Wire the `Functions` Browser entry to open the browser for the current folder.
6. Hide `Functions` from new widget selection while preserving persisted `ControlKind.Functions` handling.
7. Check existing default dimensions/captions code paths and keep them only for legacy loading where required.
8. Update documentation and picker/help descriptions.
9. Run focused tests/build and fix only issues directly caused by this change.

## Technical Constraints
- Chat output must stay German; code, UI text, comments, XML documentation, file names, and technical identifiers must stay English.
- Browser section UI text must be English, for example `Browser` and `Functions`.
- Do not introduce new dependencies.
- Prefer existing Avalonia window/dialog patterns already used in `Widgets/**`.
- Align the Browser area with existing theme resources; no fixed icon colors.
- Keep the architecture minimally fragmented: extract a shared control only if direct reuse of `FunctionsControl` would create awkward coupling.
- Preserve backward compatibility for old `Folder.yaml` files containing `ControlKind.Functions`.
- Do not change public function registry references such as `yaml:<name>`, legacy `declarative:<name>`, or Python references.
- User-visible errors and validation messages must be English.
- Browser visibility must use the existing user-level/admin mechanism rather than inventing a parallel permission model.

## Acceptance Criteria
- The right legend/sidebar has a clear upper folder-management area and a lower Browser area.
- The Browser area is visible only for Admin-level users.
- The Browser area contains a `Functions` entry.
- Clicking `Functions` opens the folder-local Function Browser without placing a `Functions` widget on the canvas.
- The Function Browser lists the same YAML and Python registry entries currently shown by the `Functions` widget.
- Add, edit, delete, refresh, run, and stop behavior remains available where it was previously available.
- New widget selection no longer offers `Functions` as a normal widget.
- Existing folders with persisted `Functions` widgets still load without data loss or hard failure.
- `folder.yaml` for new UI work no longer needs a `Functions` widget just to manage functions.
- Existing `RunFunction` button behavior still works without a `Functions` widget.
- Documentation clearly describes the Admin Browser as the primary workflow and the placed widget as legacy compatibility if it remains visible in old files.

## Verification
- `dotnet build HornetStudio.sln --no-restore`
- Run focused editor tests through the existing test executable/project workflow if affected assertions exist.
- Manually verify in the editor if possible:
  - As Admin, confirm the lower Browser area is visible in the right legend/sidebar.
  - As non-Admin, confirm the Browser area is hidden.
  - Open Function Browser from `Browser` -> `Functions`.
  - Confirm existing functions are listed.
  - Confirm adding/editing one declarative function still writes to `Scripts/Functions/`.
  - Confirm the widget picker no longer offers `Functions`.
  - Confirm an old folder containing a `Functions` widget still opens.

## Out of Scope
- Extracting Custom Signals, Enhanced Signals, or Clients to separate files/browsers.
- Building the final generic browser framework for all future resource types.
- Renaming the persisted `ControlKind.Functions` value.
- Removing legacy `FunctionsControl` rendering entirely.
- Changing function YAML schema.
- Changing release/version metadata or creating tags.

## Risks / Watchouts
- `FunctionsControl` likely assumes `DataContext` is a placed `PageItemModel`; browser hosting must provide equivalent folder context without requiring a persisted widget.
- Hiding `Functions` from the picker must not break deserialization or rendering of existing folders.
- The right legend/sidebar may already have drag/drop assumptions for folder deletion; the bottom Browser area must not interfere with those hit targets.
- Admin visibility must not hide runtime execution; only the browser entry and management surface are Admin-only.
- Documentation loaders may expect one widget description per persisted `Type`; if `Functions` is hidden from picker, keep documentation files coherent rather than deleting them blindly.
- Avoid creating two divergent function catalog UIs. Prefer one shared implementation with a thin browser wrapper.
- If browser hosting uses a temporary `PageItemModel`, ensure it is not accidentally persisted to `Folder.yaml`.

## Notes
- The architectural intent is to make `folder.yaml` primarily a UI composition file. This workitem only performs the first step for Functions.
- The Browser area should be designed as a simple extensible list, not as a large generic browser framework. `Functions` is the only browser entry in this scope.
- If the implementation reveals that `FunctionsControl` cannot be reused cleanly outside a placed widget, extract only the catalog body and actions into a focused reusable control; keep legacy `FunctionsControl` as a wrapper.
- Do not remove compatibility paths until a later cleanup workitem explicitly targets legacy widget removal.
