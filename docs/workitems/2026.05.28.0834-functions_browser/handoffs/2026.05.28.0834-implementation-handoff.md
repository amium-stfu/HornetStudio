# IMPLEMENTATION HANDOFF

## Goal
Move the folder-local Functions catalog out of the normal canvas widget workflow and make it available as an explicit Function Browser window/dialog. Keep existing `Functions` widgets loadable for compatibility, but stop presenting `Functions` as a recommended widget for new folder UI composition.

## Scope
Included:
- Reuse the existing `FunctionsControl` catalog/editor behavior as the basis for a browser/dialog where possible.
- Add an explicit Function Browser entry point from the folder editor UI, preferably near the folder/legend area or another existing folder-level command surface.
- Hide or remove `Functions` from the widget selection flow for new widget placement.
- Preserve loading/rendering of existing `ControlKind.Functions` entries from old `Folder.yaml` files.
- Keep `FunctionRegistry`, `RunFunction`, declarative YAML files, Python registry entries, execution, and button integration unchanged unless a minimal adapter is needed for the browser.
- Update documentation so Functions are described as a folder-level browser/registry workflow instead of a normal canvas widget.

Not included:
- Moving Custom Signals, Enhanced Signals, Monitor definitions, or other registries out of `Folder.yaml`.
- Changing the `Scripts/Functions/` YAML file format.
- Changing Python function registration or runtime invocation behavior.
- Release/version changes.
- Broad widget-system refactoring.

## Starting Point
- `FunctionRegistry` already exposes folder-local entries independent of any widget placement.
- Declarative function files already live outside `Folder.yaml` below `Scripts/Functions/`, with legacy discovery below `Scripts/Workflows/`.
- `FunctionsControl` currently lives under `src/HornetStudio.Editor/Widgets/Workflow/` and is rendered as a `ControlKind.Functions` widget through `PageEditorControl.axaml` and `FolderEditorControl.axaml`.
- The Functions widget currently acts as a catalog/browser/editor for all functions in the folder, so multiple placed instances show the same content.
- `RunFunction` already resolves stable registry references without requiring a `Functions` widget on the page.
- The preferred migration decision is: hide `Functions` from new widget selection, keep existing persisted widgets loadable.

## Tasks
1. Identify the existing folder-level command surface in `FolderEditorControl` or the main editor shell where a Function Browser command naturally belongs.
2. Add a Function Browser dialog/window that hosts the current function catalog/editor UI with folder context.
3. Refactor only the minimum needed so `FunctionsControl` can be hosted both by legacy widgets and the new browser, or extract the shared catalog surface into a small focused control if direct reuse is not practical.
4. Add a folder-level command such as `Functions...` or `Function Browser` that opens the browser for the active folder.
5. Remove or hide `ControlKind.Functions` from the widget selection dialog/list so new pages do not place it as a normal widget.
6. Keep `ControlKind.Functions`, `PageItemModel.IsFunctions`, and existing XAML rendering paths intact enough that older `Folder.yaml` files still open.
7. Update docs and descriptions to explain that Functions are managed through the Function Browser and are not required as a placed widget.
8. Add or update focused tests where existing test coverage asserts widget selection or default item creation behavior.

## Implementation Order
1. Locate the existing widget selection construction and folder-level UI command surface.
2. Add the Function Browser window/dialog shell using existing Avalonia dialog/window conventions from nearby widget editor dialogs.
3. Reuse or minimally adapt `FunctionsControl` so it can receive the active folder context outside canvas placement.
4. Wire the browser opening command from the folder editor UI.
5. Hide `Functions` from new widget selection while preserving persisted `ControlKind.Functions` handling.
6. Check existing default dimensions/captions code paths and keep them only for legacy loading where required.
7. Update documentation and picker/help descriptions.
8. Run focused tests/build and fix only issues directly caused by this change.

## Technical Constraints
- Chat output must stay German; code, UI text, comments, XML documentation, file names, and technical identifiers must stay English.
- Do not introduce new dependencies.
- Prefer existing Avalonia window/dialog patterns already used in `Widgets/**`.
- Keep the architecture minimally fragmented: extract a shared control only if direct reuse of `FunctionsControl` would create awkward coupling.
- Preserve backward compatibility for old `Folder.yaml` files containing `ControlKind.Functions`.
- Do not change public function registry references such as `yaml:<name>`, legacy `declarative:<name>`, or Python references.
- User-visible errors and validation messages must be English.

## Acceptance Criteria
- A user can open the folder-local Function Browser without placing a `Functions` widget on the canvas.
- The Function Browser lists the same YAML and Python registry entries currently shown by the `Functions` widget.
- Add, edit, delete, refresh, run, and stop behavior remains available where it was previously available.
- New widget selection no longer offers `Functions` as a normal widget.
- Existing folders with persisted `Functions` widgets still load without data loss or hard failure.
- `folder.yaml` for new UI work no longer needs a `Functions` widget just to manage functions.
- Existing `RunFunction` button behavior still works without a `Functions` widget.
- Documentation clearly describes the Function Browser as the primary workflow and the placed widget as legacy compatibility if it remains visible in old files.

## Verification
- `dotnet build HornetStudio.sln --no-restore`
- Run focused editor tests through the existing test executable/project workflow if affected assertions exist.
- Manually verify in the editor if possible:
  - Open Function Browser from the folder-level command.
  - Confirm existing functions are listed.
  - Confirm adding/editing one declarative function still writes to `Scripts/Functions/`.
  - Confirm the widget picker no longer offers `Functions`.
  - Confirm an old folder containing a `Functions` widget still opens.

## Out of Scope
- Extracting Custom Signals or Enhanced Signals to separate files/browsers.
- Renaming the persisted `ControlKind.Functions` value.
- Removing legacy `FunctionsControl` rendering entirely.
- Changing function YAML schema.
- Changing release/version metadata or creating tags.

## Risks / Watchouts
- `FunctionsControl` likely assumes `DataContext` is a placed `PageItemModel`; browser hosting must provide equivalent folder context without requiring a persisted widget.
- Hiding `Functions` from the picker must not break deserialization or rendering of existing folders.
- Documentation loaders may expect one widget description per persisted `Type`; if `Functions` is hidden from picker, keep documentation files coherent rather than deleting them blindly.
- Avoid creating two divergent function catalog UIs. Prefer one shared implementation with a thin browser wrapper.
- If browser hosting uses a temporary `PageItemModel`, ensure it is not accidentally persisted to `Folder.yaml`.
