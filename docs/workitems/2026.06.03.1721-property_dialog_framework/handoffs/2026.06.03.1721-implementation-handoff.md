# IMPLEMENTATION HANDOFF

## Goal
Replace the current generic widget settings/property dialog path with a small specialized property dialog framework that keeps standard sections static, makes only the `Properties` section widget-specific, and removes the current MainWindow-coupled UI-thread hydration path that still causes freezes during dialog open and section expansion.

## Scope
Included:
- New property dialog framework core for widget settings dialogs in `HornetStudio.Editor`
- Static framework-owned standard sections: `Identity`, `Design`, `Header`, `Body`, `Footer`, `SourceMeta`
- Widget-specific `Properties` extension point
- Dialog-local session/viewmodel state instead of binding directly to `MainWindowViewModel.EditorDialogSections` / `EditorDialogActionFields`
- New path enabled first for `Signal` and `ItemModel`
- Legacy property dialog path kept in parallel for other widget types during migration

Explicitly not included:
- Full migration of every widget type in one step
- Reworking UDL client dialogs or other already-responsive domain-specific dialogs
- Large redesign outside the settings/property dialog path
- Broad visual redesign of dialog styling

## Starting Point
- The current property dialog path is driven from `MainWindowViewModel` and uses dynamic `EditorDialogSection` / `EditorDialogField` generation.
- UI-freeze symptoms were reduced but not solved by local optimizations; expanding sections still causes noticeable freezes because the dialog remains coupled to the shared UI thread and global editor state.
- `CachedFolderHostControl` keeps multiple folder editors alive, which amplified earlier dialog state fan-out.
- The UDL client browser/dialog path is a good positive reference because it uses more focused, dialog-local state and a stable domain-specific layout.
- The user wants a proper reusable framework, not more local patches in the current generic dialog.

## Tasks
1. Introduce a dedicated property dialog framework core with dialog-local session state and a stable section model.
2. Define a fixed set of framework sections for all widget settings dialogs and implement them as stable renderers or stable field groups.
3. Introduce a widget-specific `Properties` provider contract that supplies only the widget-dependent property section.
4. Extract option/lookup loading out of `MainWindowViewModel` into dedicated providers that can prepare expensive data independently from dialog rendering.
5. Build a new dialog host path that opens the new framework dialog without depending on `MainWindowViewModel.IsEditorDialogOpen` or `EditorDialogSections`.
6. Migrate `Signal` and `ItemModel` to the new path first and keep all other widget types on the legacy path.
7. Verify that opening and expanding the migrated dialogs no longer causes visible MainWindow freezes.

## File-Level Changes
- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs` -> stop owning the new property dialog state for migrated types; reduce responsibility to request/open routing and commit entry points.
- `src/HornetStudio.Editor/Widgets/Common/EditorPropertyDialogWindow.axaml.cs` -> either host the new dialog session directly or be replaced by a new framework-specific host with explicit ownership.
- `src/HornetStudio.Editor/Widgets/Common/EditorPropertyDialog.axaml` -> convert from generic dynamic property inspector toward framework shell composition, or replace with a new shell if cleaner.
- `src/HornetStudio.Editor/Widgets/Common/EditorPropertyDialog.axaml.cs` -> move section toggle behavior to framework-local session logic.
- `src/HornetStudio.Editor/ViewModels/EditorDialogBindingDefinition.cs` -> legacy reference only; reuse selectively or retire for migrated types.
- `src/HornetStudio.Editor/ViewModels/EditorDialogField.cs` -> legacy reference only; do not let the new framework depend on the current global dynamic field model unless there is a clear transition layer.
- `src/HornetStudio.Editor/ViewModels/EditorDialogSection.cs` -> legacy reference only; new framework may keep a lightweight section VM but should not depend on the current rebuild/lazy workaround behavior.
- `src/HornetStudio.Editor/Widgets/FolderEditor/FolderEditorControl.axaml.cs` -> route settings requests into the new dialog host for migrated types.
- `src/HornetStudio.Editor/Widgets/FolderEditor/CachedFolderHostControl.axaml.cs` -> ensure the new dialog host path does not fan out global dialog state across cached folder editors.
- `src/HornetStudio.Editor/Widgets/UdlClient/ClientsBrowserDialogWindow.axaml.cs` -> architectural reference for focused dialog-local state and responsive window behavior.

## Implementation Order
1. Create the framework core types and dialog-local session model in a new focused namespace/folder under `src/HornetStudio.Editor`.
2. Implement the fixed standard sections and dialog shell without wiring any widget-specific `Properties` yet.
3. Add the widget-specific `Properties` extension contract and implement providers for `Signal` and `ItemModel`.
4. Extract target/property/options loading into provider services used by the new session model.
5. Add open-routing from the existing editor path so `Signal` and `ItemModel` use the new framework dialog while legacy types continue using the old dialog.
6. Implement commit/cancel/apply flow back into the underlying `FolderItemModel` data.
7. Remove migrated types from the old generic dialog path and verify no remaining direct dependency on the old `EditorDialogSections` flow for those types.

## Technical Constraints
- Keep changes limited to the settings/property dialog path and required supporting classes.
- Follow existing HornetStudio solution rules: minimal fragmentation, no unnecessary abstraction layers beyond the actual framework core.
- Keep code/comments/identifiers in English.
- Keep user-visible validation and error messages in English.
- Prefer clear explicit providers over reflection-heavy generic dialog magic.
- Do not require all widget types to migrate before the new framework can be used.
- Preserve the currently responsive UDL client path; use it as a structural reference, not as something to refactor during this work.

## Acceptance Criteria
- Opening the settings dialog for a simple `Signal` or `ItemModel` no longer causes a visible MainWindow freeze.
- Expanding `Properties` or other sections in the migrated dialog no longer causes visible freezes across MainWindow widgets.
- The new dialog path for migrated types no longer depends on `MainWindowViewModel.EditorDialogSections`, `EditorDialogActionFields`, or `IsEditorDialogOpen`.
- `Apply`, `Save`, and `Cancel` behave correctly with dialog-local state.
- Non-migrated widget types still function via the legacy dialog path.

## Verification
- Manual: open a simple signal widget settings dialog and verify there is no noticeable freeze before the dialog appears.
- Manual: expand the `Properties` section for the migrated signal/item dialog and verify MainWindow widgets remain responsive.
- Manual: edit values, use `Apply`, `Save`, and `Cancel`, and verify persisted behavior.
- Build: `dotnet build HornetStudio.sln --no-restore -c Debug`
- Optional comparison: compare perceived responsiveness with the UDL client browser/dialog path.

## Out of Scope
- Converting every widget dialog in the same implementation.
- Replacing other specialized dialogs such as UDL client, workflow, monitor, or browser dialogs unless directly needed by the new framework core.
- Solving unrelated UI performance problems outside the property dialog path.

## Risks / Watchouts
- Do not let the new framework accidentally reintroduce a dependency on `MainWindowViewModel` for field hydration or option loading.
- Watch for partial migration bugs where some logic still reads from legacy dynamic dialog fields while migrated types use the new session model.
- Registry-backed option providers must avoid synchronous heavy work on the UI thread.
- Be careful with commit semantics so `Apply` does not mutate stale or shared state unexpectedly.
- Keep the old and new dialog paths clearly separated during migration to avoid mixed lifecycle bugs.

## Notes
- The key architectural decision is fixed framework-owned standard sections plus a widget-specific `Properties` section provider.
- `Action` should remain a second explicit extension point only if needed; do not expand the initial framework scope unless implementation pressure requires it.
- The first implementation slice should be intentionally narrow: `Signal` and `ItemModel` only.
