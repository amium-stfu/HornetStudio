# IMPLEMENTATION HANDOFF

## Goal
Reduce browser-control registry event load by identifying the sources behind high `RegistryEvents` counts and introducing folder/domain-scoped registry subscriptions or an equivalent scoped dispatch path. The target is that browser controls receive only relevant registry events for their own folder/domain, not all project-wide registry traffic.

## Scope
Included:
- Extend UI responsiveness diagnostics and benchmark output so the cause of high browser `RegistryEvents` counts is visible.
- Add per-source registry event breakdowns by key prefix, folder/domain, and events-per-second where practical.
- Map current browser-control registry subscriptions that listen to `HostRegistries.Data.ItemChanged`.
- Introduce a scoped subscription/helper path so current browser controls can subscribe by folder/domain prefix instead of receiving global events and filtering locally.
- Migrate the current browser-style controls that are already part of the diagnostics: custom signals, enhanced signals, controllers, monitor view, monitor rules, and functions if it gets registry event handling.
- Keep `DispatcherPosts=0` protection in place.

Explicitly not included:
- Settings dialog profiling or optimization.
- Dialog open timing redesign.
- Large UI refactors unrelated to registry event distribution.
- New external dependencies.
- Release/versioning work.

## Starting Point
- Recent benchmark logs show browser controls receiving roughly tens of thousands of registry events per control during short runtime sessions.
- The earlier UI-thread flood has been mitigated: benchmark summaries now show `BrowserDispatcherPosts=0`.
- Remaining risk is scalability: with 5-10 folders, global event delivery can multiply CPU work even when UI-thread posts remain zero.
- `agents/solution.md` already states that browser-hosted controls must be subscription-scoped and must not react to all `HostRegistries.Data.ItemChanged` events globally.
- Current relevant controls still subscribe directly to global registry events in several places.

## Tasks
1. Inspect the current diagnostic implementation in `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs`.
2. Extend browser registry diagnostics to retain bounded top-N event source data:
   - source control name
   - registry key
   - normalized folder/domain prefix
   - accepted/ignored state
   - event counts and events-per-second for benchmark summaries
3. Keep diagnostics bounded so high-frequency runs cannot grow memory without limit.
4. Inspect current direct subscriptions to `HostRegistries.Data.ItemChanged` in browser controls and related manager/browser dialog controls.
5. Define a small internal scoped subscription API or helper using existing project patterns. It should:
   - accept one or more relevant prefixes
   - filter before invoking the control callback
   - return `IDisposable`
   - not schedule dispatcher work
   - record diagnostic dropped/accepted counts where useful
6. Migrate the current browser controls from global subscription to scoped subscription:
   - `CustomSignalsControl`
   - `EnhancedSignalsControl`
   - `ControllerControl`
   - `MonitorViewControl`
   - `MonitorControl` if registry events are introduced or already relevant through related managers
   - `FunctionsControl` only if it currently receives or should receive registry event updates
7. Ensure each control scopes by the owning folder first and by feature domain second.
8. Preserve existing relevance snapshots and coalescing/debouncing; scoped subscriptions reduce event delivery but do not replace UI-thread protections.
9. Update benchmark summary budgets or notes so high `RegistryEvents`/high ignored ratios are visible as a warning/failure condition, not just informational output.
10. Add or update focused tests for prefix matching and scoped subscription behavior.
11. Update relevant documentation if setup, benchmark output, or troubleshooting instructions change.

## Implementation Order
1. Baseline inventory:
   - Use `rg "HostRegistries\\.Data\\.ItemChanged|ItemChanged \\+=" src/HornetStudio.Editor src/HornetStudio` to confirm direct subscriptions.
   - Read the current implementations of the diagnosed browser controls before editing.
2. Diagnostics first:
   - Add bounded top-prefix/key tracking to browser registry event diagnostics.
   - Include event-rate and ignored-ratio values in benchmark summary logs.
   - Keep existing summary fields for compatibility.
3. Scoped subscription helper:
   - Implement a minimal helper that subscribes once to `HostRegistries.Data.ItemChanged`, filters by configured prefixes, then invokes the caller callback only for relevant events.
   - Prefix matching must avoid false positives such as `studio.main.controller2` matching `studio.main.controller`.
4. Migrate controls one at a time:
   - Compute owned folder/domain prefixes from the current owner/folder context.
   - Rebuild subscriptions when folder/owner context changes.
   - Dispose subscriptions when detached/unloaded.
5. Preserve current safeguards:
   - Keep existing accepted/ignored diagnostics at the control boundary where still meaningful.
   - Keep coalesced UI refresh paths.
   - Do not move expensive rebuilds into the subscription callback.
6. Tests:
   - Add prefix matching tests.
   - Add a test or diagnostic-level check that unrelated folder events do not reach the subscribed callback.
7. Verification:
   - Build.
   - Run focused tests if available.
   - Run diagnostics benchmark manually with PID active and no settings/dialog interaction.
   - Compare `RegistryEvents` per browser control before/after.

## Technical Constraints
- Use existing .NET/Avalonia patterns and existing diagnostics/logging style.
- No new external dependencies.
- Chat/user-facing text remains German, but code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Public classes and public methods must have XML documentation.
- Filter registry events before any `Dispatcher.UIThread.Post`, `Dispatcher.UIThread.InvokeAsync`, `QueueRuntimeRefresh`, `RefreshAll`, `Rebuild`, or equivalent UI work.
- Unknown/unrelated registry events must not enqueue UI work.
- Keep changes narrow; do not refactor unrelated widgets.

## Acceptance Criteria
- Benchmark output reports registry event source detail sufficient to identify the dominant event prefixes/keys.
- Benchmark output includes browser registry event rate and ignored ratio or equivalent load indicator.
- `BrowserDispatcherPosts` remains `0` for the no-dialog runtime benchmark.
- Browser controls no longer receive global project-wide registry traffic for unrelated folders.
- With multiple folders, registry events from folder B do not materially increase the `RegistryEvents` count for browser controls scoped to folder A.
- Ignored registry event counts are substantially lower than the current global-subscription baseline.
- Chart render metrics remain stable and do not regress.
- Existing browser functionality still updates when relevant owned folder/domain/runtime paths change.

## Verification
- `dotnet build HornetStudio.sln --no-restore`
- Run focused tests in `src/HornetStudio.Editor.Tests` if touched and available through the repository's console self-test pattern.
- Manual benchmark:
  - Start with `HORNETSTUDIO_UI_DIAGNOSTICS=1` and `HORNETSTUDIO_UI_BENCHMARK=1`.
  - Run 60 seconds with PID active and no settings/dialog interaction.
  - Confirm `BrowserDispatcherPosts=0`.
  - Confirm per-control `RegistryEvents` and ignored ratios are lower than the previous baseline.
- Multi-folder/manual or synthetic verification:
  - Create or simulate registry updates for a second folder.
  - Confirm controls scoped to the first folder do not receive those unrelated folder events.

## Out of Scope
- Settings dialog measurement or optimization.
- Reworking all non-browser widgets that subscribe to registry events unless they directly affect benchmarked runtime/browser performance.
- Changing registry data model semantics.
- Moving client browsers into browser views.
- Release notes or version updates.

## Risks / Watchouts
- Some controls need both folder-local definition paths and runtime/source paths; scoping too narrowly can break live updates.
- Runtime paths may not always share the same folder prefix as persisted studio definition paths. Include explicitly owned runtime roots and configured source paths where needed.
- Prefix matching must handle dot/slash separator variants consistently if both appear in registry keys.
- Diagnostics must be bounded; storing every high-frequency key indefinitely would create a new performance issue.
- Existing controls may rebuild relevance snapshots on the UI thread. Subscription updates must avoid races when folder context changes.
- Do not treat coalescing as a substitute for scoping. Both are required.
