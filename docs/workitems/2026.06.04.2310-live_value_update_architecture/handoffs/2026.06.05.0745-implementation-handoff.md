# IMPLEMENTATION HANDOFF

## Goal
Stabilize the UDL Signal startup path so public `studio.<folder>.<client>.*` items are created once and then updated in place, while the steady-state Signal value flow stays on the new `shared live value store -> shared UI cadence` path. Remove the legacy `UdlClientControl` ownership path entirely so UDL public projection has exactly one runtime-owned publisher.

## Scope
Included:
- Single-owner UDL public projection architecture
- Removal of the legacy `UdlClientControl` public projection path
- Startup churn investigation and fix for repeated public item remove/re-add
- Signal steady-state live value scheduler path
- Separation of startup structure work from steady-state value delivery
- Diagnostics updates needed to prove the startup cause and the fix

Explicitly not included:
- Broad redesign of unrelated widgets
- Compatibility migration work
- Reworking every non-UDL widget to the same architecture in this change
- Release/versioning work

## Starting Point
- The current live-value direction is already in place for steady state via `SignalValueUiScheduler`.
- Startup is still not stable. The user reports short stalls for roughly 10 seconds or longer before the UI becomes fluid.
- The current host log shows repeated `[DataRegistry] Added key=studio.main.udl1.mXXX ...` entries for the same public items inside a single app session.
- `HostRegistries.Data.UpsertSnapshot(...)` logs `Added` only for a true new root insert, not for normal updates.
- `UiFolderContext.AttachedItemLink.Dispose()` removes the public target path from the registry.
- `UdlHostRegistryProjection.SynchronizeAttachments(...)` disposes and recreates entries when an attachment no longer matches.
- There are currently two public-projection paths in the codebase:
  - runtime-managed headless projection via `UdlClientRuntimeManager` / `UdlClientRegistryProjection`
  - control-owned projection via `UdlClientControl` / local `UdlHostRegistryProjection`
- The legacy control-owned path is now considered harmful and must be removed rather than preserved.

## Tasks
1. Prove the startup churn chain with focused diagnostics for one or more repeated public items such as `studio.main.udl1.m009`.
2. Remove the legacy `UdlClientControl`-owned public projection path and any remaining parallel ownership of UDL public items.
3. Ensure the runtime-managed path is the only owner allowed to publish or rebuild `studio.<folder>.<client>.*` UDL items.
4. Keep the shared live value store and shared Signal UI scheduler as the steady-state value path.
5. Ensure startup structure changes do not repeatedly dispose and recreate the same public attachment roots once they have been established.
6. Keep structural rebind behavior only for real structural changes, not for ordinary startup value flow.
7. Update diagnostics and benchmarks so startup and steady-state can be evaluated separately and compared after the fix.

## File-Level Changes
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientControl.axaml.cs` -> remove legacy control-owned attachment/public projection behavior and any remaining competing runtime ownership responsibilities.
- `src/HornetStudio.Editor/UdlClients/UdlClientRegistryProjection.cs` -> make runtime-owned projection the sole public UDL publisher and harden attachment synchronization against repeated rebuild churn.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs` -> keep only the single-owner runtime-managed projection behavior; add focused diagnostics for replace/remove/recreate decisions if needed.
- `src/HornetStudio.Host/UiFolderContext.cs` -> preserve attachment lifecycle but ensure disposal-driven removes reflect only real owner teardown.
- `src/HornetStudio.Host/HostRegistries.cs` -> keep current registry semantics; diagnostics may be extended, but `Added` must remain a real new-root signal.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientRuntime.cs` -> keep runtime structure notifications cheap and avoid false-positive structure changes that rebuild public projection unnecessarily.
- `src/HornetStudio.Editor/UdlClients/UdlClientRuntimeManager.cs` -> confirm the runtime/projection lifetime is single-owner per folder/client and never duplicated by UI controls.
- `src/HornetStudio.Editor/Models/PageItemModel.cs` -> continue reducing dependency on registry-driven steady-state refreshes; keep startup structure refreshes distinct from scheduled value updates.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> add or refine startup-specific stages for projection remove/recreate churn and startup stabilization timing.
- `src/HornetStudio.Editor.Tests/Program.cs` -> add focused tests for single-owner projection, repeated startup structure signals, and no duplicate public-root churn.
- `src/HornetStudio.Host.Tests/Program.cs` -> add focused lifecycle tests if attachment removal semantics change materially.

## Implementation Order
1. Add minimal diagnostics to correlate:
   - runtime structure change
   - projection refresh
   - attachment replace/dispose
   - `HostRegistries.Data.Remove(...)`
   - recreated `UpsertSnapshot(...)`
2. Remove the `UdlClientControl` public projection path so UI controls no longer own `UdlHostRegistryProjection` for UDL public items.
3. Make `UdlClientRuntimeManager` + `UdlClientRegistryProjection` the only public UDL projection owner.
4. Harden attachment synchronization so stable attached public items are not removed/recreated during ordinary startup settling.
5. Verify `PageItemModel` steady-state Signal updates still flow through the live value store and scheduler, not the old registry hot path.
6. Update diagnostics and focused tests.
7. Validate with startup-focused and steady-state-focused benchmark runs.

## Technical Constraints
- Runtime ownership must stay outside visual controls.
- `UdlClientControl` must not remain as a hidden second owner of public UDL projection.
- High-frequency runtime value changes must update runtime state only; UI work is allowed only on explicit scheduler ticks or real structural changes.
- Do not introduce new external dependencies.
- Keep the architecture minimally fragmented and aligned with existing naming/patterns.
- Prefer removing legacy competing logic over adding more compatibility branches.

## Acceptance Criteria
- Within one app session, the same public UDL item such as `studio.main.udl1.m009` is not repeatedly removed and recreated during ordinary startup settling.
- Public UDL projection has one owner only: the runtime-managed path.
- `UdlClientControl` no longer owns or rebuilds public UDL attachments.
- Signal steady-state visible value updates continue to run through the shared live value scheduler.
- Startup stalls are materially reduced because the public projection roots are no longer churned repeatedly.
- Structural changes still work when attachments or definitions actually change.

## Verification
- `dotnet build HornetStudio.sln --no-restore`
- Run focused editor self-tests covering:
  - single-owner UDL projection
  - no repeated public root recreate churn for stable startup
  - Signal scheduled latest-wins updates
- Run focused host self-tests only if attachment removal/writeback semantics changed materially.
- Manual log verification against `src/HornetStudio/bin/Debug/net9.0-windows/logs/host-*.log`:
  - trace one repeated item before and after the fix
  - confirm no repeated `Added` sequence for the same stable startup item
- Run the benchmark project and inspect startup separately from steady state.

## Out of Scope
- Full chart pipeline redesign
- Full startup benchmark redesign in the same change
- Non-UDL client cleanup unrelated to the observed churn

## Risks / Watchouts
- Removing `UdlClientControl` projection responsibilities must not accidentally remove required status or attach-option UX that still belongs to the UI.
- If runtime structure notifications still fire too broadly, startup churn can remain even after deleting the legacy control path.
- Mixed ownership is worse than either single path alone; partial removal is not acceptable.
- Keep writeback and public metadata behavior intact while deleting the old projection path.
