# IMPLEMENTATION HANDOFF

## Goal
Eliminate startup and early steady-state UI stalls caused by repeated re-registration of the same attached UDL public items. Preserve the new live value architecture, but stop the attach projection from tearing down and recreating identical `studio.<folder>.<client>.*` registry roots during warmup.

## Scope
Included:
- UDL attached public item projection during startup and structure warmup
- Delta-based synchronization of attached public registry items
- Separation of structural runtime discovery from full public projection rebuilds
- Reduction of unnecessary `RefreshFolderBindings(...)` cascades caused by unchanged attachments

Explicitly not included:
- Broad redesign of the live value store
- Rework of unrelated widgets or browser controls
- Registry API cleanup beyond what is required for the attach projection path
- New benchmark infrastructure

## Starting Point
- The remaining startup stalls correlate with repeated `[DataRegistry] Added key=studio.main.udl1.m00x ...` log entries for the same attached public items.
- `DataRegistry.UpsertSnapshot(...)` logs `Added key=...` only for newly added roots, not for normal value/property updates.
- `UdlHostRegistryProjection.SynchronizeAttachments(...)` currently clears the entire projection and recreates it when the resolved attachment signature changes.
- `UiFolderContext.Dispose()` removes the old public roots from `HostRegistries.Data`, so the next projection pass re-adds the same paths as new roots.
- `UdlClientRegistryProjection.Refresh()` currently re-runs attachment synchronization on runtime structure changes, and `UdlClientControl` can trigger `RefreshFolderBindings(...)` after attachment changes.

## Tasks
1. Refactor `UdlHostRegistryProjection` to maintain attachment state per relative path instead of full-context teardown on every signature change.
2. Introduce delta synchronization so already-projected attachments remain in place, newly resolvable attachments are added, and removed attachments are disposed individually.
3. Update the UDL projection refresh path so runtime structure changes only re-evaluate missing or changed attachments instead of rebuilding unchanged public roots.
4. Tighten the signal for `attachmentsChanged` so `UdlClientControl` only requests `RefreshFolderBindings(...)` when the actual public attachment set changed.
5. Add focused tests around repeated warmup resyncs to prove that identical attachment sets do not cause repeated root recreation.
6. Validate that startup logs stop showing repeated `Added key=studio.main.udl1.m00x` groups for already projected attachments.

## File-Level Changes
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs` -> replace full rebuild logic with incremental add/remove/update of attachment projections.
- `src/HornetStudio.Host/UiFolderContext.cs` -> keep current attach/link behavior unless a minimal API extension is needed for per-attachment disposal; avoid broad redesign.
- `src/HornetStudio.Editor/UdlClients/UdlClientRegistryProjection.cs` -> only treat actual attachment-set deltas as projection changes; avoid unnecessary refresh churn.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientControl.axaml.cs` -> consume the tightened `attachmentsChanged` signal and avoid `RefreshFolderBindings(...)` when nothing structural changed.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientRuntime.cs` -> keep `RuntimeStructureChanged` semantics aligned with the new delta path; only adjust if current signaling still forces redundant full projection work.
- `src/HornetStudio.Editor.Tests/Program.cs` -> add focused coverage for repeated attachment synchronization and startup-style partial runtime discovery.

## Implementation Order
1. Isolate the current `UdlHostRegistryProjection` responsibilities and introduce an internal attachment-entry model keyed by normalized relative path.
2. Implement delta synchronization in `UdlHostRegistryProjection` so unchanged attachments survive repeated `SynchronizeAttachments(...)` calls.
3. Adjust `UdlClientRegistryProjection` and `UdlClientControl` so they only propagate structural refreshes when the projected public attachment set actually changes.
4. Add focused tests for repeated warmup synchronization with incrementally appearing runtime items.
5. Run build and focused editor validation, then confirm via log/benchmark that repeated `Added key=` bursts are gone.

## Technical Constraints
- Preserve the current solution structure and naming conventions.
- Keep runtime ownership outside visual controls.
- Do not reintroduce global registry-event-driven value delivery for steady-state signal updates.
- Prefer localized changes over new abstraction layers unless a second concrete use case appears.
- Keep `HostRegistries` responsibilities narrow; solve the churn in the UDL attach projection path, not by hiding logs.
- Avoid broad compatibility scaffolding; the repository is still pre-release.

## Acceptance Criteria
- Attached UDL public items are not removed and recreated repeatedly during startup when their resolved attachment set is unchanged.
- The host log shows each attached `studio.main.udl1.m00x` public root being added once per actual attach lifecycle, not once per warmup resync.
- Startup and first 10 to 20 seconds no longer show the current registration-correlated UI stalls caused by repeated public projection rebuilds.
- `RefreshFolderBindings(...)` is only triggered for real attachment-set changes, not for no-op resyncs.
- Existing attached public items, value references, and writeback behavior continue to function.

## Out of Scope
- Reworking the entire UDL headless projection architecture
- General `PageItemModel` structural refresh cleanup beyond the attachment-triggered path
- Realtime chart or unrelated widget startup issues
- New docs unless user-visible widget behavior changes materially

## Risks / Watchouts
- Do not keep stale attachment entries alive when an attachment is actually removed or renamed.
- If `UiFolderContext` is extended, keep disposal semantics explicit and local; avoid leaking registry roots.
- Be careful with relative-path normalization so semantically identical attachments are treated as the same key.
- Avoid false negatives in `attachmentsChanged`; newly resolvable attachments must still trigger the necessary structural refresh once.

## Notes
- The immediate root cause is structural churn: `UiFolderContext.Dispose()` removes public roots, and the next full projection pass recreates them, which shows up as repeated `Added key=` log entries.
- The preferred fix is delta synchronization in the projection layer, not additional coalescing around the old rebuild loop.
