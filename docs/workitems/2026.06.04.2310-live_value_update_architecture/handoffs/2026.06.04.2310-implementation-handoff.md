# IMPLEMENTATION HANDOFF

## Goal
Replace the current high-frequency Signal widget update path so visible value rendering no longer depends on `HostRegistries.Data.ItemChanged` fan-out per control. The target architecture is `resolve once -> shared live value store -> shared UI cadence -> widget reads latest value`.

## Scope
Included:
- Signal widget live value update architecture
- UDL live value flow for attached public signals
- Separation of structural refresh from value refresh
- Shared UI scheduler for visible value widgets
- Removal of the legacy `UdlClientControl` projection/ownership path in favor of runtime-owned behavior
- Bench and test updates needed to validate 20 visible Signal widgets at 10 Hz

Explicitly not included:
- Broad redesign of unrelated widgets
- Legacy migration compatibility work
- Large visual redesign
- Non-essential cleanup outside the hot path

## Starting Point
- Current Signal widgets are driven by `PageItemModel` reacting directly to `HostRegistries.Data.ItemChanged`.
- `PageItemModel` currently mixes target resolution, registry filtering, unresolved target gating, value refresh coalescing, dispatcher scheduling, and UI property invalidation.
- `UiFolderContext` and UDL projection already contain partial coalescing, but the UI still pays too much per value event.
- The repository is still pre-release. Existing project compatibility does not need to be preserved.
- The current benchmark scenario is `benchmarks/ui_lag_bench_project/project.aaep` with 20 Signal widgets and one UDL client.

## Tasks
1. Introduce a shared live value store for high-frequency runtime values, scoped by folder/runtime identity and independent from Avalonia controls.
2. Introduce a resolved Signal binding descriptor so Signal widgets stop re-resolving free-form target paths during normal value updates.
3. Add a shared page/window-level UI value scheduler that ticks visible Signal widgets at a controlled cadence and applies `latest wins`.
4. Refactor `PageItemModel` Signal handling so normal value display reads from the live value store instead of reacting to global registry events.
5. Restrict `HostRegistries` usage for Signals to addressing, metadata, snapshot fallback, picker data, and writeback, not primary high-frequency delivery.
6. Remove the old `UdlClientControl`-owned public projection path so UDL public items have exactly one runtime-owned projection owner.
7. Keep structural changes on a separate path: attach/detach, target change, reconnect, datatype/unit change, missing source, and rebind.
8. Align the benchmark project and diagnostics with the new architecture and verify the target scenario.

- `src/HornetStudio.Host/UiFolderContext.cs` -> stop treating public registry publication as the primary live-value path for visible Signal widgets; keep attachment and reference lifecycle.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientRuntime.cs` -> expose or feed the shared live value store from runtime updates.
- `src/HornetStudio.Editor/UdlClients/UdlClientRuntimeManager.cs` -> host runtime-scoped access to the live value store if needed.
- `src/HornetStudio.Editor/UdlClients/UdlClientRegistryProjection.cs` -> reduce responsibility to structure/public projection and integration points for resolved bindings.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientControl.axaml.cs` -> remove legacy control-owned attachment/public projection responsibilities and any remaining parallel runtime ownership behavior.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> adjust diagnostics to the new stages: runtime update, store update, UI scheduler tick, widget value applied.

- `src/HornetStudio.Host.Tests/Program.cs` -> add focused tests only if registry/writeback responsibilities change materially.

## Implementation Order
1. Define the target architecture in code boundaries:
   - live value store
   - resolved Signal binding descriptor
   - shared UI scheduler
2. Remove the legacy `UdlClientControl`-owned public projection path so only the runtime-managed path can publish `studio.<folder>.<client>.*` UDL items.
3. Wire UDL runtime updates into the live value store without involving Avalonia or dispatcher work.
4. Refactor `PageItemModel` Signal logic to bind once and read latest values from the store on scheduler ticks.
5. Separate structural rebind triggers from value-only display updates.
6. Reduce or remove obsolete Signal-specific registry hot-path logic in `PageItemModel`.
7. Update diagnostics and focused tests to reflect the new pipeline.
8. Run build, focused tests, and benchmark validation against the 20-signal scenario.

## Technical Constraints
- Keep runtime ownership outside visual controls.
- High-frequency runtime value changes must update runtime state only; UI work is allowed only on the explicit scheduler tick or structural changes.
- Do not introduce new external dependencies.
- Preserve existing solution structure and naming conventions.
- Avoid broad refactoring of unrelated widget systems.
- Keep the architecture minimally fragmented; add only the new core pieces required by the new update model.
- Continue to use the existing benchmark tooling and diagnostics infrastructure.

## Acceptance Criteria
- 20 visible Signal widgets backed by the UDL benchmark project show stable live updates without per-control registry-event fan-out.
- Visible Signal value rendering no longer depends on each widget subscribing to global `HostRegistries.Data.ItemChanged` for steady-state value delivery.
- Value-only updates do not trigger broad `RefreshTargetBindings()`-style structural UI work.
- UI updates use a shared cadence with `latest wins`, not one dispatcher post per incoming value.
- Public UDL item projection has one owner only; the old `UdlClientControl` path no longer removes/recreates the same `studio.<folder>.<client>.*` items in parallel with runtime-owned projection.
- Structural changes still rebind correctly when targets appear, disappear, or change.
- Writeback and non-high-frequency registry responsibilities continue to function.
- Benchmark evidence shows the new architecture can sustain the target scenario materially better than the current path.

## Verification
- `dotnet build HornetStudio.sln --no-restore`
- Run focused `HornetStudio.Editor.Tests` self-tests covering Signal binding and value scheduling.
- Run focused `HornetStudio.Host.Tests` self-tests only if registry/writeback behavior changed.
- Run `powershell -ExecutionPolicy Bypass -File scripts\run_ui_benchmark.ps1 -Seconds 60 -ProjectPath 'benchmarks\ui_lag_bench_project\project.aaep' -Scenario 'SignalLiveValueArchitecture-60s' -NoBuild`
- Confirm benchmark diagnostics distinguish:
  - runtime value generation
  - live store update
  - UI scheduler tick
  - Signal value apply

## Out of Scope
- Reworking every widget type to the new model in the same change
- Chart pipeline unification beyond what is needed to avoid regressions
- Full registry API simplification unrelated to Signal live values
- Release/versioning work

## Risks / Watchouts
- Avoid reintroducing hidden per-widget timers; the scheduler should be shared, not one timer per control.
- Do not let the live value store become Avalonia-aware.
- Keep structural fallback behavior clear when a target path resolves through public registry metadata but live runtime data is temporarily missing.
- Multiple widgets may bind to the same value; the architecture must not duplicate runtime polling or cache state per widget.
- Do not regress writeback, unit display, or fallback text behavior while removing registry-driven live updates.
- Be careful not to leave partial `UdlClientControl` projection code behind; mixed ownership would preserve the startup churn problem even if the live-value scheduler path is correct.

## Notes
- This is a deliberate design change, not a compatibility-preserving optimization pass.
- Do not spend implementation effort on additional warmup micro-optimizations inside the old registry-driven Signal path unless strictly required to keep the app functional during the transition.
- Prefer completing the new steady-state value architecture end-to-end before polishing secondary diagnostics or chart follow-up work.
