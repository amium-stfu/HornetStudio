# IMPLEMENTATION HANDOFF

## Goal
Restore feature parity for UDL bitmask exposure after moving from `UdlClientControl` to the file-backed Clients Browser. The old widget already supported configuring bitmask helper bits for channels such as `read`, `set`, and `alert`; the browser/file-backed model must expose the same options and create the same SubItems without requiring a `UdlClientControl` widget.

## Scope
Included:
- Identify the old working UDL bitmask/exposure implementation in `UdlClientControl` and related helper/projection code.
- Preserve the old behavior and naming as closely as possible.
- Move or map the old bitmask configuration into the file-backed UDL client attach/exposure model.
- Add missing bitmask UI fields to the new UDL Module Exposures dialog.
- Ensure the dialog lets users configure the same bitmask options as the old widget, including how many bits are created.
- Ensure Projection creates the corresponding SubItems for configured bitmask sources without needing a widget.
- Add tests that prove old-style bitmask behavior and new file-backed config produce the same SubItems.

Explicitly not included:
- Designing a new bitmask concept from scratch.
- Full generic exposure framework for other client types.
- Full ItemClient browser implementation.
- Reintroducing `UdlClientControl` as the owner of bitmask configuration.
- Release/versioning work.

## Starting Point
- The new `UDL Module Exposures` dialog shows a `Bitmask` section, but currently only exposes `Read helper bits route to Set`.
- The dialog does not expose the old choice for how many bits to create.
- The user expects bitmask configuration to define helper bits for channels such as `read`, `set`, and `alert`, which then create corresponding SubItems.
- This already worked in the old `UdlClientControl` widget.
- Current migration goal: UDL widgets can be removed completely, so all old exposure behavior must be available through file-backed clients and browser dialogs.

## Tasks
1. Inventory old bitmask implementation.
   - Search `UdlClientControl.axaml.cs`, `UdlHostRegistryProjection.cs`, `UdlModuleExposureDialogWindow.*`, and related models for bitmask/bit helper fields.
   - Identify old persisted field names and UI controls.
   - Identify how bit count, bit source, and routing options were represented.
   - Identify exactly which SubItems were created and their names/paths.
2. Document parity target in code/tests.
   - Capture the old expected behavior:
     - source channels that can get helper bits, likely `read`, `set`, and `alert`
     - bit count behavior
     - path/name pattern for generated SubItems
     - `Read helper bits route to Set` semantics
   - Do not invent new names unless the old ones are clearly broken.
3. Extend file-backed exposure model.
   - Add or align structured attach/exposure config to store old bitmask fields.
   - Preserve load of existing simple `AttachedItemPaths`.
   - Preserve compatibility with any legacy widget-local bitmask definitions if migration input exists.
   - Prefer not persisting default values when possible to keep YAML readable.
4. Update YAML codec.
   - Load/save bitmask settings under the relevant attached/exposure item.
   - Ensure roundtrip does not drop old/default attach data.
   - Validate bit count where appropriate.
5. Update the UDL Module Exposures dialog.
   - Show the old bitmask options in the `Bitmask` section.
   - Include bit count selection/control.
   - Include source selection for the old supported channels, if that existed in the old widget.
   - Keep the existing `Read helper bits route to Set` behavior.
   - Use existing theme styles and compact form layout.
6. Update projection/runtime usage.
   - Ensure file-backed bitmask config creates the same SubItems as the old widget.
   - Remove any need to read `UdlClientControl` for bitmask behavior.
   - Ensure projection refreshes after saving bitmask edits.
7. Add regression tests.
   - Old-style or migrated bitmask config creates expected SubItems.
   - File-backed bitmask config roundtrips through YAML.
   - `read`, `set`, and `alert` bit helpers are created when configured.
   - Bit count controls number of generated SubItems.
   - No `UdlClientControl` is required for the behavior.
8. Update documentation.
   - Document bitmask exposure settings in the UDL/Clients Browser docs.
   - Clarify that bitmask helper SubItems are file-backed client exposure configuration.

## Implementation Order
1. Search old widget/projection code for bitmask fields and generated SubItem logic.

3. Add tests around the current old helper/projection behavior if a callable helper exists.
4. Extend/align the file-backed exposure model with those exact fields.
5. Update YAML codec roundtrip tests.
6. Update dialog UI and bindings to expose the missing old fields, especially bit count.
7. Update browser `[Edit]` path to pass the file-backed config into the dialog and save it back.

9. Run tests/build.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Public classes and public methods require XML documentation.
- Do not invent a new bitmask behavior; restore parity with the old working widget.
- Do not require `UdlClientControl` for edit, runtime, or projection.
- Use existing models/patterns where possible.
- Do not add new external dependencies.
- Keep browser/projection runtime-independent from visual controls.
- Registry work must remain scoped; do not cause broad refreshes on high-frequency value changes.

## Acceptance Criteria
- The `UDL Module Exposures` dialog exposes the old bitmask configuration fields, including bit count.
- Users can configure helper bits for the same sources supported by the old widget, including `read`, `set`, and `alert` if those were supported before.
- Saving bitmask config writes to the file-backed UDL client definition/exposure data.
- Projection creates the same SubItems the old widget created for equivalent bitmask config.
- The behavior works after removing all `UdlClientControl` widgets from the folder.
- Tests cover bit count and generated SubItem behavior.
- Existing simple attach behavior remains compatible.

## Out of Scope
- New bitmask naming scheme unless required by old behavior.
- Generic bitmask editor for non-UDL clients.
- ItemClient browser support.
- Full redesign of the exposures dialog.
- Release/versioning.

## Risks / Watchouts
- Old behavior may be split across UI code and projection code; avoid copying UI-only dependencies into the new headless path.
- Field names may have changed during migration; preserve old compatibility where practical.
- Bit count defaults must match old widget behavior to avoid changing existing generated SubItems.
- SubItem path naming must remain stable because other widgets may bind to it.
- Avoid persisting every generated bit item individually if old behavior derived them from compact bitmask settings.
