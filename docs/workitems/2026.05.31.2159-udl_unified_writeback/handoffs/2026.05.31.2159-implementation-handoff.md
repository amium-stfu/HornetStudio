# IMPLEMENTATION HANDOFF

## Goal
Simplify UDL writeback handling so every writable channel uses one consistent pending-write path. A `.write` change on `State`, `Read`, `Set`, or `Out` must create a pending write that is retried by the writeback loop until the matching received PDO acknowledges it or the send timeout expires.

## Scope
- Included: internal writeback simplification in `src/Amium.UdlClient/UdlClient.cs`.
- Included: keep the duplicate host-side UDL implementation aligned if `src/HornetStudio.Host/HostUdlClient.cs` still contains the same writeback logic.
- Included: focused tests for the changed writeback behavior if an existing suitable test project or self-test can cover it.
- Not included: public API redesign, UI redesign, new runtime services, new dependencies, file format changes, or broad UDL architecture refactoring.

## Starting Point
- `UdlClient.Open(...)` starts `WritebackLoopAsync(...)`.
- The loop processes `_pendingCommands`, but pending entries are only created through the `State`-specific `TryWriteCommand(...)` path.
- `Read.write`, `Set.write`, and `Out.write` call `TryWrite(...)`, which sends once and does not create a pending entry.
- Received PDO types already map to writable channels:
  - Type `1` -> `State`
  - Type `3` -> `Read`
  - Type `4` -> `Set`
  - Type `5` -> `Out`
- The intended behavior is that every `.write` change follows the same secured writeback path.

## Tasks
1. Replace the State-only pending command model with a small pending write model.
2. Use a pending key that includes both `moduleId` and UDL function/type so different channels on the same module cannot overwrite each other.
3. Route every writable channel `.write` change into the same pending-write queueing method.
4. Make the writeback loop send pending writes through the existing `SendWritePdo(...)` method.
5. Acknowledge pending writes from the receive path after the matching channel read value is updated.
6. Remove or collapse the separate `TryWrite(...)`, `TryWriteCommand(...)`, `TryGetCommandRequest(...)`, and `TrackCommandState(...)` split where practical.
7. Keep the implementation local and readable; do not introduce a new service, framework, or speculative abstraction.
8. Add focused tests or update existing self-tests to prove retry, acknowledgement, and timeout behavior for at least one non-State channel.

## File-Level Changes
- `src/Amium.UdlClient/UdlClient.cs` -> Primary implementation. Introduce unified pending write handling, channel/function mapping, shared send/retry/acknowledge logic, and remove the State-only special path.
- `src/HornetStudio.Host/HostUdlClient.cs` -> Align equivalent writeback logic if this duplicate runtime path remains active.
- `src/Amium.UdlClient/Module.cs` -> No expected functional change; only touch if needed to preserve write metadata consistency.
- `src/HornetStudio.Host.Tests/Program.cs` or another existing relevant test file -> Add or adjust focused coverage if practical with current test infrastructure.
- `CHANGELOG.md` -> Update only if project convention treats this behavior fix as relevant user-facing runtime behavior.

## Implementation Order
1. Inspect `UdlClient.cs` and confirm the minimal channel mapping needed for `State`, `Read`, `Set`, and `Out`.
2. Rename the internal concepts from command-specific names to write-specific names, for example `PendingCommand` to `PendingWrite` and `_pendingCommands` to `_pendingWrites`.
3. Add a simple key for pending writes, preferably a small private readonly struct/record or tuple containing `moduleId` and `function`.
4. Replace `ProcessRequestWrite(...)` branching with a small resolver that returns the channel item and function for the changed `.write` item.
5. Queue a pending write for every resolved writable channel instead of sending immediately.
6. Update `WritebackLoopAsync(...)` to iterate pending write keys and send due writes with shared timeout handling.
7. In `HandleSubChannelPdo(...)`, after each channel's read value is updated, call a generalized acknowledgement method with `moduleId`, function/type, received value, and channel item.
8. Preserve `ClearRequestedValue(...)` behavior, but apply it from the shared acknowledgement/timeout path.
9. Align `HostUdlClient.cs` if the same duplicated logic is still present.
10. Add focused tests, then run the smallest relevant verification and a build if feasible.

## Technical Constraints
- Keep the code easy to follow for humans; prefer a direct local implementation over new layers.
- Use existing project patterns and libraries only.
- Do not add dependencies.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must stay English.
- Chat responses must stay German.
- Preserve the existing public API unless a necessary breaking change is explicitly approved.
- Use named parameters where they improve readability, especially with similar argument types.

## Acceptance Criteria
- A `.write` change on `State`, `Read`, `Set`, or `Out` creates a pending write.
- The writeback loop retries pending writes at the existing cadence until acknowledgement or timeout.
- Received PDO type `1`, `3`, `4`, or `5` acknowledges only the matching pending write for the same module and function.
- Pending writes for different channels of the same module do not overwrite each other.
- `SendWritePdo(...)` remains the single UDL write-PDO send method.
- The State-only write path is removed or reduced to the same generic path as every other channel.
- The code is shorter or at least structurally simpler than the current split-path implementation.

## Verification
- Run a focused build for the changed projects where possible.
- Run existing host/editor self-tests if they cover UDL module/writeback behavior.
- Add or run focused tests that verify:
  - `Set.write` or `Out.write` is retried when not acknowledged.
  - A matching received PDO acknowledges and clears the pending write.
  - A non-matching received PDO does not acknowledge the pending write.
  - Timeout clears the pending write and sets status consistently.

## Out of Scope
- Changing UI controls, browser layout, or attach/exposure behavior.
- Introducing per-channel UI status unless required by tests or an existing caller.
- Changing item path schema or persisted UDL client definitions.
- Reworking CAN transport, heartbeat, or runtime ownership.

## Risks / Watchouts
- `SendStatus` is currently module-level. Multiple simultaneous channel writes may still share one status value. Keep this simple unless a clear bug appears; do not expand UI/status architecture preemptively.
- Avoid triggering writeback from received bus updates. The trigger must remain `.write` changes, not `.read` updates.
- The duplicate `HostUdlClient.cs` path can diverge silently if only `Amium.UdlClient` is changed.
- Clearing `.write` too early can hide pending intent. Clearing should happen on acknowledgement or timeout, not before the write has been safely tracked.

- `State` should become just the channel with function/type `1`, not a special command subsystem.
