# IMPLEMENTATION HANDOFF

## Goal

Reduce the remaining UDLClient startup publish cost after attach-option publishing was improved.

The next implementation should focus on:

1. `PublishClientItems.ScheduleAttachedItemsRefresh`
2. remaining `PublishClientItems.PostRuntimeUpdateUi` cost
3. `PublishClientItems.LogRuntimeRootItems`
4. total `PublishClientItems` time that remains near one second

## Scope

Included:

1. Analyze why `ScheduleAttachedItemsRefresh` is now measured up to `157 ms`.
2. Make attached-items refresh scheduling cheap and idempotent.
3. Further reduce `LogRuntimeRootItems` diagnostic cost in startup publish.
4. Split or identify the remaining cost inside and outside `PostRuntimeUpdateUi`.
5. Preserve the current steady-state improvement.
6. Re-run the same `UdlDebug` benchmark scenario.

Explicitly not included:

1. RealtimeChart lifecycle/logging fixes.
2. Monitor or MonitorView work.
3. Full UDL browser implementation.
4. More sample complexity.
5. Broad registry infrastructure changes.

## Tasks

1. Inspect `ScheduleAttachedItemsRefresh` and all call sites from `PublishClientItems`.
2. Determine why scheduling itself can cost `97-157 ms`.
3. Verify whether the measured cost is from:
   - dispatcher post overhead
   - timer creation/start/stop
   - lock/contention
   - diagnostics state collection
   - repeated scheduling across clients
   - synchronous work performed before/inside the scheduling method
4. Make scheduling idempotent:
   - if a refresh is already queued for this client, do not stop/start/re-post another timer unless the target state changed
   - avoid repeated timer reconfiguration when interval and callback are already set
   - keep one pending refresh per client
5. Keep `CancelAttachedItemsRefresh` and detach/dispose behavior correct.
6. Further reduce `LogRuntimeRootItems`:
   - avoid expensive sort/signature/log construction unless runtime root structure changed
   - avoid detailed per-root logging in the normal startup benchmark path
   - prefer verbose diagnostics for detailed output if an existing verbose log path exists
7. Split remaining `PostRuntimeUpdateUi` if needed to show any hidden cost after scheduling/logging are addressed.
8. Inspect total `PublishClientItems` time outside `PostRuntimeUpdateUi`:
   - `EnumerateClientItems`
   - `BuildRuntimeStructureSignature`
   - any runtime item projection/enumeration
9. Add diagnostics around pre-`PostRuntimeUpdateUi` work only if total time remains high after scheduling/logging changes.
10. Re-run the same benchmark and compare.

4. `PostRuntimeUpdateUi` is lower than the current `461-523 ms` range, or remaining cost is clearly isolated.

7. `BrowserDispatcherPosts` remains `0`.
