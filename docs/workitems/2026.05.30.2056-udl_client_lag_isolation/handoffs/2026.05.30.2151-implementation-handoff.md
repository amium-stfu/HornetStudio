# IMPLEMENTATION HANDOFF

## Goal

Reduce UDLClient startup publish cost by targeting the newly isolated hot spots:

1. `PublishAttachOptionItems`
2. `PublishClientItems.PublishAttachOptionItems`
3. `PublishClientItems.LogRuntimeRootItems`

The previous implementation improved steady-state responsiveness but made startup publish cost more visible and higher. The next implementation should keep the steady-state improvement while reducing attach-option publishing and runtime-root logging overhead.

## Scope

Included:

1. Optimize or gate `LogRuntimeRootItems` so it does not add 100+ ms to the hot startup publish path for unchanged or low-value diagnostic output.
2. Analyze and reduce `PublishAttachOptionItems` cost.
3. Prevent attach-option registry churn when attach option structure is unchanged.
4. Keep pruning/removal correct when runtime attach options genuinely disappear.
5. Re-run the same `UdlDebug` benchmark scenario after the change.

Explicitly not included:

1. Full UDL browser implementation.
2. Chart work.
3. Monitor or MonitorView work.
4. Broad `HostRegistries.Data` redesign.
5. Adding more benchmark sample complexity.

## Tasks

1. Inspect `UdlClientControl.axaml.cs` around `LogRuntimeRootItems`, `PublishAttachOptionItems`, and attach-option removal/publishing helpers.
2. Determine whether `PublishAttachOptionItems` is called twice by design or due to duplicated publish paths.
3. Determine whether `PublishAttachOptionItems` removes/recreates registry snapshots for unchanged attach options.
4. Add a per-client attach option structure signature if one does not already exist.
5. Use that signature to skip attach-option publish work when:
   - runtime attach option paths are unchanged
   - attach option metadata relevant to registry display is unchanged
   - target client/folder identity is unchanged
6. Preserve pruning when attach options genuinely disappear.
7. Ensure attach-option pruning is scoped to this UDL client's attach-option registry root only.
8. Make `LogRuntimeRootItems` cheap:
   - avoid expensive ordering/string construction when the root signature is unchanged
   - avoid per-root log output unless the root signature changed
   - consider moving detailed root logging behind existing verbose diagnostics if available
9. Keep existing diagnostics but avoid making diagnostic-only work dominate startup.
10. Re-run the current benchmark scenario and compare against the latest baseline.

## Acceptance Criteria

1. `LogRuntimeRootItems` no longer contributes about `100-145 ms` in the common unchanged/simple startup path.
2. `PublishAttachOptionItems` no longer performs expensive registry work for unchanged attach option structure.
3. `PublishClientItems.PostRuntimeUpdateUi` is materially lower than the current `608-670 ms` range.
4. `PublishClientItems` is materially lower than the current `835-961 ms` range.
5. `P95UiDelayMs` remains close to the improved value of `5.2` and does not regress toward the earlier `15.7`.
6. `BrowserDispatcherPosts` remains `0` in the benchmark scenario.
7. Attach option UI/registry state remains correct after real runtime structure changes.
8. Removed attach options are still pruned.

## Risks / Watchouts

- Skipping attach-option publishing with an incomplete signature can leave stale registry data.
- Pruning must remain scoped to the current UDL client's attach option root.
- Runtime value changes must not invalidate attach option structure signatures unless value affects the visible option metadata.
- Logging changes should preserve enough diagnostic value when actual root structure changes.
- A lower `P95UiDelayMs` can hide startup work because startup is tracked separately; both summary and timing rows must be checked.
