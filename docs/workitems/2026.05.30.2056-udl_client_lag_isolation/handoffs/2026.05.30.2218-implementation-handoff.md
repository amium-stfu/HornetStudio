# IMPLEMENTATION HANDOFF

## Goal

Clarify and enforce that `UdlClientControl.PublishClientItems` is a structure-publish path, not a normal runtime value-update path.

The current startup benchmark remains green in steady state, but startup publish still costs around `900 ms`. Before further optimizing individual sub-phases, the next step must verify whether `PublishClientItems` can also run during normal operation and, if so, make sure it runs only for real runtime structure changes.

## Scope

Included:

1. Identify every trigger/call path that can invoke `PublishClientItems`.
2. Distinguish startup/connect/reconnect/structure-change calls from ordinary runtime value updates.
3. Add focused diagnostics that show why `PublishClientItems` ran.
4. Ensure `PublishClientItems` exits before expensive work when only values changed.
5. Keep existing steady-state behavior and benchmark improvements.
6. Re-run the same `UdlDebug` benchmark and, if possible, observe a short running session after startup.

Explicitly not included:

1. Full UDL browser implementation.
2. RealtimeChart lifecycle/logging work.
3. Monitor or MonitorView work.
4. Broad registry redesign.
5. Adding more sample widgets or folders.

## Starting Point

Current benchmark:

- Status: `Pass`
- `P95UiDelayMs=4.4`
- `Spike50Ms=3`
- `Spike100Ms=3`
- `Spike250Ms=2`
- `BrowserDispatcherPosts=0`
- `ChartRenderCount=0`

Current UDL startup timings:

- `PublishClientItems` max `935.6 ms`
- `PublishClientItems.PostRuntimeUpdateUi` max `549 ms`
- `PublishClientItems.ScheduleAttachedItemsRefresh` max `239.7 ms`
- `PublishClientItems.PublishAttachOptionItems` max `101.7 ms`
- `PublishClientItems.LogRuntimeRootItems` max `97.6 ms`

Important interpretation:

- These costs are acceptable only if they happen during startup, reconnect, or real structure changes.
- They are not acceptable if they happen repeatedly during normal runtime value updates.
- Normal read/value updates must not trigger structure publish, attach-option publishing, attach refresh scheduling, or row rebuilds.

## Tasks

1. Inspect all direct call sites of `PublishClientItems`.
2. Inspect runtime event handlers, timers, receive loops, monitor callbacks, and property change handlers that may reach `PublishClientItems`.
3. Add a lightweight reason enum/string for `PublishClientItems` call sites if needed.
4. Include the publish reason in startup diagnostics:
   - connect/startup
   - runtime structure changed
   - reconnect
   - explicit refresh
   - unknown/legacy call path
5. Confirm whether runtime value updates can call `PublishClientItems`.
6. If value updates can call it, split or guard the path so value updates update runtime state only and do not enter structure publish.
7. Ensure the runtime structure signature is checked before:
   - scheduling attached item refresh
   - logging runtime roots
   - publishing attach options
   - publishing exposure items
   - rebuilding attach/module rows
8. Ensure structure signatures do not include volatile values such as current signal value, epoch, or read timestamp unless they really change visible structure.
9. Verify `ScheduleAttachedItemsRefresh` is only scheduled after actual structure or attach-option-relevant changes.
10. Keep attach path changes and reconnect behavior correct.
11. Re-run the current benchmark scenario.
12. Review the log to confirm `PublishClientItems Count=1` per UDL client in the startup scenario and no repeated structure publish during steady state.

## Implementation Order

1. Search for all `PublishClientItems` call sites.
2. For each call site, classify it as startup, reconnect, structural update, explicit user refresh, value update, or unknown.
3. Add a local call reason parameter or equivalent low-friction diagnostic marker.
4. Make the existing diagnostic state include the call reason.
5. Check whether any value-update/receive-loop call path invokes `PublishClientItems`.
6. Add a guard before expensive work:
   - enumerate runtime items
   - build a structure-only signature
   - return early if signature is unchanged
7. Confirm signature construction excludes volatile runtime values.
8. Move or keep expensive sub-steps strictly after the structure-change decision.
9. Re-run the current `UdlDebug` benchmark.
10. Inspect the log for:
   - `PublishClientItems` counts
   - publish reasons
   - any repeated publish after warmup
   - `ScheduleAttachedItemsRefresh` counts and reasons

2. Normal runtime value updates do not trigger expensive structure-publish work.
3. `PublishClientItems` remains `Count=1` per UDL client in the current startup benchmark unless a real structure change occurs.
4. Structure-only signature excludes volatile values.
5. `ScheduleAttachedItemsRefresh` is scheduled only for actual structure or attach-relevant changes.
6. `P95UiDelayMs` remains close to the current `4.4`.
7. `BrowserDispatcherPosts` remains `0`.
8. Existing attach rows and attach option registry state remain correct after real structure changes.
