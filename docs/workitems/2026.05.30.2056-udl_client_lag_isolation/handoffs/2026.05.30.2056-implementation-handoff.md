# IMPLEMENTATION HANDOFF

## Goal

Isolate and reduce UDLClient startup and attach-related UI lag using a minimal `UdlDebug` project as the first measurement baseline.

The first implementation should focus only on UDLClient startup, runtime item publishing, attach synchronization, and attach-section UI refresh behavior. It must not continue the RealtimeChart-first lag plan.

## Scope

Included:

1. Add or use a minimal `UdlDebug` sample/project containing one folder and one `UdlClient` widget.
2. Run the existing UI responsiveness benchmark against this minimal setup.
3. Analyze and reduce lag in `UdlClientControl` startup/attach paths.
4. Keep changes aligned with the planned future direction where UDL clients move into a browser-style management view similar to Monitor, EnhancedSignals, and CustomSignals.
5. Preserve the existing full demo project as an integration/stress baseline.

Explicitly not included:

1. RealtimeChart runtime/history ownership changes.
2. Monitor runtime or MonitorView UI traffic changes.
3. Full UDL browser implementation.
4. New external dependencies.
5. Large architectural rewrites outside the UDLClient path.

## Tasks

1. Create or finalize the minimal `UdlDebug` sample/project.
2. Run a UDL-only benchmark to establish an isolated baseline.
3. Inspect the UDL startup path and identify which work is runtime state, attach projection, registry publishing, or visual row refresh.
4. Reduce unnecessary UI work in `PublishClientItems`.
5. Reduce unnecessary UI work in `OnAttachedItemsRefreshTimerTick`.
6. Ensure attach-section and module-row rebuilds are driven by structural changes, not by every runtime value change or settle timer.
7. Keep the implementation compatible with a later UDL browser view by separating reusable runtime/snapshot concepts from visual row rendering where practical.
8. Re-run the UDL-only benchmark.
9. Re-run the broader no-chart benchmark after the UDL-only numbers improve.

## Implementation Order

1. Establish the minimal `UdlDebug` sample with one `UdlClient`.
2. Run the existing UI benchmark against `UdlDebug` before changing behavior.
3. Record the UDL-only baseline values for:
   - `ConnectRuntime`
   - `PublishClientItems`
   - `PublishClientItems.PostRuntimeUpdateUi`
   - `ScheduleAttachedItemsRefresh`
   - `OnAttachedItemsRefreshTimerTick`
   - `SynchronizeAttachedItems`
   - `RebuildAttachRows`
   - `RebuildAttachSectionRows`
   - `RebuildModuleRows`
4. Inspect `PublishClientItems` and split the decision flow conceptually into:
   - runtime item enumeration
   - runtime structure signature comparison
   - registry publish/update
   - attach option projection
   - visible UI row refresh
5. Ensure `PublishClientItems` exits before UI refresh work when the runtime structure signature has not changed.
6. Inspect `OnAttachedItemsRefreshTimerTick` and ensure it only rebuilds attach rows/sections when attach projection changed or relevant structure changed.
7. Avoid `Host.RefreshFolderBindings(...)` unless attached paths actually changed.
8. Ensure high-frequency runtime value updates do not trigger attach-section or module-row rebuilds.
9. Run the UDL-only benchmark again and compare values.
10. Run the broader no-chart benchmark and compare against the current baseline.

## Technical Constraints

- Keep chat/user-facing responses in German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Do not introduce new dependencies.
- Prefer existing project patterns and diagnostics.
- Keep changes scoped to UDLClient lag isolation.
- Do not implement the future UDL browser in this workitem.
- Visual controls must not become stronger owners of long-running runtime lifecycles.
- Future client browser views must be subscription-scoped and must not react broadly to global registry events.
- Runtime events and high-frequency value changes must not enqueue UI work unless a cheap relevance and structural-change check proves that visible UI structure needs an update.

## Acceptance Criteria

1. `UdlDebug` exists as a minimal UDL-only diagnostic sample/project.
2. The full demo project remains available for integration/stress testing.
3. A pre-change UDL-only benchmark exists or is summarized.
4. `UdlClientControl` no longer performs expensive attach-section/module row rebuilds when runtime structure and attach state are unchanged.
5. `OnAttachedItemsRefreshTimerTick` does not rebuild UI rows unconditionally after synchronization.
6. `PublishClientItems` avoids UI refresh work when the runtime structure signature is unchanged.
7. No Chart or Monitor behavior is changed as part of this workitem.
8. A post-change UDL-only benchmark shows reduced UDL startup/attach timings.
9. The broader no-chart benchmark is re-run after the UDL-only improvement.

## Verification

1. Build the solution with:
   - `dotnet build HornetStudio.sln --no-restore`
2. Run the UI responsiveness benchmark with the minimal `UdlDebug` sample.
3. Run the same benchmark with the broader no-chart scenario used in `docs/workitems/2026.05.30.1934-ui_lag_without_chart_baseline/ChatHandoff.md`.
4. Compare benchmark timing summaries for UDL startup categories before and after the change.

## Out of Scope

- RealtimeChart rendering, sampling, runtime ownership, or history retention.
- MonitorRuleRow runtime extraction.
- MonitorViewControl browser/activity gating.
- Full UDL browser design or implementation.
- Release versioning, publish flow, tags, or notice file updates.

## Risks / Watchouts

- A minimal `UdlDebug` project can hide integration costs; keep the full no-chart benchmark as the second verification step.
- Reducing rebuilds must not leave attach rows stale after a real structural change.
- Runtime value changes and runtime structure changes must remain distinct.
- Attach path changes must still refresh bindings when the persisted attached paths really changed.
- Avoid burying new browser-oriented architecture inside `UdlClientControl`; keep changes focused and reusable.
