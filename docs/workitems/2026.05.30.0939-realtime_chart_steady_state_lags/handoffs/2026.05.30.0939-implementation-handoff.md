# IMPLEMENTATION HANDOFF

## Goal
Instrument and isolate recurring steady-state UI lags that are visible in the Realtime Chart after startup. The startup max spike is not the primary concern for this workitem.

## Scope
Included:
- Add focused diagnostics for ongoing UI delays after the initial startup/attach phase.
- Measure the live data pipeline before chart rendering:
  - UDL/runtime value updates
  - HostRegistry value updates and notifications
  - EnhancedSignal reactions/computation
  - Monitor rule reactions/computation
  - Realtime Chart data ingestion and UI update path
- Keep existing behavior unchanged except for obvious local no-op guards.
- Keep diagnostics low-noise and distinguish startup phases from steady-state phases.

Explicitly not included:
- Optimizing application startup max delay.
- Building the final UDL browser UI.
- Broad architecture refactoring.
- Changing persisted project format.
- Replacing the chart library or redesigning the Realtime Chart UI.

## Starting Point
- Latest log: `src/HornetStudio/bin/Debug/net9.0-windows/logs/host-20260530.log`.
- User-visible issue:
  - Realtime Chart shows recurring lags during normal operation.
  - Startup delay is not the main issue.
- Current benchmark observations:
  - `P95UiDelayMs=52.5`, close to the 50 ms threshold.
  - Many recurring spikes in the `50-200 ms` range continue after startup.
  - `ChartRenderP95Ms=2.9`, `ChartRenderMaxMs=36.4`, so rendering itself is probably not the main bottleneck.
  - `BrowserDispatcherPosts=0`, so browser dispatcher flooding is not currently indicated.
  - Monitor diagnostics show ongoing registry activity, e.g. `MonitorViewControl[main1]` sees about 25 registry events per 5 seconds.
- Current likely bottleneck:
  - data pipeline and UI callbacks before rendering, not the chart draw call itself.

## Tasks
1. Define a steady-state diagnostic window:
   - continue recording startup diagnostics, but add or label separate steady-state timings after startup/attach has completed
   - avoid treating the first startup max spike as the target signal
2. Instrument HostRegistry live value path:
   - `UpdateValue`
   - `TryUpdateUserProperty`
   - `UpsertSnapshot` only if it occurs repeatedly during steady state
   - item change notification dispatch and subscriber fan-out if accessible without broad refactoring
3. Instrument Realtime Chart non-render path:
   - registry item change handler
   - source value lookup/resolution
   - sample append / series update
   - UI collection update or dispatcher callback before rendering
   - keep existing render timing as-is
4. Instrument EnhancedSignal steady-state reaction:
   - registry event acceptance/filtering
   - source value resolution
   - computation/update publication
   - any UI-thread callback caused by runtime value changes
5. Instrument Monitor steady-state reaction:
   - registry event acceptance/filtering
   - rule evaluation
   - status/item publication
   - any UI-thread callback caused by runtime value changes
6. Add low-risk no-op guards only if clearly local:
   - skip UI work when a value did not materially change
   - skip registry reaction if the changed key is not relevant
   - skip chart sample/UI update if source path is unrelated
7. Keep diagnostics summaries readable:
   - use distinct category names such as `SteadyStateRegistry`, `SteadyStateChart`, `SteadyStateEnhancedSignal`, and `SteadyStateMonitor`
   - avoid logging every value update as an individual information line unless it is aggregated

## File-Level Changes
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> add or reuse timing collection support for steady-state categories if existing APIs are sufficient.
- `src/HornetStudio.Editor/Widgets/RealtimeChart/RealtimeChartControl.axaml.cs` -> instrument data ingestion, source resolution, sample append, and UI update path before render.
- `src/HornetStudio.Editor/Widgets/EnhancedSignals/EnhancedSignalsControl.axaml.cs` and related EnhancedSignal runtime files -> instrument accepted value-change processing and computation path if this control participates in the benchmark scenario.
- `src/HornetStudio.Editor/Widgets/Monitor/MonitorControl.axaml.cs` and/or `src/HornetStudio.Editor/Widgets/Monitor/MonitorViewControl.axaml.cs` -> instrument rule processing and steady-state registry reactions.

- `docs/workitems/2026.05.30.0939-realtime_chart_steady_state_lags/handoffs/2026.05.30.0939-implementation-handoff.md` -> this handoff.

## Technical Constraints
- Chat responses remain German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers remain English.
- Do not introduce new dependencies.
- Do not perform broad refactoring.
- Do not move runtime ownership into visual controls.
- Registry event handlers must filter relevance before scheduling UI work.
- High-frequency value changes must not trigger UI structure refreshes.
- Diagnostics on background/runtime threads must not read Avalonia UI objects.
- Keep instrumentation aggregated enough that logging itself does not create the lag being measured.

## Acceptance Criteria
- Benchmark summary still reports chart render timing.
- New timing summaries identify steady-state costs for chart ingestion, registry update/notification, EnhancedSignal, and Monitor paths where applicable.
- The recurring `50-200 ms` lag source can be attributed to at least one concrete stage or ruled out for each instrumented stage.
- Startup max delay remains separable from steady-state lag analysis.
- `BrowserDispatcherPosts=0` does not regress.
- No new thread exceptions appear.
- Realtime Chart behavior remains unchanged.

## Risks / Watchouts

- If diagnostics show the chart render remains cheap, do not optimize rendering first.
- If diagnostics point to Monitor or EnhancedSignal, create a focused follow-up before changing broad registry behavior.
- Treat recurring spikes after startup as the target signal, not one-time startup/attach spikes.
