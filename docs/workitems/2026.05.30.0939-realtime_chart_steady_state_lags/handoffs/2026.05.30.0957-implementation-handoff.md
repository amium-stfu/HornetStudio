# Implementation Handoff: RealtimeChart Sampling Lifecycle Containment

## Context

The freeze still happens shortly after startup. The widgets are not fully built before the application becomes unresponsive.

The previous per-`ChartRuntimeState` non-reentrant sampling guard improved one local path but did not remove the freeze. The latest log still shows a warning storm from `SteadyStateChart` during early startup.

Latest observed log:

- `src/HornetStudio/bin/Debug/net9.0-windows/logs/host-20260530.log`
- Benchmark enabled around `09:54:51.641`
- First UI spike around `09:54:53.649` with `DelayMs=1959.1`
- UDL attach rebuild begins around `09:54:56`
- Shortly after that, many `RealtimeChart.SampleCurrentValues.ResolveSamples` warnings appear before widgets are fully available

Observed sample durations include approximately `247 ms`, `319 ms`, `416 ms`, `502 ms`, `596 ms`, `676 ms`, `801 ms`, and `826 ms` with `ThresholdMs=10`.

The entries are distributed across many thread pool threads and occasionally the UI thread. This strongly suggests that sampling is not only reentrant inside one state, but starts from too many chart state/timer instances or starts too early during view construction/rebinding.

## Goal

Contain the RealtimeChart sampling lifecycle so startup can complete and widgets can be built before expensive sampling begins.

Sampling must only run when the chart is attached, visible/active, has a stable chart identity, and the owning page/widget is ready.

## Non-Goals

- Do not redesign the UDL browser migration.
- Do not replace the old UDL control.
- Do not redesign the full data registry.
- Do not optimize every `ResolveSamples` path before lifecycle containment is proven.
- Do not add new dependencies.

## Required Changes

1. Move eager sampling out of construction.
   - `ChartRuntimeState` construction must not immediately resolve registry samples or start expensive work.
   - Initial sampling should be triggered only after the control is attached and the page/widget is active.

2. Add lifecycle gates before sampling.
   - Skip sampling when the chart has no stable chart identity.
   - Skip sampling when the chart is detached.
   - Skip sampling when the owning page/widget is inactive or still initializing.
   - Skip sampling for `unknown` or incomplete binding contexts.

3. Ensure exactly one active sampler per stable chart identity.
   - Stop and dispose old timers on detach, rebind, or state replacement.
   - Avoid orphan `ChartRuntimeState` entries that keep timers alive.
   - If multiple runtime states can still point to the same chart identity, add a shared guard keyed by that identity.

4. Keep the existing per-state non-reentrant guard.
   - It is still useful, but it is not sufficient alone.
   - The guard should remain a second line of defense after lifecycle gating.

5. Reduce diagnostic log pressure.
   - Do not write a warning for every slow `ResolveSamples` call.
   - Replace the per-event warning storm with aggregated benchmark output, rate-limited warnings, or a much higher threshold.
   - Keep enough diagnostics to prove whether sampling still happens before widgets are built.

6. Add focused instrumentation for lifecycle transitions.
   - Log sampler start/stop with chart identity, attach state, active state, and reason.
   - Log skipped sampling reasons at a low-volume level or as an aggregate.
   - Avoid high-frequency logs inside the timer hot path.

## Suggested Implementation Order

1. Inspect `RealtimeChartControl.axaml.cs` and identify every path that creates `ChartRuntimeState`, starts a timer, calls `SampleCurrentValues`, or keeps runtime states in dictionaries.
2. Introduce explicit sampler lifecycle methods such as `StartSampling(reason)` and `StopSampling(reason)` if this matches the current class shape.
3. Remove or gate constructor-time sampling.
4. Wire start/stop to attach, detach, data-context change, chart item change, and active-page state.
5. Add identity-based cleanup so obsolete runtime states cannot continue sampling.
6. Rate-limit or aggregate `SteadyStateChart` warnings.
7. Build and run the same startup scenario with the benchmark enabled.

## Verification

Run:

```powershell
dotnet build HornetStudio.sln --no-restore
```

Manual verification:

- Start the host with the same demo/workspace that currently freezes.
- Confirm widgets are built before RealtimeChart sampling begins.
- Confirm the log no longer contains an early `SteadyStateChart` warning storm.
- Confirm there is no large thread pool burst from `RealtimeChart.SampleCurrentValues.ResolveSamples`.
- Confirm the Realtime Chart still updates after its page/widget is visible and active.

## Expected Result

Startup should no longer freeze before widgets are built. If lag remains after lifecycle containment, the next workitem should optimize `ResolveSamples` itself, especially by caching resolved source paths/items and avoiding repeated full registry scans in the timer path.
