# DEBUG REPORT

## Problem
Monitor rules from `benchmarks/ui_lag_bench_project/Folders/main/Monitoring/Monitor.yaml` were reported as not running after startup, and Monitor Browser showed no rules.

## Expected Behavior
Startup should load folder-local monitor rules from `Monitoring/Monitor.yaml`, publish runtime items, and Monitor Browser should show those same central rules. Opening Monitor Browser must not stop the folder monitor runtime.

## Actual Behavior
The first diagnosed path was a temporary Monitor Browser owner item with no embedded `MonitorDefinitions`. `MonitorControl.RebuildRules()` read only that empty property and could call `MonitorRuntimeManager.SyncDefinitions(folderName, [])`, releasing the folder runtime and rendering an empty browser rule list.

The second reported symptom was checked against the actual benchmark project. `Monitor.yaml` contains three rules, and focused tests prove the central file can be loaded and synchronized into runtime entries. Runtime logs also show `monitor_rule_1`, `monitor_rule_2`, and `monitor_rule_3` being added and executing actions. The remaining browser risk was that central-rule resolution depended on a bound `EditorViewModel`; the browser owner now also falls back to loading `Monitoring/Monitor.yaml` directly from `FolderLayoutPath`.

## Error Messages / Logs
- No exception was required for the browser-empty path.
- Runtime log evidence showed central rules running:
  - `[DataRegistry] Added key=studio.main.monitor.monitor_rule_1`
  - `[DataRegistry] Added key=studio.main.monitor.monitor_rule_2`
  - `[DataRegistry] Added key=studio.main.monitor.monitor_rule_3`
  - `[MonitorAction] trigger=OnActivated rule=monitor_rule_*`

## Relevant Code
- `src/HornetStudio.Editor/Widgets/Monitor/MonitorBrowserDialogWindow.axaml.cs`
  - Creates a temporary owner item named `MonitorBrowser`.
- `src/HornetStudio.Editor/Widgets/Monitor/MonitorControl.axaml.cs`
  - Previously parsed only `FolderItemModel.MonitorDefinitions`.
  - Now resolves browser-owner definitions through `MainWindowViewModel.GetMonitorRegistryEntries(...)`.
  - Now falls back to `FolderLayoutPath` -> `Monitoring/Monitor.yaml` for browser owners when no view model is available or registry resolution is empty.

## Attempted Fixes
- Fix 1 -> Added browser-owner definition resolution through the shared monitor registry instead of the empty temporary owner item. Result: focused build passed and browser regression tests passed.
- Fix 2 -> Added direct central-file fallback for Monitor Browser owners when `EditorViewModel` resolution is unavailable or empty. Result: focused build passed, `Monitor browser` tests passed, and `monitor sync` tests passed.

## Current Hypothesis
The diagnosed browser-empty paths are fixed. Startup central-file sync is covered by regression tests and current logs indicate the benchmark monitor rules are running. If the user still sees no rules in an already-open app instance, the likely remaining cause is that the process was started from an older build before the browser fallback fix.
