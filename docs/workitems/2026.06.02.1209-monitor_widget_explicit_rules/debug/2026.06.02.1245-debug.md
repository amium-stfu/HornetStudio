# DEBUG REPORT

## Problem
HornetStudio could not start because the Debug build could not copy `HornetStudio.Editor.dll` into the editor test output folder.

## Expected Behavior
The standard Debug solution build should complete without file-lock errors or compiler warnings so the application can start normally.

## Actual Behavior
The build failed because `.NET Host (15480)` locked `B:\HornetStudio\src\HornetStudio.Editor.Tests\bin\Debug\net9.0-windows\HornetStudio.Editor.dll`. The previous build also reported nullable warning `CS8602` in `UdlClientControl.axaml.cs`.

## Error Messages / Logs
- `The process cannot access the file 'B:\HornetStudio\src\HornetStudio.Editor.Tests\bin\Debug\net9.0-windows\HornetStudio.Editor.dll' because it is being used by another process.`
- Locking process: `dotnet.exe src\HornetStudio.Editor.Tests\bin\Debug\net9.0-windows\HornetStudio.Editor.Tests.dll`, PID `15480`.
- Warning: `CS8602` at `src\HornetStudio.Editor\Widgets\UdlClient\UdlClientControl.axaml.cs` in `AttachManagedRuntime`.

## Relevant Code
`AttachManagedRuntime` read `item.FolderName` and `item.Name` after `IsUdlClientItem(item)`, but the compiler did not infer that `item` was non-null from the helper method.

## Attempted Fixes
- Inspected PID `15480` and confirmed it was the editor self-test host from the normal Debug output folder -> confirmed root cause of the file lock.
- Stopped PID `15480` -> `PID_NOT_FOUND` on follow-up check.
- Added an explicit `item is null` guard in `AttachManagedRuntime` -> focused editor build succeeded without warnings.
- Ran standard `build-hornetstudio-debug` task -> solution build succeeded without warnings.

## Current Hypothesis
The start failure was caused by a previously launched editor self-test executable that stayed alive and locked copied editor assemblies in `src/HornetStudio.Editor.Tests\bin\Debug\net9.0-windows`. Use isolated `OutDir` for ad-hoc self-test validation when the app or test host may remain open.
