# IMPLEMENTATION HANDOFF

## Goal
Stabilize Monitor runtime, Monitor Browser, and MonitorView widget behavior across project load, project reload, and project/folder context changes.

The immediate problem is that Monitor Browser now shows and visualizes all rules, but `MonitorView` can work briefly after project load and then become undefined or stop reflecting monitor state. Project switching or project reload is suspected to leave stale runtime state, stale widget row snapshots, or stale registry subscriptions.

## Scope
Included:

- Diagnose and fix MonitorView context loss after project load/reload/project switch.
- Ensure monitor runtime synchronization is robust when projects or folders with the same technical folder name are loaded sequentially.
- Ensure MonitorView rebuilds rows, runtime snapshots, and scoped registry subscriptions from the current folder context only.
- Ensure Monitor Browser remains an all-rule management/debug view and does not stop or clear runtime accidentally.
- Add focused regression tests for project/folder rebind behavior.
- Update MonitorView/Monitor documentation if behavior or ownership rules are clarified.

Not included:

- No broad redesign of generic signal widgets.
- No new external dependencies.
- No release/version changes.
- No migration for legacy user data beyond the current pre-release project format.

## Starting Point

- Active monitor file exists at `benchmarks/ui_lag_bench_project/Folders/main/Monitoring/Monitor.yaml`.
- Monitor Browser now resolves and displays central rules.
- Recent debug findings:
  - Startup central-file sync is covered by tests and current logs showed monitor rules being registered and actions executing.
  - Monitor Browser has a direct central-file fallback via `FolderLayoutPath -> Monitoring/Monitor.yaml`.
  - MonitorView still has a suspected rebind/lifecycle issue after project load or project switch.
- Current architecture risk:
  - Runtime manager state is keyed by folder name such as `main`.
  - Public runtime registry paths are also folder-based, e.g. `studio.main.monitor.monitor_rule_2`.
  - If two projects or reload phases reuse `main`, stale runtime or stale widget subscription state can survive long enough to confuse MonitorView.

   - Review `MonitorRuntimeManager` keying and release semantics.

4. Inspect MonitorView lifecycle.
   - Review `HookObservedItem`, `OnDataContextChanged`, `RebuildRows`, `UpdateRuntimeRows`, `UpdateRegistrySubscriptionPrefixes`, and detach behavior.
   - Ensure context changes clear old `_rowSnapshot`, `_runtimeSnapshot`, timers, queued refreshes, and subscription prefixes before new rows are resolved.
   - Ensure subscription prefixes are rebuilt only after rows are resolved for the current `FolderName` and current `FolderLayoutPath`.

5. Fix stale widget state.
   - Make MonitorView reset its runtime snapshot and registry subscription prefixes when observed item, folder name, folder layout path, selected monitor IDs, or editor view model context changes.
   - Avoid transient broad subscriptions during rebuild.
   - Ensure no old selected rule path can remain accepted after a project/folder change.

6. Fix runtime state collision if confirmed.
   - If tests show folder-only runtime manager state collides across project switch/reload, use a stable internal runtime scope identity.
   - Candidate identity sources:
     - folder layout path when available
     - project root + folder name
     - fallback folder name only when no file-backed context exists
   - Keep public registry path behavior unchanged unless a separate decision is made.

7. Add focused tests.
   - Central monitor definitions load into runtime on folder-backed project load.
   - MonitorView resolves selected rules after project load.
   - MonitorView resets old rows/snapshots/subscription prefixes when the observed item is rebound to a different folder context.
   - Project reload with same folder name does not leave MonitorView subscribed to stale paths.
   - Monitor Browser opening does not clear runtime or MonitorView rows.

8. Update documentation if needed.
   - Clarify MonitorView depends on current folder-local `Monitoring/Monitor.yaml` plus explicit `SelectedMonitorIds`.
   - Clarify runtime is folder/project scoped internally and Browser/Widget are views over runtime state.
