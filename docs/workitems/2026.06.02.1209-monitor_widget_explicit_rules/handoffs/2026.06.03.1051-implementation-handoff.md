# IMPLEMENTATION HANDOFF

## Goal
Reduce MonitorRuntime steady-state UI load by making monitor registry publication state-driven instead of evaluation-cycle-driven. The runtime must evaluate configured rules and execute configured actions, but it must not continuously generate visible registry messages or root updates when the boolean monitor state did not change.

## Scope
Included:
- Change MonitorRuntime publication behavior so visible monitor registry paths are written only when observable boolean state changes.
- Keep MonitorRuntime rule evaluation and action execution behavior intact.
- Keep monitor browser/event filtering behavior intact unless a narrow adjustment is required to match the new registry contract.
- Update monitor documentation that describes runtime-published monitor paths.
- Add or update focused tests for no-op publication on unchanged monitor state.

Explicitly not included:
- Reworking the monitor rule definition format.
- Adding new dependencies.
- Reworking browser layout or general registry filtering.
- Changing non-monitor runtime publication policies.

## Starting Point
- The 120s benchmark still reports `BrowserDispatcherPosts=69` in `host-20260603.log:4082`.
- Browser summaries at `host-20260603.log:4083`, `host-20260603.log:4084`, and `host-20260603.log:4085` show child events are now filtered correctly: each row has `RegistryEvents=69`, `IgnoredRegistryEvents=46` for `.active` and `.message`, but still `AcceptedRegistryEvents=23` and `DispatcherPosts=23` on the root path.
- This means the remaining benchmark load comes from 23 visible root publications per monitor rule.
- Desired behavior: MonitorRuntime evaluates rules and executes actions, but public status is only bool yes/no and only changes are published.

## Tasks
1. Locate the MonitorRuntime code that publishes `studio.<Folder>.monitor.<Rule>` root items and child status/message items.
2. Identify which writes are done every evaluation cycle versus only on state transitions.
3. Introduce or reuse internal per-rule state tracking so the runtime can compare `previousActive` and `nextActive` before publishing.
4. Restrict public registry writes for rule status to the minimal bool status contract.
5. Remove or stop steady-state runtime publication of generated message/meta child paths unless they are required for actions or definitions.
6. Ensure `OnActivated` and `OnCleared` actions still run exactly once per transition.
7. Ensure aggregate monitor status paths, if kept, are also written only when their bool value changes.
8. Update monitor documentation to state that runtime publication is transition-based and public status is bool-only.
9. Add or update focused tests that verify repeated evaluation with unchanged state does not emit additional visible registry updates.
10. Run build/tests and the 120s benchmark scenario if feasible.

## File-Level Changes
- `src/HornetStudio.Editor/**/Monitor*Runtime*.cs` -> constrain monitor publication to state changes and keep runtime-generated display text out of steady-state registry writes.
- `src/HornetStudio.Editor/**/Monitor*.cs` -> adjust narrow callers/helpers if they currently expect `.message` or repeated root publications.
- `src/HornetStudio.Editor.Tests/**` or existing focused monitor tests -> add no-op publication and transition publication coverage.
- `src/HornetStudio/docs/**/Monitor*.md` or relevant widget/manual docs -> update public runtime path contract and behavior.
- `src/HornetStudio/docs/data-flow-and-signals.md` -> update the monitor runtime subsection if it still describes message/meta or list-style root publications as active runtime output.

## Implementation Order
1. Inspect current monitor publication paths and list every registry key written by one evaluation cycle.
2. Define the minimal public status contract:
   - rule root value is bool active, or
   - existing `.active` child remains only if the browser does not display root rows.
   Prefer the shape that removes accepted visible root events in steady state.
3. Add internal state comparison before registry writes.
4. Change root and aggregate publication helpers to skip writes when the target bool value is unchanged.
5. Remove cycle-based message/meta publication or move message display to static monitor definitions.
6. Verify action execution is still transition-based and unaffected by skipped publications.
7. Update tests.
8. Update docs.
9. Build and benchmark.

## Technical Constraints
- Answer/chat in German, but code, comments, XML docs, UI text, file names, and technical identifiers stay English.
- No new dependencies.
- Keep changes scoped to monitor runtime publication and necessary docs/tests.
- Browser controls must remain subscription-scoped and must filter before posting to the UI thread.
- Runtime events must not enqueue UI work unless a cheap relevance and change-type check proves visible UI structure needs an update.
- HostRegistry publishing from runtime adapters must be explicit and scoped.

## Acceptance Criteria
- In a steady-state monitor benchmark where rule active states do not change, monitor rule rows no longer produce repeated accepted root registry events.
- `BrowserDispatcherPosts` from monitor steady-state root publications is reduced to zero or only transition/initialization events.
- Child `.active` and `.message` events are not used as repeated runtime status traffic.
- Rule actions still execute on `OnActivated` and `OnCleared` transitions.
- Public monitor status is bool yes/no, not generated runtime messages.
- Documentation matches the new monitor runtime publication contract.

## Verification
- Run focused monitor tests or add a focused test that evaluates the same rule repeatedly without state changes and asserts no additional registry update is emitted after initial publication.
- Run `dotnet build HornetStudio.sln --no-restore` after restore has already completed.
- If feasible, run the 120s UI benchmark and compare the summary against the previous baseline:
  - previous: `BrowserDispatcherPosts=69`
  - previous row summaries: `AcceptedRegistryEvents=23`, `DispatcherPosts=23` per row on root paths
  - expected: repeated root-path accepted events disappear in steady state.

## Out of Scope
- Changing the monitor definition schema.
- Reworking chart/history runtime.
- Broad browser refresh architecture changes.
- Adding a new registry abstraction layer.
- Preserving legacy demo definitions if they conflict with the current target architecture.

## Risks / Watchouts
- If the browser relies on root item snapshots for row text, removing root writes may expose missing definition-based display data. Fix that by reading static rule definition data, not by reintroducing runtime message writes.
- If aggregate paths currently publish comma-separated event lists or JSON meta, replacing them with bool-only status may require documentation and any UI consumers to be aligned.
- Avoid writing unchanged bool values to `HostRegistries.Data`; even idempotent writes can still fire registry events.
- Do not silently suppress action transitions while suppressing registry publications.

- The desired monitor runtime contract is: evaluate rules continuously, publish public bool state only on change, execute actions only on transitions.
