# IMPLEMENTATION HANDOFF

## Goal

Correct the Monitor architecture implementation so Runtime, Browser, and Widget have distinct responsibilities:

- Runtime manages and evaluates all monitor rules in a background process/thread context, not on the UI thread.
- Browser is the editor/management layer for all monitor rules from the runtime/definitions.
- Widget renders only a body list of explicitly selected monitor rules. Each row is visually linked to the selected rule's boolean runtime state, similar to a bool `SignalWidget`, but with the Monitor-specific `[Id] [LogText]` layout.

## Scope

Included:

- Ensure monitor rule evaluation and runtime publishing are not owned by UI controls and do not run on the UI thread as a result of widget/browser presence.
- Keep the Monitor Browser as an editor/management/debug view for all rules.
- Make the Monitor Widget use only explicitly selected rules from its widget configuration.
- Render multiple selected rules per widget.
- Keep row layout equivalent to the current visual intent: `[Id] [LogText]`.
- Make each widget row observe the selected rule's runtime boolean state as its primary binding.
- Ensure unselected rules are irrelevant to the widget: no accepted widget events, dispatcher posts, row refreshes, or rebuilds.
- No migration for old widget configuration.

Not included:

- No broad redesign of generic `SignalWidget`.
- No compatibility migration for old Monitor Widget configs.
- No release/version changes.
- No new external dependencies.

## Starting Point

- The current implementation has improved dispatcher post counts, but benchmark output still shows `MonitorViewControl[main]` accepting events for all three rules.
- The user will intentionally configure the test project so only two of three rules are selected in the widget.
- If the widget still accepts events for the unselected third rule, the implementation is structurally wrong.
- Previous benchmark with all three rules present:
  - `BrowserDispatcherPosts=21`
  - `MonitorViewControl[main] RegistryEvents=122 AcceptedRegistryEvents=61 IgnoredRegistryEvents=61`
  - Top accepted rule keys included all three monitor rules.
- The real target is not more coalescing. The target is explicit binding scope.

## Tasks

1. Inspect current monitor runtime ownership.
   - Find where rule timers/evaluation loops are created.
   - Confirm whether `MonitorRuleRuntime.*.Evaluate`, `EvaluateState`, or `PublishRuntime` can run on the UI thread.
   - Move or adjust scheduling so monitor evaluation and runtime publishing are background-owned.
   - UI controls may start/configure/observe runtime services, but must not perform rule evaluation.

2. Inspect current Monitor Browser.
   - Keep it as the editor/management layer for all rules.
   - It may display all rules and runtime state.
   - It must not be required for rules to function.
   - It must not clear/release/own folder runtime based on browser open/closed state.

3. Inspect current Monitor Widget / `MonitorViewControl`.
   - Identify persisted widget configuration.
   - Identify how selected rule IDs are stored.
   - Identify whether the widget still subscribes to the folder/root monitor path and filters afterward.

4. Correct widget relevance model.
   - The widget must build a relevance snapshot only from selected rule IDs.
   - The widget must not treat the monitor folder/root as a source for all rules.
   - Exact aggregate/root events such as `studio.main.monitor` may be ignored.
   - Unselected rule paths must be ignored before any `Dispatcher.UIThread.Post`, `InvokeAsync`, runtime refresh, rebuild, or row update is scheduled.

5. Correct widget binding model.
   - Each row should bind conceptually like a bool `SignalWidget` to one selected rule runtime state item.
   - Primary state is the rule's boolean active state.
   - Display keeps Monitor-specific layout and text:
     - ID segment
     - log text/message segment
   - The widget body contains only selected rows, in configured order.

6. Validate duplicate handling.
   - Prevent duplicate rule IDs in one widget configuration.
   - Keep existing monitor rule ID duplicate protections intact.

7. Remove implicit all-rule widget behavior.
   - Since no migration is required, old implicit "show all rules" behavior should be removed or ignored.
   - Old configs should fail gracefully by rendering no selected rows or defaulting to an empty selection, not by showing all rules.

8. Add focused tests.
   - Widget configured with two selected rules renders exactly two rows.
   - Events from the unselected third rule are ignored before dispatcher scheduling.
   - Selected rule active-state changes update the matching row.
   - Browser can be closed while runtime rules continue to evaluate.
   - Monitor rule evaluation/publish is not performed by widget row controls.

9. Update documentation.
   - Update widget docs and help to describe Monitor Widget as selected-rule alarm/status visualization.
   - Clarify Browser vs Widget vs Runtime responsibility.

## Technical Constraints

- Chat response must be German; code, comments, XML docs, UI text, validation messages, and technical identifiers must be English.
- Use existing libraries, patterns, Avalonia conventions, registry APIs, and widget patterns.
- Do not introduce new dependencies without justification.
- Visual controls must not own long-running runtime lifecycles.
- Runtime events and value updates must not enqueue UI work until a cheap relevance and change check proves the event belongs to a selected visible rule.
- High-frequency runtime value changes should update runtime state only; widget UI refresh should be scoped to selected visible rows.
- Browser-hosted controls and widgets must not react broadly to `studio.*` or monitor root paths unless explicitly owned and filtered.
- Public classes and public methods added or changed must have XML documentation.

## Acceptance Criteria

- Runtime evaluates all configured monitor rules in a background runtime context and works with Browser and Widget closed.
- Browser is only editor/management/debug view for all rules.
- Widget stores and uses multiple selected rule IDs.
- Widget body renders only selected rules.
- Row layout remains Monitor-specific `[Id] [LogText]`.
- Each row observes the selected rule's boolean active runtime state, conceptually like a bool `SignalWidget`.
- Duplicate selected rule IDs in one widget are rejected.
- With a test project where 2 of 3 rules are selected:
  - the third rule does not appear in widget rows
  - the third rule does not appear as an accepted widget event
  - the third rule causes no widget dispatcher posts, row refreshes, or rebuilds
- Root aggregate monitor events are ignored by the widget before UI dispatch.
- No old implicit all-rules widget behavior remains.

- If existing instrumentation reports both Browser and Widget under `MonitorViewControl[main]`, separate or clarify instrumentation enough to prove the widget is scoped correctly.
- If runtime state identity differs from visible rule ID, choose one canonical persisted selected-rule identity and map it explicitly to runtime paths.
- Avoid using broad monitor folder subscription plus late filtering as the widget's primary model. The widget's relevance should be built from selected rule runtime paths.
