# IMPLEMENTATION HANDOFF

## Goal
Reduce Monitor and AlertWidget steady-state UI load by making monitor runtime publication and alert consumers transition-driven instead of evaluation-cycle-driven. The monitor rules must keep evaluating and executing actions correctly, but visible UI consumers must only receive meaningful active/inactive state changes.

## Scope
Included:

- Keep the current monitor definition and `Monitoring/Monitor.yaml` model.
- Keep `SetValue` action execution working for folder-scoped targets such as `studio.main.enhanced_signals.filtered_1.set`.
- Restrict monitor runtime public registry publication to initial state and actual boolean state transitions.
- Align `AlertWidgetRow` and `MonitorView` consumers with the bool-only monitor runtime contract.
- Prevent `AlertWidgetRow` from doing expensive dispatch work for unchanged or irrelevant monitor runtime events.
- Create a `MonitorOnly` benchmark/demo setup by disabling or removing the chart from the benchmark scenario before measuring this fix.
- Add or update focused tests for unchanged monitor evaluations and AlertWidget/MonitorView event filtering.
- Update monitor/alert documentation that describes public monitor runtime paths.

Explicitly not included:

- No RealtimeChart architecture or rendering rewrite.
- No SignalWidget rewrite in this step.
- No broad typed runtime-subscription framework yet.
- No Monitor Browser redesign beyond narrow compatibility with the new monitor status contract.
- No release/version work.

## Starting Point
- User observed that an untouched benchmark run behaves acceptably, while UI interaction quickly causes lag.
- Current log evidence in `src/HornetStudio/bin/Debug/net9.0-windows/logs/host-20260603.log` shows `SetValue` actions are applied successfully.
- Current log evidence also shows repeated `RealtimeChartRender`, `MonitorRuleRuntime.Evaluate`, `MonitorRuleRuntime.PublishRuntime`, and `AlertWidgetRow.ItemChangedDispatch` warnings.
- The existing handoff `docs/workitems/2026.06.02.1209-monitor_widget_explicit_rules/handoffs/2026.06.03.1051-implementation-handoff.md` already identifies repeated monitor root publications as a remaining load source.
- The chart should be disabled for the first validation pass so monitor/alert changes can be measured independently.

## Tasks
1. Create or adjust a `MonitorOnly` benchmark/demo variant where the realtime chart is disabled or removed while monitor rules, AlertWidget, MonitorView, and the signal source remain active.
2. Inspect all monitor runtime registry writes from one evaluation cycle, including rule root, aggregate root, and any legacy `.active`/`.message` children.
3. Define the public monitor runtime contract as bool-only:
   - `studio.<folder>.monitor.<rule>` value is the rule active state.
   - `studio.<folder>.monitor` value is the aggregate active state.
   - generated runtime message/status text is not steady-state public traffic.
4. Change monitor rule publication so unchanged active state does not write to `HostRegistries.Data`.
5. Change aggregate monitor publication so unchanged aggregate active state does not write to `HostRegistries.Data`.
6. Ensure `OnActivated` and `OnCleared` actions still execute exactly once per transition and are not tied to skipped registry publications.
7. Update `AlertWidgetRow` event handling so it only accepts the configured selected monitor root/aggregate bool paths and ignores unrelated descendants or legacy child paths before scheduling UI work.
8. Update `MonitorViewControl` if it still expects repeated root events or generated message children.
9. Keep Monitor Browser rule editing/loading functional, but do not broaden the browser scope.
10. Add focused tests for repeated monitor evaluations with unchanged state and for AlertWidget/MonitorView ignoring irrelevant monitor child events.
11. Run focused tests, build, and then run a `MonitorOnly` benchmark.

## File-Level Changes
- `src/HornetStudio.Editor/Monitoring/MonitorRuleRuntime.cs` -> make per-rule public publication initial/transition-only; keep action execution transition-based.
- `src/HornetStudio.Editor/Monitoring/MonitorRuntimeManager.cs` -> make aggregate publication initial/transition-only and preserve folder runtime ownership.
- `src/HornetStudio.Editor/Widgets/AlertWidget/` or current AlertWidget row files -> narrow monitor event acceptance and dispatch scheduling to selected bool state paths.
- `src/HornetStudio.Editor/Widgets/MonitorView/MonitorViewControl.axaml.cs` -> align row updates with bool-only monitor runtime paths and avoid message-child dependence.
- `src/HornetStudio.Editor/Widgets/Monitor/MonitorControl.axaml.cs` -> adjust only if Monitor Browser or rule display depends on repeated runtime status text.
- `src/HornetStudio.Editor.Tests/Program.cs` -> add or update focused monitor runtime and alert/monitor view event filtering tests.
- `src/HornetStudio/docs/widgets/Monitor.md` and matching help/description files if applicable -> document transition-based bool runtime status.
- `src/HornetStudio/docs/widgets/MonitorView.md` and `src/HornetStudio/docs/widgets/help/MonitorView.help.md` if behavior is user-visible.
- `src/HornetStudio/docs/data-flow-and-signals.md` if it documents monitor runtime publication.
- `benchmarks/ui_lag_bench_project/**` or a copied benchmark variant -> create/adjust `MonitorOnly` scenario without realtime chart.

## Implementation Order
1. Prepare the `MonitorOnly` benchmark/demo variant and record the current baseline without chart render noise.
2. Add or update a focused test that repeatedly evaluates one active monitor rule and proves only the initial public state is published.
3. Change `MonitorRuleRuntime` publication to skip unchanged public bool state.
4. Add or update a focused test for aggregate monitor state and change `MonitorRuntimeManager` accordingly.
5. Verify monitor actions still fire on `false -> true` and `true -> false` transitions as configured.
6. Inspect `AlertWidgetRow` subscriptions and filtering, then restrict accepted events to relevant selected bool paths before any dispatcher work is queued.
7. Inspect `MonitorViewControl` subscriptions and filtering, then remove reliance on repeated runtime message/root publications.
8. Update documentation for the public monitor status contract.
9. Run focused tests and `dotnet build HornetStudio.sln --no-restore`.
10. Run the `MonitorOnly` benchmark and compare `BrowserDispatcherPosts`, `AlertWidgetRow.ItemChangedDispatch`, `MonitorRuleRuntime.PublishRuntime`, and UI responsiveness spikes against the baseline.

## Technical Constraints
- Chat responses must be German; code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- No new dependencies.
- Runtime services remain owned by runtime managers, not visual controls.
- Browser-hosted controls and widgets must filter registry events before scheduling UI-thread work.
- Unknown or unrelated registry events must be ignored on the calling thread.
- High-frequency runtime value changes must not cause UI structure refreshes.
- Keep the registry as public interop/status surface; do not introduce a broad replacement event bus in this step.
- Keep changes scoped to monitor/alert/monitor-view behavior and the monitor-only benchmark setup.

## Acceptance Criteria
- Repeated monitor evaluation with unchanged bool state does not publish additional rule-root registry updates.
- Repeated aggregate state with unchanged bool value does not publish additional aggregate registry updates.
- `OnActivated` actions still execute once on inactive-to-active transitions.
- `OnCleared` actions, if configured, execute once on active-to-inactive transitions.
- AlertWidget rows do not enqueue UI work for unrelated monitor events or legacy `.active`/`.message` child events.
- MonitorView still displays selected monitor states correctly with the bool-only runtime contract.
- In the `MonitorOnly` benchmark, repeated monitor root accepted events and avoidable `AlertWidgetRow.ItemChangedDispatch` warnings disappear or are materially reduced.
- Monitor Browser edit/delete persistence remains functional.

## Out of Scope
- RealtimeChart rendering/data buffering changes.
- SignalWidget value-rendering changes.
- Full typed runtime-subscription architecture.
- Monitor definition schema redesign.
- Broad browser refactoring.
- Release versioning, tags, package publishing, or FOSS notice updates.

## Risks / Watchouts
- Do not suppress registry publications before preserving initial state visibility; consumers need one initial bool snapshot.
- Do not couple action execution to public publication; skipped publication must not skip transitions.
- If MonitorView currently displays runtime message text, move display text to static rule definitions instead of reintroducing message traffic.
- If legacy `.active`/`.message` paths still appear from older code paths, consumers should ignore them before dispatcher scheduling.
- If the chart remains visible during validation, benchmark results will mix monitor/alert fixes with chart render cost.

## Notes
- Start with the smallest useful change: transition-only monitor publication plus AlertWidget filtering.
- Treat a broader typed runtime-subscription model as a follow-up only after this proof reduces measurable load.
- Keep SignalWidget out of this implementation step, but use the same principle later: cheap value updates only, no structure rebuilds on high-frequency data.
