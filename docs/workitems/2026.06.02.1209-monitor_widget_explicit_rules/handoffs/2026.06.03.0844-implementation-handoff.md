# IMPLEMENTATION HANDOFF

## Goal
Move the remaining MonitorWidget benchmark issue to the correct runtime layer:

- Add folder-local monitor runtime settings to `Monitoring/Monitor.yaml`.
- Introduce a runtime-wide monitor startup delay setting.
- Change monitor rule runtime publication so rule root values are published only when the evaluated bool state changes, plus one initial publish after startup.
- Execute monitor actions only on the `false -> true` transition.
- Stop publishing normal `*.active`, `*.message`, status, or runtime message child items for the SignalWidget/AlertWidget path.

The intended runtime value source for SignalWidget and AlertWidget is the rule root:

```text
studio.{folder}.monitor.{rule}
```

## Scope

Included:

- Extend the folder-local `Monitoring/Monitor.yaml` document with a `runtime` section.
- Add a runtime-wide setting:
  - `runtime.startupDelayMs`
- Keep existing `rules:` format compatible.
- Load monitor runtime settings together with monitor definitions.
- Apply the startup delay per folder monitor runtime, not per rule.
- Publish rule root bool values only on initial state and bool changes.
- Execute configured monitor actions only when state changes from inactive to active.
- Remove or suppress regular `*.active` and `*.message` runtime child publishes for normal monitor rule operation.
- Update focused tests.
- Update relevant Monitor documentation if behavior/config format is documented.
- Update the benchmark project `Monitoring/Monitor.yaml` with a test value for `runtime.startupDelayMs`.

Not included:

- No Monitor Browser redesign.
- No AlertWidget/SignalWidget UI redesign.
- No project-level `project.aaep` runtime settings.
- No per-rule startup delay.
- No new dependencies.
- No release/version changes.

## Starting Point

- Monitor is folder-scoped, so `project.aaep` is not the right place for this setting.
- Benchmark monitor file:
  - `benchmarks/ui_lag_bench_project/Folders/main/Monitoring/Monitor.yaml`
- Current file has:

```yaml
rules:
- name: monitor_rule_1
  ...
```

- Desired extended shape:

```yaml
runtime:
  startupDelayMs: 1000
rules:
- name: monitor_rule_1
  ...
```

- Latest benchmark evidence:
  - Child paths are now filtered in AlertWidgetRow.
  - Remaining load comes from accepted root publishes.
  - 120s run still showed `BrowserDispatcherPosts=69`.
  - Browser summaries showed per row:
    - `RegistryEvents=69`
    - `IgnoredRegistryEvents=46` for `.active` and `.message`
    - `AcceptedRegistryEvents=23` on root path
    - `DispatcherPosts=23`
- Therefore the next fix belongs in `MonitorRuleRuntime`/`MonitorRuntimeManager`, not in the widget.

## Tasks

1. Extend monitor file model.
   - Add a `MonitorRuntimeSettings` or equivalent model.
   - Add `StartupDelayMs` with default `0`.
   - Add a `Runtime` property to `MonitorDefinitionFileDocument`.
   - Preserve backward compatibility when `runtime` is missing.

2. Extend monitor file codec.
   - `MonitorDefinitionFileCodec` currently loads/saves only definitions.
   - Add a way to load the complete document/config, including runtime settings and rules.
   - Keep existing `LoadDefinitions(...)` and `SaveDefinitions(...)` callers working.
   - When saving definitions, preserve or write runtime settings where appropriate if the existing file had them.

3. Pass runtime settings into monitor runtime manager.
   - Extend `MonitorRuntimeManager.SyncDefinitions(...)` or add a focused overload that accepts runtime settings.
   - Update folder/file loading paths so central `Monitoring/Monitor.yaml` settings reach the runtime manager.
   - Keep legacy calls without settings using default settings.

4. Implement folder-wide startup delay.
   - Apply delay once per folder monitor runtime state.
   - Prefer starting evaluation after the delay to avoid suppressed shadow state complexity.
   - Ensure existing timers/runtimes are disposed correctly if definitions are changed or folder is released during the delay.
   - Default `0` means no delay.

5. Change publish policy.
   - Each `MonitorRuleRuntime` must track the last published bool state.
   - Publish rule root once for initial evaluated state.
   - Publish rule root only when the bool changes after that.
   - Do not publish root on unchanged `true -> true` or `false -> false`.
   - Do not publish normal `*.active` or `*.message` child paths for the SignalWidget/AlertWidget route.

6. Change action policy.
   - Execute configured actions only on `false -> true`.
   - Do not execute actions on unchanged active cycles.
   - Do not execute actions on `true -> false`.
   - Decide initial active behavior explicitly:
     - Recommended: after startup delay, if initial evaluated state is `true`, publish active and execute actions once because the alarm is active.
     - If implementation chooses otherwise, document it in tests and docs.

7. Update benchmark project monitor config.
   - Add `runtime.startupDelayMs` to:
     - `benchmarks/ui_lag_bench_project/Folders/main/Monitoring/Monitor.yaml`
   - Suggested value for benchmark validation: `1000` or `2000`.
   - Keep rule definitions unchanged.

8. Add/update focused tests.
   - Monitor file codec roundtrips `runtime.startupDelayMs` plus `rules`.
   - Missing `runtime` defaults to `StartupDelayMs=0`.
   - Runtime with unchanged false state publishes initial false only.
   - Runtime with repeated unchanged true state publishes initial true only.
   - Runtime publishes on `false -> true` and `true -> false`.
   - Actions execute only on `false -> true`.
   - Startup delay defers first evaluation/publish.
   - Release/dispose during startup delay does not publish later.

9. Validate and benchmark.
   - Run focused Monitor file/runtime tests.
   - Run 120s benchmark.
   - Expected benchmark direction:
     - Child events remain ignored by AlertWidgetRow.
     - Root publish count drops from the previous `23` per rule per 120s to initial + actual bool transitions.
     - `BrowserDispatcherPosts` should drop materially from `69`.

```yaml

  startupDelayMs: 1000

- name: ...
```

- Existing monitor files without `runtime` still load with default `StartupDelayMs=0`.
- Monitor runtime starts evaluation only after the folder-level delay when configured.
- Each monitor rule root is published initially once, then only when bool state changes.
