# IMPLEMENTATION HANDOFF

## Goal

Change `MonitorWidget` from an implicit monitor overview into an explicit alarm/status widget for selected monitor rules.

The widget should let the user pick multiple monitor rules and render only those selected rules. Each rendered entry observes the runtime boolean state of its rule, similar to how a bool `SignalWidget` observes a signal item. The monitor runtime remains the only owner of rule evaluation.

## Scope

Included:

- Add or adjust widget configuration so a `MonitorWidget` stores selected monitor rule IDs.
- Add a picker/editor workflow for selecting multiple monitor rules.
- Prevent duplicate rule IDs within the same widget configuration.
- Render only the selected rules in the widget.
- Keep the visual list-entry layout close to the current design: `[Id] [LogText]`.
- Bind each rendered entry to runtime rule state, primarily the boolean active state.
- Keep active rules visually highlighted as alarms and inactive rules neutral.
- Keep the Monitor Browser as a separate management/debug view.
- Update focused tests and widget documentation for the changed behavior.

Not included:

- No migration of old widget configuration. HornetStudio is still in development, so old implicit "show all rules" configuration may be ignored or replaced.
- No new runtime dependency.
- No moving rule evaluation into UI controls.
- No broad monitor runtime refactor beyond what is required for selected-rule binding.

## Starting Point

- Monitor runtime evaluation was already moved toward a background runtime model.
- The current `MonitorView`/widget behavior still behaves too much like a browser/overview and reacts to many monitor registry events.
- The intended user-facing behavior is an alarm/status widget:
  - user selects explicit rules
  - widget shows only those selected rules
  - each entry follows the rule's runtime boolean state
- Latest benchmark showed root aggregate events are already filtered, but rule-level event pressure remains. This design correction should reduce the widget's event scope structurally.

## Tasks

1. Inspect the current monitor widget/browser implementation.
   - Identify the persisted widget type and config model.
   - Identify the current editor dialog or property editor for Monitor widgets.
   - Identify how monitor rules are loaded from folder-local monitor resources.
   - Identify current runtime state paths for rule active/message values.

2. Define the selected-rule configuration model.
   - Store an ordered list of selected rule IDs or stable event IDs, depending on the existing monitor rule identity model.
   - Prefer the identity already used by runtime state paths.
   - Preserve order so the visual list can match user selection order.
   - Reject duplicate IDs in the same widget config.

3. Add or update the rule picker.
   - Show available monitor rules from the current folder/project context.
   - Let the user select multiple rules.
   - Display at least rule ID and log text/name so selection is clear.
   - Prevent duplicate selection in the picker and in final validation.
   - Use English UI text and validation messages.

4. Update widget rendering.
   - Render only configured selected rules.
   - Keep each row visually close to the existing compact list format:
     - ID column/segment
     - log text/message segment
   - Use active runtime state to switch between alarm and neutral visual state.
   - Resolve displayed log text from selected rule metadata and/or runtime message according to existing monitor behavior.

5. Update runtime observation logic.
   - Subscribe/filter only for selected rule runtime paths.
   - Ignore unrelated monitor registry events before any UI dispatcher post.
   - Treat the widget as a view only: no rule evaluation, no timers, no runtime lifecycle ownership.
   - Keep a cheap relevance snapshot for selected rule paths if registry events are used.

6. Remove or disable implicit "show all rules" widget behavior.
   - Since no migration is required, old implicit configs can render empty, default to no selected rules, or be replaced by current defaults.
   - Do not preserve legacy behavior that subscribes broadly to all monitor rules.

7. Add focused tests.
   - Widget config rejects duplicate selected rule IDs.
   - Widget renders only selected rules, not all available rules.
   - Registry/runtime events for unselected rules do not enqueue widget UI refresh work.
   - Selected rule active state updates the corresponding row.

8. Update documentation.
   - Update the relevant widget documentation under `src/HornetStudio/docs/widgets/`.
   - Update the matching short description under `src/HornetStudio/docs/widgets/descriptions/`.
   - Update the detailed help file under `src/HornetStudio/docs/widgets/help/`.
   - Explain that `MonitorWidget` is for explicitly selected monitor rules and that Monitor Browser is for management/debug overview.

## Implementation Order

1. Read current monitor widget, editor, config, runtime-state, and tests.
2. Decide the stable selected-rule identity based on existing runtime paths.
3. Add selected-rule config and duplicate validation.
4. Update the picker/editor to select multiple rules.
5. Update widget rendering to show only selected rows in `[Id] [LogText]` format.
6. Scope registry/runtime observation to selected rule paths only.
7. Remove or disable implicit all-rule rendering behavior.
8. Add focused tests.
9. Update widget documentation.
10. Run focused build/tests and the 120-second benchmark with the MonitorView/MonitorWidget placed.

## Technical Constraints

- Chat response must be German; code, comments, XML docs, UI text, and technical identifiers must be English.
- Do not add new dependencies unless justified.
- Use existing project patterns, Avalonia controls, validation style, and registry/runtime APIs.
- Visual controls must not own long-running runtime lifecycles.
- Registry event filtering must happen before `Dispatcher.UIThread.Post`, `InvokeAsync`, `QueueRuntimeRefresh`, `RefreshAll`, `Rebuild`, or equivalent UI-thread work.
- Browser/widget controls must react only to configured selected rule paths and relevant descendants.
- Unknown or unrelated registry events must be ignored on the calling thread.
- Public classes and public methods changed or added must have XML documentation according to repository rules.

## Acceptance Criteria

- `MonitorWidget` supports multiple explicitly selected monitor rules.
- Duplicate selected rule IDs are rejected in the widget configuration/editor.
- The widget renders only selected rules and never automatically shows all monitor rules.
- Visual row layout remains compact and close to the current `[Id] [LogText]` style.
- Active rules render as alarm entries; inactive rules render neutral.
- Runtime evaluation works without Monitor Browser or MonitorWidget being open.
- Monitor Browser remains a management/debug overview and does not own runtime evaluation.
- Unselected rule events do not schedule widget UI dispatcher work.
- Existing monitor rule duplicate-ID protections remain intact.

## Out of Scope

- No compatibility migration for old widget config.
- No replacement of generic `SignalWidget`.
- No redesign of the Monitor Browser.
- No release/version changes.

## Risks / Watchouts

- If rule display uses event ID while runtime state uses another internal ID, choose one canonical identity and keep picker, persistence, runtime paths, and duplicate validation aligned.
- Avoid introducing an intermediary signal layer unless the existing architecture already exposes monitor rule state that way. The widget should behave like a bool signal view conceptually, but it does not need a new signal abstraction if runtime monitor state already provides the required boolean item.
- Do not let the selected-rule cache become runtime ownership. It is only a UI relevance snapshot.
- Since no migration is required, ensure old configs fail gracefully instead of throwing during project load.
