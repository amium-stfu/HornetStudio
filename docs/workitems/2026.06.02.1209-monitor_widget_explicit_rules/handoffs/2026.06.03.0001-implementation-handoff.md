# IMPLEMENTATION HANDOFF

## Goal
Optimize `AlertWidgetRow` so UI dispatch happens only when the observable row state actually changes, and simplify the row layout to a single line:

```text
[ID]     [Log text]
```

The existing second line for `Active`/`Inactive` status must be removed from the visible row.

## Scope

Included:

- Keep the current `AlertWidgetRow` and rebuilt `MonitorView` direction.
- Reduce dispatcher posts by checking the runtime state before scheduling UI-thread work.
- Preserve strict selected-rule path filtering.
- Keep tooltip/status detail if useful, but do not show a dedicated second status line.
- Update focused tests for unchanged runtime events and one-line layout behavior where feasible.
- Update MonitorView widget documentation if it describes the removed status line.
- Re-run focused validation and a 120s benchmark.

Not included:

- No Monitor Browser changes.
- No runtime manager redesign.
- No SignalWidget redesign.
- No new widget type persistence changes.
- No new dependencies.
- No release/version work.

## Starting Point

- `AlertWidgetRow` now exists inside `src/HornetStudio.Editor/Widgets/MonitorView/MonitorViewControl.axaml.cs`.
- `MonitorViewControl.axaml` currently displays a second line via `StatusText`/`HasStatusText`.
- Latest 120s benchmark:
  - Scenario: `MonitorWidgetCurrent-120s`
  - Status: `Warn`
  - Reason: `BrowserDispatcherPosts were elevated`
  - `BrowserDispatcherPosts=69`
  - Three rows each produced `23` dispatcher posts:
    - `AlertWidgetRow[main.monitor_rule_1]`
    - `AlertWidgetRow[main.monitor_rule_2]`
    - `AlertWidgetRow[main.monitor_rule_3]`
  - Individual dispatch work was cheap:
    - `ItemChangedDispatch` P95 about `0.6-0.9 ms`
- Therefore the remaining issue is not expensive row rendering, but unnecessary dispatch scheduling for runtime events that do not change visible row state.

## Tasks

1. Inspect the current `AlertWidgetRow` event flow.
   - Locate registry subscription callback.
   - Locate `TryApplyRuntimeChange(...)`.
   - Locate where `Dispatcher.UIThread.Post(...)`, `InvokeAsync(...)`, or equivalent dispatch is scheduled.
   - Confirm whether runtime state is read on the registry callback thread before dispatch is possible and safe.

2. Add a cheap pre-dispatch change check.
   - For relevant paths only, read the new `AlertWidgetRuntimeState`.
   - Compare the new state with the current row state before scheduling UI work.
   - Dispatch only when at least one observable state changes.
   - Observable state includes at minimum:
     - `IsActive`
     - visible log text/event detail if displayed
     - tooltip text if it is intentionally updated from runtime message
     - row colors if their source can change through this path
   - If the runtime read cannot be done safely off the UI thread, introduce a pending-state/coalescing path that still prevents multiple queued UI operations for equivalent state.

3. Keep strict relevance filtering.
   - Ignore unrelated registry paths before any state read or dispatcher scheduling.
   - Continue accepting only the selected row runtime path, active path, and message path.
   - Do not react to aggregate monitor folder paths such as `studio.main.monitor` unless it is the exact selected rule path.

4. Simplify the row layout to one line.
   - Remove the visible second line bound to `StatusText`.
   - Keep the first line as `[EventId] [EventText/log text]`.
   - Prefer a fixed-width or min-width ID segment so rows align.
   - Keep active/inactive indication through row background/border/foreground, not through a visible `Active`/`Inactive` label.
   - Ensure the row still works with compact MonitorView widget height.

5. Revisit `StatusText` semantics.
   - If `StatusText` is only used for the removed second line, remove or reduce `HasStatusText` UI plumbing.
   - If tests or tooltip behavior still need runtime message detail, keep a renamed/internal state such as `RuntimeMessage` only where useful.
   - Do not show `Inactive` as fallback text in the row body.

6. Add or update focused tests.
   - A repeated registry event with unchanged active/message state must not report a changed row state.
   - A changed active state must still update the row.
   - A changed runtime message must update tooltip/log detail only if that detail is part of the row contract.
   - Aggregate/unselected paths must still be ignored.
   - Existing delayed publish tests must continue to pass.

7. Validate and benchmark.
   - Run focused editor tests for MonitorView/AlertWidget.
   - Run a 120s benchmark with the same benchmark project and placed MonitorWidget.
   - Target result: benchmark `Pass` or at least `BrowserDispatcherPosts` materially below the previous `69`.

## Technical Constraints

- Chat response must be German; code, comments, XML documentation, UI text, validation messages, and technical identifiers must be English.
- Use existing Avalonia, registry, and diagnostics patterns.
- No new dependencies.
- Runtime services remain outside visual controls.
- Registry relevance filtering must happen before dispatcher scheduling.
- Do not use sleeps, arbitrary startup delays, or polling as the optimization.
- Keep the change tightly scoped to MonitorView/AlertWidget behavior.

## Acceptance Criteria

- Alert row visible body has exactly one line: ID plus event/log text.
- No visible `Active`/`Inactive` second line remains.
- Active state is still visible through row styling.
- Repeated unchanged runtime events do not schedule UI work.
- Changed active state still updates the row.
- Delayed runtime publish still updates a row created before runtime state exists.
- Unselected and aggregate monitor paths remain ignored.
- 120s benchmark no longer warns solely because `AlertWidgetRow` dispatcher posts are elevated, or at least shows a clear reduction from `69`.
