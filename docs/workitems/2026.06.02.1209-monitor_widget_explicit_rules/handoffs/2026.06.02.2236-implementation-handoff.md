# IMPLEMENTATION HANDOFF

## Goal
Refactor `MonitorView` so each selected monitor row observes monitor runtime state using the same robust binding behavior as the existing Signal widget path, while keeping the Monitor-specific `[EventId] [EventText]` row layout.

The key new evidence is that Signal widgets bound to the same monitor rule runtime paths work reliably, while `MonitorView` remains sporadic. Therefore the problem is now considered `MonitorView`-specific binding/subscription logic, not monitor runtime startup, `Monitor.yaml`, Monitor Browser, or project switching as the primary root cause.

## Scope
Included:

- Inspect the Signal widget implementation and identify the concrete runtime binding path that makes it reliable.
- Bring `MonitorViewRow` onto equivalent behavior for one selected monitor rule.
- Keep `MonitorView` as a selected-rule list/container only.
- Keep Monitor-specific display:
  - event id segment
  - event text/log text segment
  - active visual state
- Remove or reduce fragile `MonitorView`-specific runtime snapshot, timer, and subscription logic when the Signal widget behavior can replace it.
- Add focused tests proving Signal-equivalent binding behavior for monitor rows.

Not included:

- No generic Signal widget redesign.
- No monitor runtime manager redesign unless a focused test proves it is still needed.
- No public registry path redesign.
- No release/version changes.
- No new external dependencies.

## Starting Point

- Benchmark project: `benchmarks/ui_lag_bench_project/project.aaep`.
- Monitor rules exist in `benchmarks/ui_lag_bench_project/Folders/main/Monitoring/Monitor.yaml`.
- Signal widgets pointed at monitor rule runtime paths work reliably.
- Monitor Browser shows and visualizes all rules.
- `MonitorView` is sporadic, especially around app start.
- Current `MonitorView` has its own runtime snapshot and registry subscription model:
  - `_rowSnapshot`
  - `_runtimeSnapshot`
  - `TryUpdateRuntimeSnapshotForKey(...)`
  - `QueueRuntimeRefresh(...)`
  - `ScopedRegistryItemChangedSubscription`
- This custom logic is now suspected to be the weak point.

## Tasks

1. Inspect Signal widget binding path.
   - Find `EditorSignalControl` and related `FolderItemModel.ResolveTarget`, `RefreshTargetBindings`, target/value update behavior.
   - Identify how it handles:
     - missing runtime item at first attach
     - later registry publish
     - value/property changes
     - project load timing
     - bool active visual state

2. Define MonitorView row binding model.
   - Each selected rule row should bind to one monitor runtime boolean source.
   - Preferred source:
     - `studio.{FolderName}.monitor.{RuleName}.active`
   - Acceptable fallback if Signal widget uses root boolean value:
     - `studio.{FolderName}.monitor.{RuleName}`
   - The row display text remains from the monitor definition:
     - `EventId`
     - `EventText` or rule name fallback

3. Replace or adapt MonitorViewRow state handling.
   - `MonitorViewRow` should use the same item resolution/update mechanism as Signal widget as closely as possible.
   - Avoid duplicating a second registry timing model.
   - If direct reuse is impossible because Signal widget logic is embedded in a visual control, extract only a small local helper or copy the minimal behavior with clear naming.
   - Do not add a broad abstraction unless it clearly serves both Signal and MonitorView now.

4. Simplify MonitorView container.
   - `MonitorViewControl` should:
     - resolve selected monitor definitions
     - create rows in configured order
     - refresh rows on selected IDs/folder context/theme changes
   - It should not depend on a global runtime snapshot being non-empty at first attach.
   - It should not need periodic runtime refresh timers for normal bool state updates if row binding handles registry changes.

5. Preserve selected-rule-only behavior.
   - Unselected monitor rules must not create rows.
   - Unselected monitor rule registry events must not be accepted by `MonitorView`.
   - Folder aggregate events such as `studio.main.monitor` must not trigger row refresh.

6. Add focused tests.
   - MonitorView row bound to selected rule updates when `*.active` changes from false to true.
   - Row can be created before the runtime item exists and updates after the item is later published.
   - Two selected rules render two rows in configured order.
   - Third unselected rule does not appear and does not get accepted by the widget path.
   - SignalWidget-equivalent path test if existing test helpers allow it.

7. Re-run validation and benchmark.
   - Run focused MonitorView tests.
   - Run Monitor Browser tests to ensure all-rule view is unchanged.
   - Run 120s benchmark after implementation.

## Implementation Order

1. Read `EditorSignalControl` and identify the exact stable value binding flow.
2. Write a focused failing test for `MonitorViewRow` created before the monitor runtime item exists, then receiving a later `*.active=true` publish.
3. Modify `MonitorViewRow` to use Signal-equivalent item/value update semantics.
4. Simplify `MonitorViewControl` only as far as needed to eliminate the sporadic snapshot timing dependency.
5. Verify selected-rule-only filtering remains strict.
6. Re-run focused tests.
7. Run focused build.
8. Run benchmark/manual project load check.

## Technical Constraints

- Chat response must be German; code, comments, XML documentation, UI text, validation messages, and technical identifiers must be English.
- Use existing Avalonia and registry patterns.
- No new dependencies.
- Runtime remains owned by runtime managers, not visual controls.
- MonitorView must remain selected-rule-only.
- Registry filtering must happen before dispatcher posts.
- Avoid sleeps, arbitrary timers, or startup delays as fixes.
- Prefer existing Signal widget behavior over new speculative runtime-ready infrastructure.

## Acceptance Criteria

- Signal widgets and MonitorView rows pointed at the same monitor runtime rule behave consistently.
- MonitorView works reliably on AppStart with `benchmarks/ui_lag_bench_project/project.aaep`.
- MonitorView works reliably after manual in-app project load.
- MonitorView rows update when selected rule `*.active` state changes.
- Rows can recover when runtime items are published after the row was created.
- Browser still shows and visualizes all rules.
- Unselected rules remain irrelevant to MonitorView.

## Out of Scope

- No broad AppStart lifecycle redesign for this step.
- No MonitorRuntimeManager key redesign unless tests disprove Signal-equivalent binding as sufficient.
- No generic SignalWidget refactor unless small extraction is clearly required.
- No public registry path migration.

## Risks / Watchouts

- If `MonitorView` keeps its custom snapshot and row-level Signal-equivalent binding simultaneously, duplicate updates or conflicting visual state can occur.
- If row binding observes root rule path and `*.active` inconsistently, active state may drift.
- If direct Signal widget logic is too UI-control-specific, prefer a very small local row observer over a large abstraction.
- Do not reintroduce broad monitor aggregate subscriptions.
