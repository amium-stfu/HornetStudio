# IMPLEMENTATION HANDOFF

## Goal
Add targeted diagnostic logging that attributes remaining monitor-related `BrowserDispatcherPosts` and intermittent Monitor `SetValue` failures without changing product behavior. The diagnostics must make it clear whether repeated posts originate from Monitor runtime publication, unchanged registry writes, AlertWidget row dispatch scheduling, or action write failures.

## Scope
Included:

- Add focused diagnostics for Monitor runtime rule publication.
- Add focused diagnostics for aggregate Monitor publication.
- Add focused diagnostics for Monitor `SetValue` target resolution and write application.
- Add focused diagnostics for `AlertWidgetRow` event acceptance and dispatcher post reasons.
- Extend benchmark/browser diagnostics only as narrowly needed to include the last accepted key/reason details already tracked in runtime counters.
- Keep the diagnostics low-noise enough for a 120s benchmark log.
- Run a `MonitorOnly` benchmark after diagnostics are added.

Explicitly not included:

- No behavior fix for the dispatcher posts yet.
- No broad runtime-subscription redesign.
- No RealtimeChart work.
- No SignalWidget work.
- No new dependencies.
- No release/version work.

## Starting Point
- After the Monitor/AlertWidget fix, `#bench 120` with `MonitorOnly-NoInteraction-120s` still reports `BrowserDispatcherPosts=46`.
- Browser summary shows:
  - `AlertWidgetRow[main.monitor_rule_2] DispatcherPosts=23`
  - `AlertWidgetRow[main.monitor_rule_3] DispatcherPosts=23`
  - `TopRegistryKeys=studio.main.monitor.monitor_rule_2(23,a=23,i=0)`
  - `TopRegistryKeys=studio.main.monitor.monitor_rule_3(23,a=23,i=0)`
- Chart render noise is absent in that run: `ChartRenderCount=0`.
- User also observed that `SetValue` appeared to fail once, even though benchmark logs often show successful `SetValue applied` lines.
- Current diagnostics identify the row and registry key, but not whether the source is unchanged publication, changed publication, action side effect, or AlertWidget scheduling logic.

## Tasks
1. Add Monitor runtime publish diagnostics around rule-root publication.
2. Add aggregate publish diagnostics around `studio.<folder>.monitor` publication.
3. Add SetValue diagnostics that include configured target, resolved target, write target item path, write parameter, converted value, success/failure, and error text.
4. Add AlertWidget row dispatch diagnostics that include row name, changed key, runtime path, previous active value, next active value, visible state changed flag, accepted flag, dispatcher post flag, and reason.
5. Keep skip/no-op logs either aggregated or gated so repeated unchanged evaluations do not flood logs.
6. Make benchmark browser summaries include enough last-event context if `UiResponsivenessDiagnostics` already tracks it but does not include it in summary output.
7. Run the focused `MonitorOnly` benchmark and use the new log lines to classify the 23 posts per row.

## File-Level Changes
- `src/HornetStudio.Editor/Monitoring/MonitorRuleRuntime.cs` -> add `[MonitorRuntimePublish]` and `[MonitorActionSetValue]` diagnostics at rule publication and SetValue write points.
- `src/HornetStudio.Editor/Monitoring/MonitorRuntimeManager.cs` -> add `[MonitorAggregatePublish]` diagnostics for aggregate monitor publication and skip decisions.
- `src/HornetStudio.Editor/Widgets/MonitorView/MonitorViewControl.axaml.cs` -> add `[AlertWidgetDispatch]` diagnostics in `AlertWidgetRow` before any dispatcher post and when applying runtime state.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> include last dispatcher reason/key in benchmark browser summary if currently omitted, and avoid broad changes.
- `src/HornetStudio.Editor.Tests/Program.cs` -> add or update focused tests only if diagnostics expose a behavior-neutral helper or formatting method; do not over-test pure logging.

## Implementation Order
1. Inspect current `MonitorRuleRuntime.PublishRuntime`, `ExecuteSetValue`, `TryResolveActionTarget`, and `TryApplyActionWrite` flow.
2. Add a compact `MonitorActionSetValue` result log after target resolution and after write attempt:
   - success path
   - target unresolved path
   - write failed path
3. Add `MonitorRuntimePublish` logs around rule-root publication:
   - rule
   - runtime path
   - previous active
   - next active
   - changed
   - published
   - reason
4. Add `MonitorAggregatePublish` logs around aggregate publication with the same changed/published context.
5. Inspect `AlertWidgetRow.OnRegistryItemChanged`, `RefreshRuntimeState`, `ApplyRegistryUpdate`, and `HasVisibleStateChange`.
6. Add `AlertWidgetDispatch` diagnostics only at decision points:
   - event ignored before post
   - event accepted but no visible state change
   - dispatcher post scheduled
   - runtime state applied
7. If benchmark browser summary omits `LastRegistryKey` and `LastDispatcherReason`, add those fields to the benchmark summary log.
8. Build and run focused tests if required by touched helpers.
9. Run a 120s `MonitorOnly-Diagnostics-120s` benchmark.
10. Summarize which component generated the 23 dispatcher posts and whether the observed SetValue miss has a logged reason.

## Technical Constraints
- Chat responses must be German; code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- User-visible validation/error text must be English.
- No new dependencies.
- Do not change runtime behavior while adding diagnostics.
- Keep diagnostics scoped to Monitor/AlertWidget paths.
- Avoid logging every unchanged evaluation cycle; prefer logs when a publish/post/write decision occurs.
- Do not introduce silent catch blocks.
- Keep existing `Core.LogInfo`, `Core.LogWarn`, and diagnostics patterns.

## Acceptance Criteria
- A benchmark log can answer why `AlertWidgetRow[main.monitor_rule_2]` and `AlertWidgetRow[main.monitor_rule_3]` each post 23 times.
- A benchmark log can tell whether each monitor root publication was changed, unchanged, published, or skipped.
- A benchmark log can tell whether aggregate monitor publication contributes to dispatcher posts.
- A benchmark log can tell whether `SetValue` failed because of target resolution, writable policy, parameter selection, conversion, or registry update failure.
- No product behavior changes are introduced by the diagnostic pass.
- Log output remains readable during a 120s benchmark.

## Out of Scope
- Fixing the dispatcher post cause in the same step.
- Changing the Monitor definition schema.
- Changing RealtimeChart rendering.
- Changing SignalWidget update architecture.
- Adding a new runtime subscription framework.

## Risks / Watchouts
- Logging every 100 ms evaluation would distort the benchmark. Log only publish/post/action decisions, not all evaluations.
- If the diagnostic log changes timing enough to hide the issue, reduce noisy skip logs and rerun.
- Do not treat successful `SetValue applied` as proof that the value reached the intended semantic destination; include resolved target and write parameter details.
- If `LastRegistryKey` and `LastDispatcherReason` are already available in periodic diagnostics but not benchmark summary, extend summary output rather than adding parallel counters.
