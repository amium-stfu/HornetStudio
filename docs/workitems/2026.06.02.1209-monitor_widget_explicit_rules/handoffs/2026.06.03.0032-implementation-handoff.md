# IMPLEMENTATION HANDOFF

## Goal
Align `AlertWidgetRow` with the proven SignalWidget monitor binding semantics:

- Read `EventId` and `EventText` once from the monitor definition when the row is created.
- Observe only the monitor rule root runtime item, for example `studio.main.monitor.monitor_rule_1`.
- Interpret that root item like SignalWidget does for a formatted bool.
- Update UI only when the interpreted root bool changes.
- Do not observe or read `*.active`, `*.message`, status text, or aggregate monitor paths for normal row state.

The visible row remains a single line:

```text
[ID]     [Log text]
```

## Scope

Included:

- Change `AlertWidgetRow` runtime observation to the rule root only.
- Remove `ActivePath` and `MessagePath` subscriptions from the row.
- Remove runtime status/message text as an observed UI state for the row.
- Keep static ID/log text from `Monitoring/Monitor.yaml`.
- Keep active/inactive indication through styling only.
- Keep selected-rule-only behavior in `MonitorView`.
- Add/update focused tests proving root-only behavior and unchanged bool filtering.
- Re-run focused tests and a 120s benchmark.

Not included:

- No Monitor Browser changes.
- No monitor runtime manager redesign.
- No SignalWidget implementation changes unless inspection reveals a tiny helper is already available and directly useful.
- No public registry path migration.
- No new dependencies.
- No release/version changes.

- The remaining likely mismatch:
  - SignalWidget treats the rule root as a bool value.
  - AlertWidgetRow still appears to observe/read more semantic state than just the root bool.

## Tasks

1. Inspect SignalWidget root bool handling.
   - Confirm how `EditorSignalControl`/binding resolves and interprets a monitor rule root item.
   - Identify whether the root item value is directly bool, string-converted bool, or a structured item with a bool value.
   - Use the same conversion behavior in `AlertWidgetRow` where possible.

2. Simplify `AlertWidgetRow` observed paths.
   - Keep only `_runtimePath` as the subscribed/relevant path.
   - Remove `ActivePath` and `MessagePath` from subscription prefixes.
   - `IsRelevantRuntimePath(...)` should return true only for the exact rule root path.
   - Do not accept:
     - `studio.main.monitor`
     - `studio.main.monitor.active`
     - `studio.main.monitor.monitor_rule_1.active`
     - `studio.main.monitor.monitor_rule_1.message`
     - other descendants or aggregate paths

3. Define row visible state as static definition plus root bool.
   - Static state:
     - `EventId`
     - `EventText` or rule name fallback
   - Dynamic state:
     - `IsActive` from root runtime bool only
   - Remove runtime `StatusText`/message from visible state.
   - Tooltip may remain static if useful, but must not force UI updates on runtime publishes.

4. Filter before UI dispatch.
   - On a relevant root event, read/convert the root bool off the callback path if safe.
   - If the bool is equal to the current `IsActive`, do not schedule UI work.
   - If the bool changed, schedule one UI update and update styling.
   - Avoid coalescing broad event streams; the rule-root exact match should already keep the stream scoped.

5. Preserve creation behavior.
   - On row creation, read static ID/log text from the supplied `MonitorDefinition`.
   - Initial active state should be read from the rule root if it already exists.
   - If the root runtime item does not exist yet, start inactive and update when the root item is later published.

6. Update tests.
   - Root bool publish `false -> false` does not report a changed row state and does not require UI dispatch.
   - Root bool publish `false -> true` updates active state.
   - Root bool publish `true -> true` does not update.
   - `*.active` and `*.message` changes are ignored.
   - Aggregate monitor path changes are ignored.
   - Delayed root publish still updates a row created before runtime exists.
   - Static `EventId`/`EventText` remain from `Monitor.yaml` definition.

7. Validate and benchmark.
   - Run focused tests.
   - Run 120s benchmark with the placed MonitorWidget.
   - Compare against previous `BrowserDispatcherPosts=69`.

## Acceptance Criteria

- `AlertWidgetRow` subscribes only to the exact selected monitor rule root runtime path.
- `AlertWidgetRow` ignores `*.active`, `*.message`, aggregate monitor paths, and unselected rule paths.
- Visible text is static from `MonitorDefinition.EventId` and `MonitorDefinition.EventText`.
- Dynamic active styling is driven only by the interpreted root bool value.
- Repeated root publishes with the same bool do not schedule UI updates.
- Root bool changes still update active styling.
- SignalWidget and AlertWidget observe the same monitor rule root semantics.
- 120s benchmark shows `AlertWidgetRow` dispatcher posts reduced from the previous `69`, unless every accepted root publish genuinely toggles the bool.

## Risks / Watchouts

- If the monitor rule root item is not a plain bool, root bool conversion must match SignalWidget exactly.
- If the root item republishes a new object whose bool value is unchanged, it must still be treated as unchanged for UI purposes.
- Removing message/status observation means runtime message changes will no longer affect the row; this is intended because the visible row text is static from `Monitor.yaml`.
- Do not accidentally subscribe to descendant paths through prefix matching; exact path semantics are required here.
