# IMPLEMENTATION HANDOFF

## Goal
Replace the fragile existing `MonitorView` implementation with a simpler architecture:

- `AlertWidget` displays one selected monitor rule using SignalWidget-equivalent runtime binding behavior.
- `MonitorView` becomes a thin container whose body renders a list of `AlertWidget` rows for the configured monitor rule IDs.

The objective is to remove the sporadic AppStart behavior seen in the existing `MonitorView` while preserving selected-rule-only monitor display.

## Scope
Included:

- Treat the current `MonitorViewControl` implementation as reference material only.
- Build or introduce an `AlertWidget`-style row/control for one monitor rule.
- Reuse the reliable SignalWidget value binding approach as closely as practical.
- Rebuild `MonitorView` as layout, rule discovery, and `AlertWidget` composition only.
- Keep Monitor-specific row display:
  - event id
  - event text or rule name fallback
  - active/inactive visual state
  - optional status text when already available from existing monitor runtime state
- Keep selected monitor IDs as the persisted MonitorView configuration.
- Add focused tests for AppStart-style delayed runtime publish and selected-rule-only behavior.
- Run focused validation and benchmark.

Not included:

- No broad runtime startup redesign.
- No Monitor Browser rewrite.
- No SignalWidget redesign beyond small reusable extraction if clearly needed.
- No public registry path migration.
- No new external dependencies.
- No release/version changes.

## Starting Point

- Benchmark project: `benchmarks/ui_lag_bench_project/project.aaep`.
- Monitor rules exist in `benchmarks/ui_lag_bench_project/Folders/main/Monitoring/Monitor.yaml`.
- Signal widgets bound to the same monitor rule runtime paths work reliably.
- Monitor Browser shows and visualizes rules correctly.
- Existing `MonitorView` remains sporadic after AppStart, but works after in-app project reload.
- A 300s benchmark without MonitorView dispatcher activity passed:
  - Scenario: `NoMonitorViewBaseline-300s`
  - Status: `Pass`
  - `BrowserDispatcherPosts=0`
  - P95 UI delay around `8 ms`
- Prior 300s benchmark with the existing MonitorView path failed because `BrowserDispatcherPosts` were high.

## Tasks

1. Inspect the reliable SignalWidget path.
   - Locate `EditorSignalControl` and related `FolderItemModel` target binding behavior.
   - Identify how the control handles missing runtime items at creation time, later runtime publication, value changes, and bool visual state updates.

2. Define `AlertWidget`.
   - One instance represents exactly one monitor rule.
   - Input/configuration should include the monitor rule ID and owning folder context.
   - Runtime source should prefer the existing selected rule active path, for example `studio.{FolderName}.monitor.{RuleName}.active`, unless current SignalWidget evidence proves another path is the actual stable source.
   - Display text comes from the monitor definition, not from runtime discovery.

3. Implement SignalWidget-equivalent binding for `AlertWidget`.
   - Use the same target/value update semantics as SignalWidget where possible.
   - If SignalWidget logic is embedded too deeply in the visual control, extract a small focused reusable helper or implement a small local observer with the same behavior.
   - Do not introduce broad generic runtime infrastructure unless it is clearly required by both widgets.

4. Rebuild `MonitorView`.
   - Keep persisted `MonitorView` configuration and selected monitor IDs.
   - Resolve selected monitor definitions from the folder-local monitor resource.
   - Render configured rows in stable selected-rule order.
   - Compose `AlertWidget` rows in the body.
   - Remove or bypass the existing custom runtime snapshot, broad refresh, and timing-dependent state update model.

5. Preserve strict event scope.
   - Unselected rules must not create rows.
   - Unselected rule registry events must not enqueue MonitorView UI work.
   - Folder aggregate paths such as `studio.main.monitor` must not trigger row refresh.
   - Registry filtering must happen before dispatcher posts.

6. Add focused tests.
   - `AlertWidget` created before runtime item exists updates after the runtime item is later published.
   - `AlertWidget` updates active visual state when selected rule active value changes.
   - `MonitorView` creates one `AlertWidget` per selected rule in configured order.
   - Unselected monitor rule does not appear and does not trigger accepted widget updates.
   - Existing Monitor Browser tests still pass.

7. Validate with build, focused tests, and benchmark.
   - Run focused editor build/tests.
   - Run a 120s benchmark with the rebuilt MonitorView.
   - If stable, run a 300s confirmation benchmark.

## Implementation Order

1. Read the SignalWidget binding implementation and note the concrete source path and update flow.
2. Create a focused failing test for a single alert row created before its runtime active item exists.
3. Implement `AlertWidget` using SignalWidget-equivalent binding.
4. Verify `AlertWidget` alone with the same monitor runtime paths currently used by SignalWidget.
5. Rebuild `MonitorView` as a selected-rule container for `AlertWidget` rows.
6. Remove obsolete MonitorView runtime snapshot/dispatcher paths that are no longer used.
7. Add selected-rule-only and ordering tests.
8. Update MonitorView documentation where behavior changed.
9. Run focused build/tests.
10. Run 120s benchmark, then 300s benchmark if the 120s run is clean.

## Technical Constraints

- Chat response must be German; code, comments, XML documentation, UI text, validation messages, and technical identifiers must be English.
- Use existing Avalonia, widget, and registry patterns.
- No new dependencies.
- Runtime services remain owned by runtime managers, not visual controls.
- `MonitorView` must remain selected-rule-only.
- Browser-hosted controls must not react to all registry changes globally.
- Registry relevance filtering must happen before `Dispatcher.UIThread.Post(...)`, `InvokeAsync(...)`, refresh queues, rebuilds, or equivalent UI-thread work.
- Avoid sleeps, startup delays, arbitrary timers, or retry loops as fixes.
- Keep the implementation small and aligned with existing widget structure.

## Acceptance Criteria

- `AlertWidget` behaves consistently with SignalWidget when pointed at the same monitor rule runtime source.
- `AlertWidget` works when created before the runtime item exists and updates after later runtime publication.
- Rebuilt `MonitorView` works reliably when the benchmark project is loaded at AppStart.
- Rebuilt `MonitorView` works reliably after in-app project switching.
- Monitor Browser still shows and visualizes all monitor rules.
- Unselected monitor rules do not appear in MonitorView and do not enqueue MonitorView UI work.
- Benchmark with rebuilt MonitorView has no high `BrowserDispatcherPosts` failure.

## Out of Scope

- No AppStart runtime lifecycle redesign.
- No Monitor Browser architecture changes.
- No generic visual rule runtime redesign.
- No compatibility migration beyond preserving current `MonitorView` selected monitor IDs.
- No release/version work.

## Risks / Watchouts

- If `MonitorView` keeps old snapshot logic alongside `AlertWidget` binding, duplicate updates and dispatcher posts may remain.
- If `AlertWidget` observes aggregate monitor paths instead of selected rule paths, the previous event flood risk returns.
- If active state path selection differs from SignalWidget's proven path, the AppStart race may remain.
- If `AlertWidget` becomes a full independent widget with its own persisted page item when it only needs to be a row, persistence may become unnecessarily complex.
- Prefer a row/control implementation inside the MonitorView area unless there is a clear need for a globally selectable widget type.
