# IMPLEMENTATION HANDOFF

## Goal
Make startup project loading deterministic for runtime-backed widgets, especially `MonitorView`, by ensuring folder runtimes and registry state are initialized before widgets finalize rows, runtime snapshots, and registry subscriptions.

The user observed:

- Monitor Browser now shows all monitor rules and visualizes state.
- `MonitorView` works when the same project is loaded manually inside the already-running app.
- `MonitorView` only works briefly or becomes undefined when the project is loaded as the app start project.

This indicates an AppStart initialization ordering problem, not a `Monitor.yaml` parsing problem.

## Scope
Included:

- Align AppStart project loading and manual project loading lifecycle behavior.
- Prevent runtime-backed widgets from permanently binding to partial startup state.
- Add a project/folder runtime-ready or project-load-generation signal using existing ViewModel patterns where possible.
- Make `MonitorView` rebuild after runtime-ready when it attached too early.
- Keep runtime ownership outside visual controls.
- Add focused regression tests for AppStart-like early attach vs. later project-load readiness.

Not included:

- No broad generic widget framework rewrite.
- No public registry path redesign unless absolutely necessary.
- No new external dependencies.
- No release/version changes.

## Starting Point

- `Monitoring/Monitor.yaml` for the benchmark project is valid and contains rules.
- Focused tests already cover central monitor definition loading and Monitor Browser central-rule fallback.
- Runtime logs have shown monitor rules being registered and actions executing.
- The remaining issue appears when the project is loaded at app startup, where Avalonia controls can attach before runtime/registry/folder context is stable.

Relevant existing lifecycle:

- App `MainWindowViewModel` constructor posts `LoadStartupPage` via `Dispatcher.UIThread.Post(..., DispatcherPriority.Background)`.
- UI shell and controls may be created before or during that delayed load.
- Manual project load happens after the app shell, dispatcher, selected folder, and bindings are already stable.
- `SetFolders(...)` currently attaches pages, hierarchy, syncs runtimes, then adds pages and selects the first folder.

## Tasks

1. Inspect AppStart versus manual project load lifecycle.
   - Compare `LoadStartupPage`, `LoadStructuredBookFromDirectory`, `UpdatePagesFromWatchedPages`, `SetFolders`, and manual load command flow.
   - Identify exactly when UI controls can attach relative to `SyncMonitors`, `SyncUdlClients`, `SyncEnhancedSignals`, `SyncControllers`, and `RealtimeChartRuntimeManager` sync.

2. Define a minimal runtime-ready boundary.
   - Prefer a small ViewModel-level mechanism over a broad new framework.
   - Candidate: `ProjectLoadGeneration` or `RuntimeGeneration` incremented after `SetFolders(...)` completes runtime sync.
   - Candidate: explicit `NotifyFolderRuntimeReady(pageName)` after all folder runtimes are synced.
   - Keep it usable by other runtime-backed widgets later, but implement only what `MonitorView` needs now.

3. Make startup and manual load converge.
   - Ensure AppStart and manual project load use the same completion point after runtime sync.
   - Ensure any runtime-backed controls attached early get a deterministic rebind after that completion point.
   - Avoid making visual controls own or start runtime services.

4. Harden `MonitorView` against early attach.
   - If `RebuildRows()` runs before registry entries/runtime state are ready, it must not remain permanently empty or stale.
   - Rebuild rows when runtime-ready/project-generation changes.
   - Clear stale `_rowSnapshot`, `_runtimeSnapshot`, queued refresh state, and subscription prefixes before rebuilding for a new context.
   - Activate scoped registry subscriptions only after current selected rows are resolved.

5. Preserve Browser behavior.
   - Monitor Browser remains all-rule management/debug view.
   - Opening Browser must not clear runtime.
   - Browser can use direct central-file fallback, but should not be responsible for runtime ownership.

6. Add focused tests.
   - AppStart-like early `MonitorView` attach before runtime sync, followed by runtime-ready notification, results in selected rows.
   - Manual-load-like sequence still works.
   - Repeated project load with the same folder name does not leave stale `MonitorView` snapshots/subscriptions.
   - Browser opening after startup does not empty `MonitorView` or runtime.

7. Update docs only if the new ready boundary is user-visible or clarifies runtime/widget ownership.

## Implementation Order

1. Add a failing test that simulates early `MonitorView` attach before monitor runtime/registry readiness.
2. Inspect existing ViewModel property/event hooks available to widgets.
3. Introduce the smallest runtime-ready/generation signal after `SetFolders(...)` completes runtime sync.
4. Wire `MonitorView` to reset/rebuild on that signal.
5. Ensure `MonitorView` clears stale subscriptions before rebuilding and sets scoped prefixes only after selected rows exist.
6. Re-run the new failing test.
7. Add/re-run manual-load and Browser regression tests.
8. Run focused editor test build.
9. Run `#bench 120` after implementation if requested.

## Technical Constraints

- Chat response must be German; code, comments, XML docs, UI text, validation messages, and identifiers must be English.
- Use existing Avalonia, `ObservableObject`, ViewModel, runtime manager, and registry patterns.
- Do not introduce new dependencies.
- Runtime services remain owned by folder/client/system runtime managers, not visual controls.
- Registry filtering must happen before UI dispatch.
- MonitorView must remain selected-rule-only.
- Avoid speculative generic widget infrastructure; add only a minimal readiness boundary with clear current use.

## Risks / Watchouts

- A readiness signal emitted too early will preserve the bug.
- A readiness signal emitted repeatedly may cause excess rebuilds and dispatcher posts.
- MonitorView must not subscribe broadly while waiting for readiness.
- Do not solve this by adding sleeps, timers, or arbitrary delays.
- Avoid using Browser state as proof that MonitorView is healthy; Browser and MonitorView have different scopes.

## Notes

- The correct structural target is not literally "no UI exists before runtime"; Avalonia shell and dispatcher may exist first.
- The correct boundary is: runtime-backed widgets must not finalize rows/snapshots/subscriptions until project/folder runtime state is ready, and they must rebind deterministically when readiness arrives.
