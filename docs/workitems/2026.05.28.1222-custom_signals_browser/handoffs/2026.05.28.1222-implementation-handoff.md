# IMPLEMENTATION HANDOFF

## Goal
Move `CustomSignals` definitions out of folder-level widget data in `Folder.yaml` into folder-local resource files, and provide an Admin-only `Custom Signals` browser that can add, edit, delete, set, and publish custom signals without placing a `CustomSignals` widget on the canvas.

## Scope
- Add folder-local custom signal files under `Signals/Custom/*.yaml`.
- Keep runtime publishing behavior equivalent to the existing `CustomSignalsControl`.
- Add a `Custom Signals` browser entry in the existing browser area of the right legend panel.
- Update `samples/HornetStudioDemo/` so existing custom signals are migrated from `Folder.yaml` into the new file structure.
- Preserve focused legacy loading support in code/tests, but do not keep duplicated demo definitions in both locations.

Explicitly not included:
- Reworking the custom signal formula engine.
- Changing registry path semantics unless needed to preserve current behavior without a placed widget.
- Adding a new runtime dependency.

## Tasks
1. Introduce a file codec for `Signals/Custom/*.yaml`.
   - Use `YamlDotNet`, already present in the project.
   - Use `CustomSignalDefinitionDocument` as persisted shape.
   - Validate file names against definition names.
   - Use snake_case file names matching signal names.
   - Normalize target paths with `CustomSignalDefinitionCodec` document conversion.

2. Add file-backed custom signal loading to the application model.
   - Load `Signals/Custom/*.yaml` for the active folder.
   - Combine file-backed definitions with legacy widget definitions for runtime compatibility.
   - Prefer file-backed definitions when a duplicate name exists.
   - Report clear warnings for invalid/duplicate files using existing warning patterns.

3. Update `CustomSignalsControl` for browser-hosted usage.
   - Add nullable `EditorViewModel` property like the fixed EnhancedSignals pattern.
   - Do not assume `TopLevel.DataContext` is `MainWindowViewModel`.
   - Detect a temporary browser owner, e.g. `CustomSignalsBrowser`.
   - For the browser owner, load and save `Signals/Custom/*.yaml` directly.
   - Do not sync an empty temporary browser item into runtime or registry state.
   - Ensure browser opening does not remove already published custom signals.
   - Keep normal placed widget behavior compatible with legacy `CustomSignalDefinitions`.

4. Make Add/Edit/Delete/Set robust in browser mode.
   - `Add` and `Edit` must open even when `TopLevel.DataContext` is the browser window model.
   - Pass nullable `MainWindowViewModel` to `CustomSignalEditorDialogWindow`, because it already supports a nullable view model.
   - Resolve row actions from `CommandParameter`, `Tag`, or `DataContext`.
   - Mark click events handled at the beginning of the handler to avoid accidental outer handling.
   - Delete must remove the backing YAML file for file-backed rows.
   - Set must continue to update the runtime registry value for writable input signals.

5. Add `CustomSignalsBrowserDialogWindow`.
   - Follow the fixed EnhancedSignals browser pattern, but avoid the previous bug:
     - Do not rely on a direct generated field access that can be null.
     - Resolve the embedded control with `FindControl<CustomSignalsControl>(...)` or keep bindings only if verified.
     - Set embedded control `DataContext` and `EditorViewModel` explicitly.
   - Provide `ShowOrActivate(...)` and `UpdateFolderContext(...)`.
   - Apply folder context to a temporary `FolderItemModel` named `CustomSignalsBrowser`.

6. Add the browser entry to the right legend/browser area.
   - Only visible for Admin user level, matching the existing browser section.
   - Do not create a new side panel.
   - Reuse the existing lower browser area under the folder list.
   - Add open/activate handling in `src/HornetStudio/MainWindow.axaml.cs`.

7. Migrate the demo project.
   - Move existing `CustomSignals` definitions from `samples/HornetStudioDemo/Folders/main/Folder.yaml` into `samples/HornetStudioDemo/Folders/main/Signals/Custom/*.yaml`.
   - Remove the `CustomSignals` widget entry from `Folder.yaml`.
   - Do not keep duplicate definitions in both places.

8. Update focused tests and documentation.
   - Add or update tests for file codec load/save/delete and legacy compatibility.
   - Add or update tests for demo migration shape if existing test style supports it.
   - Update widget docs that mention `Properties.CustomSignals` as the only storage.

## Acceptance Criteria
- Opening the Custom Signals browser lists `Signals/Custom/*.yaml` definitions for the selected folder.
- Opening the browser does not remove existing custom signals from the registry or clear runtime state.
- `Add` creates a new YAML file and publishes the signal.
- `Edit` opens the editor, saves changes back to the same YAML file, and handles rename by renaming/deleting the old file.
- `Delete` removes the YAML file and unpublishes the signal.
- `Set` still works for writable input custom signals from the browser.
- The browser is visible only for Admin user level.
- `samples/HornetStudioDemo/Folders/main/Folder.yaml` no longer contains the migrated CustomSignals widget/definitions.
- Demo custom signals exist under `samples/HornetStudioDemo/Folders/main/Signals/Custom/*.yaml`.

## Out of Scope
- Migrating real external user projects.
- Removing all legacy `CustomSignalDefinitions` persistence code.
- Redesigning the CustomSignals editor UI.
- Reworking formula parser behavior.
- Implementing CustomSignals for non-admin browser visibility.

## Risks / Watchouts
- Do not repeat the EnhancedSignals browser mistakes:
  - Do not assume `TopLevel.DataContext` is `MainWindowViewModel` in browser windows.
  - Do not let a temporary browser owner with empty `CustomSignalDefinitions` clear runtime/registry state.
  - Do not rely only on `CommandParameter` for row actions.
  - Do not hard-require `MainWindowViewModel` just to open an editor dialog that accepts nullable view model.
  - Do not directly dereference generated `x:Name` fields in window constructors without a null-safe lookup.
- `CustomSignalsControl.OnDetachedFromVisualTree()` currently removes published signals. Browser mode must not accidentally unpublish signals that belong to the folder runtime when only the browser window closes.
- `CustomSignalsControl` publishes directly from its `Signals` rows. Browser mode needs one clear owner for publishing to avoid duplicate remove/publish churn between browser and placed widgets.
- Demo migration must remove the legacy widget so broken file-backed loading is immediately visible.
