# IMPLEMENTATION HANDOFF

## Goal
Create the UDL client browser layout for file-backed clients from `Clients/Udl/<client-id>.yaml`. The browser must provide a management and diagnostics UI with a left client list and a right detail view, while runtime and headless projection continue to work without the browser.

## Scope
Included:
- Add or complete a UDL client browser surface.
- Use a two-pane layout:
  - left: client list
  - right: selected client details
- Detail view structure:
  - Header: definition/properties previously visible on the old `UdlClientControl` widget
  - Body: received/attached/module management areas carried over from the old widget concept
  - Footer: diagnostics
- Load clients from `Clients/Udl/*.yaml`.
- Allow selecting a client and displaying its definition/runtime state.
- Provide editing for core definition fields and save back to `Clients/Udl/<client-id>.yaml`.
- Provide connect/disconnect actions through `UdlClientRuntimeManager`.
- Show received and attached items from runtime/headless projection state.
- Keep the browser as observer/controller only; it must not own runtime or projection lifetime.
- Update documentation for the browser workflow if user-visible behavior changes.

Explicitly not included:
- Reintroducing `UdlClientControl` as a required runtime anchor.
- Adding a separate UDL status/view widget.
- Changing the file-backed structure `Clients/Udl/<client-id>.yaml`.
- Broad redesign of runtime/projection behavior.
- Generic client browser framework for non-UDL clients.
- Release/versioning work.

## Starting Point
- File-backed UDL runtime/projection now starts cleanly.
- UDL widgets can be removed from folders because runtime and projection no longer depend on them.
- There is currently no browser, so users cannot inspect or manage UDL clients through the new file-backed architecture.
- Existing browser patterns are available in Monitor, EnhancedSignals, CustomSignals, Controller, and Functions browser windows.
- Existing UDL widget UI contains useful body concepts for received items, attached items, modules, and diagnostics, but must not remain the runtime owner.

## Tasks
1. Establish browser entry point.
   - Add/open UDL browser from the same folder/client management area where other browser-style resources are opened.
   - Use existing browser/dialog window patterns where possible.
   - Do not add a widget to the page for browser access unless existing folder editor patterns require a temporary command surface.
2. Build the browser shell.
   - Left pane lists `Clients/Udl/*.yaml`.
   - Right pane shows selected client details.
   - Empty state when no client is selected.
   - Stable sizing, no nested cards, no page-like marketing layout.
3. Implement left client list.
   - Show `Text` when available, otherwise client id.
   - Show technical client id.
   - Show connection state indicator.
   - Show `Enabled` and `AutoConnect` indicators.
   - Provide actions for add, rename, delete, and refresh if feasible in this step.
4. Implement detail header.
   - Include fields that were previously visible/configurable through UDL widget properties:
     - client id readonly or rename-driven
     - `Text`
     - `Host`
     - `Port`
     - `Enabled`
     - `AutoConnect`
     - `DebugLogging`
     - `DemoEnabled`
   - Include connect/disconnect action.
   - Save edits to the selected `Clients/Udl/<client-id>.yaml`.
   - Sync runtime definitions after save.
5. Implement detail body.
   - Carry over the old widget's useful body concepts, not necessarily its compact embedded layout.
   - Include sections for:
     - received modules/items
     - attached items / `AttachedItemPaths`
     - module/channel overview
     - demo modules where practical
   - Prefer a readable split or stacked sections over a tiny widget-like layout.
6. Implement detail footer diagnostics.
   - Show current connection state.
   - Show endpoint.
   - Show item/module counts.
   - Show message/rx/tx counters where available.
   - Show last diagnostic/error line.
   - Show relevant paths:
     - definition file path
     - status path
     - runtime root
7. Add browser data flow.
   - Load definitions through `UdlClientDefinitionFileCodec`.
   - Query/observe runtimes through `UdlClientRuntimeManager`.
   - Use existing runtime snapshots/events where available.
   - Add minimal runtime snapshot APIs only when needed.
   - Registry event subscriptions must be scoped to the selected client/runtime paths.
8. Preserve runtime/projection independence.
   - Closing the browser must not disconnect clients.
   - Switching selection must not recreate runtimes.
   - Editing/saving a definition may trigger runtime sync only when definition values actually change.
9. Add focused tests where practical.
   - Definition edit/save roundtrip.
   - Browser view model selection loads correct definition.
   - Save triggers file update and runtime sync.
   - Closing/disposal does not release runtime.
10. Update documentation.
   - Describe UDL clients as folder-local browser-managed resources.
   - Clarify that browser is management UI and status can still be displayed via existing Signal widgets.

## Implementation Order
1. Inspect existing browser dialog patterns:
   - Monitor browser
   - EnhancedSignals browser
   - CustomSignals browser
   - Controller browser
2. Choose the closest existing pattern and mirror its shell style.
3. Add the browser window with static layout first:
   - left list
   - right header/body/footer
4. Wire definition loading and selection.
5. Wire header editing/save.
6. Wire connect/disconnect.
7. Wire body received/attached display.
8. Wire footer diagnostics.
9. Add scoped refresh/subscription behavior.
10. Add tests/docs.
11. Run build and manual UI verification.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Public classes and public methods require XML documentation.
- Use existing Avalonia and project browser patterns.
- Do not introduce new dependencies.
- Browser controls must be subscription-scoped and must filter registry/runtime relevance before dispatching UI work.
- Browser must not own runtime lifecycle.
- Browser close, tab switch, or selected client switch must not disconnect or dispose runtime.
- Runtime/projection must continue to work without the browser.
- Avoid overengineering a generic client browser abstraction.
- Avoid nested cards and oversized decorative UI.

## Acceptance Criteria
- User can open a UDL clients browser.
- Browser shows a left list of clients from `Clients/Udl/*.yaml`.
- Selecting a client shows right-side details.
- Header contains the core definition properties from the old UDL widget property area.
- Body provides received/attached/module management based on the old widget concepts.
- Footer shows diagnostics.
- Editing and saving core fields updates the selected client YAML.
- Connect/disconnect actions work through the runtime manager.
- Closing the browser does not stop running clients.
- Switching selected clients does not recreate runtimes.
- Demo project remains functional without `UdlClientControl` widgets in folders.

  - Confirm body shows received/attached UDL data for `m001`.
  - Confirm footer shows diagnostics and paths.
  - Close the browser and confirm runtime/projection continue running.
  - Reopen browser and confirm state is still visible.

## Out of Scope
- UDL status/view widget.
- Generic client browser architecture.
- Major redesign of UDL runtime/projection.
- Release/versioning.
- Polishing every demo-module editor feature if a minimal body management view is enough for the first browser version.

## Risks / Watchouts
- Reusing too much of `UdlClientControl` can accidentally bring back visual-control-owned runtime behavior.
- Browser refresh must not react to all registry changes globally.
- Header save may recreate runtime too often if every UI edit syncs immediately; prefer explicit save or careful change detection.
- The old widget body was designed for embedded size; browser body should reuse behavior but not necessarily the exact layout.
- If demo module editing is large, keep first version focused on visibility and attach management, then extend editor depth later.
