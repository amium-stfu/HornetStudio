# IMPLEMENTATION HANDOFF

## Goal
Move Monitor rule ownership from placed Monitor widgets into one folder-local central monitor definition file at `Monitoring/Monitor.yaml`, make `Monitor` a browser/editor similar to `Functions`, and add a readonly `MonitorView` concept that renders selected monitor IDs only.

## Scope
- Introduce a folder-level monitor source at `Monitoring/Monitor.yaml`.
- Introduce a widget-independent monitor registry and runtime ownership model.
- Convert the existing `Monitor` widget into a browser/editor for central folder monitor entries.
- Add a `MonitorView` widget or equivalent readonly view model surface that displays only configured monitor IDs.
- Update runtime paths so monitor state is folder-stable instead of widget-name-stable.
- Update demo data, documentation, and focused tests for the new structure.
- Include migration/loading compatibility from existing `Properties.MonitorDefinitions` where needed.

Do not add unrelated monitor rule features, new action types, broad UI redesigns, or new runtime dependencies.

## Starting Point
- Current monitor definitions are stored on a placed `Monitor` widget in `Properties.MonitorDefinitions`.
- `MonitorControl` owns rule rows, evaluation timers, aggregate publication, add/edit/delete behavior, and display.
- Current runtime paths include the widget name: `studio.{FolderName}.monitor.{WidgetName}.{RuleName}`.
- VisualRules enumerate monitor sources by scanning placed `ControlKind.Monitor` items and their `MonitorDefinitions`.
- Functions already follow the desired direction: a widget-independent `FunctionRegistry` and a `FunctionsControl` that visualizes/edits registry entries.
- The selected target central file location is `Monitoring/Monitor.yaml` below each folder directory.

## Tasks
1. Define the central monitor file contract for `Monitoring/Monitor.yaml`.
2. Extract monitor discovery into a widget-independent `MonitorRegistry`.
3. Extract monitor evaluation/runtime ownership so rule evaluation does not require a visible `MonitorControl`.
4. Rework `MonitorControl` into a browser/editor over `MonitorRegistry`.
5. Add `MonitorView` as readonly selected-ID display.
6. Update VisualRules source enumeration and runtime path handling.
7. Add compatibility import/loading for existing widget-local `MonitorDefinitions`.
8. Update sample/demo project files to the new `Monitoring/Monitor.yaml` structure.
9. Update monitor documentation and widget picker descriptions/help.
10. Add focused tests for codec, registry lookup, runtime path generation, selected-ID filtering, and legacy compatibility.

## Implementation Order
1. Add central file codec support for `Monitoring/Monitor.yaml` without changing existing UI behavior yet.
2. Add `MonitorRegistry` that can enumerate central entries and optionally legacy widget-local entries.
3. Add stable monitor references and runtime path helpers:
   - Rule path: `studio.{FolderName}.monitor.{RuleName}`
   - Aggregate path: `studio.{FolderName}.monitor`
4. Extract runtime evaluation from `MonitorControl` into a folder-level runtime manager or equivalent service.
5. Wire folder load/activation so runtime evaluation starts even when no `Monitor` widget is placed.
6. Convert `MonitorControl` add/edit/delete to operate on `Monitoring/Monitor.yaml`.
7. Update source pickers and VisualRules enumeration to use `MonitorRegistry`, not placed monitor widgets.
8. Add `MonitorView` readonly display with a selected ID list.
9. Update serialization for the new `MonitorView` property and widget type registration/picker.
10. Move demo monitor definitions into `Monitoring/Monitor.yaml`.
11. Update Markdown docs.
12. Add and run focused tests, then run the relevant build.

## Technical Constraints
- Use existing project patterns from `FunctionRegistry` and `FunctionsControl` where they fit.
- Keep monitor storage folder-local and file-backed; `Folder.yaml` should not remain the authoritative source for central monitor definitions.
- Do not introduce new dependencies unless a concrete codec or YAML limitation requires it and the dependency/FOSS impact is documented.
- Keep user-visible UI strings and validation messages in English.
- Chat and planning communication remains German.
- Preserve existing normalization conventions such as snake_case runtime path segments.
- Avoid broad refactoring outside Monitor, VisualRules, folder loading, sample data, docs, and tests.

## Acceptance Criteria
- `Monitoring/Monitor.yaml` is the authoritative source for monitor rules in a folder.
- A folder can evaluate monitor rules without a placed `Monitor` widget.
- `Monitor` displays all central monitor entries and supports add/edit/delete against `Monitoring/Monitor.yaml`.
- `MonitorView` displays only selected monitor IDs and has no edit/delete controls.
- Monitor rule runtime paths no longer depend on a widget name.
- VisualRules can select and react to central monitor rule runtime paths.
- Existing legacy `Properties.MonitorDefinitions` can still be loaded or imported without silently losing definitions.
- Demo project uses the new central monitor file structure.
- Documentation describes the new ownership, file path, runtime paths, and readonly view behavior.

## Verification
- Run focused editor tests through `src/HornetStudio.Editor.Tests`.
- Run `dotnet build HornetStudio.sln --no-restore` after restore is already current.
- Manually verify in the editor:
  - Create/edit/delete a monitor rule in `Monitor`.
  - Confirm `Monitoring/Monitor.yaml` changes.
  - Remove the `Monitor` browser widget and confirm runtime monitor state still publishes.
  - Add `MonitorView`, select a subset of IDs, and confirm only selected readonly rows render.
  - Configure a VisualRule from a central monitor source and confirm it reacts to active state.

## Out of Scope
- New monitor condition types.
- New monitor action types.
- Changing Python function invocation semantics.
- Preserving duplicated demo definitions in both `Folder.yaml` and `Monitoring/Monitor.yaml`.
- Release versioning or publishing.

## Risks / Watchouts
- Moving runtime paths can break existing VisualRules unless references are migrated or legacy paths are resolved during load.
- `EventId` uniqueness must become folder-wide, not widget-local.
- Runtime evaluation must avoid duplicate timers if multiple browser/view widgets are open for the same folder.
- Registry event handlers must filter by owned monitor paths and must not react to unrelated global registry changes.
- Temporary browser/view items must not clear or overwrite central folder monitor runtime.
- File-backed central definitions should be authoritative; legacy widget definitions should be compatibility input only.

## Notes
- Prefer `Monitoring/Monitor.yaml` exactly as the central path.
- If a folder has both central and legacy widget-local monitor definitions, the central file should win as authoritative. Legacy definitions should be imported only when no central file exists, or exposed as a controlled migration path.
- The implementation should mirror the Functions principle: registry/runtime availability must not depend on placing the visual browser widget.
