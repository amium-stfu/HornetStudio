# IMPLEMENTATION HANDOFF

## Goal
Finish `MonitorView` as a readonly monitor projection with a registry-backed picker instead of free-text IDs, fix `MonitorView` type loading in runtime/project loaders, and add an `OnActiveColor` color-picker property for active rows.

## Scope
- Replace the visible `SelectedMonitorIds` free-text editing path with a multi-select picker backed by `MonitorRegistry`.
- Keep persisted `SelectedMonitorIds` as stable monitor rule names, not numeric `EventId` values.
- Fix `Type: MonitorView` so it loads as `ControlKind.MonitorView` instead of the default/fallback item.
- Add `OnActiveColor` as an optional `MonitorView` property with a color picker.
- Update YAML/document persistence, sample data, docs, and focused tests.

Do not change monitor rule evaluation, monitor action behavior, `Monitoring/Monitor.yaml` schema, or the `Monitor` browser/editor behavior beyond what is needed for the picker.

## Starting Point
- `MonitorViewControl` exists under `src/HornetStudio.Editor/Widgets/MonitorView/`.
- `FolderItemModel.SelectedMonitorIds` is a raw string and the editor property dialog currently exposes it through `BindMultiline`.
- `MonitorRegistry.ParseSelectedIds("1,2")` normalizes values to `1` and `2`, but `MonitorView` matches against monitor rule names such as `monitor_rule_1`, so numeric `EventId` values produce no rows.
- `samples/HornetStudioReference/Folders/main/Folder.yaml` currently contains `SelectedMonitorIds: ['1', '2']`.
- Editor-side `ControlKind.MonitorView` exists, but runtime `src/HornetStudio/ViewModels/MainWindowViewModel.cs` does not map `Type: MonitorView` to `ControlKind.MonitorView`.
- `MonitorView` active rows currently use `EffectiveAccentBackground`; there is no dedicated user-configurable active color.

## Tasks
1. Add a registry-backed multi-select monitor picker for `MonitorView`.
2. Persist selected monitor rule names, not numeric event IDs.
3. Fix `MonitorView` type mapping and default sizing in runtime/project loading paths.
4. Add `OnActiveColor` as an optional MonitorView color property.
5. Apply `OnActiveColor` only to active `MonitorView` rows; keep existing theme/severity behavior as fallback.
6. Update sample `MonitorView` selections from numeric IDs to rule names.
7. Update docs and focused tests.

## Implementation Order
1. Fix runtime `MonitorView` type mapping first so existing YAML loads as the right control.
2. Add `OnActiveColor` model/persistence property with default empty value.
3. Update `MonitorViewRow.GetActiveRowBackground()` to use `OnActiveColor` when present, else current fallback.
4. Add registry-backed selection option model/helper.
5. Replace the property editor free-text binding with the picker/multi-select workflow.
6. Update sample `SelectedMonitorIds` to rule names.
7. Update docs.
8. Add focused tests and run the narrow build/test checks.

## Technical Constraints
- Chat remains German; code, comments, XML docs, UI text, and validation messages remain English.
- Use existing editor property dialog and picker patterns where possible.
- Do not add dependencies.
- Keep `SelectedMonitorIds` as stable rule names in persistence.
- Avoid using `EventId` as the primary persisted selection key.
- Preserve existing `MonitorRegistry` as the source for available monitor entries.
- Keep registry event handling filtered to selected monitor runtime paths only.

## Acceptance Criteria
- `Type: MonitorView` loads as `ControlKind.MonitorView` in both editor and runtime views.
- `MonitorView` property editing offers a picker/multi-select, not only raw free text.
- Picker options display enough context: `EventId`, `EventText`, `Name`, and optionally `LogLevel`.
- Persisted `SelectedMonitorIds` contains monitor rule names such as `monitor_rule_1`.
- The sample reference folder displays the selected monitor rule after loading.
- Entering or migrating numeric `1,2` is no longer the expected workflow; docs explain stable rule names.
- `OnActiveColor` is available via color picker and overrides active row background only when configured.
- Empty `OnActiveColor` keeps the current theme/accent fallback.

## Verification
- `dotnet build src\HornetStudio.Editor\HornetStudio.Editor.csproj --no-restore`
- If the main app is not locking DLL/PDB files, run the relevant editor self-test project. If locked, build tests with a safe separate output/intermediate path after restore.
- Manual editor verification:
  - Load `samples/HornetStudioReference`.
  - Confirm `MonitorView` is not loaded as a default Signal item.
  - Open MonitorView properties and select monitor rules via picker.
  - Save and confirm `SelectedMonitorIds` stores rule names.
  - Activate a selected rule and confirm `OnActiveColor` is used.

## Out of Scope
- Changing `Monitoring/Monitor.yaml` schema.
- Changing monitor rule `EventId` semantics.
- New monitor rule evaluation modes or actions.
- Making `EventId` the persisted selection key.

## Risks / Watchouts
- Existing sample data with `SelectedMonitorIds: ['1', '2']` will not match unless migrated to rule names or a compatibility alias is added.
- If numeric compatibility is added, it must not become the primary persisted format because `EventId` can change.
- Picker must handle missing selected rule names gracefully, similar to existing function picker behavior.
- Runtime and editor loaders both need the `MonitorView` type mapping; fixing only editor loading leaves runtime/default item behavior unresolved.
