# IMPLEMENTATION HANDOFF

## Goal
Create a small, isolated Host item registry laboratory that can be tested without Avalonia, the existing editor UI, widgets, or the existing `HostRegistries.Data` implementation.

The new registry should prove the intended core model: a registry is primarily a path-to-reference map. Reads and writes go directly through the registered reference/source. A small WinForms probe app should make the behavior easy to inspect manually.

## Scope
Included:
- Add a new slim Host registry implementation next to the existing registry code.
- Add minimal reference/source abstractions for readable and writable values.
- Add focused host self-tests for the new registry basics.
- Add a small WinForms probe project that references `HornetStudio.Host` and uses only the new registry.
- Add the probe project to the solution if the repository build can support it cleanly.

Explicitly not included:
- Do not replace, rewrite, delete, or migrate `src/HornetStudio.Host/Registries/HostRegistries.cs`.
- Do not connect existing Avalonia UI controls to the new registry.
- Do not migrate existing widgets, UDL, broker, controller, Python, logger, or monitor runtimes.
- Do not introduce compatibility bridges to the old registry in this first step.

## Starting Point
- The current `HornetStudio.Host` project contains the existing large registry in `src/HornetStudio.Host/Registries/HostRegistries.cs`.
- `HornetStudio.Editor` currently references `HornetStudio.Host` directly and many UI files call `HostRegistries.Data`.
- The user wants to regain architectural control by first creating a very small, isolated testable registry core.
- WinForms is preferred as the first manual probe UI because it is easier for the user to handle than the current Avalonia editor.

## Tasks
1. Create a new slim registry file under `src/HornetStudio.Host/Registries/`.
2. Define minimal readable/writable reference abstractions.
3. Implement a small registry class backed by `Dictionary<string, IHostItemReference>` or equivalent.
4. Add one or two simple reference implementations for testing, such as an in-memory value reference and optionally an object-property reference.
5. Add focused tests to `src/HornetStudio.Host.Tests/Program.cs`.
6. Add a new WinForms probe project under `src/HornetStudio.Host.WinFormsProbe/`.
7. Make the WinForms probe display registered paths, current values, write input, refresh behavior, and change events.
8. Add the project to `HornetStudio.sln` if practical and verify build behavior.

## File-Level Changes
- `src/HornetStudio.Host/Registries/HostItemRegistry.cs` -> new slim registry and reference abstractions.
- `src/HornetStudio.Host/HornetStudio.Host.csproj` -> include the new registry source file if required by explicit compile item settings.
- `src/HornetStudio.Host.Tests/Program.cs` -> add focused tests for register, read, write, unregister/remove, duplicate path handling, and changed notification.
- `src/HornetStudio.Host.WinFormsProbe/HornetStudio.Host.WinFormsProbe.csproj` -> new WinForms probe project targeting Windows.
- `src/HornetStudio.Host.WinFormsProbe/Program.cs` -> WinForms startup and demo registry setup.
- `src/HornetStudio.Host.WinFormsProbe/MainForm.cs` -> simple probe UI for path list, current value, write input, refresh button, and event log.
- `HornetStudio.sln` -> add the WinForms probe project only if solution conventions and build constraints allow it cleanly.

## Implementation Order
1. Add `HostItemRegistry.cs` with only the minimal core types.
2. Include the file in `HornetStudio.Host.csproj`.
3. Add host self-tests that exercise the new registry without any UI.
4. Build/run the host test project.
5. Create the WinForms probe project and wire it only to the new registry.
6. Add the probe to the solution if practical.
7. Build the solution or, if the full solution is too broad, build `HornetStudio.Host` plus the probe project and document the limitation.

## Technical Constraints
- Chat responses must be in German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be in English.
- User-visible errors and validation messages must be in English.
- The new registry must not depend on Avalonia, `HornetStudio.Editor`, widgets, pages, or `HostRegistries.Data`.
- Keep the new registry intentionally small. Avoid speculative abstractions.
- Prefer clear names over clever generic machinery.
- Use the existing repository structure under `src/`.
- Because `HornetStudio.Host.csproj` uses explicit compile includes, add new source files there as needed.
- `HornetStudio.Host.Tests` is a console self-test project. Focused verification should run the built DLL directly when appropriate.

## Acceptance Criteria
- A new slim host registry exists next to the old registry.
- The old `HostRegistries.cs` remains functionally untouched.
- The new registry can register a path and reference/source.
- The new registry can read a value through the reference/source.
- The new registry can write a value through the reference/source.
- Removing/unregistering a path prevents further reads/writes for that path.
- Change notifications can be observed without UI dependencies.
- The WinForms probe can be launched independently and manually exercises the new registry.
- No existing Avalonia editor control is migrated in this workitem.

## Verification
- Build `src/HornetStudio.Host/HornetStudio.Host.csproj`.
- Build `src/HornetStudio.Host.Tests/HornetStudio.Host.Tests.csproj`.
- Run the focused host self-test executable for `HornetStudio.Host.Tests`.
- Build `src/HornetStudio.Host.WinFormsProbe/HornetStudio.Host.WinFormsProbe.csproj`.
- Optionally run the WinForms probe manually and confirm read/write/event behavior.
- If the project is added to the solution, run `dotnet build HornetStudio.sln --no-restore -v:minimal` after restore/build prerequisites are satisfied.

## Out of Scope
- Replacing the old registry.
- Any broad refactor of `PageItemModel`, widgets, broker controls, UDL controls, or monitor controls.
- Any Avalonia UI changes.
- Runtime migration from snapshots to references.
- Persisted project format changes.
- Demo/sample project migration.

## Risks / Watchouts
- Do not let the first registry version grow into a second large registry. Keep it as a laboratory core.
- Avoid storing C# `ref object` values. Use reference/source objects that expose read/write methods instead.
- Be careful with threading in changed notifications. The first implementation can be synchronous and documented as such.
- Avoid adding dependencies from `HornetStudio.Host` to WinForms. The WinForms probe must depend on Host, never the other way around.
- Keep path normalization minimal and explicit. Do not copy the old registry's complex path compatibility rules into the first version.

## Relevant Files

- `src/HornetStudio.Host/HornetStudio.Host.csproj`

- `HornetStudio.sln`

## Notes
- Preferred first type names:
  - `HostItemRegistry`
  - `IHostItemReference`
  - `HostItemChangedEventArgs`
  - `MemoryHostItemReference`
- The first implementation should favor inspectability over feature completeness.
- The WinForms probe is a deliberate human-facing test harness, not the future production UI.
