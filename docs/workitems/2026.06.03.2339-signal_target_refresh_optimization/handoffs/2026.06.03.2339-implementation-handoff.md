# IMPLEMENTATION HANDOFF

## Goal
Optimize the high-frequency Signal widget target refresh path so 20 public UDL signal values at 10 Hz can update visible Signal widgets without unnecessary target refresh work or growing UI latency.

## Scope
- Implement a focused optimization in the `PageItemModel` Signal/ItemModel target refresh path.
- Preserve current UDL runtime, public HostRegistry semantics, widget configuration, and chart behavior.
- Use the existing high-frequency signal diagnostics to verify the improvement.
- Keep changes minimal and localized.
- Do not introduce new dependencies.
- Do not perform broad refactoring of `PageItemModel`.

## Starting Point
- The benchmark scenario is `benchmarks/ui_lag_bench_project/project.aaep`.
- The latest 30s control run used scenario `HighFrequencySignalDiagnostics-30s`.
- Relevant measured result:
  - `RegistryPublish`: about `198.7/s`
  - `DemoGenerate`: about `28.9/s`
  - `SignalReceive`: about `29.0/s`
  - `TargetRefreshQueued`: about `56.2/s`
  - `TargetRefreshExecuted`: about `56.2/s`
  - `TargetRefreshExecuted DelayMaxMs`: about `3929.7`
  - `ChartRenderCount`: `0`
- The large UI spikes in that run were startup/warmup, not steady-state.
- The relevant bottleneck area is now the `PageItemModel` target refresh path, especially value-only updates that should not require full target binding refresh work.

## Tasks
1. Inspect `PageItemModel.OnDataRegistryChanged`, `RequestTargetRefresh`, `TriggerTargetRefresh`, and `RefreshTargetBindings`.
2. Classify which registry changes are value-only updates for Signal/ItemModel widgets.
3. Add a cheap value-only path for relevant target value/property updates.
4. Coalesce high-frequency value-only UI updates per widget so repeated updates do not enqueue duplicate refresh work.
5. Keep full `RefreshTargetBindings` for structural changes, target path changes, missing target resolution, property selection changes, and non-value-only cases.
6. Preserve existing behavior for non-Signal widgets and low-frequency structural refreshes.
7. Keep or extend diagnostics only enough to verify queue/execute counts and refresh delay after the optimization.
8. Verify with build and a 30s benchmark.

## File-Level Changes
- `src/HornetStudio.Editor/Models/PageItemModel.cs` -> Add value-only relevance detection and coalesced UI update path for Signal/ItemModel target updates.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> Update diagnostics only if the existing pipeline summary cannot distinguish fast-path/coalesced refreshes from full target refreshes.
- `docs/workitems/ChatHandoff.md` -> Update only if the final optimization result or benchmark interpretation should be preserved for the next chat.

## Implementation Order
1. Read the relevant `PageItemModel` methods and identify the current refresh decision points.
2. Identify the smallest state needed per `FolderItemModel` instance:
   - whether a target refresh is already queued
   - whether the pending refresh is value-only or full
   - the latest relevant changed path
   - the time the first pending update was queued for diagnostics
3. Implement a helper that determines whether a registry event is a value-only update for the current target.
4. Route value-only changes through a coalesced dispatcher update.
5. Ensure a full refresh always wins over a pending value-only refresh.
6. In the value-only execution path, update only the UI-facing value/caption state that actually depends on the target value.
7. Leave `RefreshTargetBindings` as the fallback for full refresh cases.
8. Add or adjust diagnostics labels so benchmark output can show:
   - value-only queued/executed counts
   - full refresh queued/executed counts
   - target refresh delay after coalescing
9. Build `HornetStudio.sln`.
10. Run the 30s benchmark against the existing bench project.
11. Compare the new run with `HighFrequencySignalDiagnostics-30s`.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Keep the implementation inside existing architecture and existing diagnostics patterns.
- Do not create a new service unless `PageItemModel` cannot safely own the required per-widget state.
- Do not read Avalonia UI objects from background/runtime threads.
- Registry relevance filtering must happen before any dispatcher work is posted.
- Unknown or unrelated registry events must not enqueue UI work.
- High-frequency value changes should not trigger structure rebuilds.
- Full refresh behavior must remain available for structural changes.
- Use named parameters for unclear or multi-argument method calls.

## Acceptance Criteria
- 20 Signal widgets still display the 20 UDL demo values from `udl1.m001.read` through `udl1.m020.read`.
- Value-only registry updates no longer cause duplicate full target refresh work per widget.
- Full target refresh still occurs for target changes, missing/appearing target resolution, and structural changes.
- Benchmark summary shows lower target refresh latency than the previous 30s control run.
- No growing dispatcher backlog is visible in benchmark diagnostics.
- `ChartRenderCount=0` remains separate from the Signal optimization when the chart is absent/disabled in the scenario.
- Solution build succeeds.

## Out of Scope
- Changing UDL demo generation.
- Changing public HostRegistry publish behavior.
- Changing Signal widget persisted schema.
- Optimizing chart sampling/rendering.
- Reworking the whole `PageItemModel`.
- Introducing a global scheduler or new runtime service.
- Running the full 1/5/10/20 matrix unless the 30s benchmark is inconclusive.

## Risks / Watchouts
- A value-only fast path must not skip updates that affect target binding selection, units, formatting, write state, captions, or visual rules.
- Coalescing must preserve the latest value, not the first queued value.
- A pending value-only refresh must be upgradeable to a full refresh.
- Do not hide missing-target transitions; fallback/text-like display states must still update correctly.
- Diagnostics overhead must remain low enough not to distort the benchmark.
- The existing benchmark project may still contain optional chart definitions; ensure the interpretation separates chart from Signal path if chart activity appears.
