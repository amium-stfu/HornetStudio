# IMPLEMENTATION HANDOFF

## Goal
Separate multi-folder runtime execution from browser/editor UI refresh work. All folder runtimes must continue running simultaneously, but browser-style UI controls must only live-refresh while their owning browser/folder surface is visible or active. Hidden browser controls should mark themselves dirty and perform one catch-up refresh when they become visible.

## Scope
Included:
- Add diagnostics that distinguish browser control instances by folder/scope, not only by control class name.
- Add or use an existing visibility/activity signal for browser-style controls.
- Gate browser UI rebuilds and periodic refreshes by visibility/activity.
- Preserve runtime execution for all folders, including PID controllers, monitor rules, enhanced signal runtime, UDL clients, and background registry updates.
- Keep registry subscription scoping and pre-dispatch filtering from the previous work.
- Validate with a 3-folder benchmark where only visible browser UI refreshes actively.

Explicitly not included:
- Disabling or pausing runtime logic for hidden folders.
- Settings/dialog profiling or optimization.
- Large redesign of the folder/project model.
- New external dependencies.
- Release/versioning work.

## Starting Point
- Single-folder and PID benchmark runs now pass with `BrowserDispatcherPosts=0` and low registry event counts.
- A 3-folder run failed:
  - `Status="Fail"`
  - `P95UiDelayMs=258.2`
  - `Spike250Ms=13`
  - `ChartRenderCount=288`
  - `EnhancedSignalsControl.RebuildRuntimes Count=90`, `P95Ms=146.3`
  - `CustomSignalsControl.RebuildSignalRows Count=90`, `P95Ms=84.2`
- The 3-folder log shows browser diagnostics aggregated by class name only, so it is unclear which concrete control instance/folder is doing the work.
- `BrowserDispatcherPosts=0` still holds, so the old Dispatcher flood is not the current problem.
- The current problem is that browser/editor UI refresh work scales with the number of folders, even when only one UI surface is relevant to the user.

## Tasks
1. Extend browser diagnostics source identity to include folder or owner scope:
   - Example: `CustomSignalsControl[main1]`
   - Example: `EnhancedSignalsControl[main2]`
   - Example: `MonitorViewControl[main3]`
2. Find where folder/browser controls are hosted and how visibility is represented:
   - page/folder editor host
   - cached folder host
   - browser dialog windows
   - `IsVisible`, attach/detach, selected folder/tab, or active screen state
3. Define a minimal browser activity model:
   - active when the control is visible/attached and its folder/browser surface is selected or open
   - inactive when hidden, detached, cached, or not selected
4. Add per-control dirty-state behavior:
   - relevant registry/runtime event while inactive marks the control dirty
   - inactive controls must not rebuild rows/lists/runtimes or schedule UI refresh work
   - when active again, perform one coalesced refresh if dirty
5. Apply the activity gate to current browser-style UI operations:
   - `CustomSignalsControl.RebuildSignalRows`
   - `EnhancedSignalsControl.RebuildRuntimes`
   - `ControllerControl.RebuildControllers`
   - `MonitorViewControl.RebuildRows`
   - `MonitorControl.RebuildRules`
   - `FunctionsControl.RefreshFunctions`
6. Preserve runtime behavior:
   - do not pause PID/controller runtimes
   - do not pause enhanced signal runtime calculation
   - do not pause monitor rule evaluation
   - do not pause UDL runtime/client data flow
7. Update benchmark summaries so rebuild counts can be evaluated per instance/folder.
8. Add focused tests for the activity gate if the current test harness supports these controls or the extracted gate logic.
9. Update documentation only if diagnostic usage or benchmark interpretation changes for users.

## Implementation Order
1. Inventory current host lifecycle:
   - Use `rg -n "IsVisible|AttachedToVisualTree|DetachedFromVisualTree|CachedFolderHost|Selected|Active" src/HornetStudio.Editor`.
   - Determine the existing way to know whether a folder/browser control is visible or active.
2. Improve diagnostics identity first:
   - Add helper logic in each browser control to compute a scoped source name from the current owner/folder.
   - Ensure benchmark summary can distinguish instances rather than aggregating all controls under `CustomSignalsControl`.
3. Add a minimal activity/dirty gate:
   - Prefer a small shared helper or base-control method only if it avoids duplicated fragile logic.
   - Keep it simple: `IsBrowserActive`, `IsBrowserRefreshDirty`, `MarkBrowserRefreshDirty`, `RefreshIfActiveOrMarkDirty`.
4. Apply the gate to one control first:
   - Start with `EnhancedSignalsControl` because it is the largest offender in the 3-folder run.
   - Verify inactive controls do not call `RebuildRuntimes`.
5. Apply the same pattern to the remaining browser controls.
6. Ensure visible/active transition performs one catch-up refresh:
   - on visible/attached/selected
   - coalesced if multiple events arrived while inactive
7. Run focused tests/build.
8. Run manual benchmarks:
   - single folder with PID
   - three folders with identical setup and only one visible/active browser surface
   - switch visible folder once and confirm catch-up refresh works

## Technical Constraints
- Runtime work must not be paused because hidden folders may represent active systems.
- UI refresh/rebuild work must be visibility/activity scoped.
- Registry event filtering must still happen before Dispatcher UI work is scheduled.
- Unknown/unrelated registry events must not enqueue UI work.
- Keep `BrowserDispatcherPosts=0` as a hard requirement.
- Use existing Avalonia lifecycle/visibility patterns where possible.
- No new dependencies.
- Public classes and public methods must have XML documentation.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Chat responses remain German.

## Acceptance Criteria
- Browser diagnostics identify control instances by folder/owner scope.
- In a 3-folder benchmark, browser operation counts are not blindly `3x` for hidden/inactive browser surfaces.
- `EnhancedSignalsControl.RebuildRuntimes` count and P95 are substantially lower in the 3-folder benchmark when only one folder/browser surface is visible.
- `CustomSignalsControl.RebuildSignalRows` count and P95 are substantially lower in the same scenario.
- Hidden/inactive browser controls mark dirty state without performing live rebuilds.
- Switching to a previously hidden folder performs one catch-up refresh and shows current data.
- All folder runtimes continue working simultaneously while their UI browser controls are hidden.
- `BrowserDispatcherPosts=0` remains true.
- `P95UiDelayMs` returns near the single-folder/PID baseline or at least passes the benchmark soft budgets.
- Chart render count and P95 recover compared with the failed 3-folder run.

## Out of Scope
- Pausing or redesigning runtime services.
- Optimizing Settings dialogs.
- Deep chart renderer changes unless a new chart-specific regression appears after browser refresh gating.
- Full multi-client browser migration.
- Release/version updates.

## Risks / Watchouts
- Avalonia `IsVisible` can mean layout visibility, not necessarily selected/active folder. Confirm the real host behavior before relying on it.
- Cached folder hosts may keep controls attached but hidden; activity must reflect user-visible relevance, not just object lifetime.
- Dialog-hosted browser controls are visible while the dialog is open and should remain live during that time.
- If a hidden control suppresses too much, users may see stale data after switching folders. The dirty/catch-up path is mandatory.
- Diagnostics aggregated by class name can hide whether scoping is correct; fix this before using the next benchmark as proof.
- Do not solve this by stopping runtimes. The runtime/UI separation is the main architectural requirement.
