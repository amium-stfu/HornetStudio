# IMPLEMENTATION HANDOFF

## Goal
Move `ControllerWidget` PID controller definitions out of folder-level widget data in `Folder.yaml` into folder-local controller files, and provide an Admin-only `Controllers` browser that can add, edit, delete, and inspect controllers without placing a `ControllerWidget` on the canvas.

## Scope
- Add folder-local controller files under `Controllers/*.yaml`.
- Keep current PID controller runtime behavior and registry path semantics.
- Add a `Controllers` browser entry in the existing lower browser area of the right legend panel.
- Update `samples/HornetStudioDemo/` so existing controller definitions are migrated from `Folder.yaml` into the new file structure.
- Preserve focused legacy loading support in code/tests, but do not keep duplicated demo definitions in both locations.

Explicitly not included:
- Redesigning PID runtime internals.
- Changing PID tuning behavior or formulas.
- Adding controller types beyond existing `ControllerType.PID`.
- Changing registry path shape unless required to preserve behavior without a placed widget.

## Tasks
1. Introduce a file codec for `Controllers/*.yaml`.
   - Use `YamlDotNet`, already present in the project.
   - Persist one controller definition per file using `ControllerDefinitionDocument`.
   - Validate file name matches controller `Name`.
   - Enforce snake_case names via existing helper rules where applicable.
   - Preserve existing `ControllerDefinitionCodec` normalization.

2. Add file-backed controller loading to the application model.
   - Load `Controllers/*.yaml` for each folder.
   - Merge file-backed definitions with legacy placed `ControllerWidget` definitions.
   - Prefer file-backed definitions on duplicate names.
   - Report duplicate/invalid file warnings using existing warning patterns.
   - Ensure `GetControllerRuntimes(...)` can return all folder controllers for a browser owner.

3. Update `ControllerControl` for browser-hosted usage.
   - Add nullable `EditorViewModel` property.
   - Do not assume `TopLevel.DataContext` is `MainWindowViewModel`.
   - Detect a temporary browser owner, e.g. `ControllersBrowser`.
   - For browser owner, add/edit/delete against `Controllers/*.yaml`.
   - Do not let an empty temporary browser item release or recreate folder runtimes.
   - Ensure opening and closing the browser does not stop running controllers.

4. Make Add/Edit/Delete robust in browser mode.
   - `Add` and `Edit` must open even if `TopLevel.DataContext` is the browser window model.
   - `ControllerEditorDialogWindow.ShowAsync(...)` already accepts nullable `MainWindowViewModel`; use that.
   - Resolve row actions from `CommandParameter`, `Tag`, or `DataContext`.
   - Mark click events handled at the beginning of handlers.
   - Delete must remove the backing YAML file for file-backed rows.
   - Edit rename must save the new file and remove/rename the old file.

5. Add `ControllersBrowserDialogWindow`.
   - Reuse the fixed browser initialization pattern:
     - Embed `ControllerControl` with an `x:Name`.
     - Resolve the embedded control via `FindControl<ControllerControl>(...)`.
     - Set embedded control `DataContext` and `EditorViewModel` explicitly.
     - Avoid direct generated-field dereference in the window constructor.
   - Provide `ShowOrActivate(...)` and `UpdateFolderContext(...)`.
   - Use a temporary `FolderItemModel` named `ControllersBrowser`.

6. Add the browser entry to the right legend/browser area.
   - Admin-only.
   - Reuse the existing lower browser section.
   - Do not create a new side panel or canvas area.
   - Add open/activate handling in `src/HornetStudio/MainWindow.axaml.cs`.

7. Migrate the demo project.
   - Move existing `ControllerDefinitions` from `samples/HornetStudioDemo/Folders/main/Folder.yaml` into `samples/HornetStudioDemo/Folders/main/Controllers/*.yaml`.
   - Remove the placed `ControllerWidget` entry from `Folder.yaml`.
   - Do not keep duplicate demo definitions in both places.

8. Update focused tests and documentation.
   - Add/update tests for file codec load/save/delete/rename.
   - Add/update tests for file-backed runtime merge if current test shape supports it.
   - Update widget docs that currently describe `ControllerDefinitions` as stored on the folder item.

## Acceptance Criteria
- Opening the Controllers browser lists `Controllers/*.yaml` definitions for the selected folder.
- Opening the browser does not stop, release, or clear existing controller runtimes.
- Running controller state remains visible after browser open/close.
- `Add` creates a new YAML file and synchronizes runtime.
- `Edit` opens the editor, saves changes back to YAML, and handles rename by replacing/removing the old file.
- `Delete` removes the YAML file and releases only that controller runtime.
- Browser entry is Admin-only.
- `samples/HornetStudioDemo/Folders/main/Folder.yaml` no longer contains the migrated `ControllerWidget`/`ControllerDefinitions`.
- Demo controllers exist under `samples/HornetStudioDemo/Folders/main/Controllers/*.yaml`.

## Out of Scope
- Real external user project migration.
- Removing all legacy `ControllerDefinitions` persistence code.
- Reworking PID controller runtime behavior.
- Adding non-PID controller types.
- Redesigning the controller editor UI.

## Risks / Watchouts
- Controller runtimes are more stateful than signal definitions. Avoid releasing the entire folder runtime just because the temporary browser owner has no embedded `ControllerDefinitions`.
- Do not repeat the EnhancedSignals browser mistakes:
  - Do not assume `TopLevel.DataContext` is `MainWindowViewModel` in browser windows.
  - Do not let a temporary browser owner with empty `ControllerDefinitions` clear runtime state.
  - Do not rely only on `CommandParameter` for row actions.
  - Do not hard-require `MainWindowViewModel` just to open an editor dialog that accepts nullable view model.
  - Do not directly dereference generated `x:Name` fields in window constructors without a null-safe lookup.
- `ControllerRuntimeManager.ReleaseFolder(...)` must not be called for a folder that only lacks placed controller widgets but has file-backed controllers.
- Rename/edit behavior can recreate runtime; preserve existing setpoint/current values where existing runtime manager already supports it, and do not introduce extra resets.
- Demo migration must remove the legacy widget so broken file-backed loading is immediately visible.
