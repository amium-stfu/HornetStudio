# IMPLEMENTATION HANDOFF

## Goal
Move Enhanced Signal definitions from normal widget-owned `Folder.yaml` content toward folder-local resource files under `Signals/Enhanced/*.yaml`, managed through an Admin-only `Enhanced Signals` browser entry in the existing right sidebar Browser section. Keep old placed `EnhancedSignals` widgets and old `Folder.yaml` definitions loadable for compatibility.

## Scope
Included:
- Add folder-local Enhanced Signal file storage under `Folders/<folder>/Signals/Enhanced/*.yaml`.
- Define and implement a small file codec/provider for Enhanced Signal definitions using existing `ExtendedSignalDefinition` semantics.
- Add an Admin-only `Enhanced Signals` browser entry below `Browser` in the right sidebar, next to/under `Functions`.
- Reuse the existing `EnhancedSignalsControl` and `EnhancedSignalEditorDialogWindow` behavior where practical.
- Hide `EnhancedSignals` from new normal widget placement if the browser fully replaces the management surface.
- Preserve existing `ControlKind.EnhancedSignals` loading/rendering for old `Folder.yaml` files.
- Update runtime synchronization so folder-level file definitions participate without requiring a placed widget.
- Keep legacy definitions inside existing placed `EnhancedSignals` widgets readable and runnable.
- Update `samples/HornetStudioDemo/` so at least one Enhanced Signal is represented under `Folders/main/Signals/Enhanced/*.yaml`.
- Update widget/manual documentation to describe the browser and file-based ownership.

Not included:
- Extracting `CustomSignals`.
- Extracting Clients, Applications, Monitor rules, or Controller definitions.
- Renaming runtime registry paths such as `studio.<folder>.enhanced_signals.<name>`.
- Removing the legacy `EnhancedSignals` widget type.
- Building a generic registry framework for all future browser resources.
- Release/version changes.

## Starting Point
- `EnhancedSignalsControl` currently reads and writes `FolderItemModel.EnhancedSignalDefinitions`.
- `Folder.yaml` currently persists Enhanced Signal definitions in placed `EnhancedSignals` widget payloads.
- `MainWindowViewModel.SyncEnhancedSignals(...)` currently discovers definitions by scanning `page.Items.Where(item => item.IsEnhancedSignals)` and parsing each item's raw `EnhancedSignalDefinitions`.
- Runtime publishing uses `EnhancedSignalRuntimeManager.SyncDefinitions(...)` and `EnhancedSignalRuntime.BuildRegistryPath(...)`.
- Existing tests cover editor name validation and runtime path behavior.
- `samples/HornetStudioDemo/Folders/main/Signals/Enhanced/` already exists with `.gitkeep`.
- `samples/HornetStudioDemo/Folders/main/Folder.yaml` still contains an `EnhancedSignals` widget with `EnhancedSignals:` data.
- The desired file location is `Folders/<folder>/Signals/Enhanced/<signal-name>.yaml`.

## Tasks
1. Define the Enhanced Signal YAML file shape for one signal per file, based on `ExtendedSignalDefinitionDocument` fields and existing naming rules.
2. Add a folder-local codec/provider that can enumerate, load, validate, save, and delete files below `Signals/Enhanced/`.
3. Adapt runtime synchronization so it reads file-based Enhanced Signal definitions for the folder even when no `EnhancedSignals` widget is placed.
4. Preserve legacy widget-owned definitions by merging them into the same runtime sync input during transition.
5. Decide conflict precedence explicitly:
   - File-based definitions should be the preferred source for new definitions.
   - If a file and legacy widget define the same name, prefer the file and surface/log the duplicate as a warning where practical.
6. Add an `Enhanced Signals` browser entry under the existing Admin-only right sidebar `Browser` section.
7. Add an `Enhanced Signals Browser` window/dialog or browser host that reuses the existing list/editor UI with folder context.
8. If direct reuse of `EnhancedSignalsControl` is awkward because it assumes a placed `FolderItemModel`, extract only a small shared catalog/editor surface or use a temporary non-persisted browser item carefully.
9. Update add/edit/delete flows so new browser changes write `Signals/Enhanced/*.yaml`, not `Folder.yaml`.
10. Keep legacy placed widget edit behavior compatible; either keep it writing legacy definitions or route it to the file provider only if that is low-risk and clearly documented.
11. Remove/hide `EnhancedSignals` from the widget picker once the browser can manage definitions.
12. Migrate the demo project:
    - create at least one real YAML file under `samples/HornetStudioDemo/Folders/main/Signals/Enhanced/`
    - remove or reduce the demo's placed `EnhancedSignals` widget only if the new browser/runtime path is ready
    - keep the demo loadable
13. Update docs:
    - widget summary/help
    - picker description
    - manual/browser/resource guidance
    - demo README
14. Add focused tests for file codec, runtime sync without widget placement, legacy compatibility, duplicate precedence, and demo sample parsing.

9. Hide `EnhancedSignals` from new widget selection if browser management is complete.

## Technical Constraints
- Chat output must stay German; code, UI text, comments, XML documentation, file names, and technical identifiers must stay English.
- Do not add new dependencies.
- Use existing `ExtendedSignalDefinition`, `ExtendedSignalDefinitionCodec`, editor dialog, validation rules, and runtime manager patterns.
- Do not introduce a broad generic resource registry abstraction in this workitem.
- Preserve compatibility with existing `Folder.yaml` files containing placed `EnhancedSignals` widgets.
- User-visible errors and validation messages must be English.
- Keep Browser area Admin-only using the existing `IsAdminBrowserVisible` mechanism.
- Keep runtime execution independent from browser/window visibility.
- Do not commit runtime logs or generated files in `samples/HornetStudioDemo`.

## Acceptance Criteria
- Enhanced Signal definitions can be loaded from `Folders/<folder>/Signals/Enhanced/*.yaml`.
- At least one Enhanced Signal publishes at runtime without requiring a placed `EnhancedSignals` widget.
- Existing placed `EnhancedSignals` widgets still load and publish definitions.
- New browser-managed Enhanced Signal definitions are saved to `Signals/Enhanced/<name>.yaml`.
- Duplicate names between file and legacy widget definitions prefer the file definition and do not crash the runtime sync.
- The right sidebar Admin Browser includes `Enhanced Signals`.
- Non-Admin users do not see the `Enhanced Signals` browser entry.
- `EnhancedSignals` is no longer offered as a normal widget if the browser fully covers management.
- `samples/HornetStudioDemo` contains at least one real Enhanced Signal YAML file under `Folders/main/Signals/Enhanced/`.
- Documentation describes file ownership, browser workflow, and legacy compatibility.

## Out of Scope
- Full automatic migration command for every old project.
- Removing legacy widget rendering.
- Extracting CustomSignals.
- Reworking EnhancedSignal runtime filtering/adjustment logic.
- Changing registry path casing or semantics.
- Creating a generic Browser framework beyond the small entry/window needed here.

## Risks / Watchouts
- `EnhancedSignalsControl` currently assumes an owning `FolderItemModel` and writes raw definitions to that item; browser hosting must not accidentally persist a temporary item into `Folder.yaml`.
- Runtime manager persists updated definitions through a raw definitions getter/setter; this may need a file-backed setter strategy for updates triggered by runtime feedback.
- One-file-per-signal is cleaner for diffs, but existing codecs serialize lists. Avoid ad hoc YAML string manipulation; reuse structured conversion where possible.
- Existing demo `Folder.yaml` may contain multiple Enhanced Signal definitions. Do not remove legacy data until the file-backed path is verified.
- Hidden widget picker entry must not break deserialization or rendering of old folders.
- Source and write path picking must keep folder-relative resolution behavior.
- Empty `Signals/Enhanced/.gitkeep` should be removed if real signal files are added and the directory no longer needs it.

- The architectural goal is the same as Functions: `Folder.yaml` should primarily describe UI composition, while reusable folder resources live in dedicated files.

- Keep the first implementation intentionally narrow. Do not solve CustomSignals or Clients in the same pass.
