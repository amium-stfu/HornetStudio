# DEBUG REPORT

## Problem
Opening the Admin Browser -> Enhanced Signals window initially cleared the file-backed enhanced signal runtime. After that was fixed, the browser actions `Add`, `Edit`, and likely `Delete` did not open their dialogs. A later fix caused a `TargetInvocationException` with an inner `NullReferenceException` while opening the browser.

## Expected Behavior
Opening the browser should list the folder-local `Signals/Enhanced/*.yaml` definitions, must not clear or replace the folder runtime with an empty definition set, and row actions should open the edit or delete workflows for the selected definition.

## Actual Behavior
The signal is visible after application start and the YAML file exists. The browser listed it correctly, but clicking `Add` or `Edit` did not open a dialog. After directly referencing the named browser control field, the browser failed during construction.

## Error Messages / Logs
The browser open failure surfaced as `System.Reflection.TargetInvocationException` with an inner `System.NullReferenceException`. The direct generated-field access to `EnhancedSignalsBrowserControl` could be null after XAML loading in this window path.

## Relevant Code
- `src/HornetStudio.Editor/Widgets/EnhancedSignals/EnhancedSignalsControl.axaml.cs`
- `src/HornetStudio.Editor/Widgets/EnhancedSignals/EnhancedSignalsBrowserDialogWindow.axaml`
- `src/HornetStudio.Editor/Widgets/EnhancedSignals/EnhancedSignalsBrowserDialogWindow.axaml.cs`
- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs`

## Attempted Fixes
- Fix 1 -> Added an explicit `EditorViewModel` property to `EnhancedSignalsControl`, bound it from `EnhancedSignalsBrowserDialogWindow`, and made `GetEnhancedSignalRuntimes(...)` return all folder runtimes for the non-persisted browser owner. Result: `dotnet build src/HornetStudio/HornetStudio.csproj --no-restore` succeeds with 0 warnings and 0 errors.
- Fix 2 -> Guarded `EnhancedSignalsControl.RebuildRuntimes()` so browser-hosted controls never use the legacy empty-widget fallback when `EditorViewModel` has not been bound yet. Added rebuild on `EditorViewModel` property changes and a file-backed browser fallback. Result: `dotnet build src/HornetStudio/HornetStudio.csproj --no-restore` succeeds with 0 warnings and 0 errors.
- Fix 3 -> Replaced the row-action handlers' direct `Button.CommandParameter` pattern match with a shared `TryResolveSignalRow(...)` helper that accepts either the command parameter or the button data context. `Edit` and `Delete` now use the same row-resolution path. Result: `dotnet build src/HornetStudio/HornetStudio.csproj --no-restore` succeeds with 0 warnings and 0 errors.
- Fix 4 -> Removed the unnecessary `MainWindowViewModel` hard guard from `Add` and `Edit`, because the enhanced signal editor supports a nullable view model and the browser can save file-backed definitions without it. Set the embedded browser control's `DataContext` and `EditorViewModel` directly from `EnhancedSignalsBrowserDialogWindow` code-behind instead of relying on XAML binding timing. Added `Tag` row fallback to the shared row resolver. Result: `dotnet build src/HornetStudio/HornetStudio.csproj --no-restore` succeeds with 0 warnings and 0 errors.
- Fix 5 -> Replaced direct generated-field access with `FindControl<EnhancedSignalsControl>("EnhancedSignalsBrowserControl")` and a descriptive exception if the XAML name cannot be resolved. The browser control context is attached after setting the window `DataContext`. Result: `dotnet build src/HornetStudio/HornetStudio.csproj --no-restore` succeeds with 0 warnings and 0 errors.

## Current Hypothesis
- The browser window's `TopLevel.DataContext` is the browser window model, not `MainWindowViewModel`.
- Before the fix, `EnhancedSignalsControl.ViewModel` was `null` in the browser.
- The control therefore used the fallback `EnhancedSignalRuntimeManager.SyncDefinitions(...)` call with the temporary browser item's empty `EnhancedSignalDefinitions`.
- That empty sync replaced/released the folder runtime and produced an empty browser list.
- The first fix still allowed an early attach/build pass before the binding had set `EditorViewModel`, so the same empty fallback could still run once.
- The `Edit` and `Delete` buttons shared a fragile row-resolution guard. If `CommandParameter` was not populated in the browser template, the handler returned silently before opening the dialog or confirmation.
- Since `Add` also did not open, the remaining failure was not only row resolution. The browser-hosted control needed a direct context assignment and should not require `MainWindowViewModel` just to open the file-backed editor dialog.
- Direct generated-field access for `x:Name` was not reliable in the browser window constructor. Resolving through the Avalonia name scope avoids the null field access and gives a clear diagnostic if the XAML name changes.
