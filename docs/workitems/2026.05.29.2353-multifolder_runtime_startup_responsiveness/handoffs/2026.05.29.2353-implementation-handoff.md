# IMPLEMENTATION HANDOFF

## Goal
Improve UI responsiveness during multi-folder runtime startup and UDL client connection. Three or more folder runtimes may start/connect in parallel, but runtime initialization, registry item registration, and UI-visible status propagation must not block the Avalonia UI thread long enough to cause multi-second freezes.

## Scope
Included:
- Add focused diagnostics around multi-folder runtime startup, UDL client connect, runtime item registration, enhanced signal source resolution, monitor registration, and UI-thread scheduling during startup.
- Identify which startup phase causes the large UI responsiveness spike seen in the 3-folder benchmark.
- Move or batch non-UI startup work off the UI thread where feasible.
- Coalesce/batch registry/status updates that are produced during connect/startup.
- Preserve the requirement that all folder runtimes can run simultaneously.
- Preserve browser visibility/activity gating from the previous work.

Explicitly not included:
- Pausing hidden folder runtimes.
- Browser UI rebuild optimization beyond preserving existing gates.
- Settings/dialog profiling or optimization.
- Reworking the complete runtime architecture.
- New external dependencies.
- Release/versioning work.

## Starting Point
- Browser refresh gating improved the 3-folder run:
  - browser operation timings dropped to only `MonitorViewControl[main*].RebuildRows`
  - per-instance diagnostics now exist
  - `BrowserDispatcherPosts=0` remains true
- The 3-folder benchmark still fails:
  - `Status="Fail"`
  - `MaxUiDelayMs=11900.4`
  - `P95UiDelayMs=91`
  - `Spike50Ms=79`
  - `Spike100Ms=33`
  - `Spike250Ms=8`
  - `ChartRenderCount=889`
  - `ChartRenderMaxMs=43.2`
  - `ChartRenderP95Ms=9.9`
- The largest spike appears immediately after starting/connecting three UDL clients/folder runtimes:
  - `main1` connect starts around `23:49:47.877`
  - `main2` connect starts around `23:49:50.580`
  - `main3` connect starts around `23:49:51.327`
  - `UI responsiveness spike DelayMs=11900.4` at `23:49:52.237`
- Current logs do not yet identify whether the freeze is caused by UDL connect, registry registration, source resolution, monitor registration, runtime scope startup, or UI status propagation.

## Tasks
1. Add phase-level diagnostics for runtime startup/connect:
   - folder runtime startup begin/end
   - UDL connect begin/end per folder/client
   - simulated host client/module creation
   - runtime items update
   - runtime root module update
   - attach option registration
   - primary runtime registry item registration
   - enhanced signal source availability/resolution
   - monitor registry update
2. Include thread and UI context information in these diagnostics:
   - elapsed milliseconds
   - folder/client id
   - item count
   - whether the phase ran on the UI thread if this can be detected cheaply
3. Add registry burst diagnostics during startup:
   - count registry writes per folder and top prefixes during the startup window
   - optionally count status writes separately from runtime item writes
4. Inspect `UdlClientControl` connect/startup flow for synchronous work on the UI thread.
5. Inspect runtime scope startup and folder runtime activation flow for synchronous loops that touch UI controls or dispatch repeatedly.
6. Inspect registry add/update APIs used during startup for lock contention, synchronous event fan-out, or UI-thread event handlers.
7. Based on the diagnostics, implement the narrowest fix:
   - move non-UI work to background async paths
   - batch registry item additions where appropriate
   - coalesce startup status updates
   - yield between large startup chunks if they must remain on the UI thread
   - stagger UI-visible startup refreshes without delaying runtime execution
8. Preserve all current runtime behavior:
   - all folders still start
   - PID/controllers still run
   - enhanced signals still resolve sources
   - monitor rules still evaluate
   - UDL clients still publish runtime items
9. Update benchmark acceptance notes so startup responsiveness is measured separately from steady-state runtime responsiveness.
10. Add focused tests for any new batching/coalescing helper logic where feasible.

## Implementation Order
1. Instrument first, do not guess:
   - Add low-overhead phase timing around the suspected startup/connect phases.
   - Ensure timings are emitted only when UI diagnostics are enabled or when existing benchmark diagnostics are enabled.
2. Run or ask for the same 3-folder benchmark log:
   - identify the dominant phase(s) around the `11900 ms` spike.
3. Fix the dominant phase:
   - if UDL connect blocks UI: make connect path asynchronous/non-blocking.
   - if registry writes fan out synchronously: batch/coalesce startup writes or defer non-visible UI reactions.
   - if source resolution scans too much on UI thread: cache, move off-thread, or split into chunks.
   - if monitor/runtime startup refreshes UI: preserve runtime registration and defer only UI-visible refresh.
4. Re-run 3-folder benchmark.
5. Iterate once on the next largest phase if the first fix only partly improves the run.
6. Update docs/tests only for actual behavior or diagnostic-output changes.

## Technical Constraints
- Runtime must remain active for all folders.
- Hidden UI browser controls must remain gated as planned in `2026.05.29.2329-visible_browser_refresh_scope`.
- Do not move Avalonia UI object access off the UI thread.
- Do not introduce `.Result` or `.Wait()`.
- Use `async`/`await` correctly.
- Registry event filtering must still happen before UI work is scheduled.
- No new dependencies.
- Public classes and public methods must have XML documentation.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Chat responses remain German.

## Acceptance Criteria
- 3-folder benchmark reports phase timings that make the startup bottleneck attributable to concrete code paths.
- After fixes, 3-folder startup no longer causes a multi-second UI-thread freeze comparable to `11900 ms`.
- `BrowserDispatcherPosts=0` remains true.
- Browser rebuild counts remain low and per-instance.
- All three folder runtimes/UDL clients still start and publish required runtime/status items.
- Steady-state `P95UiDelayMs` passes benchmark soft budgets or is close to the single-folder PID baseline.
- Chart render count recovers materially from `889` toward the single-folder/PID baseline.
- Chart render P95 does not regress.
- No hidden folder runtime is paused as a workaround.

## Out of Scope
- Settings/dialog timing fixes.
- Runtime semantic changes.
- Full registry architecture replacement.
- UI design changes.
- Release/version changes.

## Risks / Watchouts
- The biggest spike may be caused by synchronous event fan-out rather than the visible connect method itself; instrument the call chain before changing behavior.
- Batching registry writes can change event timing. Preserve final state and avoid dropping required notifications.
- Moving work off the UI thread must not access Avalonia controls or observable collections directly.
- Staggering UI status propagation is acceptable; delaying runtime execution is not.
- Some startup work may be intentionally serialized. Do not parallelize shared mutable runtime state without understanding locking and ownership.
- The benchmark currently includes startup and steady-state in one run; report both when possible so improvements are not hidden by startup-only spikes.
