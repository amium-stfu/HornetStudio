# IMPLEMENTATION HANDOFF

## Goal
Isolate and explain the first-seconds update delays after starting UDL/Signal updates, then propose the smallest targeted fix. The main suspicion is a startup/warmup burst in the HostRegistry-to-`PageItemModel` refresh path, with `SignalFallbackRegistryPathUsed` as an important diagnostic signal but not yet proven as the root cause.

## Scope
- Diagnose startup/warmup delays in the 20 UDL Signal widget benchmark scenario.
- Separate warmup behavior from steady-state behavior.
- Trace why `SignalFallbackRegistryPathUsed` remains high and whether it represents real fallback rendering or repeated getter-time diagnostics.
- Focus on `PageItemModel` target resolution/refresh, HostRegistry effective reference resolution, and UDL attachment projection startup bursts.
- Produce a narrowly scoped fix only after measurement identifies the first expensive stage.

Explicitly not included:

- No broad widget framework redesign.
- No new global HostRegistry architecture.
- No new Signal-specific runtime fastpath unless measurement proves the generic path is wrong.
- No chart-specific optimization unless the benchmark shows chart work contributes to the warmup delay.
- No release/versioning work.

## Starting Point
- The current UDL HostRegistry reference model is functionally implemented: HostRegistry owns effective public read resolution and public UDL paths remain stable.
- Recent benchmark notes show startup/warmup delays can be multi-second while steady-state may later run acceptably.
- `SignalFallbackRegistryPathUsed` has appeared at very high rates in benchmark summaries.
- Prior startup experiment that simply routed initial `ResolveTarget()` refreshes through `RequestTargetRefresh()` made the benchmark worse and was reverted.
- `docs/workitems/ChatHandoff.md` currently recommends inspecting startup/warmup UI cost and not reopening steady-state value-refresh coalescing unless fresh measurements show a steady-state regression.

## Tasks
1. Run a fresh benchmark against `benchmarks/ui_lag_bench_project/project.aaep` and capture phase-separated warmup versus steady-state numbers.
2. Inspect whether the first visible slowdown correlates with `TargetRefreshExecuted[Warmup->Warmup]`, `TargetValueRefreshExecuted[Warmup->Warmup]`, `SignalFallbackRegistryPathUsed`, registry publication bursts, or projection attach/snapshot bursts.
3. Trace every `SignalFallbackRegistryPathUsed` emission in `PageItemModel.ResolveTargetProperty(...)` and classify the reason for fallback:
   - effective public reference missing,
   - target not yet resolved,
   - selected property missing,
   - compatibility `valueRef` fallback path,
   - repeated display getter calls against an otherwise valid target.
4. Add bounded diagnostics only where existing counters cannot distinguish warmup causes; avoid high-frequency irrelevant-event diagnostics.
5. Determine whether startup work is caused by broad target refreshes, repeated `ResolveTarget()` calls, projection snapshots, effective reference resolution, or Avalonia binding/layout invalidation.
6. Propose and implement the narrowest fix only for the measured hot path.
7. Re-run focused tests/build plus a benchmark comparison.
8. Update `docs/workitems/ChatHandoff.md` with cause, fix, validation, and remaining risk.

## Implementation Order
1. Start with measurement, not code changes.
2. Compare warmup and steady-state counters from the latest benchmark:
   - `DemoGenerate`
   - `RegistryPublish`
   - `SignalReceive`
   - `SignalFallbackRegistryPathUsed`
   - `SignalValueRefResolved`
   - `TargetRefreshExecuted[Warmup->Warmup]`
   - `TargetValueRefreshExecuted[Warmup->Warmup]`
   - `TargetRefreshExecuted[SteadyState->SteadyState]`
   - `TargetValueRefreshExecuted[SteadyState->SteadyState]`
   - `BrowserDispatcherPosts`
   - `ChartRenderCount`
3. If `SignalFallbackRegistryPathUsed` is high only in warmup, trace startup target/projection ordering before changing steady-state logic.
4. If `SignalFallbackRegistryPathUsed` remains high in steady-state, inspect `PageItemModel.ResolveTargetProperty(...)` and HostRegistry effective item resolution first.
5. Add minimal classified diagnostics if the existing counters cannot explain the path.
6. Apply a focused fix to the first measured bottleneck.
7. Run focused tests and build.
8. Run a 60s benchmark and compare warmup delay and steady-state throughput.

## Technical Constraints
- Chat responses are German; code, comments, XML docs, UI text, file names, and technical identifiers are English.
- No new dependencies.
- Do not add noisy per-event logging.
- Registry event filtering must happen before UI dispatcher work is scheduled.
- Unknown or unrelated registry/runtime events must not enqueue UI work.
- Runtime remains source of truth for UDL live values.
- Widgets should continue to consume public HostRegistry paths.
- Do not bypass existing public writeback behavior.

## Acceptance Criteria
- The first-seconds delay has a documented root cause with phase-separated measurements.
- `SignalFallbackRegistryPathUsed` is classified as either real fallback rendering or diagnostic/getter noise.
- Warmup `TargetRefreshExecuted` / `TargetValueRefreshExecuted` delay is reduced or a concrete blocker is documented.
- Steady-state throughput and latency do not regress materially.
- `BrowserDispatcherPosts=0` and `ChartRenderCount=0` remain true for the no-chart benchmark scenario unless the benchmark project intentionally includes chart work.
- Any added diagnostics are bounded and do not create a new hot-path regression.

## Out of Scope
- General chart optimization.
- Replacing the HostRegistry reference-backed architecture.
- Reworking all widget target resolution.
- Changing UDL module semantics.
- Release/versioning work.

## Risks / Watchouts
- `SignalFallbackRegistryPathUsed` may be a misleading counter if emitted from frequently evaluated display getters.
- Coalescing initial refreshes blindly already made a prior run worse; do not repeat that without new evidence.
- Warmup delays may be caused by ordering between projection, registry reference registration, and widget target resolution rather than by steady-state update delivery.
- Broad diagnostics for irrelevant registry events can create the regression being measured.
- Fixes that reduce warmup work must not drop required initial target binding updates.
