# IMPLEMENTATION HANDOFF

## Goal
Reduce the remaining warmup full-refresh backlog and sporadic short stalls after the successful target availability gate. The latest benchmark shows value refresh and steady-state delivery are healthy, but too many broad `TargetRefreshExecuted[Warmup->Warmup]` callbacks still run after targets become available.

## Scope
- Focus on warmup full-refresh deduplication, full-refresh source attribution, and stale refresh cancellation.
- Preserve the existing target availability gate and reference-backed HostRegistry UDL attachment behavior.
- Keep steady-state value-only refresh behavior intact.
- Classify sporadic short stalls by refresh reason/source before changing unrelated paths.
- Implement a narrow fix in `PageItemModel` unless attribution proves projection or HostRegistry notification churn is the source.

Explicitly not included:

- No broad rewrite of `PageItemModel`.
- No new runtime or Signal-specific fastpath.
- No replacement of reference-backed HostRegistry attachments.
- No chart optimization unless benchmark attribution points to chart-triggered work.
- No release/versioning work.

## Starting Point
- Latest benchmark: `StartupTargetAvailabilityGate-60s`.
- Improvements:
  - `P95UiDelayMs`: `11.2` -> `9.9`.
  - `SignalTargetUnresolved`: `378` -> `254`.
  - `TargetValueRefreshExecuted[Warmup->Warmup]` P95: `4316.8 ms` -> `274.6 ms`.
  - `TargetValueRefreshExecuted[SteadyState->SteadyState]` P95: `5.5 ms` -> `1.3 ms`.
- Remaining issue:
  - `TargetRefreshExecuted[Warmup->Warmup]` P95 improved from `4971.6 ms` to `3277.8 ms`, but is still too high.
  - `TargetRefreshExecuted[Warmup->Warmup]` count increased from `164` to `524`.
  - Startup feels better but still not good, with small sporadic stalls.
- Interpretation:
  - The unresolved target wait/retry phase is no longer the main bottleneck.
  - After the first successful availability transition, too many broad warmup full refreshes are still queued or executed.

## Tasks
1. Confirm the latest benchmark numbers and append them to `docs/workitems/ChatHandoff.md` as the new baseline.
2. Attribute every warmup `TargetRefreshExecuted` to a scheduling reason:
   - initial target resolve,
   - unresolved target became available,
   - pending unresolved retry,
   - registry structure event,
   - snapshot upsert,
   - ancestor event,
   - visual rule affected,
   - manual/selection refresh,
   - fallback/unknown.
3. Add bounded counters for stale/dropped/coalesced full refreshes if not already present.
4. Inspect whether old pending full-refresh callbacks from an earlier unresolved or pre-availability generation still execute after the target is resolved.
5. Introduce a target binding generation concept if attribution shows stale callbacks:
   - increment when target availability/resolution state changes,
   - capture generation when scheduling a broad refresh,
   - drop or downgrade stale broad refresh callbacks when a newer generation has already completed the required full binding refresh.
6. Deduplicate warmup broad refresh scheduling per Signal target:
   - if a broad refresh is already pending for the same target/generation, coalesce instead of scheduling another,
   - after the first successful full refresh, route value/property updates to value-only refresh where possible.
7. If attribution shows duplicate projection/registry structural events are the source, fix batching or event emission there instead of adding widget-side suppression.
8. Add focused tests for missing target -> target becomes available -> exactly one required broad refresh plus value-only follow-up behavior.
9. Build, benchmark, and update the handoff notes.

## Technical Constraints
- Chat responses are German; code, comments, XML docs, UI text, file names, and technical identifiers are English.
- No new dependencies.
- Avoid noisy per-event logging.
- Registry event filtering must happen before dispatcher scheduling.
- Unknown or unrelated registry/runtime events must not enqueue UI work.

- Widgets continue consuming public HostRegistry paths.
- Public writeback must not be bypassed.
- Do not suppress the first required successful full refresh after target availability.

## Acceptance Criteria
- Warmup full-refresh scheduling sources are classified.
- Duplicate broad warmup refreshes for the same Signal target/generation are reduced.
- Stale pre-availability callbacks no longer execute broad refresh work after a newer successful target binding refresh has completed.
- `TargetRefreshExecuted[Warmup->Warmup]` count and/or P95 improves materially from `524` and `3277.8 ms`.
- `TargetValueRefreshExecuted[SteadyState->SteadyState]` remains healthy, near the latest `P95=1.3 ms` range.
- `TargetValueRefreshExecuted[Warmup->Warmup]` does not regress materially from `P95=274.6 ms`.
- Sporadic stalls are attributed or shown as not reproduced in the verification run.

## Risks / Watchouts
- Dropping stale callbacks must not skip the first full binding refresh needed for correct initial visual state.
- Snapshot/ancestor events can represent real structure changes; dedupe must distinguish structure refresh from value-only changes.
- Pending full-refresh state must be scoped per widget/target, not global.
- Broad diagnostics can create the hot path being measured; keep attribution bounded and aggregate.
- If projection/registry is the true duplicate source, widget-side suppression can hide symptoms while leaving startup event churn.
