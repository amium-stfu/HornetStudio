# IMPLEMENTATION HANDOFF

## Goal
Reduce the remaining startup/warmup delay and sporadic short update stalls by fixing startup ordering around unresolved Signal targets. The latest benchmark shows steady-state value refresh is healthy, while warmup target refreshes still sit in the multi-second range and the remaining focus is `SignalTargetUnresolved`.

## Scope
- Focus on startup target availability and unresolved Signal target retry behavior.
- Treat steady-state value delivery as healthy unless a new comparable benchmark proves otherwise.
- Preserve reference-backed HostRegistry UDL attachments and public widget target paths.
- Prevent repeated expensive full refresh work for the same missing UDL public target during warmup.
- Classify sporadic post-start stalls by event source and refresh type.

Explicitly not included:

- No broad rewrite of `PageItemModel`.
- No replacement of HostRegistry reference-backed attachments.
- No Signal-specific runtime value fastpath.
- No chart-specific work unless a comparable benchmark shows chart-triggered stalls.
- No release/versioning work.

## Starting Point
- Benchmark: `StartupWarmupSignalFallback-Fix-60s`.
- Improvements:
  - `P95UiDelayMs`: `35.6` -> `11.2`.
  - `TargetRefreshExecuted[Warmup->Warmup]`: `274 / P95=5289.8 ms` -> `164 / P95=4971.6 ms`.
  - `TargetValueRefreshExecuted[SteadyState->SteadyState]`: `P95=22.2 ms` -> `P95=5.5 ms`.
  - `TargetRefreshCoalesced`: `869` hits.
- Remaining issue:
  - `TargetRefreshExecuted[Warmup->Warmup]` and `TargetValueRefreshExecuted[Warmup->Warmup]` remain multi-second.
  - User still observes poor start behavior and sporadic short stalls.
  - Current evidence points to startup ordering and `SignalTargetUnresolved`.
- Previous blind startup coalescing made a benchmark worse; any new coalescing must be target-availability aware and must not drop the required first successful target binding.

## Tasks
1. Confirm the latest benchmark numbers and record them in `docs/workitems/ChatHandoff.md` as the new baseline.
2. Trace `SignalTargetUnresolved` in warmup:
   - count per target path,
   - first unresolved timestamp,
   - first successful resolve timestamp,
   - number of full refreshes scheduled before first successful resolve,
   - registry/projection event that finally made the target available.
3. Identify whether unresolved targets originate from:
   - widgets resolving before UDL public attachment projection,
   - public snapshot/reference registration arriving in multiple bursts,
   - target path normalization/candidate mismatch,
   - registry event ordering,
   - temporary projection rebuild/dispose windows.
4. Design a target availability gate for Signal targets:
   - unresolved target paths are recorded cheaply,
   - repeated unresolved refreshes for the same target are coalesced,
   - no broad UI refresh is scheduled for unrelated registry events,
   - exactly one full resolve/refresh runs when the relevant target path or ancestor appears.
5. Add bounded diagnostics for sporadic stalls after warmup:
   - refresh kind,
   - source event path,
   - target path,
   - phase,
   - queue delay,
   - whether the target was unresolved, newly resolved, or already stable.
6. Implement the smallest fix in the measured layer:
   - `PageItemModel` unresolved retry control if widgets repeatedly refresh missing targets,
   - UDL projection ready/batch notification if projection creates repeated target availability churn,
   - HostRegistry event normalization fix if target availability events do not match configured Signal paths.
7. Run focused tests and benchmark.
8. Update `docs/workitems/ChatHandoff.md` with cause, fix, validation, and any remaining spike evidence.

## Implementation Order

   - `ResolveTarget()`,
   - `OnDataRegistryChanged(...)`,
   - `QueueRegistryRefresh()`,
   - `RequestTargetRefresh()`,
   - `RequestTargetValueRefresh()`,
   - `TriggerTargetRefresh()`,
   - `RefreshTargetBindings()`.
3. Add minimal diagnostic classification if unresolved source and retry count are not already visible.
4. Re-run a short benchmark or focused scenario to confirm the source of unresolved retries.
5. Implement target-availability-aware unresolved retry control:
   - store pending unresolved target identity,
   - suppress repeated broad refreshes while unresolved,
   - listen only for relevant public target/ancestor availability events,
   - perform one resolve plus full refresh when the target becomes available.
6. If the source is projection churn instead, batch or stabilize projection notifications before changing widget logic.
7. Add focused tests around missing target -> relevant registry event -> single successful resolve.
8. Build and run benchmark comparison.

## Technical Constraints
- Chat responses are German; code, comments, XML docs, UI text, file names, and technical identifiers are English.
- No new dependencies.
- Do not add noisy per-event logging.
- Registry event filtering must happen before dispatcher scheduling.
- Unknown or unrelated registry/runtime events must not enqueue UI work.
- Runtime remains source of truth for UDL live values.
- Widgets keep using public HostRegistry paths.
- Public writeback must not be bypassed.
- Startup coalescing must not drop the first required successful target refresh.

## Acceptance Criteria
- `SignalTargetUnresolved` warmup cause is documented with affected paths and retry counts.
- Repeated broad refreshes for the same unresolved target are reduced or eliminated.
- The first successful target resolve still updates the widget correctly.
- Warmup `TargetRefreshExecuted[Warmup->Warmup]` and/or `TargetValueRefreshExecuted[Warmup->Warmup]` P95 improves materially from the current multi-second baseline, or a concrete external blocker is documented.
- Steady-state `TargetValueRefreshExecuted[SteadyState->SteadyState]` remains healthy, near the current `P95=5.5 ms` range.
- Sporadic post-start stalls are attributed to a source or shown not reproduced in the verification run.
- `BrowserDispatcherPosts=0` remains true for the benchmark scenario.

## Out of Scope
- General chart optimization.
- General widget target-resolution redesign.
- Removing reference-backed HostRegistry attachments.
- UDL module semantic changes.
- Release/versioning work.

## Risks / Watchouts
- Suppressing unresolved refreshes too aggressively can leave a widget visually stale if the final availability event is missed.
- Public target paths may appear via ancestor snapshot events rather than exact target events; availability matching must include relevant ancestor/descendant checks.
- Projection rebuild/dispose windows can briefly remove targets; retry control must distinguish temporary missing targets from real invalid configuration.
- Warmup queue delay may be caused by work scheduled before benchmark steady-state, so verify phase-specific metrics.
- Broad diagnostics for every unresolved or irrelevant event can create a new hot path.
