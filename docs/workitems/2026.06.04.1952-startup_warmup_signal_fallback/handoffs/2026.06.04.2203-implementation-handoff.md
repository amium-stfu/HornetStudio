# IMPLEMENTATION HANDOFF

## Goal
Add cheap, spike-centered diagnostics for the remaining startup warmup stalls so the next benchmark run can correlate each sporadic UI delay spike with the active refresh backlog, unresolved-target state, and dominant module/source without adding measurable hot-path overhead.

## Scope
- Focus on bounded diagnostics and benchmark interpretation for startup/warmup spikes.
- Reuse the current `StartupTargetAvailabilityGate-60s` baseline and keep the existing target-availability gate behavior unchanged.
- Prefer sampling only on rare events such as a detected UI spike, warmup-to-steady-state transition, or unusually large refresh bursts.

Explicitly not included:

- No new broad refresh reason attribution on every `PageItemModel` refresh request.
- No new warmup dedupe or stale-callback suppression logic in this step.
- No projection/runtime architecture changes unless required only to expose a cheap bounded counter.
- No release/versioning work.

## Starting Point
- Current best baseline is documented in `docs/workitems/ChatHandoff.md` as `StartupTargetAvailabilityGate-60s`:
  - `Status=Pass`
  - `P95UiDelayMs=9.9`
  - `MaxUiDelayMs=3516.7`
  - `SignalTargetUnresolved=254`
  - `TargetRefreshExecuted[Warmup->Warmup]=524`, `P95=3277.8 ms`
  - `TargetValueRefreshExecuted[Warmup->Warmup] P95=274.6 ms`
  - `TargetValueRefreshExecuted[SteadyState->SteadyState] P95=1.3 ms`
- The latest attempted hot-path attribution experiment regressed materially and was rolled back:
  - scenario family `StartupTargetAvailabilityGate-60s-ReasonAttribution-*`
  - example `...-Retry5`: `P95UiDelayMs=79.9`, `TargetValueRefreshExecuted[SteadyState->SteadyState] P95=101.6 ms`
- Working assumption: the benchmark already shows the symptom, but it still does not correlate a spike to the local backlog shape cheaply enough to pick the next safe fix.

## Tasks
1. Confirm the current baseline numbers from `docs/workitems/ChatHandoff.md` and use them as the comparison target for this diagnostic-only step.
2. Extend `UiResponsivenessDiagnostics` with a bounded spike snapshot facility that records only on rare events:
   - a detected `UI responsiveness spike`,
   - warmup-to-steady-state transition,
   - optionally a clearly abnormal refresh burst if one already has a cheap signal.
3. For each snapshot, capture a compact correlation payload such as:
   - current phase,
   - broad/value refresh executed counts by phase pair,
   - unresolved-target counters,
   - coalesced refresh counters,
   - active top module/source summary if already available cheaply,
   - any existing queue/backlog counters that can be read without touching Avalonia objects from background threads.
4. If the required counters are not already exposed, add the smallest possible bounded counters at the source of truth, but avoid per-event string attribution or extra dispatcher work in `PageItemModel`.
5. Emit the snapshot into the benchmark-visible diagnostics/log output in a form that makes it easy to line up a spike with the surrounding refresh activity.
6. Run build plus the 60-second benchmark and append the new observations to `docs/workitems/ChatHandoff.md`, explicitly stating whether the captured spikes correlate with warmup broad refresh bursts, unresolved retries, or neither.

## Technical Constraints
- Chat responses remain German; code, comments, XML docs, UI text, file names, and technical identifiers remain English.
- No new dependencies.
- Keep diagnostics bounded and rare-event-driven.
- Diagnostics on background/runtime threads must not read Avalonia UI objects directly.
- Do not add broad per-event strings, per-refresh allocations, or extra dispatcher posts in the measured hot path.
- Preserve existing target-availability gate and value-only refresh behavior.

## Acceptance Criteria
- Benchmark output can show at least one bounded correlation snapshot for a detected UI spike or a confirmed absence of spikes in the measured window.
- Each captured spike snapshot identifies enough context to distinguish between:
  - warmup broad refresh burst,
  - unresolved-target retry/availability activity,
  - steady-state value refresh pressure,
  - or an unrelated source.
- The diagnostic-only change does not materially regress the current baseline:
  - `P95UiDelayMs` should stay near the current `9.9` range,
  - `TargetValueRefreshExecuted[SteadyState->SteadyState]` should remain near the current low-millisecond baseline, not the regressed attribution numbers.
- `docs/workitems/ChatHandoff.md` states the observed correlation and recommends the next concrete fix direction.

## Out of Scope
- Warmup dedupe implementation.
- Target generation/stale-callback cancellation.
- Projection batching redesign.
- General chart optimization.

## Risks / Watchouts
- Even bounded diagnostics can skew results if they allocate too much or run on every refresh; keep capture rate rare and payload compact.
- Snapshot collection must not read Avalonia-owned state from non-UI threads.
- If no spikes reproduce in the run, the handoff update must still record that outcome and recommend the next step based on the absence of reproduced spikes.
- Avoid turning the snapshot format into a second large log stream; it should stay benchmark-oriented and easy to diff between runs.
