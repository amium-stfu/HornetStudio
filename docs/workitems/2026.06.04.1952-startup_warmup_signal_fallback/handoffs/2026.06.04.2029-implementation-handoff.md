# IMPLEMENTATION HANDOFF

## Goal
Reduce the remaining first-seconds UDL/Signal update delay and classify the short intermittent delays observed after startup. The latest benchmark evidence shows the old `SignalFallbackRegistryPathUsed` counter was misleading: effective public HostRegistry resolution is used heavily, true invalid-reference fallback is rare, and the real remaining problem is the warmup refresh backlog.

## Scope
- Focus on warmup/startup refresh backlog in the UDL 20 Signal widget benchmark scenario.
- Treat `SignalFallbackRegistryPathUsed` as reclassified/mostly resolved unless new measurements contradict this.
- Investigate intermittent post-start spikes separately from the initial warmup backlog.
- Preserve the reference-backed HostRegistry architecture and normal public-path widget consumption.
- Add only bounded diagnostics needed to attribute warmup and spike causes.
- Implement the smallest fix once the measured source of warmup or spike work is identified.

Explicitly not included:

- No broad Signal widget rewrite.
- No replacement of HostRegistry reference-backed UDL attachments.
- No new runtime fastpath bypassing public writeback.
- No chart work unless the benchmark proves chart-related spikes.
- No release/versioning work.

## Starting Point
- Latest reported run: `StartupWarmupSignalFallback-60s-ReclassifiedLock`.
- The run was comparable and did not reproduce the previous `ObjectDisposedException` chain.
- New diagnostic split:
  - `SignalEffectiveTargetPropertyUsed`: about `1442/s`.
  - Real invalid-reference fallback: about `1.75/s`.
- Interpretation: the old fallback counter mostly represented effective/normal display resolution or diagnostic noise, not real invalid-reference fallback.
- Remaining problem:
  - `TargetRefreshExecuted[Warmup->Warmup]` P95 about `5289.8 ms`.
  - `TargetValueRefreshExecuted[Warmup->Warmup]` P95 about `4637 ms`.
  - `TargetValueRefreshExecuted[SteadyState->SteadyState]` P95 about `22.2 ms`.
- User observed startup is a bit better but not good, and short delays can still occur in between.

## Tasks
1. Confirm the latest benchmark summary and capture the phase-separated numbers in `docs/workitems/ChatHandoff.md`.
2. Stop treating `SignalFallbackRegistryPathUsed` as the primary root-cause counter; keep only the reclassified diagnostics that distinguish effective target usage from real invalid-reference fallback.
3. Trace warmup `TargetRefreshExecuted[Warmup->Warmup]` and `TargetValueRefreshExecuted[Warmup->Warmup]` back to their scheduling sources.
4. Classify warmup refresh work by source:
   - initial `ResolveTarget()` calls,
   - `QueueRegistryRefresh()` calls,
   - broad `TriggerTargetRefresh()` calls,
   - value-only `RequestTargetValueRefresh()` calls,
   - UDL attachment projection snapshot/reference registration,
   - HostRegistry public-path notifications,
   - Avalonia binding/layout refresh after broad property invalidation.
5. Add bounded spike attribution for delays after warmup:
   - event phase,
   - changed path/module,
   - refresh kind,
   - scheduled source,
   - queue delay,
   - execution duration if already measured locally.
6. Identify whether warmup needs batching in projection/registry notification, refresh coalescing in `PageItemModel`, or ordering changes between projection and target resolution.
7. Implement the smallest targeted fix.
8. Run focused tests, solution build, and a 60s benchmark comparison.
9. Update `docs/workitems/ChatHandoff.md` with the root cause, fix, benchmark delta, and any remaining intermittent spike evidence.

- Warmup root cause is documented with phase-separated evidence.
- `SignalEffectiveTargetPropertyUsed` and true fallback counters remain clearly separated.
- Warmup `TargetRefreshExecuted[Warmup->Warmup]` and/or `TargetValueRefreshExecuted[Warmup->Warmup]` P95 improves materially, or a concrete external blocker is documented.
- Steady-state `TargetValueRefreshExecuted[SteadyState->SteadyState]` does not regress materially from the latest about `22.2 ms` P95 state.
- Short intermittent delays are either attributed to a specific event/source or explicitly shown as not reproduced in the verification run.
- `BrowserDispatcherPosts=0` and no-chart `ChartRenderCount=0` remain intact for the benchmark scenario.

## Risks / Watchouts
- Warmup queue delay can be caused by scheduled UI work before benchmark steady-state, not by slow execution of the measured method itself.
- Reclassifying diagnostics can make the system look healthier without fixing the warmup backlog; verify actual delay metrics.
- Blindly coalescing startup refreshes was previously tried and made the benchmark worse. Any coalescing must preserve required initial target binding updates.
- Broad diagnostics for irrelevant registry events can create the same performance issue being measured.
- Intermittent spikes may require event-source attribution beyond P95 summaries.
