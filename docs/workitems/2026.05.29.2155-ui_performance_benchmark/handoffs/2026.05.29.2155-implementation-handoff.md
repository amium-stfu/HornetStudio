# IMPLEMENTATION HANDOFF

## Goal
Create a small, repeatable UI performance benchmark layer that uses the existing responsiveness diagnostics to summarize UI latency, browser registry pressure, Dispatcher work, chart render cost, and selected dialog/settings startup costs.

## Scope
Included:
- Add an opt-in UI benchmark mode.
- Reuse `UiResponsivenessDiagnostics` as the metric source where possible.
- Produce compact benchmark summaries in the host log.
- Add a VS Code launch configuration for benchmark runs.
- Start with manual/reproducible scenarios, not full automation.
- Define initial soft budgets for regression tracking.

Explicitly NOT included:
- Do not optimize chart rendering in this workitem.
- Do not implement full UI automation.
- Do not make benchmark failures fail the build yet.
- Do not introduce new runtime dependencies.
- Do not add CI integration yet.

## Starting Point
- `UiResponsivenessDiagnostics` already logs:
  - UI thread latency spikes
  - browser registry event counts
  - accepted/ignored event counts
  - Dispatcher post counts
  - chart render timing scopes
  - dialog timing scopes
- Recent PID/browser-registry fixes reduced browser Dispatcher posts to `0` in the tested scenario.
- Remaining performance questions:
  - chart render cost can still exceed `25-50 ms`
  - dialog/settings opening can still freeze the UI briefly
  - startup has known multi-second UI stalls
  - future browser/client views need objective regression guards

## Tasks
1. Add benchmark mode configuration:
   - environment variable: `HORNETSTUDIO_UI_BENCHMARK=1`
   - optional command line switch: `--ui-benchmark`
   - benchmark mode should imply UI diagnostics enabled.
2. Extend `UiResponsivenessDiagnostics` or add a minimal adjacent helper to collect aggregate metrics:
   - total duration
   - max UI delay
   - p95 UI delay
   - spike counts over `50 ms`, `100 ms`, and `250 ms`
   - browser registry event totals by source
   - browser accepted/ignored totals by source
   - browser Dispatcher post totals by source
   - chart render count, max, and p95 by chart name
   - dialog/settings timing count, max, and p95 by operation/category
3. Add a timed benchmark session:
   - default duration: `60 s`
   - configurable duration if simple, for example `HORNETSTUDIO_UI_BENCHMARK_SECONDS`
   - log a summary when the session ends and on application shutdown.
4. Add initial scenario labels:
   - default label: `Manual`
   - allow environment variable `HORNETSTUDIO_UI_BENCHMARK_SCENARIO`
   - no automated scenario driving yet.
5. Add soft budgets to the summary:
   - `MaxUiDelayMs <= 250` after startup
   - `P95UiDelayMs <= 50`
   - `ChartRenderP95Ms <= 33`
   - `BrowserDispatcherPosts` should remain low for unrelated registry events
   - mark result as `Pass`, `Warn`, or `Fail` in the log, but do not fail the process.
6. Add a VS Code launch entry:
   - `.NET Launch (HornetStudio UI Benchmark)`
   - set `HORNETSTUDIO_UI_BENCHMARK=1`
   - set `HORNETSTUDIO_UI_DIAGNOSTICS=1`
7. Document the benchmark workflow in `src/HornetStudio/docs/manual/troubleshooting.md`.
8. Build the full solution.

## File-Level Changes
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> add aggregate metric collection and benchmark summary output, or delegate to a small adjacent helper.
- `src/HornetStudio/App.axaml.cs` -> initialize benchmark mode from startup arguments/environment and flush summary on shutdown.
- `src/HornetStudio/Program.cs` -> no change unless startup argument forwarding needs adjustment.
- `.vscode/launch.json` -> add a dedicated UI benchmark launch configuration.
- `src/HornetStudio/docs/manual/troubleshooting.md` -> document benchmark activation, scenarios, summary fields, and interpretation.

## Implementation Order
1. Inspect the existing diagnostics class and startup wiring.
2. Add benchmark enablement and ensure benchmark mode enables diagnostics.
3. Add in-memory aggregate metric structures with low overhead when disabled.
4. Feed existing spike/timing/browser diagnostic events into the aggregates.
5. Add summary logging on benchmark timer end and shutdown.
6. Add VS Code launch configuration.
7. Update troubleshooting documentation.
8. Build with `dotnet build HornetStudio.sln --no-restore`.
9. Run one manual benchmark scenario and confirm summary log lines are emitted.

## Technical Constraints
- Use existing `HostLogger`.
- Keep diagnostics disabled by default.
- Keep benchmark disabled by default.
- Avoid new dependencies.
- Avoid UI thread blocking.
- Avoid visual-tree traversal inside high-frequency paths.
- Do not turn benchmark into broad UI automation in this workitem.
- Code, comments, XML documentation, and user-visible messages must be English.
- Chat responses must be German.

## Acceptance Criteria
- Normal launch still has diagnostics and benchmark disabled by default.
- Diagnostics launch enables diagnostics only.
- Benchmark launch enables diagnostics and benchmark summary collection.
- Benchmark summary logs at least:
  - scenario
  - duration
  - max UI delay
  - p95 UI delay
  - spike counts over `50/100/250 ms`
  - browser totals by source
  - chart render max/p95 if chart rendered
  - result status
- The first benchmark run can be executed manually with the PID/chart scenario.
- Build succeeds with `0` errors.

## Verification
- Build: `dotnet build HornetStudio.sln --no-restore`
- Manual:
  - Start `.NET Launch (HornetStudio UI Benchmark)`.
  - Confirm log contains benchmark enabled/configured line.
  - Run a manual PID/chart scenario for at least the configured duration.
  - Confirm log contains `UI benchmark summary`.
  - Confirm browser Dispatcher post totals remain low after the registry-filter fix.

## Out of Scope
- Automated clicking/opening of UI windows.
- CI benchmark enforcement.
- Chart optimization.
- Settings/dialog optimization.
- Benchmark file export beyond normal host log.
- Release/versioning.

## Risks / Watchouts
- Aggregation must not distort the measured performance.
- P95 calculation should avoid unbounded memory growth; keep bounded samples or simple sorted snapshots for the first 60-second run.
- Startup spikes can dominate results. Record them, but consider tagging future summaries with a warmup window.
- Dialog lifetime timing is currently misleading for open-cost; if not fixed in this workitem, label it clearly as lifetime timing or exclude it from hard budgets.
- Budget values should start as soft warnings until enough baseline data exists.
