# IMPLEMENTATION HANDOFF

## Goal
Reduce UI stalls caused by browser/runtime controls reacting too broadly to high-frequency registry events, especially when the PID controller is running.

## Scope
Included:
- Add background-thread-safe pre-filtering before `Dispatcher.UIThread.Post(...)` in browser/runtime registry handlers.
- Reduce unnecessary UI work in:
  - `ControllerControl`
  - `EnhancedSignalsControl`
  - `MonitorViewControl`
  - `CustomSignalsControl`
- Preserve existing runtime behavior for relevant registry updates.
- Keep the existing diagnostics so the same PID scenario can verify improvement.

Explicitly NOT included:
- Do not optimize `RealtimeChartControl`.
- Do not change PID controller runtime semantics.
- Do not redesign `HostRegistries`.
- Do not replace browser-hosted widgets with native UI.
- Do not remove the UI responsiveness diagnostics.

## Starting Point
- Diagnostics were enabled and confirmed in `src/HornetStudio/bin/Debug/net9.0-windows/logs/host-20260529.log`.
- The PID scenario produced repeated UI thread stalls:
  - `DelayMs=360.2`
  - `DelayMs=368.9`
  - many recurring `50-150 ms` spikes
- Browser diagnostics showed event/post floods during PID activity:
  - `CustomSignalsControl RegistryEvents=12808 IgnoredRegistryEvents=12808 DispatcherPosts=12299`
  - `EnhancedSignalsControl RegistryEvents=12825 AcceptedRegistryEvents=12300 DispatcherPosts=915`
  - `ControllerControl RegistryEvents=12825 AcceptedRegistryEvents=12300 DispatcherPosts=915`
  - `MonitorViewControl RegistryEvents=12825 AcceptedRegistryEvents=12325 DispatcherPosts=4395`
- Example high-frequency keys:
  - `studio.main.controller.pid_1.out`
  - `studio.main.controller.pid_1.out.scaled`
  - `studio.main.udl_client_control_1.m001.read`
  - `studio.main.enhanced_signals.enhanced_signal_1`
- Repository rule: browser-hosted controls and widgets must not react to all `HostRegistries.Data.ItemChanged` events globally.

## Tasks
1. Inspect current registry handlers and runtime match APIs in the target controls.
2. Add cheap relevance checks that can run on background threads before posting to the UI thread.
3. For `CustomSignalsControl`, prevent ignored events from posting to the UI thread.
4. For `EnhancedSignalsControl`, only queue runtime refresh when the registry key matches a known runtime/source path or a configured relevant path.
5. For `ControllerControl`, only queue runtime refresh when the registry key matches a known controller runtime path or configured controller input/output path.
6. For `MonitorViewControl`, only queue runtime refresh when the key matches one of the displayed monitor rows.
7. Keep coalescing where it already exists, but ensure coalescing happens after relevance filtering.
8. Re-run the same PID scenario with `HORNETSTUDIO_UI_DIAGNOSTICS=1`.
9. Build the full solution.

## File-Level Changes
- `src/HornetStudio.Editor/Widgets/CustomSignals/CustomSignalsControl.axaml.cs` -> split registry relevance from UI-thread handling; call the relevance check before `Dispatcher.UIThread.Post(...)`.
- `src/HornetStudio.Editor/Widgets/EnhancedSignals/EnhancedSignalsControl.axaml.cs` -> add a cheap `IsRelevantRegistryChange(...)`-style check before `QueueRuntimeRefresh()`.
- `src/HornetStudio.Editor/Widgets/Controller/ControllerControl.axaml.cs` -> add a cheap `IsRelevantRegistryChange(...)`-style check before `QueueRuntimeRefresh()`.
- `src/HornetStudio.Editor/Widgets/MonitorView/MonitorViewControl.axaml.cs` -> add a cheap displayed-row path match before `QueueRuntimeRefresh()`.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> keep existing diagnostics; update only if needed to make accepted/ignored semantics reflect pre-filtering accurately.
- `src/HornetStudio/docs/manual/troubleshooting.md` -> update only if the diagnostic workflow or interpretation changes.

## Implementation Order
1. Start with `CustomSignalsControl` because the log shows it posting even for fully ignored events.
2. Fix `MonitorViewControl` because it posts thousands of refreshes and should only care about displayed monitor paths.
3. Fix `ControllerControl` relevance filtering for controller runtime paths.
4. Fix `EnhancedSignalsControl` relevance filtering for enhanced signal runtime/source paths.
5. Keep each control's behavior unchanged for accepted relevant events.
6. Run `dotnet build HornetStudio.sln --no-restore`.
7. Run the PID reproduction with diagnostics enabled and compare browser diagnostic counts.

## Technical Constraints
- Use existing helper methods and runtime `MatchesPath(...)` methods where possible.
- Do not add dependencies.
- Do not introduce broad new services or abstractions unless the same exact relevance logic is needed by multiple controls.
- Filtering must be cheap and safe on a background thread.
- Do not access Avalonia visual tree, UI collections, or mutable UI-only collections from background threads unless access is already synchronized or copied safely.
- Avoid `.Result` and `.Wait()`.
- Preserve current UI behavior for actual relevant registry changes.
- Chat responses must be German; code, comments, docs, and user-visible messages must be English.

## Acceptance Criteria
- With the same PID reproduction, browser diagnostics show a large reduction in unnecessary posts:
  - `CustomSignalsControl DispatcherPosts` should not stay in the five-digit range when all events are ignored.
  - `MonitorViewControl DispatcherPosts` should be reduced significantly.
  - `ControllerControl AcceptedRegistryEvents` should not include unrelated enhanced signal or UDL keys unless they are truly configured controller dependencies.
  - `EnhancedSignalsControl AcceptedRegistryEvents` should not include unrelated controller/monitor keys unless they are truly configured enhanced signal dependencies.
- UI responsiveness spikes are materially reduced during PID run.
- Relevant UI values still update.
- Build succeeds with `0` errors.

## Verification
- Build: `dotnet build HornetStudio.sln --no-restore`
- Manual diagnostics run:
  - Start `.NET Launch (HornetStudio Diagnostics)`.
  - Confirm log contains `UI responsiveness diagnostics configured. Enabled=true`.
  - Activate PID controller using the same scenario.
  - Compare `Browser UI diagnostics` counts before and after.
  - Confirm chart/timeline visibly lags less.
- Optional: run `dotnet-counters monitor --process-id <PID> System.Runtime` during the same scenario to ensure the primary reduction is Dispatcher/registry work, not only GC variance.

## Out of Scope
- Chart rendering optimization.
- PID runtime optimization.
- Monitor/enhanced/controller feature redesign.
- File-backed browser resource migration.
- Release/versioning.

## Risks / Watchouts
- Filtering too aggressively can stop visible rows from updating.
- Some controls derive relevant dependencies dynamically; use existing row/runtime match APIs where possible.
- `CustomSignalsControl` has computed signals that may depend on arbitrary source paths; do not filter out configured source changes.
- `EnhancedSignalsControl` and `ControllerControl` currently refresh broad runtime state; narrowing must still include source, command, and runtime output paths.
- Background-thread filtering must not enumerate mutable UI collections unsafely. If needed, maintain a small snapshot of relevant paths updated on the UI thread.
