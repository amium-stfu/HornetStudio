# MonitorView Dispatcher Posts Follow-Up Implementation Handoff

## Context

The first MonitorView optimization is implemented and the 120-second benchmark no longer fails, but it still reports `Warn` because MonitorView dispatcher posts remain elevated.

Latest benchmark result:

- Status: `Warn`
- Reason: `BrowserDispatcherPosts were elevated`
- `BrowserDispatcherPosts`: `70`
- `MonitorViewControl[main] RegistryEvents`: `140`
- `AcceptedRegistryEvents`: `70`
- `IgnoredRegistryEvents`: `70`
- `IgnoredRatio`: `0.5`
- Root aggregate key `studio.main.monitor` is now ignored correctly.
- Remaining accepted events are rule-level events:
  - `studio.main.monitor.monitor_rule_2`: `24`
  - `studio.main.monitor.monitor_rule_1`: `23`
  - `studio.main.monitor.monitor_rule_3`: `23`
- Runtime refresh cost is low, but refreshes are still scheduled for every accepted rule event:
  - `MonitorViewControl[main].RuntimeRefresh Count=66 MaxMs=14.8 P95Ms=0.8`
  - `MonitorViewControl[main].ItemChangedDispatch Count=132 MaxMs=1.3 P95Ms=0.6`
  - `MonitorViewControl[main].RebuildRows Count=2 MaxMs=14.1 P95Ms=14`

The remaining issue is not the root aggregate notification anymore. It is that rule-level registry publishes are still treated as UI-relevant even when they do not change visible MonitorView state.

## Goal

Reduce MonitorView dispatcher posts by filtering rule-level runtime registry events before posting to the UI thread.

The MonitorView browser/widget must remain only a view. Runtime evaluation must stay owned by the background runtime process/service.

## Scope

Focus on the MonitorView/browser widget registry-event path only.

Expected files to inspect first:

- `src/HornetStudio.Editor/Widgets/Monitor/MonitorViewControl.axaml.cs`
- Related monitor runtime/state classes touched by the recent implementation
- Existing monitor browser/widget tests

Do not move runtime ownership back into UI controls. Do not add new dependencies.

## Implementation Plan

1. Inspect the current `MonitorViewControl` implementation after the first optimization.
   - Confirm how registry events are subscribed.
   - Confirm how accepted/ignored events and dispatcher posts are counted.
   - Confirm which registry keys are treated as root aggregate, rule parent, and rule state leaves.

2. Add state-change gating for rule-level events before any UI dispatcher post is scheduled.
   - Keep a small cached snapshot per visible rule row.
   - The snapshot should contain only state that affects visible MonitorView output, for example:
     - runtime path or registry key
     - active state
     - message/status text if shown
   - Compare incoming/resolved rule state with the cached snapshot on the background event path.
   - If the visible state did not change, count the event as ignored and do not post to the dispatcher.

3. Keep thread ownership explicit.
   - Do not read or mutate Avalonia controls or observable collections from the registry callback thread.
   - Maintain a thread-safe, UI-independent cache for pre-dispatch comparison.
   - Update the cache after the UI refresh applies the accepted state.

4. Preserve the existing root aggregate filter.
   - Exact aggregate events such as `studio.main.monitor` must remain ignored.
   - Rule events should only be accepted when they change visible row state.

5. Coalesce accepted changes without relying on coalescing as the primary filter.
   - Multiple changed rule paths may be merged into one pending UI update.
   - Coalescing is only a secondary optimization; unchanged rule publishes must be filtered before dispatch.

6. Update or add focused tests.
   - Cover duplicate unchanged rule-level registry events.
   - Verify unchanged rule events do not schedule dispatcher work.
   - Verify changed active/message state still refreshes the affected row.
   - Keep tests focused on MonitorView registry filtering and avoid introducing UI-runtime ownership in tests.

7. Run focused validation.
   - Build focused editor/test project if the full editor output is locked.
   - Run focused Monitor tests.
   - Run the benchmark again with the MonitorView widget placed.

## Acceptance Criteria

- A 120-second benchmark with `benchmarks/ui_lag_bench_project/project.aaep` and MonitorView widget placed should not report `BrowserDispatcherPosts were elevated`.
- `BrowserDispatcherPosts` should drop significantly below `70`; expected value should be close to actual visible state transitions, not raw rule publish count.
- `MonitorViewControl[main] IgnoredRegistryEvents` should be greater than `70` because unchanged rule publishes are now filtered too.
- `RuntimeRefresh Count` should drop sharply from the latest `66`.
- MonitorView UI behavior remains correct:
  - rule rows update when runtime state changes
  - root aggregate changes do not trigger unnecessary UI work
  - browser/widget remains a view over runtime state

## Risks

- Registry callbacks may arrive before all related leaf values are visible. The comparison logic should resolve a consistent best-effort visible state and only dispatch when that state differs from the cached UI snapshot.
- Do not let the cache become a second runtime owner. It is only a view-side optimization cache for filtering UI work.
- Avoid broad refactoring in the monitor runtime while fixing MonitorView dispatcher pressure.
