# IMPLEMENTATION HANDOFF

## Goal
Reduce `MonitorViewControl` UI-thread dispatcher posts so the 120-second UI benchmark with a placed `MonitorView` widget passes.

## Scope
- Optimize `MonitorViewControl` registry event handling.
- Keep `MonitorView` as a read-only view of selected monitor rule states.
- Preserve selected monitor rule behavior, row active styling, footer counts, and theme refresh behavior.
- Add focused tests for event relevance and state-change gating.
- Update MonitorView documentation if behavior wording changes.

Explicitly not included:
- Do not redesign MonitorView UI.
- Do not change Monitor runtime rule evaluation.
- Do not change Monitor browser/editor behavior.
- Do not introduce new dependencies.

## Starting Point
- Benchmark command:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_ui_benchmark.ps1 -Seconds 120 -ProjectPath benchmarks\ui_lag_bench_project\project.aaep -Scenario BenchModeValidation-120s
```

- Benchmark with `MonitorView` placed failed:
  - Status: `Fail`
  - BudgetNotes: `BrowserDispatcherPosts were high`
  - `BrowserDispatcherPosts=133`
  - `MonitorViewControl[main] RegistryEvents=140`
  - `AcceptedRegistryEvents=140`
  - `IgnoredRegistryEvents=0`
  - `IgnoredRatio=0`
  - Top keys:
    - `studio.main.monitor`: `70`
    - `studio.main.monitor.monitor_rule_2`: `24`
    - `studio.main.monitor.monitor_rule_1`: `23`
    - `studio.main.monitor.monitor_rule_3`: `23`
- Timing itself is cheap:
  - `MonitorViewControl[main].ItemChangedDispatch Count=132 MaxMs=5.4 P95Ms=0.8`
  - `MonitorViewControl[main].RuntimeRefresh Count=126 MaxMs=6.8 P95Ms=0.3`
- The failure is caused by too many UI posts, not by one expensive UI operation.

## Tasks
1. Narrow `MonitorViewControl` registry relevance so aggregate/root events do not cause per-rule refreshes unless they are actually needed for displayed rows.
2. Add state-change gating before scheduling UI work: do not post to the UI thread if active/message state for displayed rows did not change.
3. Coalesce multiple relevant monitor rule events into a single pending UI refresh.
4. Ensure diagnostics count ignored redundant monitor events so benchmark summaries show improved filtering.
5. Add focused tests for relevance filtering, aggregate/root event handling, redundant event ignoring, and selected-rule updates.
6. Run focused tests and the 120-second UI benchmark with the benchmark project containing `MonitorView`.

## File-Level Changes
- `src/HornetStudio.Editor/Widgets/MonitorView/MonitorViewControl.axaml.cs` -> tighten event matching, add runtime-state snapshot/change gate, reduce dispatcher posts, preserve row UI updates.
- `src/HornetStudio.Editor.Tests/Program.cs` -> add or update focused tests for `MonitorViewControl` relevance and refresh behavior.
- `src/HornetStudio/docs/widgets/MonitorView.md` -> update only if behavior details need clarification.
- `src/HornetStudio/docs/widgets/help/MonitorView.help.md` -> update only if user-facing help should mention efficient selected-rule observation.
- `src/HornetStudio/docs/widgets/descriptions/MonitorView.md` -> update only if concise description becomes inaccurate.

## Implementation Order
1. Inspect current `MonitorViewControl.OnRegistryItemChanged`, `QueueRuntimeRefresh`, `IsRelevantRowPath`, and `MonitorViewRow.RefreshRuntime`.
2. Replace broad relevance matching with a cheap snapshot that distinguishes:
   - selected rule runtime paths
   - selected rule `.active` / `.message` descendants
   - aggregate root `studio.{folder}.monitor`
3. Treat aggregate/root events as non-refresh events for row UI unless they represent data the view actually displays.
4. Add a lightweight per-row runtime state snapshot, for example active/message values keyed by runtime path.
5. On background registry events, read only the affected selected row state when possible; if the visible state did not change, record the event as ignored and do not call `Dispatcher.UIThread.Post`.
6. For multiple state-changing events, keep the existing interlocked coalescing so only one UI refresh is queued while a refresh is pending.
7. On the UI thread, update only rows whose runtime state changed where practical; full row refresh is acceptable only after coalescing and state-change gating.
8. Ensure `RebuildRows` rebuilds the relevance/state snapshot before subscription starts reacting to the new context.
9. Add focused tests using direct helper methods or reflection if needed, following existing test style in `Program.cs`.
10. Run focused tests, then run the benchmark.

## Technical Constraints
- Keep code, comments, XML documentation, UI text, and technical identifiers in English.
- Chat responses remain German.
- Do not add dependencies.
- Do not move MonitorView runtime ownership into the UI. MonitorView remains a view only.
- Registry filtering must happen before any UI-thread work is scheduled.
- Unknown, aggregate-only, redundant, or non-visible events must be ignored on the calling thread.
- Preserve existing `ScopedRegistryItemChangedSubscription` pattern.
- Keep changes focused to MonitorView and tests/docs directly related to MonitorView.

## Acceptance Criteria
- The 120-second benchmark with `MonitorView` placed passes.
- `BrowserDispatcherPosts` for `MonitorViewControl[main]` drops sharply from `133`; target is near the number of actual visible row state changes, not every monitor publish.
- `IgnoredRegistryEvents` and `IgnoredRatio` increase for redundant aggregate/root or unchanged-state events.
- `AcceptedRegistryEvents` no longer equals total `RegistryEvents` when aggregate/root monitor events are present.
- `MonitorViewControl[main].RuntimeRefresh` count is significantly lower than the previous `126`.
- MonitorView still displays selected rules in configured order.
- Active rows still update color and tooltip when rule state changes.
- Footer active count remains correct.
- No regression for theme refresh and `SelectedMonitorIds` changes.

## Out of Scope
- Fixing startup/warmup spikes unrelated to MonitorView.
- Changing chart rendering.
- Changing monitor rule formula evaluation or action execution.
- Reworking `MonitorRuntimeManager` beyond what is required by MonitorView state observation.
- Release/versioning work.

## Risks / Watchouts
- Do not ignore actual selected-rule active/message changes.
- Avoid reading large registry subtrees on every event; read only affected paths.
- Root aggregate updates currently account for half the observed events; suppressing them is likely necessary for the benchmark.
- Coalescing alone is insufficient because benchmark budget counts dispatcher posts.
- Background registry handlers must not touch Avalonia UI objects.
- Existing dirty worktree may contain unrelated changes; do not revert them.
