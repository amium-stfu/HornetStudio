# IMPLEMENTATION HANDOFF

## Goal
Fix the UDL Module Exposures dialog so bitmask rows are shown and editable even when runtime channel metadata does not currently expose a bit format such as `b4`, `b8`, or `b16`. In module-scoped browser editing, users must be able to configure `read`, `set`, and `alert` bit helpers and bit counts from file-backed intent, not only from runtime-detected formats.

## Scope
Included:
- Fix `UdlModuleExposureDialogWindow` module-scoped bitmask row creation.
- Ensure the Bitmask section shows rows for relevant UDL channels even when `SupportsBitExposure` is false because runtime format is missing or non-bit.
- Preserve existing behavior when runtime format or saved definitions already provide bit count/format.
- Make saved definitions always visible/editable after reopening.
- Add focused tests for module-scoped bitmask row fallback behavior.

Explicitly not included:
- Redesigning the entire exposure model.
- Rewriting projection behavior unless a small adjustment is required for the corrected definitions.
- Full ItemClient support.
- New visual design beyond making the existing controls visible and usable.
- Release/versioning work.

## Starting Point
- `UdlModuleExposureDialogWindow.axaml` already contains UI for `Publish Bits` and `Count` in the Bitmask section.
- `UdlModuleExposureDialogWindow.axaml.cs` already has:
  - `UdlModuleExposureBitmaskRow`
  - `BitCountText`
  - `ExposeBits`
  - `BuildBitmaskRows(...)`
- Current `BuildBitmaskRows(...)` only includes rows where `row.SupportsBitExposure` is true.
- `SupportsBitExposure` depends on `EffectiveBitCount > 0`.
- `EffectiveBitCount` currently comes from explicit `BitCount` or format-derived `b4`, `b8`, `b16`.
- When the browser opens the module-scoped dialog for `m001` and runtime channel metadata does not provide bit formats, `BitmaskRows` is empty, so only `Read helper bits route to Set` is visible.
- This is a migration regression: old widget workflows allowed the user to configure bitmask helper bits.

   - If still unknown, use a conservative editable default rather than hiding the row.
4. Adjust `SupportsBitExposure` semantics for module-scoped bitmask rows.
   - The Bitmask section must not hide a row solely because runtime format is missing.
   - Avoid breaking the generic channel view where runtime-detected support may still matter.
   - Prefer adding a module-scoped row creation path or a flag to distinguish intent-editable rows from runtime-supported rows.
5. Preserve saved definitions.

   - Saving should keep the definition in the serialized result.
6. Add tests.

## Risks / Watchouts
- Creating fallback rows for channels that do not exist at runtime may produce definitions that only take effect once those channels appear. That is acceptable for file-backed intent editing.
- If `TryBuildResult(...)` filters out rows too aggressively, fallback definitions may disappear on save.
- Default bit count must be conservative and explicit enough that users can correct it before saving.
- Avoid duplicate rows when both runtime and fallback channels include `read`, `set`, or `alert`.
