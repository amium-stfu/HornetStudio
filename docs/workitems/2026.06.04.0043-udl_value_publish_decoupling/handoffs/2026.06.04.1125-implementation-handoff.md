# IMPLEMENTATION HANDOFF

## Goal
Fix the UDL demo/runtime throughput collapse where adding modules lowers the per-module update rate because one sequential update loop is slowed by synchronous public registry and attachment fan-out.

Target behavior:

- One demo module continues to run at about 10 Hz.
- 20 demo modules run at about 10 Hz each, about 200 `DemoGenerate` events per second total.
- Whole-module UDL attachments remain a valid normal scenario.
- Public UI/registry publication must not throttle the UDL receive or demo generation loop.

## Scope
- Focus on the runtime-to-public-registry coupling that slows the sequential UDL update loop.
- Keep the demo value calculation model simple and deterministic.
- Preserve current UDL module structure and whole-module attachment support.
- Preserve immediate structural updates and direct writeback.
- Do not implement UI rendering optimizations in this workitem.
- Do not require users to attach only `*.read` leaf paths.

## Starting Point
- `SimulatedHostUdlClient.SimulationLoopAsync` uses one sequential loop for all modules.
- Each loop updates every `_moduleStates` entry, then waits `100 ms`.
- Effective rate is therefore:

```text
module_rate = 1 / (time_to_update_all_modules_and_sync_side_effects + 100 ms)
```

- With one module the loop is close to 10 Hz.
- With 20 modules the latest benchmark showed:
  - `DemoGenerate`: `1380` over about `30.5s`, about `45.31/s` total.
  - Per module: `69 / 30.5 = ~2.26 Hz`.
  - `RegistryPublish[SteadyState]`: about `207.77/s`.
  - `RegistryPublishDuration PropertyUpdated.read`: `P95Ms=297.8`, `MaxMs=700.2`.
  - `SignalReceive`: about `39.27/s`.
  - `ChartRenderCount=0`.
  - `BrowserDispatcherPosts=0`.
- This strongly indicates synchronous follow-up work from item property changes through `UiFolderContext` and `HostRegistries.Data` is blocking the sequential UDL loop.
- The same benchmark also exposed a disposal/threading failure:
  - `System.InvalidOperationException: Collection was modified; enumeration operation may not execute.`
  - Stack includes `UiFolderContext.Dispose()` and `FlushPendingSourcePublications()`.

## Tasks
1. Confirm the exact synchronous call chain from `SimulatedHostUdlClient.UpdateModuleState` to public registry publication.
2. Fix the architectural coupling so UDL runtime value updates are cheap and do not synchronously execute public publish/subscriber work.
3. Ensure source runtime state is updated immediately and completely for every module tick.
4. Add a bounded latest-wins publication path for high-frequency source-to-public value/property changes.
5. Keep structural snapshot publication immediate for attach, detach, module creation/removal, and shape changes.
6. Keep public target writeback to runtime source direct for `set`/`write` use cases.
7. Make the publication queue/threading lifecycle safe during dispose and attachment rebuild.
8. Add focused tests for rate-decoupling semantics and dispose safety where the code is testable.
9. Build and run a 30s benchmark with the existing whole-module 20-module project.
10. Document final measurements in `docs/workitems/ChatHandoff.md`.

- `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs` -> Inspect attachment lifecycle. Adjust only if needed to pass a scoped publish policy or avoid unnecessary attachment rebuilds.
- `src/HornetStudio.Editor/UdlClients/UdlClientRegistryProjection.cs` -> Inspect `OnExposureTargetChanged`; avoid calling `SynchronizeAttachments()` on high-frequency value echo paths unless required.
- `src/HornetStudio.Editor/Widgets/UdlClient/SimulatedHostUdlClient.cs` -> Do not redesign. Use only for validation or minimal diagnostics if necessary.
- `src/HornetStudio.Host/HostRegistries.cs` -> Do not broadly refactor. Touch only if current registry APIs lack a safe way to publish coalesced updates.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> Add bounded diagnostic counters only if existing benchmark output cannot prove the improvement.
- `src/HornetStudio.Editor.Tests/Program.cs` or `src/HornetStudio.Host.Tests/Program.cs` -> Add focused tests for changed behavior.
- `docs/workitems/ChatHandoff.md` -> Update with final before/after numbers and remaining risks.

## Implementation Order
1. Trace and document the current synchronous path:
   - `SimulatedHostUdlClient.ApplyModuleSnapshot`
   - source `ItemModel` property change event
   - `UiFolderContext.AttachedItemLink.OnSourceChanged`
   - `HostRegistries.Data.UpdateProperty` / `UpdateValue`
   - `DataRegistry.RaiseItemChanged`
   - `UdlClientRegistryProjection.OnExposureTargetChanged`
   - `PageItemModel.OnDataRegistryChanged`
2. Verify whether `UdlClientRegistryProjection.OnExposureTargetChanged` calls `SynchronizeAttachments()` for high-frequency attached value/property changes and whether that rebuilds or clears projections.
3. Add a small diagnostic if needed to count time spent inside source-change-to-public-publish before changing behavior.
4. Implement a thread-safe pending publication mechanism in the attachment link:
   - key by public target path plus parameter name/change kind.
   - store latest value and epoch only.
   - schedule one flush per link or context.
   - use a fixed initial flush cadence of about 100 ms unless an existing project constant/policy is already present.
5. Route high-frequency value/property changes through pending publication when they are source-to-public telemetry updates:
   - `ValueUpdated`
   - `PropertyUpdated` for `read`
   - possibly `PropertyUpdated` for telemetry-like `unit`/display metadata only if currently high-frequency; otherwise keep metadata direct.
6. Keep these direct/immediate:
   - snapshot upserts.
   - structural property changes.
   - source tree shape changes.
   - target-to-source writeback.
   - missing-target fallback snapshot creation.
7. Make `Dispose()` safe:
   - stop future flush scheduling.
   - prevent concurrent mutation while enumerating `_links`.
   - dispose links over a stable snapshot or under a clear lock.
   - ensure stale pending updates cannot publish after the link/context is disposed.
8. Revisit `UdlClientRegistryProjection.OnExposureTargetChanged`:
   - if high-frequency public value events trigger `SynchronizeAttachments()` unnecessarily, narrow that call so only writeback or structural/exposure-relevant changes resynchronize attachments.
9. Add tests:
   - repeated source `read` updates do not synchronously publish every intermediate update.
   - latest value is eventually published.
   - structural snapshot still appears immediately.
   - writeback reaches the source immediately.
   - disposing while a flush is pending does not throw or publish stale data.
10. Run `dotnet build HornetStudio.sln --no-restore`.
11. Run the 30s benchmark with the unchanged whole-module bench project.
12. Compare against the baseline:
   - `DemoGenerate` should move from about `45/s` toward about `200/s`.
   - `RegistryPublishDuration PropertyUpdated.read` should no longer show hundreds of milliseconds P95 from synchronous publish.
   - `SignalReceive` should be stable and close to the effective public publish cadence.
   - no fatal dispose exception.
13. Update `docs/workitems/ChatHandoff.md`.

## Out of Scope
- UI layout/render optimization.
- Chart optimization.
- Rewriting the UDL simulator to use one timer per module.
- Requiring users to change UDL attachment style.
- Broad `PageItemModel` refactoring.
- Release/versioning work.

## Risks / Watchouts
- Coalescing changes public telemetry semantics: subscribers may stop seeing every intermediate value. This is intended for high-frequency read/display telemetry, but command/event paths must remain direct.
- A global `UiFolderContext` change can affect non-UDL attachments. If risk is high, implement the policy as scoped/opt-in from `UdlHostRegistryProjection`.
- Calling `SynchronizeAttachments()` from a registry event triggered by the attachment itself can cause reentrancy and projection churn.
- Flush timers/tasks must not outlive disposed attachments.
- Full snapshots must supersede or clear pending value publications to avoid stale writes after structural changes.
