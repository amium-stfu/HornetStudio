# IMPLEMENTATION HANDOFF

## Goal
Close the remaining throughput gap in the public registry to Signal widget delivery path for the 20 UDL demo module benchmark.

Target scenario:

- 20 UDL demo modules.
- About `10 Hz` per module.
- About `200 read updates/s` visible through 20 Signal widgets.
- No relevant steady-state UI backlog.

## Scope
- Continue from the current `PageItemModel` signal delivery diagnostics.
- Verify whether the narrowed irrelevant-event diagnostics fixed the previous benchmark regression.
- Identify the first failing stage between public `read` publication and Signal target value application.
- Implement only the smallest fix in the registry-to-Signal delivery or target-update path if the measured stage proves a real loss or under-scheduling.
- Update the workitem handoff documentation after validation.

Explicitly not included:

- No UDL demo scheduler changes.
- No UDL runtime frame-loop changes.
- No chart optimization.
- No broad `PageItemModel` refactoring.
- No benchmark YAML restructuring unless read-only inspection proves the current scenario is invalid.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Do not introduce dependencies.
- Registry filtering must happen before dispatcher scheduling.
- Unknown or unrelated registry events must not enqueue UI work.
- Keep coalescing; do not replace it with one dispatcher post per value event.
- Diagnostics must be bounded and must not add per-event log spam.
- Do not read Avalonia UI objects from background/runtime threads.

## Acceptance Criteria
- The first measured loss point between `RegistryPublish read` and Signal apply is identified.
- `SignalRegistryEventRelevant` is close to visible-path `RegistryPublish read`, or the difference is explicitly explained by path scope.
- `SignalReceive` and/or `SignalLatestValueApplied` moves toward `200/s` for the 20 visible `*.read` signals.
- `TargetValueRefreshExecuted[SteadyState->SteadyState]` remains low latency and does not create growing backlog.
- `BrowserDispatcherPosts=0` remains true or any change is explained.
- `ChartRenderCount=0` remains true for this scenario.
- No fatal exceptions.
- Build succeeds.

## Risks / Watchouts
- `RegistryPublish read` can include paths that are not visible Signal targets; verify path overlap before calling events lost.
- `SignalReceive` name may be misleading if it counts accepted relevant events rather than displayed values.
- `RefreshRateMs=100` means expected visible apply cadence is bounded but should still allow about `200/s` total for 20 widgets.
- Diagnostic counters can distort throughput if they record irrelevant events too broadly.
- Full target refresh must still take precedence over value-only refresh when structure or selected property changes.
