# IMPLEMENTATION HANDOFF

## Goal
Make UDL demo and real UDL module value ingestion resilient for normal scenarios with 20 or more modules by preventing high-frequency public HostRegistry publishing from synchronously slowing the UDL receive/simulation loop.

Target scenario:

- 20 UDL modules.
- Each module should deliver about 10 Hz.
- Visible Signal widgets should receive about 200 `*.read` updates per second in total, subject to configured publishing policy.
- Runtime/CAN/demo receive must not be throttled by synchronous public registry fan-out or UI consumers.

## Scope
- Confirm the exact synchronous bottleneck between UDL module updates, attachment projection, `HostRegistries.Data`, and Signal receive.
- Implement a narrow runtime/projection-side fix for high-frequency value publishing.
- Preserve direct structure publication for module creation/removal/attach/detach/configuration changes.
- Preserve direct writeback semantics for `set`/`write` paths.
- Keep UI-specific optimization out of scope unless the confirmation measurement disproves the current hypothesis.

## Starting Point
- `SimulatedHostUdlClient` currently updates all module states once per loop, records `DemoGenerate`, raises `FrameReceived`, and then waits `100 ms`.
- The simulator does not distribute updates round-robin; all modules are updated per tick.
- `benchmarks/ui_lag_bench_project/Folders/main/Clients/Udl/udl1.yaml` is the active file-backed UDL definition for `udl1`.
- The file-backed definition attaches whole module roots `m001` through `m020`.
- Whole-module attachments publish high-frequency child changes for `read`, `set`, `out`, `state`, and `alert`, not only the visible `read` values.
- Prior handoffs show `TargetValueRefreshExecuted[SteadyState]` is fast, `ChartRenderCount=0`, and no relevant steady-state UI backlog.
- Prior measurements show a mismatch where public registry publishing is much higher than actual `DemoGenerate`/`SignalReceive`, consistent with synchronous fan-out slowing the simulation loop.

## Implementation Order
1. Read the current source-change flow from `SimulatedHostUdlClient.ApplyModuleSnapshot` through `ItemModel` change events, `UiFolderContext.AttachedItemLink.OnSourceChanged`, `HostRegistries.Data`, and `PageItemModel.OnDataRegistryChanged`.
2. Add minimal timing/counter diagnostics around the suspected synchronous boundary, preferably aggregated and path-scoped.
3. Build the solution.
4. Run a baseline benchmark with the current whole-module `udl1.yaml`.
5. Interpret rates for `DemoGenerate`, `RegistryPublish`, `SignalReceive`, target refresh, and any new blocking-boundary diagnostics.
6. If `UiFolderContext` source-to-target publishing is confirmed as the blocker, implement an internal latest-wins pending value queue for high-frequency source child value/property updates.
7. Flush pending public value updates at a controlled cadence, initially aligned to 100 ms unless a project-local constant/policy already exists.
8. Ensure pending value updates are flushed or discarded correctly when an attachment is disposed, a structural snapshot is published, or a target path disappears.
9. Keep non-value structural changes immediate; do not delay module creation/removal, attach/detach, or snapshot upserts.
10. Keep public target writeback to source direct and avoid routing write commands through the coalesced publish queue.
11. Add focused tests covering:
    - multiple fast source value changes publish latest value only.
    - structural snapshot still publishes immediately.
    - writeback still reaches the source.
    - disposal does not publish stale pending values.
12. Build the solution again.
13. Run the benchmark again with the same whole-module `udl1.yaml`.
14. Compare before/after rates and delays, then update the handoff/chat documentation.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Do not introduce new dependencies.
- Do not perform broad UI refactoring.
- Do not optimize Avalonia rendering in this workitem.
- Do not require users to attach only leaf `*.read` paths; whole-module UDL attachments are a normal scenario.
- Runtime receive/simulation must not depend on Avalonia UI thread availability.
- High-frequency value changes must update runtime state completely, even if public registry publishing is coalesced.
- Registry event filtering rules from `agents/solution.md` remain in force.
- User-visible error and validation messages must be English.

## Acceptance Criteria
- Whole-module UDL attachments for 20 modules remain supported.
- UDL demo generation or real receive processing is no longer synchronously slowed by public registry fan-out.
- Benchmark with 20 modules shows `DemoGenerate` close to the expected 200/s steady-state target, allowing small scheduling variance.
- `SignalReceive` for visible `*.read` paths is close to the configured public publish/display target.
- `TargetValueRefreshExecuted[SteadyState]` remains low latency.
- `ChartRenderCount=0` remains true for the no-chart benchmark.
- There is no growing UI dispatcher backlog.
- Structural changes and writeback behavior are not delayed in a user-visible way.
- Solution build succeeds.

## Out of Scope
- UI visual redesign or Signal widget rendering optimization.
- Replacing `HostRegistries.Data`.
- Changing the UDL persisted schema unless measurement proves a schema-level publish policy is required.
- Requiring benchmark users to attach only leaf paths.
- Optimizing chart sampling/rendering.
- Broad `PageItemModel` refactoring.
- Release versioning or packaging.

## Risks / Watchouts
- Coalescing public values can hide intermediate states from public registry subscribers. This is acceptable for display/read telemetry only if runtime state remains complete and write/control paths stay direct.
- Some non-UI consumers may currently assume every public value transition is emitted. If such consumers exist, the publish policy must distinguish telemetry/display paths from event/command paths.
- A global `UiFolderContext` behavior change may affect non-UDL attachments. Prefer a scoped or opt-in policy if tests show broader risk.
- Flushing from background threads must not read Avalonia UI objects.
- Timer/task lifetime must be disposed cleanly with each attachment context.
- A full snapshot must supersede stale pending value updates to avoid publishing old values after structural changes.
