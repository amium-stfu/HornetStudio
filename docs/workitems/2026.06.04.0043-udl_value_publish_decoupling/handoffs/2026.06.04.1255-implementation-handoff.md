# IMPLEMENTATION HANDOFF

## Goal
Fix the remaining demo throughput gap by changing the simulator loop from fixed post-work delay to a drift-corrected periodic scheduler.

Current interpretation:

- Reduced diagnostics did not explain the remaining gap.
- `DemoGenerate` remains around `170/s` instead of the target `200/s`.
- The current loop likely behaves as:

```text
update all modules
perform side effects
await Task.Delay(100)
```

- This makes the period equal to `work duration + 100 ms`.
- If work takes about `15-20 ms`, the effective loop rate becomes about `8.3-8.7 Hz`, matching recent measurements.

Target behavior:

- The simulator should target a fixed 100 ms period:

```text
scheduled tick every 100 ms
update all modules
delay only until the next scheduled tick
```

- Effective period should be `max(100 ms, work duration)`, not `100 ms + work duration`.

## Scope
- Change only the demo simulator scheduling behavior in `SimulatedHostUdlClient`.
- Keep one loop for all modules.
- Do not introduce one timer per module.
- Preserve existing module value semantics and public publication behavior.
- Add lightweight overrun/drift counters if needed.
- Do not optimize UI, registry, chart, or attachment code in this step.

## Starting Point
- `SimulatedHostUdlClient.SimulationLoopAsync` updates all `_moduleStates` and then waits with a fixed delay.
- The demo value calculation uses `elapsedSeconds` from `_startedUtc`, so periodic scheduling should preserve deterministic value generation.
- Recent benchmarks show the simulator is stable but under target, consistent with fixed-delay-plus-work timing.

## Implementation Order
1. Read `SimulationLoopAsync` and confirm the current `await Task.Delay(100, token)` location.
2. Introduce a named tick interval constant, for example `DemoTickInterval = TimeSpan.FromMilliseconds(100)`.
3. Initialize `nextTickUtc` before the loop starts.
4. In each loop:
   - capture `now`.
   - calculate `elapsedSeconds`.
   - update every module once.
   - increment `nextTickUtc` by the tick interval.
   - compute `delay = nextTickUtc - DateTimeOffset.UtcNow`.
   - if `delay > TimeSpan.Zero`, wait that delay.
   - if `delay <= TimeSpan.Zero`, count an overrun and avoid adding an extra 100 ms delay.
5. Add overrun handling that avoids runaway catch-up loops:
   - if the loop is more than one interval behind, reset `nextTickUtc` to `DateTimeOffset.UtcNow + DemoTickInterval`.
   - otherwise keep the scheduled cadence.
6. Keep cancellation handling equivalent to the current behavior.
7. Avoid per-tick logging.

## Risks / Watchouts
- A periodic scheduler can create back-to-back ticks if work regularly exceeds 100 ms. Avoid runaway catch-up with a reset rule.
- Wall-clock scheduling can be affected by system load; use benchmark averages, not single spikes, for judgment.
- This fix applies to the demo simulator. If real UDL/CAN receive still has throughput issues, that must be evaluated separately.
- Do not use the scheduler change to hide real public-publish backpressure; keep `RegistryPublish` and `SignalReceive` in the benchmark.
