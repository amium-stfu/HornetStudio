# IMPLEMENTATION HANDOFF

## Goal
Introduce a small `valueRef` based live-value path for UDL-backed Signal widgets so high-frequency UDL values do not depend exclusively on global `HostRegistries.Data.ItemChanged` public value events.

The goal is to keep a single authoritative value source:

```text
UDL runtime item state = source of truth
HostRegistry public item = metadata, structure, attach visibility, valueRef
Signal widget = resolves valueRef and applies latest runtime value on its refresh cadence
```

## Scope
- Add or reuse a lightweight metadata representation for a public attached UDL channel to point at the authoritative runtime item and parameter.
- Initial scope is UDL public attachments and Signal widgets only.
- Preserve the existing public registry value path as fallback.
- Keep the existing `Module.Read.Properties["read"]` and `Module.Read.Properties["set"]` semantics.
- Avoid a second authoritative value store.
- Avoid per-event/per-widget logging; diagnostics must remain aggregate and low overhead.

Explicitly not included:

- No broad widget framework redesign.
- No global replacement of `HostRegistries.Data`.
- No changes to UDL module semantics.
- No chart path changes in the first implementation.
- No removal of existing registry publication before fallback behavior is proven.

## Starting Point
- Latest 60s benchmark:
  - `DemoGenerate`: about `190.329/s`, around `9.52 Hz` per module.
  - `RegistryPublish read`: about `310.409/s`.
  - `SignalReceive`: about `167.979/s`.
  - `SignalLatestValueApplied`: about `146.280/s`.
  - `TargetValueRefreshExecuted[SteadyState->SteadyState]`: about `145.947/s`, `P95=7 ms`, `Max=90.2 ms`.
  - `BrowserDispatcherPosts=0`.
  - `ChartRenderCount=0`.
- The remaining issue is not a steady-state UI backlog. It is the general public registry value-delivery path being used as a live telemetry bus.
- UDL module shape is:

```text
UdlModule
  Read -> Item
    Properties["read"] = current measured value
    Properties["set"] = writable/requested value when applicable
```

- The public attached path currently looks like `studio.main.udl1.m001.read` with parameter `read`.
- A `valueRef` should therefore describe:

```text
itemPath: runtime.udl_client.udl1.m001.read
parameter: read
```

## Tasks
1. Inspect how UDL attachments are created and published:
   - `UdlClientRuntime.GetAttachmentProjectionInput(...)`
   - `UdlHostRegistryProjection.SynchronizeAttachments(...)`
   - `UiFolderContext.Attach(...)`
   - `UiFolderContext` source-to-public publish handling.
2. Identify the least invasive place to add metadata to the public attached item:
   - preferred: attach/projection metadata on the public item.
   - fallback: a property pair on the public item if metadata is not extensible enough.
3. Define the exact `valueRef` shape using English technical names. Prefer explicit fields:
   - `valueRefPath`
   - `valueRefParameter`
4. Ensure `valueRef` points to the authoritative runtime channel item, not to another public registry copy.
5. Add a runtime value resolver/subscription mechanism with no persistent second value store:
   - resolve current value from runtime item path + parameter.
   - mark subscribed widgets dirty when the runtime source changes.
   - apply latest value on the widget refresh cadence.
6. Integrate only Signal widgets first:
   - when the target public item has a valid `valueRef`, Signal uses the live value path.
   - otherwise Signal keeps current registry-based behavior.
7. Preserve writeback rules:
   - writes must still go through existing runtime/registry writeback paths.
   - live delivery must not become an authoritative write target.
8. Add aggregate diagnostics to distinguish:
   - valueRef resolved.
   - valueRef dirty event received.
   - valueRef latest value applied.
   - fallback registry path used.
9. Add focused tests for:
   - public UDL attachment includes correct `valueRef`.
   - Signal target resolves `valueRef`.
   - missing/invalid `valueRef` falls back to current registry behavior.
   - no stale value overrides a user writeback path.
10. Build and run a 60s benchmark.
11. Update `docs/workitems/ChatHandoff.md` with architecture decision, implementation result, benchmark numbers, and next step.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- No new dependencies.
- No second source of truth.
- `valueRef` is a pointer to the authoritative runtime item and parameter, not a copied value store.
- High-frequency registry event handlers must filter before dispatcher scheduling.
- Unknown or unrelated registry/runtime events must not enqueue UI work.
- Keep existing registry behavior as fallback.
- Keep writes routed through existing writeback semantics.
- Avoid broad refactoring in `PageItemModel`.

## Acceptance Criteria
- UDL public attached read items expose a correct `valueRefPath` and `valueRefParameter`.
- Signal widgets use `valueRef` when present and fallback when absent.
- Runtime remains the authoritative value owner.
- No duplicate authoritative value state is introduced.
- The 20 UDL Signal benchmark improves visible/apply throughput toward the runtime cadence:
  - target: closer to `190/s` runtime generation than the current `~146/s` applied value rate.
- `BrowserDispatcherPosts=0` remains true for the benchmark.
- `ChartRenderCount=0` remains true for the benchmark.
- Steady-state `TargetValueRefreshExecuted` latency does not regress materially.
- Build succeeds.

## Out of Scope
- Removing public registry value publication.
- Reworking all widget target resolution.
- Chart live-value subscriptions.
- EnhancedSignal migration.
- Startup/warmup spike fix unless the new implementation directly affects it.
- Release/versioning work.

## Risks / Watchouts
- A careless implementation can create two truths. Avoid any persistent `LiveValueStore` that can diverge from runtime state.
- If Signal polls runtime blindly every `RefreshRateMs`, CPU may improve less than expected. Prefer dirty-marking plus cadence-bound apply.
- If `valueRef` is placed in ordinary properties, existing UI may display it unless hidden/metadata semantics are respected.
- Existing `TargetPath + Parameter` behavior must keep working for non-UDL and legacy targets.
- Writeback must not be bypassed by reading/writing directly through the live path.

```text

```

- This is an architecture correction for live telemetry delivery, not another micro-optimization of registry event diagnostics.
