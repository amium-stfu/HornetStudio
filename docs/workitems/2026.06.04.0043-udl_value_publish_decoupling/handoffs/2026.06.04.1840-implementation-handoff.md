# IMPLEMENTATION HANDOFF

## Goal
Introduce reference-backed HostRegistry items for UDL attachments so public paths such as `studio.main.udl1.m001.read` stay stable while their displayed read value is resolved from the authoritative UDL runtime item, for example `runtime.udl_client.udl1.m001.read.Properties["read"]`.

The Runtime remains source of truth. The HostRegistry must no longer act as a second live-value store for UDL attachment reads.

## Scope
- Add a small HostRegistry reference mechanism for UDL public attachments only.
- Keep public HostRegistry paths stable.
- Keep widgets as normal registry consumers as much as possible.
- Preserve existing public snapshot behavior as fallback.
- Preserve writeback through the existing public-path and UDL runtime writeback route.
- Keep `Module.Read.Properties["read"]`, `Module.Read.Properties["set"]`, and existing UDL module semantics unchanged.

Explicitly not included:

- No global HostRegistry redesign.
- No Signal-specific live-value fastpath as the primary architecture.
- No direct widget writes to `runtime.udl_client.*`.
- No removal of the existing coalesced snapshot/publication fallback until reference-backed behavior is proven.
- No new dependencies.

## Starting Point
- `UiFolderContext.Attach(...)` currently clones Runtime items into public `studio.*` items and `AttachedItemLink` mirrors source changes into `HostRegistries.Data`.
- `UiFolderContext.AttachedItemLink` currently coalesces UDL source publishes at `100 ms`, but still stores public live values.
- `UdlHostRegistryProjection` already adds `valueRefPath` and `valueRefParameter` metadata to public UDL `read` items.
- `PageItemModel` currently contains Signal-specific `valueRef` resolution and diagnostics.
- `HostRegistries.Data` currently resolves snapshots and indexed items, but does not own reference-backed item semantics.
- Existing tests cover basic `valueRef` metadata and Signal fallback behavior; those tests should be adapted or extended for HostRegistry-owned reference semantics.

## Tasks
1. Define the narrow reference contract in `HostRegistries.Data`.
2. Move UDL read reference ownership from Signal widget logic toward HostRegistry resolution.
3. Extend `UiFolderContext.Attach(...)` so UDL attachments can register public-to-runtime read references.
4. Keep source-to-public structure synchronization and fallback snapshot behavior intact.
5. Route public writes exactly as today through `AttachedItemLink.OnTargetChanged(...)` and existing UDL writeback.
6. Reduce or isolate Signal-specific `valueRef` code once generic HostRegistry resolution handles the UDL read path.
7. Add focused host/editor tests for reference-backed attach, read, eventing, writeback, and fallback.
8. Run focused tests, solution build, and a 60s UI benchmark.
9. Update `docs/workitems/ChatHandoff.md` with the final architectural decision, validation, and benchmark numbers.

## File-Level Changes
- `src/HornetStudio.Host/HostRegistries.cs` -> Add the minimal reference metadata/model and registry operations needed to register, resolve, notify, and remove reference-backed public item parameters.
- `src/HornetStudio.Host/UiFolderContext.cs` -> Extend attachment lifecycle so UDL read attachments register and dispose HostRegistry references; keep snapshot fallback and protected property preservation.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs` -> Pass or declare UDL read reference mappings when synchronizing attachments; keep `valueRefPath` / `valueRefParameter` metadata as protected compatibility/diagnostic fields.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientRuntime.cs` -> Confirm runtime item references are stable enough for attachment reference registration; avoid cloning for the live reference path.
- `src/HornetStudio.Editor/Models/PageItemModel.cs` -> Remove or narrow Signal-specific runtime reference resolution after HostRegistry can supply effective values through normal target resolution; preserve value-only UI refresh behavior.
- `src/HornetStudio.Editor.Tests/Program.cs` -> Update existing `valueRef` tests toward generic registry-consumer behavior and writeback preservation.
- `src/HornetStudio.Host.Tests/Program.cs` -> Add focused tests for `DataRegistry` and `UiFolderContext` reference-backed UDL attachment behavior.
- `docs/workitems/ChatHandoff.md` -> Document implementation result and benchmark state.

## Implementation Order
1. Add a small `DataRegistryValueReference`-style concept to HostRegistry with public path, public parameter, source item/path, source parameter, and optional metadata fields.
2. Add registry APIs for registering/removing references without changing existing `TryResolve`, `UpdateValue`, `UpdateProperty`, and `UpsertSnapshot` callers broadly.
3. Implement effective read resolution so consumers resolving the public item/property see the runtime-backed value when the reference is valid.
4. Implement public change notification for referenced source changes so `ItemChanged` still reports the public path and parameter, not a widget-specific runtime path.
5. Integrate the reference registration into `UiFolderContext.AttachedItemLink` only for UDL runtime attachments and initially only for `read` channel parameter `read`.
6. Keep `PublishSnapshotUpsert(...)` as the fallback path for structural changes, missing references, invalid source items, and non-UDL attachments.
7. Update `UdlHostRegistryProjection` so it declares the reference mapping at attach/projection time instead of relying on widgets to interpret `valueRef*`.
8. Simplify `PageItemModel` by preferring normal registry target resolution; keep any existing Signal `valueRef` path only as temporary legacy fallback if tests show it is still needed.
9. Add/adjust tests in Host first, then Editor.
10. Build and benchmark.

## Technical Constraints
- Chat, handoffs, and explanations are German-facing where applicable; code, comments, XML docs, UI text, file names, and technical identifiers are English.
- Use existing Amium item models and HostRegistry patterns.
- Do not introduce new runtime dependencies.
- Do not make visual controls own UDL runtime lifecycles.
- Registry event handlers must filter before scheduling UI work.
- No broad registry scanning or global event reaction.
- Reference-backed items must not create two authoritative values.
- Public protected properties such as `valueRefPath` and `valueRefParameter` must remain hidden from user-facing pickers and guarded writes.

## Acceptance Criteria
- Public UDL attachment paths remain unchanged.
- Public UDL `read` items resolve their read value from the authoritative runtime item when the reference is valid.
- Public HostRegistry snapshots no longer need to be the authoritative live-value storage for UDL reads.
- Widgets can keep using public HostRegistry paths without UDL-specific runtime knowledge.
- Existing writeback behavior still updates the public write target and reaches the UDL runtime writeback loop.
- Invalid or missing references fall back to the previous snapshot behavior.
- Non-UDL attachments behave as before.
- Signal-specific `valueRef` logic is removed or clearly demoted to compatibility fallback.
- No high-frequency per-event logging is introduced.

## Out of Scope
- Chart-specific reference handling.
- EnhancedSignal migration.
- Full Registry API redesign.
- Removing legacy snapshot publication entirely.
- Startup/warmup UI spike investigation unless this change directly regresses it.
- Release/versioning work.

## Risks / Watchouts
- If `TryResolve` returns mutable runtime-backed item objects directly, writes could bypass the public writeback route. Reads must be effective, writes must remain guarded.
- If public `ItemChanged` events are raised with runtime paths, widgets will need runtime-specific knowledge again. Events for public attachments must remain public-path scoped.
- If snapshots overwrite protected reference metadata, references can silently disappear and fallback will mask the issue.
- If both public snapshot values and runtime references are updated as independent live values, the two-truth problem remains.
- If the reference registry stores stale `ItemModel` references after detach/disconnect, public paths may resolve old runtime values.

## Notes
- The existing `valueRefPath` / `valueRefParameter` names are acceptable as compatibility metadata, but the architectural owner should be `HostRegistries.Data`, not `PageItemModel`.
- The initial reference target is specifically the UDL read subitem plus parameter:

```text
runtime.udl_client.<client>.<module>.read + read
```

- Keep the first implementation narrow. A later workitem can decide whether reference-backed items should become a broader registry capability.
