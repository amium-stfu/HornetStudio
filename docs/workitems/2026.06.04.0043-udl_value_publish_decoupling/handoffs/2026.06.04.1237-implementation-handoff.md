# IMPLEMENTATION HANDOFF

## Goal
Determine whether the remaining UDL throughput gap is caused partly or mostly by the detailed per-module diagnostics added during the isolation work.

Current measurement:

- Scenario: `UdlLoggingOverheadCheck-30s`
- `DemoGenerate`: about `165.73/s`, about `8.30 Hz` per module.
- Target: about `200/s`, about `10 Hz` per module.
- `DemoLoopTotal`: about `8.26/s`, `P95=14.3 ms`, `Max=28.5 ms`.
- Fine-grained diagnostic stages recorded thousands of events per run:
  - `DemoSetRead`
  - `DemoSetOut`
  - `DemoSetSet`
  - `DemoSetState`
  - `DemoSetAlert`
  - `DemoApplyModuleSnapshot`
  - `DemoComputeTargetValue`
  - `DemoFrameReceived`
  - `UdlRuntimeFrameReceived`
- The remaining gap may be distorted by measurement overhead.

## Scope
- Add a way to disable or heavily sample fine-grained UDL loop diagnostics during benchmark runs.
- Keep high-level benchmark stages needed for comparison.
- Run an A/B benchmark:
  - A: current detailed diagnostics.
  - B: reduced UDL detail diagnostics.
- Do not change UDL product behavior unless the A/B result proves diagnostics are the rest bottleneck.
- Do not remove all diagnostics permanently; keep a practical way to re-enable detailed diagnostics when debugging.

## Starting Point
- The runtime/product path has already improved from about `45/s` to about `165/s`.
- Detailed loop-stage diagnostics now record enough events to plausibly affect the measured throughput.
- The product goal is still about `200/s`.
- The next step must distinguish real product overhead from diagnostic overhead.

## Tasks
1. Locate all new or existing per-module UDL loop diagnostic recording calls.
2. Classify diagnostics into:
   - high-level diagnostics to keep by default.
   - fine-grained diagnostics to disable or sample.
3. Add a benchmark-safe switch or sampling guard for fine-grained UDL diagnostics.
4. Keep these high-level stages active:
   - `DemoGenerate`
   - `RegistryPublish`
   - `SignalReceive`
   - `TargetValueRefreshExecuted`
   - UI benchmark summary.
5. Disable or sample these fine-grained stages by default:
   - `DemoSetRead`
   - `DemoSetOut`
   - `DemoSetSet`
   - `DemoSetState`
   - `DemoSetAlert`
   - `DemoApplyModuleSnapshot`
   - `DemoComputeTargetValue`
   - `DemoFrameReceived`
   - `UdlRuntimeFrameReceived`
   - `UdlProjectionFrameReceived`
   - `DemoLoopUpdateModules`
   - `DemoLoopTotal`
6. Build.
7. Run a 30s benchmark with reduced detail diagnostics.
8. Compare directly against `UdlLoggingOverheadCheck-30s`.
9. If reduced diagnostics bring `DemoGenerate` near `200/s`, document that the remaining measured gap was diagnostic overhead.
10. If reduced diagnostics do not materially improve throughput, continue with product-path optimization based on the remaining high-level counters.
11. Update `docs/workitems/ChatHandoff.md`.

## Implementation Order
1. Search for diagnostic stages:

```powershell
rg -n "DemoSet|DemoApplyModuleSnapshot|DemoComputeTargetValue|DemoFrameReceived|DemoLoop|UdlRuntimeFrameReceived|UdlProjectionFrameReceived|UdlSynchronizeBitValues" src
```

2. Inspect how `UiResponsivenessDiagnostics.RecordSignalPipelineEvent` gates and aggregates events.
3. Add a clear, low-overhead guard for fine-grained UDL detail diagnostics. Prefer one of:
   - a static `ShouldCaptureUdlDetailDiagnostics()` helper.
   - an environment variable read once and cached.
   - a benchmark detail level already supported by existing diagnostics.
4. Default the fine-grained stages to off for normal benchmark runs.
5. Preserve `DemoGenerate` and the existing registry/signal/target summaries.
6. Build:

```powershell
dotnet build HornetStudio.sln --no-restore
```

7. Run:

```powershell
scripts\run_ui_benchmark.ps1 -Seconds 30 -ProjectPath 'benchmarks\ui_lag_bench_project\project.aaep' -Scenario 'UdlReducedDiagnostics-30s'
```

8. Compare:
   - `DemoGenerate`
   - `SignalReceive`
   - `RegistryPublish[SteadyState]`
   - `TargetValueRefreshExecuted[SteadyState->SteadyState]`
   - UI summary.
9. Optional, only if the switch supports it cleanly: run a detail-on benchmark with the same build to confirm the delta is caused by diagnostics.
10. Update `docs/workitems/ChatHandoff.md`.

## Out of Scope
- Further product-path optimization before the A/B result.
- Changing UDL module timers.
- Changing attachment shape.

## Risks / Watchouts
- A diagnostic guard that checks environment variables per event may itself become overhead. Cache any setting once.
- Removing too much diagnostics can make the benchmark inconclusive; keep high-level counters.
- If throughput improves only partially, diagnostics may be one contributor but not the whole remaining gap.
- Make sure reduced diagnostics are disabled only for detail stages, not for the benchmark summary itself.
