# DEBUG REPORT

## Problem
UDL-backed Signal widgets are very slow after startup, then recover, and benchmark telemetry oscillates between severe warmup delay and much better steady-state throughput.

## Expected Behavior
Signal widgets should resolve their live display value from the runtime-backed UDL read source without long startup stalls, and benchmark status should remain within budget during warmup and steady state.

## Actual Behavior
Before the cache fix, the 60-second benchmark failed badly with very low steady-state `TargetValueRefreshExecuted[SteadyState->SteadyState]` throughput. After caching Signal `valueRef` metadata/runtime resolution in `PageItemModel`, the same benchmark improved from `Fail` to `Warn`, with steady-state throughput recovering strongly, but warmup still exceeded the soft budget. A follow-up attempt to coalesce initial `ResolveTarget()` refreshes worsened the result back to `Fail` and was reverted.

- `UdlSignalValueRef-DebugCache-60s`: warmup still showed `TargetValueRefreshExecuted[Warmup->Warmup] DelayP95Ms=5194.8` and `TargetRefreshExecuted[Warmup->Warmup] DelayP95Ms=5059.8`.
- `UdlSignalValueRef-StartupCoalesce-60s`: `Status=Fail`, `MaxUiDelayMs=9154.4`, `P95UiDelayMs=122.7`, `SignalLatestValueApplied=122.654/s`, `TargetValueRefreshExecuted[SteadyState->SteadyState]=122.321/s`, `TargetRefreshExecuted[Warmup->Warmup] DelayP95Ms=7786.5`.
- No `SignalValueRefResolved` benchmark summary stage appeared in the runtime log for either scenario, while `SignalFallbackRegistryPathUsed` remained dominant.

## Relevant Code
- `src/HornetStudio.Editor/Models/PageItemModel.cs`
  - `RefreshSignalValueReferenceCache()` caches `valueRefPath`, `valueRefParameter`, and the resolved runtime item when `Target` changes.
  - `ResolveTargetProperty(...)` still records `SignalFallbackRegistryPathUsed` heavily during the benchmark.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs`
  - Publishes `valueRefPath` and `valueRefParameter` onto public attached UDL read items.
- `src/HornetStudio.Host/UiFolderContext.cs`
  - Preserves protected `valueRef*` properties across snapshot refreshes.

## Attempted Fixes
- Fix 1 -> Publish and preserve `valueRef` metadata on public attached UDL read items; focused tests passed, but full 60-second benchmark still failed.
- Fix 2 -> Cache Signal `valueRef` metadata/runtime resolution in `PageItemModel`; focused tests passed and benchmark improved from `Fail` to `Warn`, restoring strong steady-state throughput.
- Fix 3 -> Route initial `ResolveTarget()` refreshes through `RequestTargetRefresh()` to coalesce startup work; benchmark worsened back to `Fail`, so the change was reverted.

## Current Hypothesis (optional)
- The primary steady-state regression came from repeated getter-time reconstruction of Signal `valueRef` resolution, which the cache fix removed.
- The remaining startup slowness is not caused by the immediate `ResolveTarget()` refresh path alone.
- `SignalFallbackRegistryPathUsed` likely over-counts fallback reads inside display-property resolution or another high-frequency binding/getter path, so diagnostics currently overstate how often the system truly misses the runtime-backed `valueRef` path.
- The next targeted debug step should inspect where `ResolveTargetProperty(...)` records `SignalFallbackRegistryPathUsed` and distinguish real fallback decisions from repeated display-value reads using already-cached state.
