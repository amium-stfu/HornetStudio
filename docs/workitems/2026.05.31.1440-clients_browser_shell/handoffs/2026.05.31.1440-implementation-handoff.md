# IMPLEMENTATION HANDOFF

## Goal
Replace the UDL-only browser direction with a generic folder-local `ClientsBrowser` shell that resolves the folder's `Clients/` directory. The first implementation supports UDL clients from `Clients/Udl/*.yaml`; the shell should be shaped so ItemClient support can be added later without redesigning the browser.

## Scope
Included:
- Create or rename the current UDL browser concept into a generic `ClientsBrowser` UI.
- The browser resolves only the selected folder's `Clients/` directory and builds the visible client list from discovered client definition files.
- First supported client type: UDL via `Clients/Udl/*.yaml`.
- Left pane: generic client list.
- Right pane: type-specific detail area; first detail implementation is UDL.
- UDL detail layout:
  - Header similar to the old `UdlClientWidget`.
  - Body contains only `Received` and `Attached`.
  - Footer contains diagnostics.
- Runtime, auto-start, projection, and ItemTree publishing remain completely independent from the browser.
- Browser can query/command runtime managers, but must not own, create as a prerequisite, or dispose runtime/projection lifetimes.
- Prepare the left-list model and shell boundaries for future ItemClient entries, but do not fully implement ItemClient unless it is trivial and already file-backed under `Clients/`.

Explicitly not included:
- Full ItemClient browser/detail implementation.
- A generic client framework with broad abstractions beyond the shell/list boundary.
- A UDL status/view widget.
- Reintroducing UDL widgets as runtime anchors.
- Changing the `Clients/Udl/<client-id>.yaml` file layout.
- Moving runtime startup into the browser.
- Release/versioning work.

## Starting Point
- File-backed UDL clients now start and project without `UdlClientControl` widgets.
- A UDL browser layout plan exists, but the target has changed to a generic `ClientsBrowser` shell.
- User wants the browser itself to be only visualization/editor over `./Clients`.
- User wants runtime ownership fully separated from the browser.
- Current desired detail layout is closer to the old UDL widget:
  - Header: compact state/config summary.
  - Body: `Received` and `Attached` only.
  - Footer: diagnostics.
- Left client list item must be 3 lines:
  - Header: client name plus `[Status]`
  - Type
  - Socket

## Tasks
1. Define the generic browser shell.
   - Name the UI `ClientsBrowser` or project-consistent equivalent.
   - Resolve the active folder's `Clients/` directory.
   - Enumerate known type directories under `Clients/`.
   - For this first step, support `Clients/Udl/*.yaml`.
   - Ignore unsupported directories gracefully, optionally logging/debugging but not failing.
2. Define the generic left-list item model.
   - Required fields:
     - `ClientId`
     - `Text`
     - `ClientType`
     - `StatusText`
     - `SocketText`
     - `DefinitionFilePath`
   - Layout:
     - line 1: display name/client name and status badge
     - line 2: type, e.g. `UDL Demo` or `UDL Hardware`
     - line 3: socket, e.g. `192.168.178.151:9001`
   - Keep it usable for future ItemClient entries without adding full ItemClient support now.
3. Implement UDL adapter/source.
   - Load UDL entries from `Clients/Udl/*.yaml` using `UdlClientDefinitionFileCodec`.
   - Build generic list entries from UDL definition and runtime snapshot/status.
   - Save UDL changes back to the same definition file.
   - Query/command `UdlClientRuntimeManager` only as observer/controller.
4. Implement the right-side detail host.
   - Select detail UI by `ClientType`.
   - Initially implement only UDL detail.
   - Show an empty or unsupported state for unknown future types.
5. Implement UDL detail header.
   - Match the compact old-widget feel:
     - large client text/name
     - mode and socket line: `Demo | host:port` or `Hardware | host:port`
     - connection state text
     - status badge
     - connect/disconnect action
     - compact settings/edit entry for properties
   - Properties represented in header/settings:
     - `Text`
     - `Host`
     - `Port`
     - `Enabled`
     - `AutoConnect`
     - `DebugLogging`
     - `DemoEnabled`
     - client id readonly or rename-driven
   - Avoid a large permanent form dominating the browser.
6. Implement UDL detail body.
   - Body contains only two main panels:
     - `Received`
     - `Attached`
   - `Received` panel:
     - header button `[All]`
     - header button `[AddDemo]` only when `DemoEnabled == true`
     - each row shows item/module name and status indicator
     - each row has `[Attach]` or disabled `[Attached]`
   - `Attached` panel:
     - each row shows item/module name and status indicator
     - each row has `[Edit]` and `[Detach]`
   - Do not keep a separate `Modules` panel in the first layout.
7. Implement UDL detail footer.
   - Show diagnostics compactly:
     - connection state
     - endpoint/socket
     - counters
     - last diagnostic/error
     - definition file path
     - status path
     - runtime root
   - Footer should not compete with the body as the primary workflow.
8. Ensure browser/runtime separation.
   - Opening browser must not start runtime if folder lifecycle did not already do so, except explicit user commands such as Connect.
   - Closing browser must not disconnect or release runtime.
   - Selecting another client must not recreate runtime.
   - Saving definition may ask runtime manager to sync definitions, but runtime ownership remains outside the browser.
9. Add tests where practical.
   - UDL client source enumerates `Clients/Udl/*.yaml`.
   - Generic list entry fields are built correctly for UDL.
   - Browser close/dispose does not release runtime.
   - Save writes to UDL YAML and triggers sync only through the runtime manager boundary.
10. Update documentation.
   - Describe `ClientsBrowser` as folder-local `Clients/` editor/inspector.
   - Document that first supported type is UDL.
   - Clarify that runtimes and headless projection run without the browser.

## Implementation Order
1. Inspect existing browser windows and the current UDL browser implementation if present.
2. Create/rename the browser shell to `ClientsBrowser`.
3. Implement folder `Clients/` enumeration with UDL-only support first.
4. Implement the 3-line left-list layout.
5. Implement type-specific detail host with UDL detail.
6. Rework UDL header to compact old-widget-style summary/settings rather than large form.
7. Rework UDL body to only `Received` and `Attached`.
8. Move module-only information into received rows or diagnostics as needed; do not keep a separate `Modules` panel.
9. Implement footer diagnostics.
10. Wire connect/disconnect and save through existing manager/codec boundaries.
11. Verify runtime is unaffected by browser open/close/selection changes.
12. Add tests/docs/build.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Public classes and public methods require XML documentation.
- Use existing Avalonia/browser dialog patterns.
- Do not add new external dependencies.
- Browser is a visualization/editor over `./Clients`; it is not runtime owner.
- Runtime startup belongs to folder lifecycle and explicit connect commands, not browser initialization.
- Projection and ItemTree publishing must keep working without browser.
- Browser subscriptions must be scoped to selected/visible client paths and must filter before UI dispatch.
- Avoid a generic framework beyond the minimal shell/list/detail boundary until ItemClient support is actually implemented.
- Keep the first implementation focused on UDL support.

## Acceptance Criteria
- A `ClientsBrowser` opens for a folder and resolves that folder's `Clients/` directory.
- UDL clients from `Clients/Udl/*.yaml` appear in the left list.
- Left list items show:
  - client name plus status on line 1,
  - type on line 2,
  - socket on line 3.
- Selecting a UDL client shows UDL-specific details on the right.
- UDL header is compact and similar in purpose to the old widget header.
- UDL body contains only `Received` and `Attached`.
- `Received` has `[All]`, conditional `[AddDemo]`, and row-level `[Attach]` or disabled `[Attached]`.
- `Attached` has row-level `[Edit]` and `[Detach]`.
- Footer shows diagnostics.
- Opening/closing the browser does not start, stop, dispose, or otherwise own runtime/projection.
- Runtime/projection continue to work when the browser is closed.
- The design can later add ItemClient entries without replacing the browser shell.

  - Confirm received/attached interactions behave as expected.
  - Close the browser and confirm runtime/projection remains active.

## Out of Scope
- Complete ItemClient implementation.
- Generic client plugin/provider framework.
- Separate UDL status/view widget.
- Moving runtime or projection ownership into the browser.
- Major redesign of UDL runtime/projection.
- Release/versioning.

## Risks / Watchouts
- Naming the browser generically can tempt over-abstraction. Keep only the shell generic and UDL detail concrete.
- Reusing `UdlClientControl` code must not reintroduce visual-control-owned runtime behavior.
- Runtime status snapshots may not yet expose all diagnostics needed for the footer; add narrow snapshot APIs rather than coupling to UI controls.
- Unsupported directories under `Clients/` should not crash the browser.
- If ItemClient currently is not file-backed under `Clients/`, do not force it into this step.
