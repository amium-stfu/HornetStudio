# IMPLEMENTATION HANDOFF

## Goal
Instrument the high-frequency public signal update path so benchmark runs can identify the first bottleneck between UDL demo value generation and visible Signal widget updates.

## Scope
- Add lightweight diagnostics for the update chain described in `docs/workitems/ChatHandoff.md`.
- Measure rates and delays for 20 UDL demo values at 10 Hz shown as 20 Signal widgets.
- Reuse the existing benchmark/diagnostics infrastructure where possible.
- Keep changes focused on observability.
- Do not optimize, throttle, coalesce, or refactor the update path in this workitem.
- Do not introduce new runtime dependencies.

## Starting Point
- The suspected bottleneck is not the UDL demo runtime itself.
- The suspected bottleneck is the path:
  `UDL demo value update -> attached public HostRegistry item update -> HostRegistries.Data.ItemChanged -> SignalWidget/PageItemModel target refresh -> Avalonia binding/text render`.
- The current benchmark project is `benchmarks/ui_lag_bench_project/project.aaep`.
- Expected load for the target scenario is about 200 public value updates per second.
- `docs/workitems/active.yaml` is a FIFO queue; do not remove entries during implementation.

## Tasks
1. Inspect the current diagnostics implementation in `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs`.
2. Locate or confirm the current replacement/path for the referenced `UdlSignalGapDiagnostics` file if it does not exist.
3. Add benchmark aggregation for named high-frequency signal pipeline stages:
   - `DemoGenerate`
   - `RegistryPublish`
   - `SignalReceive`
   - `TargetRefreshQueued`
   - `TargetRefreshExecuted`
   - optional chart stages only if already naturally present in the existing chart diagnostics.
4. Add instrumentation at the relevant code points without changing behavior.
5. Include per-stage total count, per-second rate, top path/module summaries, and delay/timing summaries where available.
6. Ensure the instrumentation is active only when existing UI diagnostics or benchmark mode is enabled.
7. Keep non-benchmark overhead minimal, preferably an early return when diagnostics are disabled.
8. Run the focused benchmark after build if possible and summarize where the first measurable drop or delay appears.

## File-Level Changes
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> Extend existing benchmark aggregation with high-frequency signal pipeline counters and summary logging.
- `src/HornetStudio.Editor/Widgets/UdlClient/SimulatedHostUdlClient.cs` -> Record `DemoGenerate` events when demo frames are produced.
- `src/HornetStudio.Editor/UdlClients/UdlClientRegistryProjection.cs` and/or `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs` -> Record `RegistryPublish` when attached public values are written to `HostRegistries.Data`.
- `src/HornetStudio.Editor/Models/PageItemModel.cs` -> Record `SignalReceive`, `TargetRefreshQueued`, and `TargetRefreshExecuted` around the existing target refresh path.
- `scripts/run_ui_benchmark.ps1` -> Update only if the existing benchmark output cannot surface the new summary clearly.
- `docs/workitems/ChatHandoff.md` -> Update only if implementation discovers a corrected file path or important measurement convention that future chats need.

## Implementation Order
1. Search for existing diagnostics calls and benchmark summary logging to match local style.
2. Add a small public diagnostics API to `UiResponsivenessDiagnostics`, for example `RecordSignalPipelineEvent(...)` and timing/delay helpers if needed.
3. Add benchmark-session storage for stage counters and path summaries.
4. Emit the new high-frequency signal summary in the existing benchmark summary log.
5. Instrument UDL demo generation.
6. Instrument public registry projection writes.
7. Instrument `PageItemModel` receive/queue/execute points.
8. Build the solution.
9. Run one benchmark with 20 attached values without chart if practical.
10. Use results to decide whether the full 1/5/10/20 matrix is still needed.

## Technical Constraints
- Follow existing diagnostics patterns and `HostLogger` usage.
- Code, comments, XML documentation, UI text, and technical identifiers must be English.
- Chat responses must be German.
- Do not read Avalonia UI objects from background/runtime threads in diagnostics.
- Registry event filtering must happen before scheduling UI work.
- Do not introduce new services or abstractions unless the existing diagnostics class cannot reasonably hold the measurement.
- Prefer named parameters for unclear or multi-parameter calls.

## Acceptance Criteria
- Benchmark logs include a distinct high-frequency signal pipeline summary.
- The summary can compare expected vs observed counts/rates for `DemoGenerate`, `RegistryPublish`, `SignalReceive`, `TargetRefreshQueued`, and `TargetRefreshExecuted`.
- The summary includes enough path/module detail to see whether all 20 values participate.
- The instrumentation is disabled unless diagnostics/benchmark mode is enabled.
- No behavior-changing optimization is included.
- The solution builds.

## Verification
- `dotnet build HornetStudio.sln --no-restore`
- If build succeeds and benchmark execution is practical:
  `scripts\run_ui_benchmark.ps1 -Seconds 120 -ProjectPath 'benchmarks\ui_lag_bench_project\project.aaep' -Scenario 'HighFrequencySignalDiagnostics-20x10Hz'`
- Inspect the latest benchmark log summary for the new pipeline stages.

## Out of Scope
- Coalescing Signal widget UI updates.
- Adding a value-only fast path.
- Changing UDL demo behavior.
- Changing public HostRegistry semantics.
- Reworking chart sampling/rendering.
- Broad refactoring of `PageItemModel`.

## Risks / Watchouts
- Per-event logging would distort the benchmark; aggregate in memory and log summaries.
- Path summaries must be bounded to avoid unbounded memory growth.
- Avoid adding dispatcher work just for diagnostics.
- Do not assume `UdlSignalGapDiagnostics.cs` exists; confirm the current file layout first.
- If `PageItemModel` receives all registry events globally, instrumentation must distinguish total events from relevant Signal widget events.
