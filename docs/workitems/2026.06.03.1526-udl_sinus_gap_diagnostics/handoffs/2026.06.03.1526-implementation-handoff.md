# IMPLEMENTATION HANDOFF

## Goal
Add focused diagnostics that prove whether the minimal UDL demo sine signal is generated, received, published, and recorded at stable intervals before investigating chart rendering or widget settings lag.

## Scope
- Add lightweight aggregated gap diagnostics for the UDL sine value path used by the minimal benchmark project.
- Measure timing gaps without logging every value.
- Keep the diagnostics narrow enough that they do not materially add load.
- Use the diagnostics to run a clean benchmark baseline without UI interaction, then a second benchmark with SignalWidget settings opened.
- Do not refactor chart rendering, SignalWidget settings, monitor actions, or UDL runtime ownership in this workitem unless the diagnostics prove that a tiny local fix is required to make the measurements valid.

## Starting Point
- The current minimal demo contains only one `SignalWidget` with `History=120s`, one `UdlClient`, and one demo module.
- The previous broader 120s interactive benchmark failed with UI-thread spikes during chart creation/editing and repeated chart render warnings.
- The current missing evidence is whether the UDL sine value itself has timing gaps before the chart or SignalHistory display path.
- The log was deleted by the user to provide a clean basis.

## Tasks
1. Locate the UDL demo module value generation path for the sine signal, likely the source for `udl1.m001`.
2. Locate the UDL client receive/publish path that forwards the value into the host/runtime registry.
3. Locate the SignalWidget or SignalHistory append path used by the current minimal demo.
4. Add aggregated gap diagnostics at the narrowest useful points:
   - generation or demo-module output, if available
   - UDL receive or runtime input
   - registry publish or runtime value publish
   - SignalHistory append, if the path is easy to identify
5. Emit periodic summary log lines, not per-value logs.
6. Run a clean baseline benchmark without UI interaction.
7. Run a second benchmark where the SignalWidget settings are opened once and the timestamp is recorded.
8. Compare whether gaps already exist before UI/SignalHistory, or only appear after SignalWidget/UI interaction.

## Implementation Order
1. Search for the source path `udl1.m001`, demo module update loop, and UDL publish calls.
2. Identify the fewest reliable instrumentation points.
3. Add a small in-process aggregator that tracks `Count`, `AvgGapMs`, `P95GapMs`, `MaxGapMs`, `GapsOver250Ms`, and `GapsOver1000Ms` per source.
4. Ensure the aggregator logs periodically, for example every 5 seconds, and can be scoped to `udl1.m001` or equivalent benchmark signal.
5. Build the solution.
6. Run `#bench 120` or the equivalent benchmark script without UI interaction.
7. Run a second `120s` benchmark with one SignalWidget settings-open interaction.
8. Summarize whether the gap source is UDL generation, UDL receive/publish, registry/history, or UI/display only.

## Technical Constraints
- Chat responses must be in German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be in English.
- Do not add new dependencies.
- Prefer existing diagnostics/logging patterns.
- Keep runtime diagnostics cheap and aggregated.
- Do not log every value in steady state.
- Avoid UI-thread reads from background diagnostics.
- Do not broaden registry reactions or add dispatcher posts.

## Acceptance Criteria
- Benchmark logs contain aggregated gap lines for the sine signal path.
- The diagnostics identify at least one of these outcomes:
  - gaps exist at demo generation
  - gaps appear at UDL receive/publish
  - gaps appear only after registry/history
  - gaps are not present in the value pipeline and the issue is UI/display-side
- A clean no-interaction benchmark can be interpreted without relying on visual chart judgment.
- A settings-open benchmark can be correlated to the same gap diagnostics.
- No per-value log flood is introduced.

## Verification
- Build: `dotnet build HornetStudio.sln --no-restore`
- Baseline benchmark: `powershell -ExecutionPolicy Bypass -File scripts\run_ui_benchmark.ps1 -Seconds 120 -ProjectPath benchmarks\ui_lag_bench_project\project.aaep -Scenario UdlSinusGapBaseline-120s`
- Interaction benchmark: `powershell -ExecutionPolicy Bypass -File scripts\run_ui_benchmark.ps1 -Seconds 120 -ProjectPath benchmarks\ui_lag_bench_project\project.aaep -Scenario UdlSinusGapSettingsOpen-120s`
- Log review: search for the diagnostic prefix, UI responsiveness spikes, SignalWidget settings timing, UDL publish timing, and benchmark summaries.

## Out of Scope
- Reworking chart rendering.
- Reworking SignalWidget settings UI.
- Reworking UDL runtime architecture.
- Changing demo project structure beyond what is necessary to keep the minimal benchmark usable.
- Adding permanent high-volume logging.

## Risks / Watchouts
- Logging every value would distort the benchmark; use aggregate summaries only.
- Instrumenting only the chart side will not prove whether UDL is healthy.
- Measuring on the UI thread can turn the diagnostic into the source of the problem.
- If source names differ from `udl1.m001` in the reduced demo, adapt the diagnostic matching to the actual runtime path.
