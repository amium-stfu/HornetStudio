# IMPLEMENTATION HANDOFF

## Goal
Make file-backed UDL clients from `Clients/Udl/<client-id>.yaml` visible and useful without requiring an existing `UdlClientControl` widget or a browser UI. A folder/client-scoped headless projection must publish UDL status and explicitly attached client items into the HostRegistry/ItemTree according to the new architecture.

## Scope
Included:
- Add or complete a headless UDL client projection layer for file-backed clients.
- Ensure `Clients/Udl/<client-id>.yaml` definitions are logged/diagnosable when loaded and synchronized.
- Ensure `AutoConnect=true` and `DemoEnabled=true` create/start the runtime for a file-backed client.
- Publish status for file-backed clients without a visual control.
- Publish explicitly attached items from `AttachedItemPaths` without a visual control.
- Keep raw received items/internal runtime data out of the public project tree unless explicitly attached/published.
- Keep existing legacy `UdlClientControl` widgets as temporary UI/management adapters only; they must not be required for ItemTree projection.
- Update the demo project so the file-backed UDL client is the effective source for `udl1`.
- Add focused tests for file-backed load -> runtime sync -> headless projection behavior where practical.

Explicitly not included:
- Building the final UDL browser UI.
- Adding a separate UDL status/view widget.
- Broad redesign of the ItemTree.
- Introducing a generic client framework for future client types.
- Reverting to widget-owned UDL runtime or widget-owned registry publishing.
- Release/versioning work.

## Starting Point
- The demo still contains `UdlClientControl` widgets in folders.
- `samples/HornetStudioDemo/Folders/main/Clients/Udl/udl1.yaml` exists and contains `AutoConnect: true`, `DemoEnabled: true`, and `AttachedItemPaths: [m001]`.
- The log shows legacy status paths such as `studio.main.udl_client_control_1.status.*`, but no clear evidence that `Clients/Udl/udl1.yaml` is loaded as `udl1` or projected as `studio.main.udl1.*`.
- There is no browser yet, so users have no UI fallback for observing file-backed UDL clients.
- `src/HornetStudio.Editor/UdlClients/UdlClientRuntimeManager.cs` owns runtime synchronization.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs` already exists and may be reusable, but it is currently tied to widget/control flows.
- `UdlClientControl.axaml.cs` still contains status publishing and attach projection code paths, which is the wrong long-term owner.

## Tasks
1. Define the headless projection responsibility.
   - Input: folder name, client definition, active `UdlClientRuntime`.
   - Output: HostRegistry status branch and public attached item branches.
   - No Avalonia control dependency.
   - No visual tree dependency.
2. Define stable registry paths.
   - Status path should be based on the file-backed client id, for example `studio.<folder>.<client-id>.status.*`.
   - Runtime/internal path should remain scoped, for example existing `runtime.udl_client.<client-id>` conventions unless a compatibility reason requires otherwise.
   - Attached public items must appear where existing item selection/Signal widgets can consume them.
   - Do not publish broad raw received data into the public project tree.
3. Integrate projection with runtime manager lifecycle.
   - Create/update projection when a runtime is created or synchronized from a definition.
   - Refresh projection when runtime structure changes, attached paths change, or client definition changes.
   - Dispose/remove projection when a folder is released, a client is deleted, disabled, disconnected where appropriate, or runtime identity changes.
4. Make file-backed load/sync diagnosable.
   - Log loaded UDL client definition count per folder.
   - Log runtime sync/start failures with folder and client id.
   - Log projection attach failures with folder, client id, and attached path.
   - Avoid noisy logs on high-frequency value updates.
5. Move projection logic out of widget ownership.
   - Reuse existing projection code if possible, but relocate ownership to the UDL clients runtime/projection layer.
   - `UdlClientControl` may observe and command the runtime; it must not be the only publisher.
   - Avoid duplicated status publishing from both widget and headless projection for the same client.
6. Preserve explicit attach semantics.
   - If `AttachedItemPaths` contains `m001`, publish `m001` without needing the widget to be visible.
   - If `AttachedItemPaths` is empty, status may publish, but raw module items must remain internal/unpublished.
7. Fix the demo behavior.
   - Ensure `udl1.yaml` produces visible status and attached `m001`.
   - Remove or neutralize stale legacy UDL widget assumptions if they conflict with file-backed `udl1`.
   - Do not rely on a browser to make the demo observable.
8. Add tests.
   - File-backed client with demo module and `AttachedItemPaths` creates expected projection after runtime sync.
   - File-backed client without `AttachedItemPaths` does not publish raw public item branches.
   - Folder release removes/disposes projection-owned status/attached state as expected.
   - Legacy widget is not required for projection.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Public classes and public methods require XML documentation.
- Use existing libraries and patterns; do not add dependencies.
- Do not build a browser as a workaround for missing projection.
- Do not add a new UDL status/view widget.
- Runtime and projection ownership must be folder/client-scoped, not visual-control-scoped.
- Registry event handling must be scoped and filtered before any UI-thread dispatch.
- High-frequency runtime values must not trigger broad UI/tree rebuilds.
- Receiving raw UDL data must not create public HostRegistry items unless attached/published explicitly.
- Preserve `Clients/Udl/<client-id>.yaml` as the authoritative definition source.

## Acceptance Criteria
- A UDL client defined only by `Clients/Udl/udl1.yaml` can publish status without any visible `UdlClientControl`.
- `AttachedItemPaths: [m001]` publishes the attached `m001` item into the ItemTree/public registry without needing a widget or browser.
- A UDL client without attached paths does not publish raw received module data into the public project tree.
- Logs show whether UDL client files were loaded and whether runtime/projection startup succeeded or failed.
- The demo project shows usable UDL status/data from the file-backed `udl1` configuration.
- Existing legacy `UdlClientControl` widgets are not required for the projection to work.
- No duplicate/conflicting status branches are produced for the same file-backed client.

## Out of Scope
- UDL browser implementation.
- UDL view/status widget implementation.
- Generic client architecture.
- Migration tooling for released user data.
- Performance benchmarking beyond checking that projection does not enqueue broad UI work.
- Release/versioning tasks.

## Risks / Watchouts
- Existing widget code may still publish legacy paths like `studio.main.udl_client_control_1.status.*`, which can hide whether file-backed paths work.
- If projection runs before the demo runtime has received/generated module data, attached item creation may need a delayed refresh on runtime structure change.
- Fire-and-forget auto-connect can hide startup failures unless explicitly logged.
- Public path choice must be stable because Signal widgets will bind to it.
- Avoid treating the browser as the owner; browser absence must not prevent runtime or projection.
- Avoid publishing every received UDL item publicly; only explicit attach/publish configuration should do that.
