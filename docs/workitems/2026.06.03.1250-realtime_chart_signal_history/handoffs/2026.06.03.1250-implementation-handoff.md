# IMPLEMENTATION HANDOFF

## Goal
Refactor RealtimeChart history ownership so SignalWidget defines which signals are recorded and how quickly they are recorded. HistoryRuntime records only those configured SignalWidget sources. ChartControl no longer owns history, no longer samples item values, and only passes its `ViewSeconds` and series selection to a ChartDataProvider that returns ready-to-render snapshots.

## Scope
Included:
- Move history recording policy from ChartControl to SignalWidget configuration.
- Add or adapt a central HistoryRuntime that records only explicitly configured SignalWidget sources.
- Add a ChartDataProvider between HistoryRuntime and RealtimeChartControl.
- Change RealtimeChartControl to consume render-ready chart snapshots and keep only UI/render responsibilities.
- Update persistence, YAML defaults, widget property editing, docs, and focused tests for the new ownership model.

Explicitly not included:
- Long-term persistent recording such as SQLite.
- Redesigning chart interaction UX beyond fields required by the ownership change.
- Reworking unrelated widgets or global registry behavior.
- Adding new runtime dependencies.

## Starting Point
- `RealtimeChartRuntimeManager` currently parses chart series, resolves `Item` sources, samples values on a timer, stores chart-owned `List<ChartPoint>` history, trims by chart `HistorySeconds`, and exposes snapshots to the UI.
- `RealtimeChartControl` currently renders ScottPlot, owns render timing, calls `_chartState.GetSeriesSnapshots()`, creates `double[]` arrays during `RenderPlot()`, and performs nearest-point lookup through chart runtime state.
- `ChartControl` currently persists `RefreshRateMs`, `HistorySeconds`, `ViewSeconds`, and `ChartSeriesDefinitions`.
- `SignalWidget.yaml` already has `RefreshRateMs`, but it does not yet explicitly own chart history recording policy.
- Desired target:
  - `SignalWidget` owns `HistorySeconds` and `RecordingIntervalMs`.
  - `HistorySeconds = 0` means no history recording.
  - `HistoryRuntime` records only sources configured by SignalWidgets.
  - `ChartControl` owns `ViewSeconds`, render refresh, axes/style, and selected series only.
  - `ChartDataProvider` receives the chart visible range/series and returns immutable render-ready arrays.

   - returns `double[] timestamps` and `double[] values` ready for ScottPlot.
6. Refactor RealtimeChartRuntimeManager so it no longer owns chart history or samples current values.
7. Refactor RealtimeChartControl so render flow only applies provider snapshots to ScottPlot.
8. Adjust crosshair/nearest-point lookup to use provider snapshot data or provider API, not chart-owned raw history.
9. Update ChartControl docs and SignalWidget docs/help to explain ownership:
   - SignalWidget records.
   - ChartControl displays.
   - `ViewSeconds` belongs to ChartControl.
   - `HistorySeconds` and `RecordingIntervalMs` belong to SignalWidget.
10. Add focused tests for recording activation, no-history behavior, snapshot range extraction, and chart-provider behavior when a chart references a signal without enabled history.
11. Build and run focused validation.

## Technical Constraints
- Always answer in German in chat; code, comments, XML docs, UI text, file names, and technical identifiers remain English.
- Do not add new dependencies.
- Use existing `TargetPathHelper`, `HostRegistries.Data`, and `HostRegistries.Signals` patterns.
- Do not introduce global registry scans.
- HistoryRuntime must record only explicitly configured SignalWidget sources.
- Visual controls must not own long-running runtime lifecycles.
- UI thread must only render; expensive range extraction, filtering, and downsampling must happen outside the UI thread.
- `HistorySeconds = 0` means history disabled.
- ChartControl must not trigger hidden recording for missing history.

## Acceptance Criteria
- A SignalWidget with `HistorySeconds = 0` does not register or record history.
- A SignalWidget with `HistorySeconds > 0` and `RecordingIntervalMs > 0` records only its configured source.
- RealtimeChart no longer samples `Item.Value` directly and no longer owns per-chart history buffers.
- ChartControl passes only display concerns to the provider: series selection, `ViewSeconds`, render dimensions or max render points, axes/style metadata.
- ChartDataProvider returns immutable render-ready snapshots with `double[]` timestamps and `double[]` values.
- If a chart references a signal without enabled history, the chart shows no data for that series and does not start recording implicitly.
- UI render path no longer allocates chart arrays from raw `ChartPoint` history on every render.
- Documentation reflects SignalWidget recording ownership and ChartControl display ownership.

## Out of Scope
- Persistent disk recording.
- Replay UI.
- Statistics/export/report features.
- Broad SignalRegistry redesign.
- Changing monitor runtime behavior.
- Cleaning up the accidental monitor workitem artifacts from earlier chat context.

## Risks / Watchouts
- `FolderItemModel` currently uses shared properties for multiple widget kinds; avoid creating mixed ownership where ChartControl still writes `HistorySeconds`.
- Existing persisted ChartControl layouts may contain `HistorySeconds`; read compatibility can remain, but it must not become active recording ownership.
- If SignalWidget lifecycle is tied to visual controls, do not make visual controls own the long-running HistoryRuntime. Registration can be driven by loaded folder/widget definitions instead.
- Multiple SignalWidgets may reference the same source with different history policies. HistoryRuntime must define deterministic effective retention and interval behavior, preferably max retention and fastest required recording interval.
- Avoid UI-thread downsampling and LINQ array creation in `RenderPlot()`.
