# IMPLEMENTATION HANDOFF

## Goal
Refactor RealtimeChart history ownership so SignalWidget defines which signals are recorded and at which interval. HistoryRuntime records only those configured SignalWidget sources. ChartControl no longer owns history, no longer samples item values, and only passes its display range to a chart-specific ChartDataProvider.

## Scope
Included:
- Use SignalWidget `HistorySeconds` as the only history retention setting.
- Use SignalWidget `RefreshRateMs` as the history recording interval when `HistorySeconds > 0`.
- Do not introduce `RecordingIntervalMs`.
- Add or adapt a central HistoryRuntime that records only explicitly configured SignalWidget sources.
- Ensure each chart has its own ChartDataProvider, preferably owned by chart runtime state rather than the visual control.
- Change RealtimeChartControl to consume render-ready snapshots and keep only UI/render responsibilities.
- Fix the provider/UI thread boundary so provider background work never reads Avalonia properties directly or indirectly.
- Update persistence, YAML defaults, widget property editing, docs, and focused tests for the new ownership model.

Explicitly not included:
- Long-term persistent recording such as SQLite.
- Replay, statistics, reports, or export.
- Redesigning chart interaction UX beyond fields required by the ownership change.
- Reworking unrelated widgets or global registry behavior.
- Adding new runtime dependencies.

## Starting Point
- Current implementation has moved toward `HistoryRuntime` and `ChartDataProvider`, but the provider currently raises `SnapshotUpdated` from a background loop.
- The current log shows a thread-boundary violation:
  - `ChartDataProvider.RefreshLoopAsync`
  - `RealtimeChartControl.OnChartSnapshotUpdated`
  - `RealtimeChartControl.PageIsActive`
  - Avalonia `Call from invalid thread`
- `RealtimeChartControl.OnChartSnapshotUpdated` currently reads `PageIsActive` before dispatching to the UI thread.
- `ChartDataProvider` currently acts as a chart projection component. It must not be created by SignalWidget or HistoryRuntime.
- A chart provider is chart-specific because different charts can render the same history with different `ViewSeconds`, series, axes, render widths, and later custom visible ranges.
- Desired target:
  - `SignalWidget.RefreshRateMs` = display refresh and history recording interval for that signal.
  - `SignalWidget.HistorySeconds = 0` = no history recording.
  - `SignalWidget.HistorySeconds > 0` = record this source at `SignalWidget.RefreshRateMs`.
  - `HistoryRuntime` records only explicitly configured SignalWidget sources.
  - `ChartControl.ViewSeconds` defines visible range.
  - `ChartControl.RefreshRateMs` defines chart render/provider refresh cadence.
  - `ChartDataProvider` is per chart and reads shared HistoryRuntime data.
  - `RealtimeChartControl` reads Avalonia properties only on the UI thread.

## Technical Constraints
- Always answer in German in chat; code, comments, XML docs, UI text, file names, and technical identifiers remain English.
- Do not add new dependencies.
- Use existing `TargetPathHelper`, `HostRegistries.Data`, and `HostRegistries.Signals` patterns.
- Do not introduce global registry scans.
- HistoryRuntime must record only explicitly configured SignalWidget sources.
- Visual controls must not own long-running runtime lifecycles.
- Provider and HistoryRuntime must not depend on Avalonia.
- UI thread must only render; expensive range extraction, filtering, and downsampling must happen outside the UI thread.
- Avalonia properties and visual bounds may only be read on the UI thread.
- `HistorySeconds = 0` means history disabled.
- ChartControl must not trigger hidden recording for missing history.

## Acceptance Criteria
- SignalWidget exposes and uses only `RefreshRateMs` and `HistorySeconds` for signal timing/history.
- No `RecordingIntervalMs` field remains in the RealtimeChart/SignalWidget history path.
- A SignalWidget with `HistorySeconds = 0` does not register or record history.
- A SignalWidget with `HistorySeconds > 0` records only its configured source at `RefreshRateMs`.
- RealtimeChart no longer samples `Item.Value` directly and no longer owns per-chart history buffers.
- ChartDataProvider is chart-specific and can project the same shared history into different `ViewSeconds` windows for different charts.
- A chart referencing a signal without enabled history shows no data and does not start recording implicitly.
- Provider background work never directly or indirectly reads `PageIsActive`, `IsVisible`, `Bounds`, or other Avalonia state.
- The invalid-thread exception path from `ChartDataProvider.RefreshLoopAsync` to `RealtimeChartControl.PageIsActive` is eliminated.
- UI render path applies immutable render-ready arrays instead of building arrays from raw history on every render.
- Documentation reflects SignalWidget recording ownership and ChartControl display ownership.

## Out of Scope
- Persistent disk recording.
- Replay UI.
- Statistics/export/report features.
- Broad SignalRegistry redesign.
- Changing monitor runtime behavior.
- Broad LogControl layout hardening, except noting it as a possible follow-up if log floods still expose layout errors.

## Risks / Watchouts
- `FolderItemModel` currently uses shared properties for multiple widget kinds; avoid mixed ownership where ChartControl still writes or owns `HistorySeconds`.
- Existing persisted ChartControl layouts may contain `HistorySeconds`; read compatibility can remain, but it must not become active recording ownership.
- If SignalWidget lifecycle is tied to visual controls, do not make visual controls own the long-running HistoryRuntime. Registration should be driven by folder/widget definitions or a folder-scoped runtime owner.
- Multiple SignalWidgets may reference the same source with different `HistorySeconds` or `RefreshRateMs`. HistoryRuntime must define deterministic effective policy, preferably max retention and fastest required interval.
- Avoid UI-thread downsampling and LINQ array creation in `RenderPlot()`.
- Avoid unobserved `Task.Run` failures in provider loops; background work must be observed/logged and cancellable.
