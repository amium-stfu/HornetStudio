# IMPLEMENTATION HANDOFF

## Goal
Introduce the next small architecture boundary for the UDL client migration toward a browser-backed client view. The UDL runtime must expose received modules/items as a snapshot without automatically projecting them into `HostRegistries.Data`, and explicit attachments must be the only path that creates public HostRegistry items.

## Scope
Included:
- Split received-item snapshot handling from HostRegistry projection.
- Keep the existing `UdlClientControl` working as a temporary adapter/view.
- Move or isolate attachment-to-HostRegistry publishing behind a clear projection boundary.
- Add diagnostics around attachment synchronization and HostRegistry projection so the next benchmark identifies whether the remaining UI delay is projection work or downstream registry reactions.
- Preserve Demo Mode and hardware identifier parity.
- Preserve current persisted `UdlAttachedItemPaths` behavior unless a narrow compatibility adapter is required.

Explicitly not included:
- Building the final UDL browser UI.
- Redesigning the current visual layout.
- Broad refactoring of Monitor, EnhancedSignals, MainWindow, or registry infrastructure.
- Pausing or disabling folder runtimes as a performance workaround.
- Release/versioning work.

  - The next likely source is attachment/HostRegistry projection or downstream reactions to projected UDL items.

## Tasks
1. Inspect the current UDL runtime and control boundary:
   - identify where received runtime items are stored
   - identify where attach options are published
   - identify where attached items are synchronized into `HostRegistries.Data`
   - identify which paths still create `studio.<folder>.<client>.<module>` entries automatically
2. Define a minimal received snapshot responsibility:
   - runtime owns connection and received module/item state
   - snapshot can be read by the existing control and later by a browser
   - snapshot updates must not create public HostRegistry items
3. Define a minimal projection responsibility:
   - projection input is folder name, client name, runtime snapshot, and explicit attached paths
   - projection output is only the public HostRegistry items required for attached items
   - projection is idempotent by signature and skips unchanged attachment sets
   - projection must not publish every received root as public data
4. Adapt `UdlClientControl` as an adapter:
   - display received items from the runtime snapshot
   - call attachment synchronization/projection only for explicit attached paths
   - avoid adding new ownership or long-running runtime behavior to the control
5. Add focused diagnostics:
   - record timing for attachment synchronization
   - record timing for HostRegistry projection
   - if practical, distinguish projection work from UI-thread attach-section refreshes
6. Add or update focused tests where feasible:
   - received module exists in runtime snapshot before Attach
   - received module does not create a public HostRegistry item before Attach
   - Attach creates expected public HostRegistry item
   - multiple folders/clients do not collide on identical module names like `m001`

## File-Level Changes
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientRuntime.cs` -> keep runtime snapshot state and isolate attachment synchronization from automatic received-item publishing.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientControl.axaml.cs` -> reduce to adapter behavior and route attachment projection through the new or isolated boundary.
- `src/HornetStudio.Editor/Widgets/UdlClient/UdlHostRegistryProjection.cs` -> create only if it keeps projection small and clearer than leaving it inside `UdlClientRuntime`; responsible for explicit attachment projection only.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> reuse existing timing hooks if possible; add no broad diagnostics framework unless required.
- `src/HornetStudio.Host.Tests/Program.cs` or the most appropriate existing focused test harness -> add runtime/attach semantics coverage if dependencies allow.
- `src/HornetStudio/docs/widgets/`, `src/HornetStudio/docs/widgets/descriptions/`, `src/HornetStudio/docs/widgets/help/` -> update only if user-visible UDL behavior changes.

## Implementation Order
1. Read the current relevant methods:
   - `UdlClientControl.ConnectInternal`
   - `UdlClientControl.PublishClientItems`
   - `UdlClientControl.SynchronizeAttachedItems`
   - `UdlClientRuntime.SynchronizeAttachments`
   - `UdlClientRuntime.ClearAttachments`
2. Map the current paths that write to `HostRegistries.Data`.
3. Ensure received runtime snapshot updates do not create public `studio.<folder>.<client>.<module>` entries.
4. Extract or isolate explicit attachment projection:
   - prefer a small `UdlHostRegistryProjection` class if it removes coupling
   - otherwise keep a clearly named private projection method in `UdlClientRuntime`
5. Add signature-based no-op behavior around projection if not already sufficient.
6. Update `UdlClientControl` to rebuild received rows from the snapshot and trigger projection only from attached paths.
7. Add diagnostics around the new projection boundary.
8. Add focused tests or a console self-test path for the core semantics.
9. Run verification and repeat the manual benchmark.

## Technical Constraints
- Chat responses remain German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers remain English.
- Do not introduce new dependencies.
- Keep `Amium.UdlClient` UI-independent and HostRegistry-independent.
- Runtime code must not depend on Avalonia controls.
- Do not solve responsiveness by disabling folder runtimes or delaying runtime execution.
- Use async/await correctly; do not introduce `.Result` or `.Wait()`.
- Keep changes tightly scoped to UDL runtime/projection/adapter behavior.
- Public classes and public methods need XML documentation.
- Browser-style future views must be subscription-scoped and must not react broadly to all registry changes.

## Acceptance Criteria
- Received UDL modules/items can exist in the runtime snapshot without creating public HostRegistry data items.
- Explicit Attach creates the expected public HostRegistry items.
- Detach or attachment removal continues to remove or stop projecting the relevant public items according to current conventions.
- The existing UDL control still shows received and attached items.
- Demo Mode and hardware-like identifiers remain stable and do not introduce demo-specific paths.
- Multiple folders/clients remain isolated.
- Benchmark timing includes a distinguishable projection/attachment phase.
- `ConnectRuntime` remains off the UI thread.
- `BrowserDispatcherPosts=0` remains true.

## Verification
- Build:
  - `dotnet build HornetStudio.sln --no-restore`
- Focused host self-test when relevant:
  - `dotnet src/HornetStudio.Host.Tests/bin/Debug/net9.0/HornetStudio.Host.Tests.dll`
- Manual benchmark:
  - run the same 3-folder Demo Mode scenario
  - confirm `m001` appears in received items
  - confirm no public HostRegistry item appears before explicit Attach
  - attach one received module
  - confirm only attached module is projected publicly
  - compare benchmark summary and new projection timing

## Out of Scope
- Final UDL browser implementation.
- Full migration of persisted UDL definitions into browser resource files.
- General Monitor or EnhancedSignals optimization unless diagnostics prove a direct regression caused by this change.
- Registry infrastructure redesign.
- Release notes, tags, package versions, or Notice file updates.

## Risks / Watchouts
- Existing demo projects may currently rely on pre-attached `UdlAttachedItemPaths`; preserve that path as explicit attachment state, not as received-item auto-publication.
- EnhancedSignals and Monitor may react to public UDL items after Attach; this is expected, but should not happen before Attach.
- If the biggest spike remains after projection is isolated, the next workitem should inspect downstream registry reactions, especially `MainWindowViewModel`, `EnhancedSignal`, and `Monitor` paths.
- Avoid adding a broad abstraction tree. One small projection boundary is enough for this step.
