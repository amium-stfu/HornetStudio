# IMPLEMENTATION HANDOFF

## Goal
Define and implement the first migration step toward a browser-ready, folder-scoped UDL client runtime architecture. The UDL client runtime must be independent from Avalonia UI controls, support multiple clients per folder, preserve demo/hardware parity, and create HostRegistry items only when a received module/item is explicitly attached.

## Scope
Included:
- Analyze and split current `UdlClientControl` responsibilities into UI, runtime, client backend, received-item snapshot, attachment management, HostRegistry publishing, and write forwarding.
- Introduce a folder-scoped UDL client runtime/service boundary that can later be reused by a client browser.
- Keep `Amium.UdlClient` UI-independent and HostRegistry-independent.
- Preserve Demo Mode as a transport/backend mode that uses the same CAN IDs, UDL modules, attachments, writes, and registry paths as hardware mode.
- Ensure received modules/items can be viewed without automatically creating HostRegistry items.
- Ensure HostRegistry items are created only by explicit Attach.
- Keep the current UI working as an adapter/view during the transition.

Explicitly not included:
- Building the final client browser UI.
- Redesigning the visual layout beyond what is needed for adapter compatibility.
- Removing the existing `UdlClientControl` in one step.
- Changing `Amium.UdlClient` semantics unless a minimal interface adaptation is required.
- Pausing folder runtimes as a performance workaround.
- Release/versioning work.

## Starting Point
- Current diagnostics show `UdlClientControl.ConnectInternal` and related publishing phases run on the UI thread and cause multi-second freezes in multi-folder startup.
- Current direction is to avoid investing heavily in the old UI-control-owned runtime because UDL clients are planned to move into a folder-level browser.
- Existing `Amium.UdlClient` is assumed to be UI-independent and responsible for connection, CAN/UDL receive processing, module/item dictionary creation, write forwarding, and write processing confirmation.
- Desired behavior:
  - Before Attach, the UI can read a low-level received module/item dictionary and show entries such as `m001`.
  - Attach creates HostRegistry items and makes the item available to the rest of HornetStudio.
  - Edit behavior after Attach remains aligned with the current implementation.
  - Multiple clients can exist per folder.
  - Demo Mode lets users build projects without hardware using real CAN IDs and later disable Demo Mode without changing project structure.

## Tasks
1. Inventory the current `UdlClientControl` responsibilities:
   - connection lifecycle
   - demo/hardware selection
   - received module/item dictionary handling
   - runtime item/status publishing
   - attach option creation
   - attached item creation/edit/detach
   - write forwarding
   - UI state and visual controls
2. Define the target runtime contract:
   - folder id/name
   - client id/name
   - endpoint/transport settings
   - demo mode flag
   - received module/item snapshot
   - attached item list
   - connect/disconnect commands
   - attach/detach/edit commands
   - status snapshot/events
   - write forwarding path
3. Define persisted client configuration responsibilities:
   - client definition belongs to a folder
   - multiple clients per folder are supported
   - demo mode is persisted as backend/transport configuration
   - attachments are persisted independently from demo/hardware mode
4. Introduce the runtime/service layer with minimal surface area:
   - no Avalonia dependency
   - no direct visual control ownership
   - asynchronous connect/disconnect
   - snapshot/events suitable for both current control and future browser
5. Preserve Demo Mode parity:
   - Demo and hardware backends produce the same module/item keys for the same CAN IDs.
   - Attachments and HostRegistry paths must not contain demo-specific names.
   - Writes go through the same runtime API in both modes.
6. Change HostRegistry publishing semantics:
   - receiving a module/item must not automatically create HostRegistry items.
   - Attach creates the registry item(s).
   - Detach removes or disables the registry integration according to current project conventions.
7. Adapt the existing `UdlClientControl` to consume the new runtime/service:
   - keep visible behavior close to current behavior where possible
   - avoid UI-thread-owned connect/runtime work
   - show received modules/items from runtime snapshot
   - show attached items from runtime attachment state
8. Keep diagnostics:
   - verify connect/runtime phases no longer run as long UI-thread blocks
   - keep multi-folder startup benchmark usable
9. Add tests for runtime semantics:
   - received item does not create HostRegistry item before Attach
   - Attach creates expected registry paths
   - Demo and hardware-like backend snapshots use the same identifiers when fed equivalent data
   - multiple clients in one folder remain isolated by client id

## Implementation Order
1. Read current UDL implementation:
   - `rg -n "class UdlClientControl|ConnectInternal|PublishStatusItems|Attach|Detach|Demo|SimulatedHostUdlClient|HostRegistries" src/HornetStudio.Editor src/HornetStudio.Host`
   - inspect `UdlClientControl.axaml.cs` and related model/codec files.
2. Write a short local design note in the handoff or code comments only if needed; do not create extra plan files unless requested.
3. Extract or introduce runtime contracts:
   - keep names English and project-consistent
   - prefer small interfaces/classes over a broad abstraction tree
4. Implement received snapshot first:
   - connect/demo backend can populate received modules/items
   - UI can display received entries without HostRegistry publishing
5. Implement Attach/Detach semantics:
   - Attach creates HostRegistry item(s)
   - Detach removes/disables the registry integration
   - attached state is folder/client scoped
6. Move connect/runtime work out of the visual control:
   - UI triggers commands
   - runtime performs work asynchronously
   - UI observes snapshots/status
7. Rewire current `UdlClientControl` as adapter/view.
8. Run focused tests/build.
9. Run manual multi-folder demo-mode benchmark:
   - 3 folders
   - clients connected in Demo Mode
   - no automatic registry items before Attach
   - attach one module and verify only that module appears in HostRegistry
   - confirm no multi-second UI-thread `ConnectInternal` spike remains.

## Technical Constraints
- `Amium.UdlClient` remains UI-independent and HostRegistry-independent.
- Demo Mode is a backend/transport mode, not a separate project model.
- Runtime code must not depend on Avalonia controls.
- UI code must not perform long-running connect/receive/write processing on the UI thread.
- Use async/await; do not introduce `.Result` or `.Wait()`.
- HostRegistry items are created on explicit Attach, not by receiving modules/items.
- Multiple clients per folder must be isolated by folder and client id.
- Registry paths must be stable across Demo Mode and hardware mode.
- No new external dependencies without justification.
- Public classes and public methods must have XML documentation.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Chat responses remain German.

## Acceptance Criteria
- A folder-scoped UDL client runtime/service boundary exists and is usable without an Avalonia visual control.
- The existing UDL UI still works through the new runtime/service boundary.
- Received modules/items can be listed without creating HostRegistry items.
- Explicit Attach creates expected HostRegistry item(s).
- Demo Mode and hardware mode use the same identifiers, attachments, registry paths, and write semantics.
- Multiple clients can exist in one folder without shared runtime state collisions.
- Multi-folder demo startup no longer shows long UI-thread `ConnectInternal` phases comparable to 5-7 seconds per client.
- `BrowserDispatcherPosts=0` remains true in diagnostics.
- Runtime remains active for all folders; hidden UI/browser surfaces are not used as runtime owners.

## Verification
- `dotnet build HornetStudio.sln --no-restore`
- Focused runtime tests in the relevant console self-test harness.
- Manual test:
  - create or use 3 folders with equivalent UDL client definitions
  - enable Demo Mode
  - connect clients
  - verify received modules are visible
  - verify HostRegistry does not get module items before Attach
  - Attach one received module
  - verify HostRegistry item appears only for the attached item
  - run benchmark diagnostics and confirm no long UI-thread connect phase remains
- Manual mode switch concept check:
  - confirm persisted identifiers/attachments do not contain demo-specific names and can remain valid when Demo Mode is disabled.

## Out of Scope
- Final client browser UI implementation.
- Full migration of every client type beyond UDL unless directly required by shared abstractions.
- Project migration tooling for released user projects.
- Settings/dialog performance.
- Release/version updates.

## Risks / Watchouts
- The existing UI may assume registry items exist immediately after connect. Replace those assumptions carefully.
- Attach/Detach persistence must be clearly scoped by folder and client id to avoid collisions when multiple clients use identical module names like `m001`.
- Write forwarding must keep current safety semantics: requests must be written and processed/confirmed as before.
- Demo Mode must use real CAN IDs; do not create fake identifiers that later break hardware transition.
- Avoid over-abstracting for hypothetical future clients. Build the smallest runtime boundary that supports UDL and later browser reuse.
- Do not solve UI freezes by delaying runtime execution; solve them by moving runtime ownership out of visual controls and limiting HostRegistry publishing.
