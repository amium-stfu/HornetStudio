# IMPLEMENTATION HANDOFF

## Goal
Move UDL clients from widget-owned runtime state to a folder-scoped, browser-managed client architecture. UDL client definitions must be stored as one flat YAML file per client under `Clients/Udl/<client-id>.yaml`, while runtimes are managed by folder and client identity instead of by Avalonia controls.

## Scope
Included:
- Introduce folder-local UDL client definition files at `Clients/Udl/<client-id>.yaml`.
- Treat the file name without `.yaml` as the technical client id.
- Use `Text` in the YAML file as the optional user-visible label.
- Add or align a UDL client definition codec/registry that enumerates, loads, saves, renames, and deletes client definition files.
- Introduce a folder/client-scoped UDL runtime manager that owns runtime creation, synchronization, connection, disconnection, and disposal.
- Convert the current `UdlClientControl` direction toward a browser-style management surface, or add a dedicated UDL client browser surface if that matches existing browser patterns better.
- Ensure the browser observes and commands runtimes but does not own long-running runtime lifecycles.
- Keep status and client data available through scoped runtime/registry paths so existing widgets such as Signal can display status when needed.
- Preserve focused legacy compatibility for existing `UdlClientControl` definitions as migration input only.
- Update samples/demo projects to use the new file-backed structure instead of embedding new UDL client definitions in layout/widget YAML.
- Update relevant documentation for the new client-browser concept and file-backed definition layout.

Explicitly not included:
- Creating a separate `UdlClientView`, status widget, readonly projection widget, or operator-facing UDL view.
- Adding a generic client framework for non-UDL clients before there is a concrete second client type.
- Adding new external dependencies.
- Release/versioning work.
- Preserving repository sample definitions in both legacy widget-local and new file-backed form.

## Starting Point
- `UdlClientControl` currently contains runtime, publishing, attach, diagnostics, and UI state in one visual control.
- `UdlClientRuntime` already exists under `src/HornetStudio.Editor/Widgets/UdlClient/`, but it is still consumed as part of widget/control ownership.
- Monitor and EnhancedSignals already demonstrate the preferred direction: file-backed folder resources plus runtime managers, with browser/control surfaces acting as editors/observers.
- Repository rules require browser/client runtime reactions to be scoped and filtered before UI-thread dispatch.
- Repository rules also state that visual controls must not own long-running runtime services.

## Tasks
1. Define the UDL client file model.
   - File path: `Clients/Udl/<client-id>.yaml`.
   - Technical client id: file name without `.yaml`.
   - YAML field `Text`: optional user-visible label.
   - YAML fields should include at least `Host`, `Port`, `AutoConnect`, `DebugLogging`, `Enabled`, and any existing attach/demo configuration that must persist.
   - Do not add a YAML `Name` field as the source of identity.
2. Add a file codec/registry for UDL client definitions.
   - Enumerate `Clients/Udl/*.yaml`.
   - Load definitions with client id derived from the file name.
   - Save definitions without duplicating identity into YAML.
   - Validate client ids for stable path/file use.
   - Handle duplicate or invalid files explicitly and with diagnostics.
3. Introduce or finalize a `UdlClientRuntimeManager`.
   - Scope runtime state by normalized folder name and client id.
   - Create/update runtimes from loaded file definitions.
   - Auto-connect only enabled clients with `AutoConnect=true`.
   - Keep runtime alive across browser open/close, tab changes, selection changes, and other UI-only changes.
   - Dispose runtime when the folder is released, the client file is deleted, the client id changes, or endpoint/runtime identity changes require recreation.
4. Separate runtime ownership from UI.
   - UI controls may invoke connect/disconnect and observe snapshots.
   - UI controls must not own receive loops, timers, writeback loops, or HostRegistry publishing lifetime.
   - Runtime code must be usable without Avalonia controls.
5. Define registry publishing boundaries.
   - Use explicit, scoped runtime roots per folder/client.
   - Unknown or unrelated registry events must be ignored before any UI dispatcher work is scheduled.
   - Receiving data must not create public HostRegistry items unless the user/configuration explicitly attaches or publishes them.
   - Status should be available through normal registry paths so existing Signal widgets can display it.
6. Build the UDL browser structure.
   - Browser lists clients loaded from `Clients/Udl/*.yaml`.
   - Browser can create, edit, rename, delete, connect, disconnect, and inspect clients.
   - Browser shows runtime status, received modules/items, attach options, and diagnostics.
   - Browser does not implement a separate readonly view mode.
7. Migrate current widget behavior carefully.
   - Existing legacy `UdlClientControl` data can be read as compatibility input where needed.
   - New definitions should be written only to `Clients/Udl/<client-id>.yaml`.
   - New samples/demo project data should use the new file-backed structure.
   - Do not keep duplicated sample definitions in both legacy layout and new client files.
8. Update documentation.
   - Update handbook/manual documentation for UDL clients as folder-level browser-managed resources.
   - Update or retire widget docs for `UdlClientControl` if its role changes or it is no longer a normal widget.
   - Document that status display should use existing widgets, such as Signal, bound to published runtime paths.
9. Add focused tests.
   - File codec load/save and id derivation from file names.
   - Runtime manager creates, updates, and releases runtimes by folder/client id.
   - Browser/runtime state remains active when only UI changes.
   - Receiving data does not create public registry items before attach/publish configuration.
   - Multiple clients in one folder remain isolated.

## Implementation Order
1. Inventory current UDL persistence and runtime usage.
   - Search for `UdlClientHost`, `UdlClientPort`, `UdlClientAutoConnect`, `UdlClientDebugLogging`, `UdlClientDemoEnabled`, `UdlClientRuntime`, and `UdlClientControl`.
2. Add the UDL client definition model and file codec.
   - Keep it small and specific to UDL.
   - Derive client id from file name.
3. Add tests for the codec before wiring UI.
4. Add or align `UdlClientRuntimeManager`.
   - Synchronize from loaded definitions.
   - Add explicit release-by-folder and release-by-client behavior.
5. Wire folder lifecycle to load/sync UDL client files.
   - Follow the Monitor/EnhancedSignals pattern where applicable.
6. Move runtime ownership out of the visual control.
   - Keep the old UI working as a management adapter only if needed during migration.
7. Add the browser surface or convert the existing surface to browser semantics.
   - Keep registry subscriptions scoped to selected/visible client paths.
8. Update samples to `Clients/Udl/<client-id>.yaml`.
9. Update docs.
10. Run focused tests and solution build.

## Technical Constraints
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Chat responses must remain German.
- Public classes and public methods must include XML documentation.
- Prefer existing YAML patterns/codecs and repository conventions.
- Do not add dependencies without justification.
- Avoid a generic client abstraction until a second real client type requires it.
- Runtime services must not depend on Avalonia controls.
- Browser/client registry event handling must filter relevance before any UI-thread dispatch.
- High-frequency runtime value changes must update runtime state only; UI structure refresh is for structural changes or explicit selection/configuration changes.
- Use async/await correctly; do not use `.Result` or `.Wait()`.
- Use explicit, scoped HostRegistry publishing; do not publish received data broadly by default.

## Acceptance Criteria
- UDL client definitions are loaded from `Clients/Udl/<client-id>.yaml`.
- The client id is derived from the file name and is not duplicated as YAML `Name`.
- YAML uses `Text` for the display label.
- Multiple UDL clients in one folder can be loaded and synchronized independently.
- Runtime lifetime is folder/client-scoped and survives UI/browser switching.
- Runtime is released on folder release, client deletion, or identity-changing definition updates.
- No separate UDL view/status widget is introduced.
- Status can be displayed through existing widgets by binding to published runtime paths.
- Receiving UDL data does not create public HostRegistry items before explicit attach/publish configuration.
- Demo/sample project definitions are represented in the new file-backed structure.

## Verification
- Run focused codec/runtime tests added for this work.
- Run `dotnet build HornetStudio.sln --no-restore`.
- Manual verification:
  - Create two files under `Clients/Udl/`, for example `udl1.yaml` and `udl2.yaml`.
  - Open the folder and verify both clients appear in the browser.
  - Connect/disconnect one client without affecting the other.
  - Close/reopen or switch the browser UI and verify runtime state is not disposed by UI-only changes.
  - Verify status can be selected/displayed through existing registry-backed widgets.
  - Verify no public attached module tree appears until attach/publish is explicitly configured.

## Out of Scope
- `UdlClientView`, readonly status widget, or any new display-only UDL widget.
- Full generic `Clients` framework for all future client types.
- Release versioning, tags, or packaging.
- Large visual redesign unrelated to the UDL browser management workflow.
- Compatibility migration tooling for already released user projects.

## Risks / Watchouts
- Existing code may assume UDL runtime state exists only while `UdlClientControl` is attached to the visual tree.
- Existing code may assume receiving UDL modules immediately creates HostRegistry items.
- File rename semantics must be handled carefully because rename changes the technical client id.
- Runtime path compatibility may be needed for old layouts; keep compatibility explicit and temporary.
- Avoid duplicated definitions between legacy layout properties and new `Clients/Udl/*.yaml` sample files.
- Do not solve UI lag by delaying work or tying runtime to hidden UI; solve it through proper ownership and scoped registry work.
