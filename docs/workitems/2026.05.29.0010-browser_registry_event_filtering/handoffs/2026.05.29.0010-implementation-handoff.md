# IMPLEMENTATION HANDOFF

## Goal
Reduce the performance regressions introduced by the new Admin Browser windows by filtering registry-change handling to only relevant paths. The primary target is the Custom Signals browser/control, which currently republishes computed `OnSourceChange` signals on unrelated registry events such as UDL demo module updates.

## Scope
Included:
- Fix overly broad registry event handling in `CustomSignalsControl`.
- Align Custom Signals browser behavior with the existing source-path filtering already used by `MainWindowViewModel`.
- Review and, where directly needed, tighten registry event handling in `EnhancedSignalsControl` and `ControllerControl` so unrelated UDL events do not refresh all browser rows.
- Add focused tests for the event-filtering behavior if the existing test structure supports it.
- Keep existing file-backed resource storage and browser workflows unchanged.

Not included:
- Changing UdlClient demo simulation behavior.
- Changing UDL registry path semantics.
- Reworking Custom Signal formula evaluation.
- Redesigning Browser windows or the right sidebar.
- Migrating additional project data.
- Adding new dependencies.

## Starting Point
- Performance issues appear after moving Functions, Enhanced Signals, Custom Signals, and Controllers to Browser windows.
- `samples/HornetStudioReference` contains a computed custom signal in `Folders/main/Signals/Custom/demo_custom_computed.yaml`.
- That computed custom signal does not specify `trigger`, so `CustomSignalComputationTrigger.OnSourceChange` is the default.
- `samples/HornetStudioDemo` contains only simple input custom signals under `Signals/Custom`, so it does not trigger the same behavior.
- `CustomSignalsControl.OnRegistryItemChanged(...)` currently republishes all signals when any registry event occurs and any row is computed with `OnSourceChange`.
- `MainWindowViewModel.OnCustomSignalRegistryItemChanged(...)` already avoids this by calling `IsCustomSignalSourceChange(...)`.
- `EnhancedSignalsControl` and `ControllerControl` queue broad refreshes when registry events arrive off the UI thread, then filter only after dispatching.

## Tasks
1. Inspect `CustomSignalsControl.OnRegistryItemChanged(...)` and identify the exact path set each browser/control instance owns:
   - published custom signal registry paths
   - manual trigger paths
   - computed source paths from variables and legacy `SourcePath`, `SourcePath2`, `SourcePath3`
2. Add a focused relevance check for Custom Signals registry changes:
   - direct published path changes update rows
   - manual trigger changes remain supported
   - computed `OnSourceChange` signals republish only when the changed registry path matches one of their configured source paths
   - unrelated UDL runtime changes do not republish custom signals
3. Prefer reusing or mirroring the existing `MainWindowViewModel` source-path matching semantics:
   - use `TargetPathHelper.EnumerateResolutionCandidates(...)`
   - compare exact path, descendant path, and ancestor path consistently
   - avoid ad hoc string matching
4. Ensure file-backed browser mode and legacy widget mode both use the same event relevance behavior.
5. Review `CustomSignalsControl.RebuildSignalRows()` so opening the browser does not create duplicate publish churn beyond the required initial sync.
6. Inspect `EnhancedSignalsControl.OnRegistryItemChanged(...)`:
   - avoid queuing `QueueRuntimeRefresh()` for unrelated paths when possible
   - keep runtime row refresh behavior for matching enhanced signal runtime paths
7. Inspect `ControllerControl.OnRegistryItemChanged(...)`:
   - avoid queuing `QueueRuntimeRefresh()` for unrelated paths when possible
   - keep runtime row refresh behavior for matching controller runtime paths
8. Add focused tests if practical:
   - computed custom signal is not republished for unrelated registry events
   - computed custom signal is republished for its actual source path
   - browser-hosted custom signals do not clear or duplicate unrelated runtime state
9. Update documentation only if user-visible browser behavior or resource semantics change. Pure event-filtering fixes likely do not require docs.

## File-Level Changes
- `src/HornetStudio.Editor/Widgets/CustomSignals/CustomSignalsControl.axaml.cs` -> add source-path relevance filtering before `PublishSignals(preserveInputValues: true)`; keep manual trigger and published-path handling intact.
- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs` -> expose or duplicate only minimal source-path matching logic if needed; avoid broad ViewModel coupling from the control if a local helper is simpler.
- `src/HornetStudio.Editor/Widgets/EnhancedSignals/EnhancedSignalsControl.axaml.cs` -> optionally filter off-thread registry refreshes before queueing UI work.
- `src/HornetStudio.Editor/Widgets/Controller/ControllerControl.axaml.cs` -> optionally filter off-thread registry refreshes before queueing UI work.
- `src/HornetStudio.Editor.Tests/Program.cs` -> add focused tests if existing APIs allow testing without large UI construction.

## Implementation Order
1. Implement the Custom Signals event relevance helper in `CustomSignalsControl`.
2. Apply the helper in `OnRegistryItemChanged(...)` so unrelated registry changes return early.
3. Verify manual trigger and direct published-path updates still work.
4. Add focused tests around source-change matching if feasible.
5. Tighten Enhanced Signals and Controller browser event queueing only if inspection confirms low-risk, direct improvements.
6. Run focused editor tests.
7. Build `HornetStudio.sln` with `--no-restore`.

## Technical Constraints
- Chat responses must stay German; code, comments, XML documentation, UI text, file names, and technical identifiers must stay English.
- Do not add dependencies.
- Use existing `TargetPathHelper` path normalization and resolution semantics.
- Keep changes tightly scoped to browser/registry event handling.
- Do not change UdlClient demo module simulation or registry path shape.
- Do not introduce a generic browser event framework unless the local helper becomes duplicated in at least two real places and the duplication is harmful.

## Acceptance Criteria
- Opening Admin Browser -> Custom Signals while UdlClient demo modules are running no longer causes repeated custom signal republishing for unrelated UDL paths.
- A computed custom signal with `OnSourceChange` still updates when its configured source path changes.
- Manual custom signal triggers still work.
- Input custom signals still preserve and publish their values.
- Browser-hosted Custom Signals does not clear existing file-backed definitions or runtime state.
- If Enhanced Signals or Controllers browsers are open, unrelated UDL registry events do not force unnecessary full-row refreshes where avoidable.
- `samples/HornetStudioReference` remains loadable with its computed custom signal and UdlClient demo module.
- `samples/HornetStudioDemo` remains loadable and behavior stays unchanged.

## Out of Scope
- Solving unrelated performance issues in charts, UdlClient simulation, or registry internals.
- Replacing the browser architecture.
- Moving additional resources out of `Folder.yaml`.
- Changing release/version metadata.

## Risks / Watchouts
- Filtering too aggressively could prevent computed custom signals from updating when a child path or ancestor path changes.
- Custom Signal definitions can reference sources through variables and legacy `SourcePath` fields; both must be included.
- Browser windows have `TopLevel.DataContext` set to their own window model, not `MainWindowViewModel`; do not rely on that for matching logic.
- `CustomSignalsControl` can publish its own registry items. The existing `_isPublishing` guard must remain effective to avoid self-triggered loops.
- Manual trigger paths are command-like registry items and must not be filtered out accidentally.
- Avoid repeating the previous browser-hosting issue where a temporary empty browser owner clears or replaces folder runtime state.

## Notes
- The main structural issue is event ownership: browser controls should behave as views over folder resources, not as global registry listeners that recompute on every data change.
- The most likely high-impact fix is local to `CustomSignalsControl.OnRegistryItemChanged(...)`.
- If only one file is changed, prefer that over a broader refactor.
