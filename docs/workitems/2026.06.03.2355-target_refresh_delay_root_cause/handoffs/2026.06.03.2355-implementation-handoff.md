# IMPLEMENTATION HANDOFF

## Goal
Find and fix the real cause of the remaining 4-5 second target refresh execution delays after the initial Signal widget value-refresh optimization.

## Scope
- Diagnose whether `TargetRefreshExecuted` and `TargetValueRefreshExecuted` delays come from startup/warmup queued work or from steady-state UI backlog.
- Improve diagnostics if needed so benchmark summaries separate startup, warmup, steady-state, and shutdown refresh work.
- Apply only the smallest targeted fix once the root cause is identified.
- Preserve the existing value-only fast path unless proven incorrect.
- Do not rewrite the UDL runtime, public HostRegistry projection, chart runtime, or the full `PageItemModel` architecture.

## Starting Point
- The optimization work has been implemented but did not deliver a meaningful visible improvement.
- The latest benchmark scenario was `SignalTargetRefreshOptimization-30s`.
- Relevant benchmark results:
  - `RegistryPublish`: `4500`, about `149.9/s`
  - `DemoGenerate`: `660`, about `22.0/s`
  - `SignalReceive`: `660`, about `22.0/s`
  - `TargetValueRefreshQueued`: `594`, about `19.8/s`, `DelayMaxMs=1.1`, `P95=0`
  - `TargetValueRefreshExecuted`: `594`, about `19.8/s`, `DelayMaxMs=4611`, `P95=2.6`
  - `TargetRefreshQueued`: `80`, about `2.7/s`, `DelayMaxMs=2.1`, `P95=0.2`
  - `TargetRefreshExecuted`: `80`, about `2.7/s`, `DelayMaxMs=4784.5`, `P95=4770.6`
  - `ChartRenderCount=0`
  - `BrowserDispatcherPosts=0`
- The large UI spikes in that run were during startup/warmup:
  - `23:52:19`: `1875.4ms` while loading project/registry
  - `23:52:24`: `5125.9ms` while creating/attaching many startup runtimes
- The most suspicious current interpretation is that refreshes queued during startup/warmup are executed much later and pollute the benchmark summary, or that stale queued refreshes are not being canceled/upgraded/phase-tagged correctly.

## Tasks
1. Inspect the current diagnostics timestamps for queued and executed refresh stages.
2. Confirm how delay is calculated for:
   - `TargetRefreshQueued`
   - `TargetRefreshExecuted`
   - `TargetValueRefreshQueued`
   - `TargetValueRefreshExecuted`
3. Determine whether `Executed` delay uses the original queue timestamp, a stale timestamp, or an unrelated benchmark/session timestamp.
4. Add phase-aware diagnostics if the current summary cannot distinguish startup/warmup/steady-state refreshes.
5. Add enough context to identify stale queued work:
   - queue time
   - execute time
   - phase at queue time
   - phase at execute time
   - refresh kind (`Full` or `ValueOnly`)
   - widget/path
   - whether the refresh was superseded or upgraded
6. Run a short benchmark and inspect whether the 4-5 second delays are all startup/warmup-originated.
7. If delays are stale startup/warmup work, fix the queue handling:
   - avoid carrying stale value-only work into steady-state
   - clear or replace pending value-only state when a full refresh happens
   - ensure full refresh completion resets obsolete pending timestamps
8. If delays are true steady-state backlog, inspect the exact UI-thread work inside the execute path and make the smallest focused fix.
9. Verify with a 30s benchmark.

1. Read the current `PageItemModel` refresh implementation after the recent optimization.
2. Trace all fields used for pending refresh state and delay measurement.
3. Verify that value-only and full refresh queues cannot leave stale timestamps behind.
4. Inspect `UiResponsivenessDiagnostics` signal pipeline aggregation and confirm whether it records queue phase vs execute phase.
5. Add minimal diagnostics to separate:
   - queued during startup/warmup, executed during startup/warmup
   - queued during startup/warmup, executed during steady-state
   - queued during steady-state, executed during steady-state
6. Build the solution.
7. Run `SignalTargetRefreshDelayRootCause-30s`.
8. Interpret phase-aware summaries before changing behavior further.
9. Apply the smallest fix based on the measured root cause.
10. Build and run a final 30s benchmark.

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Keep changes local to existing diagnostics and `PageItemModel` refresh state.
- Do not introduce new dependencies.
- Do not perform broad refactoring.

## Acceptance Criteria
- Benchmark diagnostics can clearly say whether 4-5 second delays are startup/warmup-originated or steady-state-originated.
- Stale queued refresh timestamps do not pollute steady-state summaries.
- If stale pending work exists, it is cleared, replaced, or completed consistently.
- If steady-state backlog exists, the responsible execute path is identified and fixed narrowly.
- `TargetRefreshExecuted` and `TargetValueRefreshExecuted` delay summaries no longer report multi-second P95/Max values from stale startup-origin refreshes as steady-state evidence.
- Solution build succeeds.
- A 30s benchmark after the fix has no unexplained 4-5 second target refresh execute delay in the steady-state phase.

## Risks / Watchouts
- Current benchmark summaries may aggregate startup/warmup and steady-state together; do not call that a steady-state bottleneck without phase evidence.
- `TargetRefreshExecuted P95=4770.6ms` with only 80 events strongly suggests stale or phase-mixed delay data; verify before optimizing more.
- `DemoGenerate` and `SignalReceive` were lower than the previous run, so benchmark-to-benchmark comparisons must account for input-rate differences.
- If chart runtimes are created during startup even when `ChartRenderCount=0`, classify that as startup/warmup cost, not Signal steady-state rendering.
- Avoid hiding real missing-target or target-appeared transitions while clearing stale value-only work.
