# IMPLEMENTATION HANDOFF

## Goal
Measure and fix why visible Signal widget values still appear far below 10 Hz even though the steady-state target value refresh path is fast.

## Scope
- Focus on the path after `TargetValueRefreshExecuted`.
- Measure the effective visible update rate for Signal widgets.
- Determine whether the issue is missing UI-bound property updates, missing `PropertyChanged`, formatting/rounding, Avalonia layout/render invalidation, or intentional/accidental coalescing.
- Apply only a narrow fix once the first failing visual stage is proven.
- Preserve UDL runtime, public HostRegistry projection, chart behavior, and existing value-only fast path unless proven directly responsible.

## Starting Point
- The latest benchmark scenario `SignalTargetRefreshDelayFix-30s` shows steady-state internals are fast:
  - `TargetValueRefreshExecuted[SteadyState->SteadyState]`: `756`, about `25.2/s`, `DelayMaxMs=2.2`, `P95=0.7`
  - `TargetValueRefreshQueued[SteadyState->SteadyState]`: `756`, about `25.2/s`, `DelayMaxMs=0.1`, `P95=0`
  - `ChartRenderCount=0`
  - `BrowserDispatcherPosts=0`
- The user still observes visible values far below 10 Hz.
- Therefore the next suspected bottleneck is after target value refresh execution:
  `TargetValueRefreshExecuted -> display text/value state -> PropertyChanged -> Avalonia binding/layout/render`.

## Tasks
1. Inspect which `PageItemModel` properties are actually bound by Signal widget UI templates.
2. Identify which properties the value-only fast path updates.
3. Add diagnostics for the visual update chain:
   - raw target value changed
   - resolved display value changed
   - formatted display text changed
   - relevant `PropertyChanged` raised
   - optional UI/render invalidation if there is an existing safe hook
4. Aggregate per widget/path rates instead of logging per event.
5. Distinguish unchanged formatted text from missed UI updates.
6. Run a 30s benchmark and compare:
   - `SignalReceive`
   - `TargetValueRefreshExecuted[SteadyState->SteadyState]`
   - display value/text changes
   - `PropertyChanged` for bound display properties
7. If formatted display text changes but `PropertyChanged` does not fire, fix notification.
8. If raw value changes but formatted display text does not, inspect formatting/rounding and adjust only if it is incorrect for Signal widgets.
9. If `PropertyChanged` fires at rate but visible rendering still lags, add a targeted render/layout invalidation or inspect the Signal widget template binding.
10. Verify with benchmark and, if possible, a simple visual-rate diagnostic summary.

## File-Level Changes
- `src/HornetStudio.Editor/Models/PageItemModel.cs` -> Inspect Signal UI-bound properties, update value-only path, and add/record display-state transition diagnostics.
- `src/HornetStudio.Editor/Monitoring/UiResponsivenessDiagnostics.cs` -> Extend signal pipeline aggregation with visual-stage counters only if existing diagnostics cannot record them.
- Signal widget view/template files under `src/HornetStudio.Editor/**` -> Inspect bindings only; change only if the binding target is wrong or not notified.
- `docs/workitems/ChatHandoff.md` -> Update only if the final visual update finding should be preserved for future continuation.

## Implementation Order
1. Search for Signal widget bindings and identify the exact display properties.
2. Read the current value-only fast path in `PageItemModel`.
3. Add bounded diagnostics stages, for example:
   - `TargetRawValueChanged`
   - `SignalDisplayValueChanged`
   - `SignalDisplayTextChanged`
   - `SignalDisplayPropertyChanged`
4. Include per-path counts and rates in benchmark summaries.
5. Build the solution.
6. Run:
   `scripts\run_ui_benchmark.ps1 -Seconds 30 -ProjectPath 'benchmarks\ui_lag_bench_project\project.aaep' -Scenario 'SignalVisualUpdateRate-30s'`
7. Identify the first stage where rate drops below expected visible rate.
8. Apply the smallest fix for that stage.
9. Build again and run:
   `scripts\run_ui_benchmark.ps1 -Seconds 30 -ProjectPath 'benchmarks\ui_lag_bench_project\project.aaep' -Scenario 'SignalVisualUpdateRateFix-30s'`

## Technical Constraints
- Chat responses must be German.
- Code, comments, XML documentation, UI text, file names, and technical identifiers must be English.
- Do not introduce new dependencies.
- Keep diagnostics aggregated and bounded; do not log every value update.
- Do not read Avalonia UI objects from background/runtime threads.
- Registry relevance filtering must remain before dispatcher scheduling.
- High-frequency value updates must not trigger structural refreshes.
- Avoid broad `PageItemModel` refactoring.
- Do not change formatting semantics unless measurements prove formatting is the visual rate bottleneck.

## Acceptance Criteria
- Benchmark diagnostics show the effective visible display-state update rate per Signal widget.
- The first failing stage after `TargetValueRefreshExecuted` is identified.
- If the fix is applied, visible display text/property changes occur close to the expected 10 Hz per visible Signal widget, subject to actual input rate.
- `TargetValueRefreshExecuted[SteadyState->SteadyState]` remains low-latency.
- No new steady-state UI dispatcher backlog is introduced.
- Solution build succeeds.

## Out of Scope
- UDL demo runtime redesign.
- Public HostRegistry projection changes.
- Chart rendering optimization.
- Full UI startup/warmup optimization.
- New global render scheduler.
- Full 1/5/10/20 matrix unless the 30s run is inconclusive.

## Risks / Watchouts
- A fast internal refresh can still fail visually if it updates a property that the template does not bind.
- Display formatting may hide changes if the value changes are smaller than the displayed precision.
- `PropertyChanged` may fire for a parent property while the template binds a different derived property.
- Avalonia may not render every property change as a distinct frame; measure display-state changes before assuming render failure.
- If the input rate is below target during a run, compare visible rate to actual `SignalReceive`, not to theoretical 10 Hz.
