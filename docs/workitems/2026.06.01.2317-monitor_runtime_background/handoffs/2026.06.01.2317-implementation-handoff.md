# IMPLEMENTATION HANDOFF

## Goal
Make Monitor rules run as folder-level background runtime services independent of whether the Monitor browser/view is open.

## Scope
- Move monitor rule evaluation ownership out of `MonitorControl` and into the folder-scoped monitor runtime.
- Keep the Monitor browser/control as a view and editor for folder monitor definitions.
- Ensure monitor rule timers, formula evaluation, transition actions, runtime state publication, and aggregate publication continue after closing the Monitor browser.
- Ensure edited definitions with unchanged names update the running runtime.
- Keep existing folder-local `Monitoring/Monitor.yaml` as the authoritative monitor definition file.

Explicitly not included:
- Do not redesign the monitor editor UI.
- Do not introduce new external dependencies.
- Do not change public persisted YAML field names except where required for validation fixes.
- Do not implement release/versioning work.

## Starting Point
- `MainWindowViewModel.SyncMonitors` currently releases `MonitorRuntimeManager` and returns an empty runtime list when any `ControlKind.Monitor` item exists on the page.
- `MonitorControl` currently creates and owns `MonitorRuleRow` instances from `RebuildRules`.
- `MonitorRuleRow` contains runtime concerns: timer, evaluation, formula handling, transition actions, runtime publishing, and state.
- `MonitorRuntimeManager` currently reuses `MonitorRuleRow`, so runtime logic is still tied to the UI widget file.
- `MonitorRuntimeManager.UpdateDefinitions` compares only the rule name list and ignores content changes when names stay the same.
- Recent validation work makes duplicate names and duplicate `EventId` detectable from central `Monitor.yaml`; preserve that behavior.

## Tasks
1. Introduce a UI-independent monitor rule runtime model under `src/HornetStudio.Editor/Monitoring/`.
2. Move evaluation, timer lifecycle, transition action execution, state publication, and aggregate input state out of `MonitorRuleRow` into the new runtime class.
3. Update `MonitorRuntimeManager` so it always owns folder monitor runtimes and returns UI-consumable state snapshots or row view models without requiring a Monitor control.
4. Remove the `hasMonitorBrowser` runtime shutdown behavior from `MainWindowViewModel.SyncMonitors`.
5. Update `MonitorControl` so it observes and edits the runtime-managed monitor registry instead of owning timers/evaluation.
6. Ensure saving monitor definitions from the browser re-syncs `MonitorRuntimeManager` immediately.
7. Add or update tests covering runtime behavior with and without an open Monitor browser.
8. Update relevant monitor documentation to state that the Monitor browser is a view/editor and the runtime runs folder-wide in the background.

## File-Level Changes
- `src/HornetStudio.Editor/Monitoring/MonitorRuntimeManager.cs` -> Own folder monitor runtime lifecycle, compare full definition signatures, publish aggregate runtime state, expose state for views.
- `src/HornetStudio.Editor/Monitoring/MonitorRuleRuntime.cs` -> New UI-independent runtime extracted from `MonitorRuleRow`.
- `src/HornetStudio.Editor/Monitoring/MonitorRuleState.cs` -> Optional small immutable state model if needed for UI binding and aggregate generation.
- `src/HornetStudio.Editor/Widgets/Monitor/MonitorControl.axaml.cs` -> Remove timer/evaluation ownership; bind to runtime state and keep edit/add/delete commands.
- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs` -> Always call `MonitorRuntimeManager.SyncDefinitions`; do not release runtime because a Monitor browser exists.
- `src/HornetStudio.Editor.Tests/Program.cs` -> Add focused tests for background monitor runtime and browser-independent behavior.
- `src/HornetStudio/docs/widgets/Monitor.md` -> Update behavior documentation if it currently implies widget-owned evaluation.
- `src/HornetStudio/docs/widgets/help/Monitor.help.md` -> Update user-facing help for background runtime semantics.
- `src/HornetStudio/docs/widgets/descriptions/Monitor.md` -> Update concise picker description only if wording currently implies the browser owns rules.

## Implementation Order
1. Inspect current `MonitorRuleRow` responsibilities and split pure runtime logic from UI-only properties.
2. Create `MonitorRuleRuntime` using existing logic from `MonitorRuleRow` with no Avalonia control dependency.
3. Update `MonitorRuntimeManager.MonitorFolderRuntimeState` to store `MonitorRuleRuntime` instances instead of `MonitorRuleRow`.
4. Add a robust definition signature comparison in `MonitorRuntimeManager.UpdateDefinitions`; include name, source path, mode, limits, formula, variables, refresh rate, timeout, inhibit, event metadata, log level, and actions.
5. Change `MainWindowViewModel.SyncMonitors` so the runtime sync happens regardless of whether `ControlKind.Monitor` exists.
6. Rework `MonitorControl` to populate visible rows from runtime state and perform edit operations against `Monitoring/Monitor.yaml`; after save/delete, call the same folder runtime sync path.
7. Keep aggregate publication in exactly one owner: `MonitorRuntimeManager`.
8. Remove any `MonitorControl` detach behavior that deletes folder monitor runtime paths.
9. Add tests for:
   - Runtime publishes monitor state without Monitor control.
   - Runtime still publishes monitor state when a Monitor control exists.
   - Closing/discarding a Monitor control does not remove folder monitor runtime state.
   - Updating a rule formula/action with the same name causes runtime rebuild/update.
   - Duplicate `EventId` validation remains active for central monitor files.
10. Update monitor documentation.
11. Run focused editor tests and then the solution build.

## Technical Constraints
- Code, comments, XML documentation, UI text, and technical identifiers must be English.
- Chat response must be German.
- Do not add dependencies.
- Follow existing `Monitoring` namespace and current registry/path helper patterns.
- Runtime classes must not read Avalonia UI objects or own UI controls.
- UI controls may configure and observe runtime services but must not own timer/evaluation lifecycles.
- Registry publication must stay scoped to `studio.{folder}.monitor` and `studio.{folder}.monitor.{rule}`.
- Keep changes focused; do not refactor unrelated widget systems.

## Acceptance Criteria
- Monitor rules evaluate and execute actions when no Monitor browser/view is open.
- Monitor rules continue evaluating after the Monitor browser/view is closed.
- Opening a Monitor browser/view does not stop, duplicate, or replace the folder monitor runtime.
- Monitor aggregate paths remain published by the runtime and are not removed by closing the view.
- Edited rules with unchanged names update the running runtime.
- Duplicate rule names and duplicate `EventId` values are still rejected.
- Existing MonitorView and VisualRules continue resolving `studio.{folder}.monitor.{rule}` paths.

## Out of Scope
- New visual design for the Monitor browser.
- Runtime architecture changes for UDL, controller, enhanced signals, charts, or workflows.
- Release notes, package publishing, tags, or version changes.
- Migration tooling for released user projects.

## Risks / Watchouts
- Avoid creating two runtimes for the same folder/rule when the browser opens.
- Do not let `MonitorControl.DetachedFromVisualTree` remove folder-level runtime registry paths.
- Definition comparison by names only is insufficient and must be replaced.
- `MonitorRuleRow` currently mixes UI row styling with runtime state; preserve visual behavior while removing runtime ownership.
- Transition actions must remain one-shot on activation/clear transitions, not fire repeatedly on every timer tick.
- InvokeFunction currently blocks with `GetAwaiter().GetResult()`; do not make this worse while moving runtime ownership.
- Existing dirty worktree may contain unrelated changes; do not revert them.
