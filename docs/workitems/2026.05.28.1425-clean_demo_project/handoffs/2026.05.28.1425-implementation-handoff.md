# IMPLEMENTATION HANDOFF

## Goal
Create a clean, intentional HornetStudio demo project that can be used as a stable reference for the ongoing migration from widget-embedded `Folder.yaml` data to folder-local resource files. The demo must have clear naming, no dummy leftovers, and registry paths that make ownership problems immediately visible.

## Scope
- Replace or rebuild the current `samples/HornetStudioDemo/` into a clean reference demo.
- Keep the demo small and focused.
- Use naming that matches the target architecture for resource roots.
- Remove accidental leftovers such as `dummy_*`, duplicated `application_explorer`/`applications` confusion, and widget-owner paths used as resource roots.
- Keep one main folder, unless a second folder is needed for a focused cross-folder example.
- Update demo README/documentation to explain intended roots and sample purpose.

Explicitly included:
- Clean sample resources for functions, custom signals, enhanced signals, controllers, and applications when those systems already exist.
- Clear placeholder/test names only when they are intentionally test data.
- Migration target directories such as `Signals/Custom`, `Signals/Enhanced`, `Controllers`, `Scripts/Workflows`, and `Applications`.

Explicitly not included:
- Implementing missing browser/resource migration features.
- Reworking runtime code unless a demo-only bug exposes a hard blocker.
- Keeping legacy demo data just for compatibility.

## Starting Point
- Existing demo root:
  - `samples/HornetStudioDemo/`
- Current observed issues:
  - Registry/tree shows both `applications` and `application_explorer`.
  - Custom signal examples appear under `application_explorer`/widget-owner style paths.
  - `button_*` items show repeated generic subitems.
  - Existing references include `dummy_bool`, `dummy_input`, `inputt_1`, `custom_signals_browser.*`, and `custom_signals_1.*`.
  - `samples/HornetStudioDemo/Folders/main/Folder.yaml` still contains mixed demo state and old references.
- Existing project rule:
  - Demo projects should represent the current target architecture and should be migrated immediately when concepts move out of `Folder.yaml`.

## Target Naming Model
Use predictable resource roots:

- `studio.main.functions...`
- `studio.main.signals.custom...`
- `studio.main.signals.enhanced...`
- `studio.main.controllers...`
- `studio.main.applications...`
- `studio.main.ui...` only if a UI widget must publish UI-owned state.

Avoid these as resource roots:

- `application_explorer_1.*`
- `custom_signals_1.*`
- `custom_signals_browser.*`
- `button_1.dummy_*`
- generated widget instance names for fachliche resources.

## Tasks
1. Decide cleanup strategy.
   - Prefer rebuilding `samples/HornetStudioDemo/` as the canonical clean demo if current content is mostly generated/noisy.
   - If preserving some files is valuable, keep only deliberate samples and remove accidental leftovers.
   - Do not create a second competing demo unless there is a clear reason; one canonical demo is easier to validate.

2. Define the minimal demo contents.
   - One folder: `main`.
   - One simple UI screen with a small number of widgets.
   - One or two Buttons with meaningful names, not `button_1` through `button_7`.
   - One Function example.
   - One Custom Signal example under `Signals/Custom` if file-backed custom signals are implemented; otherwise clearly mark legacy only until migration.
   - One Enhanced Signal example under `Signals/Enhanced`.
   - One Controller example under `Controllers` once controller file-backed loading is implemented; otherwise omit until ready.
   - One Application/Python example under `Applications/Python/raw` or a better clearly named application folder.

3. Clean `Folder.yaml`.
   - Keep only UI layout and visual widget configuration.
   - Remove resource definitions that already have folder-local files.
   - Remove obsolete widget instances used only to host resources.
   - Remove references to `dummy_bool`, `dummy_input`, `inputt_1`, `custom_signals_browser`, and accidental generated widget owners.

4. Clean folder-local resources.
   - Keep folder-local resources under clear directories:
     - `Signals/Custom/*.yaml`
     - `Signals/Enhanced/*.yaml`
     - `Controllers/*.yaml`
     - `Scripts/Workflows/*.yaml`
     - `Applications/Python/<application_name>/`
   - Rename files and definitions to stable snake_case names.
   - Ensure file names match definition names where codecs require that.

5. Update all internal references.
   - Update widget target paths, functions, workflow steps, logs, CSV paths, chart paths, and formulas to the target naming model.
   - Remove references to old names after migration.
   - Check `Scripts/Workflows/*.yaml`, Python sample docs, and `Folder.yaml`.

6. Add a demo naming contract document.
   - Update `samples/HornetStudioDemo/README.md`.
   - Document intended roots and what the demo is supposed to prove.
   - State that no generated widget instance name should be used as a fachliche resource root.

7. Add validation checklist or lightweight test if practical.
   - Search-based validation is acceptable for the first cleanup:
     - no `dummy_`
     - no `custom_signals_browser`
     - no `custom_signals_1`
     - no `application_explorer_1` references outside UI widget identity, if the widget remains at all.
   - If an existing test harness can load the sample, add a focused test that asserts expected roots.

## Implementation Order
1. Inventory current demo paths and references with `rg`.
2. Decide whether to rebuild `samples/HornetStudioDemo/` in place or surgically clean it; prefer in-place canonical cleanup.
3. Define the final resource root list and sample names.
4. Clean or regenerate `Folder.yaml` so it contains UI layout only.
5. Clean resource directories and YAML files.
6. Update functions/workflows/application docs/path references.
7. Update `README.md`.
8. Run search checks, then build/load validation where available.

## Technical Constraints
- Chat answers must stay German; code, UI text, comments, file names, and technical identifiers stay English.
- File and resource names should be snake_case.
- Keep paths portable; no machine-specific absolute paths, credentials, or secrets.
- Do not add new dependencies.
- Do not keep duplicate definitions in `Folder.yaml` and resource files for the canonical demo.
- Do not delete unrelated user work outside `samples/HornetStudioDemo/` without explicit approval.

## Acceptance Criteria
- `samples/HornetStudioDemo/` is the single canonical clean demo.
- The demo has no accidental `dummy_*` resources.
- The demo has no stale `custom_signals_browser.*` or `custom_signals_1.*` references.
- The tree no longer shows custom signals under `application_explorer`.
- `applications` is used only for application resources; `application_explorer` is either absent or strictly a UI widget identity, not a resource root.
- Buttons do not publish repeated generic subitems unless intentionally documented.
- Resource files and names use stable snake_case naming.
- README explains the naming model and demo intent.

## Out of Scope
- Completing `CustomSignals`, `ControllerWidget`, or `ApplicationExplorer` browser migrations inside this cleanup task.
- Supporting historical demo data.
- Building a large showcase application.
- Changing runtime registry semantics globally without a separate plan.

## Risks / Watchouts
- Some current invalid-looking paths may be symptoms of runtime code, not only demo data. If cleanup alone cannot fix the tree, stop and create a focused debug report.
- Do not hide unresolved migration gaps by keeping legacy widgets on the canvas.
- Avoid creating a second demo that splits attention; one clean canonical demo is preferred.
- If a feature is not file-backed yet, either keep its example out of the clean demo or explicitly isolate it as temporary legacy with a TODO.
- Preserve useful Python sample files only if their names and docs match the new root model.
