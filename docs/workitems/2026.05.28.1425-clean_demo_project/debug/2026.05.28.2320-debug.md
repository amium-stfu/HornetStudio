# DEBUG REPORT

## Problem
Project startup and runtime became sluggish or froze when a UDL demo module and then a PID controller were added.

## Expected Behavior
Demo UDL modules may update values continuously, but they should not force broad UI/resource resynchronization on every tick. A PID controller should only publish runtime updates while it is running or when a command/setpoint changes.

## Actual Behavior
Adding the UDL demo already caused noticeable delays. Adding a PID controller made it worse. The PID runtime started its compute timer immediately and published a runtime snapshot every `ComputeIntervalMs` even while stopped.

## Error Messages / Logs
No exception was required to reproduce the issue. The behavior was load-related.

Focused validation:

- `dotnet build src\HornetStudio.Host\HornetStudio.Host.csproj --no-restore` passed.
- `dotnet build src\HornetStudio.Editor\HornetStudio.Editor.csproj --no-restore` passed.
- `dotnet build src\HornetStudio.Host.Tests\HornetStudio.Host.Tests.csproj --no-restore` passed.
- `dotnet src\HornetStudio.Host.Tests\bin\Debug\net9.0\HornetStudio.Host.Tests.dll` passed: `Host registry tests passed: 55`.

## Relevant Code
- `src/HornetStudio.Host/PidControllerRuntime.cs`
  - previously started the compute timer in the constructor
  - now starts the timer only when `run=true` is requested and stops it again on `run=false`

- `src/HornetStudio.Editor/Widgets/UdlClient/UdlClientControl.axaml.cs`
  - attach option snapshots are no longer upserted again when the path already exists
  - volatile status/footer updates are throttled to roughly 1 Hz

- `src/HornetStudio.Host.Tests/Program.cs`
  - added a regression test proving a stopped PID runtime does not emit repeated registry events

## Attempted Fixes
- Fix 1 -> Stop PID runtime timer while the controller is stopped. Result: Host and Editor builds pass; Host self-tests pass with new regression coverage.
- Fix 2 -> Avoid repeated unchanged UDL attach-option snapshot upserts. Result: reduces registry item-change events during the UDL monitor loop.
- Fix 3 -> Throttle volatile UDL status/footer updates. Result: reduces UI and registry churn from message counters.

## Current Hypothesis (optional)
- The slowdown was caused by high-frequency registry churn from demo UDL updates plus a stopped PID controller publishing snapshots every compute interval. The "Host First" direction is conceptually fine, but runtime publishers must update only meaningful changes and avoid full snapshot upserts for high-frequency values.
