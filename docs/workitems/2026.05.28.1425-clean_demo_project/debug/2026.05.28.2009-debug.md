# DEBUG REPORT

## Problem
After central custom signal recomputation was added, writable input custom signals could no longer be manipulated. Values jumped back to their original YAML/default value.

## Expected Behavior
When a writable input custom signal is changed through the registry, the changed value should remain the current runtime value. Computed signals should then read that current value as their source.

## Actual Behavior
Manual changes were reverted during the next central custom signal synchronization.

## Error Messages / Logs
No exception was required to reproduce the issue.

Focused validation:

- `dotnet build src\HornetStudio.Editor\HornetStudio.Editor.csproj --no-restore` passed with `0` warnings and `0` errors.
- `dotnet build src\HornetStudio.Editor.Tests\HornetStudio.Editor.Tests.csproj --no-restore` passed with `0` warnings and `0` errors.

## Relevant Code
- `src/HornetStudio.Host/HostRegistries.cs`
  - `UpdateValue(...)` updates `Item.Value`.
  - It does not update the custom snapshot property named `value`.

- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs`
  - custom signal preserve/source reads previously preferred `item.Properties["value"].Value`
  - this could read a stale snapshot value after `UpdateValue(...)`

## Attempted Fixes
- Fix 1 -> Changed central custom signal value reads to prefer `Item.Value` and use the `value` property only as fallback. Result: focused editor and editor-test builds succeed.

## Current Hypothesis (optional)
- The manual-change regression was caused by mixing snapshot metadata (`Properties["value"]`) with the live registry value (`Item.Value`). Runtime logic should treat `Item.Value` as authoritative.
