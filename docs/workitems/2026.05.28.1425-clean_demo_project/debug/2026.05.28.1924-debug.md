# DEBUG REPORT

## Problem
Folder-local custom signal resource files under `Folders/<folder>/Signals/Custom/*.yaml` were not published into the data registry when no `CustomSignals` widget was placed on the canvas.

## Expected Behavior
A custom signal file such as `Folders/main/Signals/Custom/demo_custom_numeric.yaml` should be available independently of canvas widgets and should appear in the item tree under a stable resource root such as `studio.main.signals.custom.demo_custom_numeric`.

The signal's `writePath` may remain empty. It is an optional external write target for writable input signals, not the signal's own registry path.

## Actual Behavior
The signal file existed on disk, but the item tree did not show the signal. Opening or not opening the browser did not create a stable folder-level registry entry.

## Error Messages / Logs
No exception was required to reproduce the issue. Focused validation showed:

- `dotnet build src\HornetStudio.Editor\HornetStudio.Editor.csproj --no-restore` passed with `0` warnings and `0` errors.
- `dotnet build src\HornetStudio\HornetStudio.csproj --no-restore` was blocked by locked output assemblies from a running/debugged HornetStudio process.
- `dotnet build src\HornetStudio.Editor.Tests\HornetStudio.Editor.Tests.csproj --no-restore` was blocked by the same locked output assemblies before test execution.

## Relevant Code
The relevant ownership boundary is `MainWindowViewModel`, because folder-local resources must be published even when no widget instance exists.

- `src/HornetStudio.Editor/ViewModels/MainWindowViewModel.cs`
  - syncs custom signal files during folder setup and folder binding refresh
  - publishes folder-level snapshots into `HostRegistries.Data`
  - removes stale custom signal paths per folder

- `src/HornetStudio.Editor/Widgets/CustomSignals/CustomSignalsControl.axaml.cs`
  - now builds paths as `studio.<folder>.signals.custom.<name>`
  - no longer removes centrally published custom signal paths when a browser/widget visual detaches

- `src/HornetStudio.Editor.Tests/Program.cs`
  - updates the manual trigger path expectation to the new stable root

## Attempted Fixes
- Fix 1 -> Moved file-backed custom signal publication into `MainWindowViewModel` folder synchronization and changed the path root from widget-owned paths to `studio.<folder>.signals.custom.<name>`. Result: focused editor build succeeds.
- Fix 2 -> Removed visual-detach cleanup for custom signal registry entries from `CustomSignalsControl`, so opening/closing a browser cannot delete centrally owned resource entries. Result: compile validation succeeds for the editor project.

## Current Hypothesis (optional)
- The same root pattern should be reviewed for every folder-local browser resource: resource files should be loaded and published by folder/runtime synchronization, while browser widgets should only view/edit those files.
- EnhancedSignals and Controllers already follow a central runtime-manager style more closely, but their final registry root naming should still be checked separately for consistency.
